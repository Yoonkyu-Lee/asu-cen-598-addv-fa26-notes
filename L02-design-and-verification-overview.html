01

추상화 수준

Levels of abstraction

같은 덧셈기를 네 가지 높이에서 쓸 수 있다. 어느 높이에서 쓰느냐가 곧 무엇을 자동화에 맡기느냐다.

The same adder can be written at four heights, and the height you pick decides how much you hand to the tools.

용어 뜯어보기 · behavioral / structuralUnpacking the jargon · behavioral and structural
behavioral"무슨 일이 일어나야 하는가"를 적는다. result = a + b 처럼. 부품 목록이 없다.
structural"어떤 부품이 어떻게 연결되는가"를 적는다. and_gate g(...) 처럼 인스턴스를 나열한다.
구별 기준모듈 인스턴스를 나열하고 있으면 structural, 동작을 서술하고 있으면 behavioral.
왜 RTL이 사이인가RTL은 always_ff 안에서 동작을 서술(behavioral)하면서도, 어느 register에 언제 들어가는지를 못 박아 구조를 사실상 결정한다.
헷갈리는 것이건 언어의 구분이 아니다. 같은 Verilog 파일 안에 behavioral 블록과 structural 인스턴스가 섞여 있을 수 있다. 실제 설계는 대개 섞여 있다.
behavioralWrites down what should happen, as in result = a + b. No parts list.
structuralWrites down which parts connect to which, listing instances such as and_gate g(...).
The testListing module instances means structural; describing behaviour means behavioral.
Why RTL is in betweenRTL describes behaviour inside an always_ff, yet by pinning down which register gets written and when, it effectively fixes the structure.
Easy to misreadThis is not a distinction between languages. One Verilog file can hold behavioral blocks and structural instances side by side, and real designs usually do.
함정: "합성 가능"은 문법이 아니라 관행이다Trap: "synthesisable" is a convention, not grammar

슬라이드가 "behavioral은 합성이 안 될 수 있다"고 적었는데, 이게 문법 오류가 난다는 뜻이 아니다. 시뮬레이터는 멀쩡히 돌린다. 합성 도구가 그 구문을 게이트로 바꾸는 법을 모를 뿐이다.

그래서 오류가 늦게 터진다. 시뮬레이션은 통과하는데 합성에서 처음 걸린다. 08절 lint가 존재하는 이유가 이것이다. 합성까지 가기 전에 미리 잡으려는 것이다.

The slide says behavioral code may not synthesise, and that does not mean it is a syntax error. The simulator runs it happily. The synthesis tool simply does not know how to turn that construct into gates.

Which means the error surfaces late: simulation passes and synthesis is the first thing to complain. That is exactly why §08, linting exists, to catch it before you get that far.

02

Data Path와 Control Path

Data path and control path

어떤 디지털 시스템이든 이 둘로 쪼개서 본다. 이 습관 하나가 나중에 verification plan을 쓸 때 그대로 쓰인다.

Any digital system splits into these two, and that habit carries straight over into writing a verification plan later.

일반적인 관점The general view
  • Data Path (계산부): 값이 실제로 흘러가며 변형되는 곳. 산술 회로, memory와 storage가 여기 있다.
  • Control Path (제어부): 언제 무엇을 할지 정하는 곳. state machine이 여기 있다.
  • The data path, or computation unit, is where values actually flow and get transformed. Arithmetic circuits, memory and storage live here.
  • The control path, or controller, decides when to do what. State machines live here.

왜 이 구분이 실무에서 쓸모 있나. 버그의 성격이 다르기 때문이다. Data path 버그는 값이 틀린다. Control path 버그는 타이밍이나 순서가 틀린다. 그리고 control path 버그가 훨씬 잡기 어렵다. 특정 순서로 사건이 겹쳐야만 드러나기 때문이다.

이게 16절의 랜덤 자극이 왜 필요한지로 이어진다. 값을 다양하게 넣는 것만으로는 control path를 흔들 수 없고, 타이밍과 순서도 같이 흔들어야 한다.

Why the split earns its keep. The bugs differ in kind. A data path bug produces a wrong value. A control path bug produces wrong timing or wrong ordering, and those are far harder to catch because they only appear when events overlap in one particular way.

That leads straight into why §16 needs random stimulus. Varying values alone will not shake the control path; you have to randomise timing and ordering too.

설계자의 하루

Life of a design engineer

RTL을 쓰는 시간은 이 여덟 칸 중 한 칸이다. 나머지는 읽고, 계획하고, 남과 맞추는 일이다.

The speaker notes carry this line: hardware is parallel, computers run programs sequentially, and a simulator has to imitate parallel hardware on a sequential machine, so it needs a way to model that parallelism. It leads directly into the simulated time versus wall clock time distinction in §14.

04

Synthesis

Lecture 1에서 이름만 나왔던 칸이다. 실제로는 번역기다. 당신이 쓴 +를 foundry가 만들 수 있는 부품으로 바꾼다.

The cell that was only a name in Lecture 1. It is really a translator: it turns the + you wrote into parts the foundry can actually manufacture.

Synthesis

상위 수준 HDL 코드를 netlist로 바꾸는 것. netlist는 wire로 연결된 building block들의 목록이다.

  • building block은 foundry가 준다. 이 묶음을 tech library 또는 standard cell library라고 부른다. 그 공장이 실제로 만들 수 있는 cell들이다.
  • 보통 gate와 flip-flop이다. 이걸 standard cell이라고 한다.
  • 예: HDL의 + 연산자를 덧셈기를 구성하는 게이트들로 바꾼다.
  • 흔한 도구: Synopsys Design Compiler, Cadence Genus

Turning higher level HDL into a netlist, a list of building blocks joined by wires.

  • The building blocks come from the foundry. The bundle is called a tech library or standard cell library, and it holds the cells that particular fab can actually make.
  • They are usually gates and flip-flops, known as standard cells.
  • For example, a + operator in the HDL becomes the gates that make up an adder.
  • Common tools: Synopsys Design Compiler, Cadence Genus.
용어 뜯어보기 · standard cellUnpacking the jargon · standard cell
한 줄foundry가 미리 만들어 두고 특성까지 재놓은 부품. AND 게이트 하나, flip-flop 하나가 각각 하나의 cell이다.
왜 "standard"높이가 전부 같게 설계돼 있어서 줄 세워 늘어놓을 수 있기 때문이다. 그래야 place and route가 자동화된다.
누가 만드나back-end의 library 엔지니어. 트랜지스터를 직접 배치하고, 특성을 측정하고, 실제 test chip으로 대조한다.
왜 설계자가 알아야 하나당신의 RTL은 이 목록에 있는 것으로만 만들어진다. 목록에 없는 형태를 상상해서 쓰면 도구가 비싼 조합으로 흉내 낸다.
In one lineA part the foundry has already built and already characterised. One AND gate is a cell, one flip-flop is a cell.
Why "standard"They are all designed to the same height so they can be laid out in rows, which is what makes place and route automatable.
Who makes themBack end library engineers, who lay out the transistors, measure the characteristics, and check them against real test chips.
Why a designer caresYour RTL can only be built out of what is on that list. Imagine a shape that is not on it and the tool will imitate it with an expensive combination.

Static Timing Analysis

Static timing analysis

"입력 벡터 없이" 타이밍을 검증하는 방법. 슬라이드가 "slack이 뭐냐"고 직접 물어보니 그것부터 답한다.

Checking timing with no input vectors at all. The slide asks outright what slack is, so that gets answered first.

STA

모든 timing path를 분석해서 디지털 회로의 타이밍 성능을 검증하는 방법. "static"인 이유는 입력 벡터가 관여하지 않기 때문이다.

A way of validating a circuit's timing performance by analysing every timing path. It is static because no input vectors are involved.

timing path 네 종류Four kinds of timing path뜻Meaning
PI to Flop칩 입력 핀에서 첫 flip-flop까지from a primary input pin to the first flip-flop
Flop to Flopflip-flop에서 flip-flop까지. 클럭 주파수를 결정하는 것이 대개 이것이다flip-flop to flip-flop, usually the one that sets the clock frequency
Flop to PO마지막 flip-flop에서 칩 출력 핀까지from the last flip-flop to a primary output pin

용어 뜯어보기 · slack (슬라이드가 물어본 것)Unpacking the jargon · slack, the question on the slide
한 줄여유 시간. 신호가 도착해야 하는 시각에서 실제로 도착한 시각을 뺀 값이다.
부호양수면 통과(제때 왔다), 음수면 위반(늦었다). 음수 slack을 timing violation이라고 부른다.
어디에 쓰나합성과 STA 리포트의 핵심 숫자다. "worst negative slack이 얼마냐"가 곧 "이 설계가 얼마나 안 되고 있냐"다.
왜 static인가실제 값을 흘려보지 않고 경로의 지연만 더해서 판단하기 때문이다. 그래서 빠르고 빠짐없이 볼 수 있다. 대신 그 경로가 실제로 쓰이는지는 모른다.
연결그래서 false path와 multicycle path를 사람이 알려줘야 한다. 다음 항목의 timing constraint가 그 일을 한다.
In one lineSpare time. The time a signal was required by, minus the time it actually arrived.
SignPositive means it passes, it got there in time. Negative means a violation, it was late. Negative slack is what people call a timing violation.
Where it shows upIt is the headline number in synthesis and STA reports. "What is the worst negative slack" is the same question as "how badly is this design failing".
Why staticBecause it adds up path delays rather than pushing real values through, which makes it fast and exhaustive. The cost is that it does not know whether the path is ever used.
The linkWhich is why a human has to declare false paths and multicycle paths. That is the job of the timing constraints below.

두 가지 타이밍 규칙

The two timing rules

슬라이드가 규칙을 두 줄로 적었는데, 언뜻 보면 같은 말을 반복한 것 같다. 아니다. 정반대 방향의 두 실패를 막는 규칙이다.

The slide states the rules in two lines that look at first like the same sentence twice. They are not. They block two failures pointing in opposite directions.

슬라이드의 문장What the slide says막으려는 실패What it prevents
FF1이 CLK1의 E1에서 내보낸 데이터는 FF2가 CLK2의 E2에서 잡아야 한다 Data launched by FF1 on E1 of CLK1 should be captured by FF2 on E2 of CLK2 너무 늦게 도착하는 것. 경로가 길면 다음 엣지 전에 못 온다. Arriving too late: if the path is long it does not make the next edge.
FF1이 CLK1의 E1에서 내보낸 데이터는 FF2가 CLK2의 E1에서 잡으면 안 된다 Data launched by FF1 on E1 of CLK1 should not be captured by FF2 on E1 of CLK2 너무 빨리 도착하는 것. 경로가 짧으면 같은 엣지에 실려서 한 칸을 건너뛴다. Arriving too early: a short path rides the same edge and skips a stage.
함정: 빨라서 나는 버그가 있다Trap: being fast can be the bug

두 번째 규칙이 처음 보면 이상하다. 신호가 빨리 오면 좋은 것 아닌가? 아니다. flip-flop은 클럭 엣지 직후에도 입력이 잠깐 안정돼 있어야 한다. 앞단의 새 값이 그 창 안에 들이닥치면, 받는 쪽이 이번 엣지에 이미 그 값을 잡아버린다. 한 클럭이 통째로 사라진다.

이게 실무에서 왜 무서우냐면, 클럭을 느리게 해도 안 고쳐진다. 늦어서 나는 문제는 주파수를 낮추면 사라지지만, 빨라서 나는 문제는 주파수와 무관하다. 그래서 이건 실리콘이 나온 뒤에 발견되면 대개 재제작이다.

The second rule looks wrong at first. Surely arriving early is good? No. A flip-flop needs its input to stay steady for a moment after the clock edge too. If the new value from the previous stage barges into that window, the receiving flop captures it on this edge instead, and a whole clock cycle disappears.

What makes this frightening in practice is that slowing the clock does not fix it. Problems from being late go away when you drop the frequency; problems from being early do not care about frequency at all. So finding one after silicon usually means a respin.

Timing ConstraintsTiming constraints

요구되는 타이밍 동작을 명시한 것. 합성 도구의 입력이다. 즉 사람이 써서 도구에게 넘겨주는 것이지 도구가 알아서 아는 게 아니다.

  • Clock period — 목표 주파수
  • Input과 output delay — 칩 바깥에서 얼마나 걸려서 오고 가는지
  • Timing exception — false path(실제로는 안 쓰이는 경로), multicycle path(한 클럭 안에 안 끝나도 되는 경로)
  • Clock uncertainty — clock skew 같은 것

A statement of the timing behaviour that is required. They are an input to the synthesis tool, which is to say a human writes them and hands them over. The tool does not work them out on its own.

  • Clock period, the target frequency.
  • Input and output delays, how long things take outside the chip.
  • Timing exceptions: false paths that are never really used, and multicycle paths that are allowed more than one clock.
  • Clock uncertainty, such as clock skew.
현장 감각On the job

합성 리포트에 worst negative slack이 -0.4 ns로 찍혔다. 경로를 따라가 보니 configuration register에서 나와 데이터 경로 깊숙이 들어가는 길인데, 그 register는 칩이 부팅될 때 한 번 쓰고 그 뒤로는 안 바뀐다. 무엇을 해야 하나?

The synthesis report shows a worst negative slack of -0.4 ns. Following the path, it runs from a configuration register deep into the data path, and that register is written once at boot and never changes afterwards. What now?

생각해본 뒤 펼치기Think first, then open

회로를 고치기 전에 constraint를 의심한다. 부팅 때 한 번 쓰고 안 바뀌는 신호라면, 그 경로가 한 클럭 안에 끝나야 할 이유가 없다. multicycle path로 선언하면 STA가 여러 클럭을 허용하고 slack이 양수가 된다.

이게 STA가 "static"인 것의 대가다. 도구는 그 경로가 실제로 언제 쓰이는지 모른다. 모든 경로를 똑같이 "매 클럭 동작한다"고 가정하고 잰다. 그 가정이 틀린 곳을 사람이 알려줘야 한다.

단, 여기가 위험한 지점이다. multicycle path나 false path를 잘못 선언하면 진짜 위반을 도구가 조용히 무시한다. 리포트는 깨끗해지는데 실물이 안 돈다. 그래서 timing exception은 리뷰 대상이고, 왜 그렇게 선언했는지를 근거와 함께 남긴다.

Before touching the circuit, suspect the constraints. A signal written once at boot and then left alone has no reason to settle within one clock. Declare it a multicycle path, STA allows several clocks, and the slack goes positive.

This is the price of STA being static. The tool has no idea when a path is actually exercised; it measures every path as though it runs every clock. Where that assumption is wrong, a human has to say so.

And this is where it gets dangerous. Declare a multicycle or false path wrongly and the tool quietly ignores a real violation. The report goes clean and the physical part does not work. Timing exceptions therefore get reviewed, and the reasoning behind each one gets written down.

Slide 59 asks what role a technology library plays in synthesis. The skeleton of the answer:

  • Synthesis turns RTL into parts, and the tech library is what supplies the parts list. Without it there is nothing to build out of.
  • It also supplies the delay, area and power figures for each part, which is what lets the tool choose among candidate implementations and still meet the constraints.
  • So the tech library defines both what can be built and what it costs, at the same time.

Coming from software, linters feel like taste and therefore skippable. Hardware is different. Four of the six above are causes of the physical part behaving differently from the code.

The unintended latch is the nastiest. The code looks fine and simulation gives the right answer most of the time. Then synthesis creates a storage element that should not exist, and it breaks timing or holds a stale value that shows up later as strange behaviour.

Lint is not verification. It only asks whether the code follows rules, never whether the design matches the spec. Think of it as the first net, cheap and fast.

Goals and trade-offs

일곱 가지 목표가 있고, 슬라이드가 한 줄로 정리한다: "공짜 점심은 없다."

Seven goals, and the slide sums the situation up in one line: there is no free lunch.

설계의 일곱 목표The seven goals of design

Area · Timing · Performance · Power · Security · Safety/Reliability · Testability

Timing과 Performance가 따로 적혀 있는 게 눈에 띈다. 같은 말이 아니다. Timing은 "클럭 주기 안에 들어오는가"이고, Performance는 "단위 시간에 일을 얼마나 하는가"다. 파이프라인을 깊게 하면 timing은 좋아지는데(각 단이 짧아지므로) 한 건의 지연은 오히려 늘어난다.

Area, timing, performance, power, security, safety and reliability, testability.

Notice that timing and performance are listed separately. They are not the same. Timing asks whether you fit inside the clock period; performance asks how much work gets done per unit time. Deepening a pipeline improves timing, because each stage gets shorter, while making the latency of a single item worse.

복습 문제 2번: 목표들이 어떻게 서로 충돌하나Review question 2: how the goals conflict

슬라이드 59쪽이 "디지털 설계의 흔한 목표들은 무엇이고 서로 어떻게 충돌하는가"를 묻는다. 일곱 개를 나열만 하면 절반짜리 답이다. 충돌하는 짝을 들어야 한다.

  • Timing ↔ Area: 위 곡선 그대로. 빠른 회로가 더 크다.
  • Performance ↔ Power: 병렬로 더 많이 돌리면 전력이 는다. DVFS는 성능을 깎아 전력을 아끼는 장치다.
  • Testability ↔ Area와 Timing: scan chain을 넣으면 flip-flop마다 mux가 붙어서 면적이 늘고 경로가 길어진다. 테스트를 쉽게 하려고 설계를 느리게 만드는 것이다.
  • Reliability ↔ Area: TMR은 같은 논리를 세 벌 만들어 다수결한다. 면적이 3배가 넘는다.
  • Security ↔ Performance: side-channel 대응은 대개 동작 시간을 일정하게 만드는 것이라, 빠를 수 있는 경우에도 못 빠르게 한다.

이게 왜 중요한가: 이 충돌들이 검증 계획에도 그대로 나타난다. "성능이 목표치를 만족하는가"와 "기능이 맞는가"는 서로 다른 테스트고, 하나를 통과해도 다른 하나를 모른다.

Slide 59 asks what the common goals of digital design are and how they conflict. Listing seven of them is half an answer; you have to name the conflicting pairs.

  • Timing against area: the curve above. Faster circuits are bigger.
  • Performance against power: more parallel work draws more power. DVFS exists to trade performance away for power.
  • Testability against area and timing: scan chains put a mux on every flip-flop, adding area and lengthening paths. You slow the design down in order to make it testable.
  • Reliability against area: TMR builds the same logic three times and votes. That is more than triple the area.
  • Security against performance: side channel defences usually mean making operations take constant time, so you cannot be fast even when you could be.

Why it matters: the same conflicts reappear in the verification plan. "Does it hit the performance target" and "is it functionally correct" are different tests, and passing one tells you nothing about the other.

왜 느린가

Why it is slow

  • 시뮬레이션은 아주 느리다. 그리고 설계가 복잡해질수록 더 느려진다. 크기(게이트 수)와 추상화 수준(gate-level이 RTL보다 훨씬 느리다) 둘 다에 비례한다.
  • Simulation time과 wall clock time은 다르다. 슬라이드의 표현대로 5분 동안 돌려서 5 ns를 본다. 앞의 5분은 당신이 기다린 시간이고 뒤의 5 ns는 회로 안에서 흐른 시간이다.
  • 효과는 검증 엔지니어의 상상력에 달려 있다. 테스트할 시나리오를 사람이 생각해내야 하기 때문이다.
  • 전체 상태 공간을 다 훑는 건 사실상 불가능하다. 랜덤 벡터가 도움이 된다.
  • Simulation is very slow, and it gets slower as the design grows. It scales with size in gate count and with abstraction level, since gate level is far slower than RTL.
  • Simulation time is not wall clock time. As the slide puts it, five nanoseconds in five minutes. The five minutes is what you waited; the five nanoseconds is what elapsed inside the circuit.
  • Its effectiveness rests on the verification engineer's imagination, because a person has to think of the scenarios.
  • Exercising the whole state space is essentially impossible. Random vectors help.
이 슬라이드는 강의에서 넘어갔다 (34쪽): 시뮬레이터 내부Skipped in class (slide 34): inside the simulator

숨김 슬라이드지만 "왜 느린가"의 진짜 답이라 적어둔다. 시뮬레이터는 두 단계로 나뉜다.

  1. Compile: Analyze(문법 해석) → Elaborate(계층을 펼치고 연결을 확정)
  2. Simulation 루프: Determine events → Active Events → NBA events → Advance simulation time → 다시 처음으로. 이벤트가 더 없으면 Done.

이벤트 처리는 Evaluate → Update → Schedule 세 동작이다. 여기서 두 가지가 보인다.

  • 시간이 이벤트 단위로 흐른다. 신호가 바뀌는 곳마다 이벤트가 생기므로, 설계가 크면 한 클럭을 넘기는 데 처리할 이벤트가 폭증한다. 이게 느린 이유다.
  • NBA events가 따로 있다. non-blocking assignment(<=)를 다른 큐에서 처리한다는 뜻이다. blocking(=)과 섞어 쓰면 안 되는 이유가 여기 있다. 08절 lint가 그걸 잡는 것도 같은 이유다.

Hidden, but recorded here because it is the real answer to why simulation is slow. A simulator has two phases.

  1. Compile: analyze, meaning parse, then elaborate, meaning flatten the hierarchy and fix the connections.
  2. The simulation loop: determine events, active events, NBA events, advance simulation time, and back to the start. When no events remain, done.

Event handling itself is three moves: evaluate, update, schedule. Two things follow.

  • Time advances event by event. Every signal that changes creates an event, so on a large design the number of events needed to get through one clock explodes. That is the slowness.
  • NBA events are a separate stage, which is to say non-blocking assignments (<=) are processed from a different queue. That is exactly why mixing them with blocking assignments (=) is a hazard, and why lint in §08 flags it.

이게 Lecture 1의 emulation과 이어진다. 시뮬레이션이 느리다는 이 사실 하나 때문에 전용 하드웨어를 사는 산업이 생겼다. 그리고 그 대가가 "안이 안 보인다"였다. 지금 보면 왜 그런지도 알 수 있다. 시뮬레이터가 느린 이유가 곧 모든 이벤트를 하나씩 처리하기 때문이고, 그래서 모든 것을 볼 수 있는 것이다.

This connects to emulation in Lecture 1. An entire industry sells dedicated hardware because of this one fact, and the price was losing visibility. Now you can see why: the simulator is slow precisely because it processes every event one at a time, and that is the same reason it can show you everything.

정의와 한계Definition and limits

검증 문제를 수학으로 푼다. 설계를 수식으로 표현하고, 주어진 제약 아래 그것이 성립함을 증명한다.

  • Exhaustive하다. 모든 경우를 다 본 것과 같다. 시뮬레이션이 절대 못 하는 것이다.
  • 대신 state explosion problem에 걸린다. 상태 수가 폭발해서 계산이 불가능해진다.
  • 확장성이 나쁘다. 어느 정도 복잡한 설계만 되어도 불가능해진다.

It solves the verification problem with mathematics: express the design as a formula and prove that it holds under the given constraints.

  • It is exhaustive, equivalent to having checked every case. Simulation can never do that.
  • In exchange it runs into the state explosion problem, where the number of states blows up beyond computation.
  • It does not scale. Even a fairly complicated design puts it out of reach.

Stimulus, checkers, coverage. The entire back half of this course stands on these three words, and labs 4, 5 and 6 take one each.

셋이 함께여야 하는 이유Why all three or none
  • Stimulus만 있으면: 자극은 들어가는데 아무도 결과가 옳은지 안 본다. 시뮬레이션은 항상 통과한다.
  • Stimulus + Checkers면: 틀리면 잡는다. 그런데 무엇을 안 해봤는지 모른다.
  • 셋 다 있으면: 자극을 넣고, 틀리면 잡고, 무엇을 아직 안 해봤는지 안다. 그제야 "다 했다"고 말할 근거가 생긴다.
  • With stimulus alone: things go in, but nobody checks whether the answer is right. The simulation always passes.
  • With stimulus and checkers: mistakes get caught, but you have no idea what you never tried.
  • With all three: you drive it, you catch mistakes, and you know what is still untouched. Only then is there any basis for saying you are done.

  • Reactive: DUT에서 무슨 일이 벌어지면 그에 반응한다.

Inputs applied to stimulate the DUT. There are two kinds.

  • Active: drive values into the DUT.
  • Reactive: respond to something that happened inside the DUT.

슬라이드가 directed test를 "좋기도 하고 나쁘기도 하다"고 적었다. 발표자 노트가 양쪽을 다 풀어놨다.

  • 좋은 점: 아주 잘 제어된다. 원하는 특정 시나리오를 정확히 만들어낼 수 있다.
  • 나쁜 점: 몇 개나 쓸 수 있겠나? 가능한 시나리오를 사람이 다 생각해낼 수 없다.

그래서 randomization이 예상 못 한 버그를 찾는 데 좋다. 대신 constraint로 불법 입력값이 들어가는 걸 막아야 한다. 아무거나 넣으면 설계가 애초에 대응할 필요 없는 상황에서 실패하고, 그건 버그가 아니다.

무엇을 randomize 하나

  • 값: data, addr 같은 것. 다만 값 자체보다 값의 분포가 더 중요한 경우가 많다.
  • randomize 대상은 DUT의 입력일 수도 있고 DUT의 상태일 수도 있다.
  • 타이밍과 순서: Pkt1 → 지연 → Pkt2 처럼.
  • 몇 개의 인터페이스를 동시에 흔들지.

뒤의 둘이 핵심이다. 02절에서 control path 버그는 순서와 타이밍이 겹칠 때만 드러난다고 했다. 값만 랜덤하게 넣으면 그 버그는 영원히 안 나온다.

The slide calls directed tests "good and bad", and the speaker notes unpack both halves.

  • Good: extremely controllable. You can construct exactly the scenario you want.
  • Bad: how many can you write? You cannot think of all the possible scenarios.

Hence randomisation is great for finding unexpected bugs, with constraints to stop illegal input values getting through. Throw anything at it and the design fails in a situation it was never required to handle, and that is not a bug.

What you can randomise

  • Values, such as data and addresses. Though the distribution of values often matters more than the values themselves.
  • What you randomise can be an input to the DUT or the state of the DUT.
  • Timing and ordering, as in packet 1, then a delay, then packet 2.
  • How many interfaces to wiggle at once.

The last two are the important ones. §02 said control path bugs only appear when ordering and timing overlap a certain way. Randomising values alone will never surface them.

Confirming the DUT behaves correctly and raising an error when something illegal happens. There are two layers.

Coverage

DUT를 얼마나 잘 두들겼는지를 정량화한 것. 모든 테스트를 돌리고, 커버리지 결과를 합치고(merge), 점수를 낸다. 점수가 높을수록 stimulus의 품질이 높다.

A quantitative measure of how well the DUT was exercised. Run all the tests, merge the coverage results, produce a score. The higher the score, the better the quality of the stimulus.

실패한 테스트는 커버리지에서 뺀다Drop failing tests from coverage

슬라이드가 짧게 한 줄로 적었지만 실무에서 계속 사고 나는 지점이다. 실패한 테스트의 커버리지를 세면 안 된다. 그 테스트는 도중에 죽었거나 잘못된 상태로 갔을 수 있는데, 그 경로를 "확인했다"고 세면 커버리지 점수가 거짓말을 한다.

One line on the slide, but a recurring accident in practice. Never count coverage from a failing test. That run may have died partway or wandered into a bad state, and counting the path as "checked" makes the coverage score lie to you.

복습 문제 6번: code coverage의 한계Review question 6: the limits of code coverage

슬라이드가 code coverage 항목 아래에 "Limitations?"이라고만 적어놓고 넘어갔다. 복습 문제 6번이 같은 걸 다시 묻는다. 답은 셋이다.

  1. 실행된 것과 옳은 것은 다르다. line coverage 100%는 모든 줄이 한 번씩 돌았다는 뜻일 뿐이다. checker가 없으면 그 줄이 틀린 값을 내도 커버리지는 100%다.
  2. 코드에 없는 시나리오는 셀 수 없다. "FIFO가 가득 찬 상태에서 write가 들어왔다"는 상황은 코드 어느 줄에도 대응하지 않는다. 각 줄은 다 돌았어도 그 조합은 한 번도 안 일어났을 수 있다.
  3. 도달할 수 없는 코드가 점수를 깎는다. 반대 방향의 문제다. 실제로 절대 안 도는 코드가 있으면 100%가 영원히 안 나오고, 그걸 일일이 면제(waive) 처리해야 한다.

functional coverage가 2번을 해결한다. "이런 상황을 보고 싶다"를 직접 적어두면, 그 상황이 실제로 벌어졌는지를 센다. 대신 사람이 무엇을 볼지 미리 정해야 하므로 상상력의 한계가 다시 들어온다. 그래서 둘을 같이 쓴다.

The slide writes "Limitations?" under code coverage and moves on, and review question 6 asks it again. Three answers.

  1. Executed is not the same as correct. 100% line coverage only says every line ran once. With no checker, a line can produce a wrong value and coverage is still 100%.
  2. It cannot count scenarios that are not lines of code. "A write arrived while the FIFO was full" corresponds to no single line. Every line may have run and that combination never occurred.
  3. Unreachable code drags the score down. The opposite problem: if code genuinely never runs, 100% is unattainable and each case has to be waived by hand.

Functional coverage solves the second one. Write down the situation you want to see and it counts whether that situation actually happened. The cost is that a person must decide in advance what to look for, so the imagination limit comes back. Which is why both are used together.

TLM

신호를 하나하나 흔드는 대신 "쓰기 한 건"을 통째로 다루는 방식. Testbench가 왜 그렇게 생겼는지의 배경이다.

Handling "one write" as a whole instead of wiggling signals one at a time. It is the background to why testbenches look the way they do.

Transaction Level Modeling

디지털 시스템을 RTL보다 높은 추상화 수준에서 모델링하는 것.

  • 세부가 적다 · 코딩이 쉽다 · 시뮬레이션이 빠르다
  • 기존 방식: 블록 A(RTL) ↔ 블록 B(RTL)를 신호 다발로 연결
  • TLM 방식: 블록 A ↔ 블록 B를 write(address, data) 같은 호출로 연결

Modelling digital systems at a higher level of abstraction than RTL.

  • Fewer details, easier to code, faster to simulate.
  • Traditional: block A in RTL wired to block B in RTL by a bundle of signals.
  • TLM: block A talks to block B through a call such as write(address, data).

발표자 노트가 이 대목을 이렇게 요약했다: "개별 신호를 다루는 대신 transaction 단위로 이야기하라. pin accurate하고 cycle accurate한 것과 대비된다."

왜 이게 testbench 이야기의 앞에 나오나. 다음 절의 testbench 구성도를 보면 Stimulus와 Driver가 분리되어 있다. 그 경계가 정확히 여기다. Stimulus는 "주소 0x40에 0xDEAD를 써라"라는 transaction을 만들고, Driver가 그것을 실제 신호 흔들기로 번역한다. TLM을 모르면 왜 두 칸으로 나눴는지가 안 보인다.

The speaker notes summarise it as: talk in terms of transactions rather than handling individual signals, as opposed to being pin accurate and cycle accurate.

Why this comes just before the testbench. In the next section's diagram, stimulus and driver are separate boxes, and this is exactly the boundary between them. Stimulus produces a transaction that says "write 0xDEAD to address 0x40", and the driver translates that into actual signal wiggling. Without TLM the split looks arbitrary.

The plan and the verifier's day

앞의 삼각대가 문서로 굳으면 verification plan이 된다. 그리고 그 문서가 검증 엔지니어의 하루를 만든다.

Verification Plan

DUT를 어떻게 검증할 것인지를 적은 문서. 담기는 것은 이렇다.

  • 전략
  • 방법론: simulation인지 formal인지
  • testbench 구성 요소
  • sign-off 기준: 무엇을 만족하면 끝났다고 할 것인가
  • 기능 목록, 그리고 기능마다 세 가지:
    • Stimulus: "입력 A → B → C를 넣고 D는 0으로 유지한다"
    • Checking: "상태 X에 들어갈 때마다 E가 1이 되는지 확인한다"
    • Coverage: "상태 X에 도달했다"

형식은 여러 가지다. Word, Excel, Synopsys HVP, Cadence VPlan.

A document describing how you will verify a DUT. It holds:

  • Strategy.
  • Methodology: simulation, formal, or both.
  • Testbench components.
  • Sign-off metrics: what has to hold before you call it finished.
  • Features, and for every feature three things:
    • Stimulus: "apply inputs A then B then C, holding D at 0".
    • Checking: "check that E goes to 1 every time we enter state X".
    • Coverage: "state X was reached".

Formats vary: Word, Excel, Synopsys HVP, Cadence VPlan.

기능마다 세 줄이 곧 삼각대다. 16절의 stimulus·checkers·coverage가 문서 양식으로 굳은 것이 verification plan이다. 그래서 plan을 쓰는 일은 형식 작업이 아니라 "이 기능을 어떻게 두들기고, 무엇으로 옳다고 판정하고, 무엇을 보면 다 했다고 할지"를 미리 정하는 일이다.

Three lines per feature is the trifecta. Stimulus, checkers and coverage from §16, frozen into a document format. Writing a plan is therefore not paperwork: it is deciding up front how you will exercise a feature, what will judge it correct, and what will tell you it is finished.

03절의 설계자 그림과 나란히 놓으면 두 직무가 거울이다. 둘 다 "사양 읽기"에서 시작해서 "계획 세우기"로 간다. 그다음이 갈린다. 설계자는 RTL을 쓰고, 검증자는 testbench를 쓴다. 그리고 둘 다 "상대와 주고받기"가 정식 단계로 들어 있다.

원칙The principle

시스템을 각각 하나의 고유한 목적만 갖는 부분들로 쪼개는 것.

Splitting a system into parts that each serve one single, unique purpose.

무엇을 무엇에서 떼나What gets separated안 떼면 생기는 일What happens if you do not
Checking을 Stimulus에서Checking from stimulus 스스로 검사하는 stimulus는 "항상 켜져" 있지 않다. 그 테스트를 돌릴 때만 검사한다. 다른 테스트가 같은 버그를 밟아도 안 잡힌다. Self-checking stimulus is not always on. It checks only while that test runs, so another test can step on the same bug and nothing fires.
Coverage를 Stimulus에서Coverage from stimulus 흔한 함정: "내가 stimulus를 썼으니 어떤 시나리오를 커버하는지 안다." 아니다. 설계나 testbench가 바뀌면 같은 stimulus가 다른 커버리지를 낸다. FIFO 깊이나 클럭 주파수만 바뀌어도 그렇다. The classic trap: "I wrote the stimulus, so I know what it covers." You do not. If the design or testbench changes, the same stimulus achieves different coverage. A FIFO depth or a clock frequency is enough.
Testbench를 Stimulus에서Testbench from stimulus 흔한 함정: testbench 부품을 특정 DUT 전용으로 만든다. 그러면 다음 프로젝트에서 통째로 다시 써야 한다. The classic trap: making a testbench component specific to one DUT. Then the next project starts from zero.

슬라이드는 사람도 나눈다고 적었다. Stimulus / Checkers / Coverage를 서로 다른 엔지니어가 맡고, Architecture / Design / Verification도 서로 다른 사람이 맡는다.

The slide extends it to people: different engineers own stimulus, checkers and coverage, and architecture, design and verification go to different people too.

왜 사람까지 나누나. Lecture 1에서 verification의 목적이 "설계가 사양대로인지"를 확인하는 것이라고 했다. 설계한 사람이 검증하면 사양을 잘못 읽었을 때 같은 오해를 두 번 한다. 검증이 독립적이어야 하는 이유가 게으름 방지가 아니라 같은 착각을 반복하지 않기 위해서다.

Why separate the people too. Lecture 1 said verification exists to confirm the design matches the spec. If the designer verifies their own work, a misreading of the spec gets made twice. Independence is not about preventing laziness, it is about not repeating the same misunderstanding.

언어와 방법론

Languages and methodologies

왜 Verilog만으로는 부족한가, 그리고 왜 UVM 같은 것이 생겼는가. 학기 후반 세 강의(20·21·22)의 예고편이다.

Why Verilog alone is not enough, and why something like UVM exists. A trailer for lectures 20, 21 and 22.

HDL로는 왜 부족한가Why HDLs are not sufficient
  • 프로그래밍 세계의 기능이 없다. class, enum 같은 것.
  • assertion, randomization, coverage에 대한 native 지원이 없다.

그래서 검증 전용 언어가 생겼다: SpecMan e, OpenVera, 그리고 SystemVerilog. 슬라이드가 SystemVerilog를 "Verilog++"라고 부르고, 표준 번호가 IEEE 1800이라고 적었다.

  • No features from the programming world, such as classes and enums.
  • No native support for assertions, randomisation and coverage.

Hence dedicated verification languages: SpecMan e, OpenVera, and SystemVerilog. The slide calls SystemVerilog "Verilog++" and gives the standard number as IEEE 1800.

강의계획서가 선수과목으로 객체지향 프로그래밍(CSE 205)을 요구하는 이유가 여기 있다. 검증 파트에서 class, inheritance, polymorphism, factory pattern, virtual class를 그대로 쓴다. Verilog를 아는 것과 UVM을 쓰는 것 사이의 간극은 하드웨어 지식이 아니라 객체지향 지식이다.

This is why the syllabus lists object oriented programming, CSE 205, as a prerequisite. The verification half uses classes, inheritance, polymorphism, the factory pattern and virtual classes directly. The gap between knowing Verilog and using UVM is not hardware knowledge, it is object oriented knowledge.

방법론Methodologies

표준화가 핵심이고, 재사용이 아주 중요한 측면이다. 그래서 VIP(Verification IP)라는 말이 나온다. 예를 들어 EDA 벤더에게서 checker를 사서 우리 testbench에 끼워 넣는 식이다.

표준으로는 셋이 언급된다: VMM(Verification Methodology Manual), OVM(Open Verification Methodology), UVM(Universal Verification Methodology).

Standardisation is the key, and reuse is a very important aspect, which is where the term VIP, verification IP, comes from: you can buy a checker from an EDA vendor and plug it into your testbench.

Three standards get named: VMM, the Verification Methodology Manual, OVM, Open Verification Methodology, and UVM, Universal Verification Methodology.

용어 뜯어보기 · 방법론이란 무엇인가Unpacking the jargon · what a methodology even is
한 줄언어가 아니라 라이브러리 + 관행의 묶음. UVM은 SystemVerilog로 쓰인 class 라이브러리다.
무엇을 정하나testbench 부품의 이름과 모양과 붙이는 방법을 정한다. agent는 이렇게 생겼고, driver는 이 함수를 가져야 하고, 하는 식이다.
왜 필요한가정해진 모양이 있어야 남이 만든 것을 가져다 쓸 수 있다. VIP를 사서 끼워 넣는다는 게 이 뜻이다.
순서VMM과 OVM이 먼저 있었고 UVM이 그 둘을 합쳐 표준이 됐다. 지금 새로 배우는 건 UVM이고, 나머지 둘은 예전 코드에서 마주칠 이름이다.
헷갈리는 것UVM은 언어가 아니다. SystemVerilog를 모른 채로 UVM만 배울 수 없고, 그래서 이 과목이 Lecture 17에서 SystemVerilog for Verification을 먼저 한다.
In one lineNot a language but a library plus a set of conventions. UVM is a class library written in SystemVerilog.
What it fixesThe names, shapes and connection rules of testbench components: this is what an agent looks like, this is the method a driver must have.
Why it is neededAgreed shapes are what make it possible to use something somebody else built. That is what plugging in a purchased VIP means.
The orderVMM and OVM came first and UVM merged them into the standard. UVM is what you learn now; the other two are names you meet in older code.
Easy to misreadUVM is not a language. You cannot learn UVM without SystemVerilog, which is why this course does SystemVerilog for Verification first, in Lecture 17.

검증의 과제 (57쪽)

Challenges in verification (slide 57)

  • 설계는 커지고, 사이클 타임은 짧아지고, 도구는 그만큼 확장되지 않는다. 12절의 productivity gap 그래프가 이 문장의 그림 버전이다.
  • 사양을 붙잡고 문서화하는 일 자체가 어렵다.
  • use case를 찾아내는 일이 어렵다. 무엇을 테스트해야 하는지를 아는 것이 곧 문제다.
  • Security verification: 칩이 해서는 안 되는 일을 하지 않는지를 검증하는 것.
  • Safety verification: 고장이 났을 때 시스템이 안전한지.
  • Designs get larger, cycle times get shorter, and tools do not scale to match. The productivity gap chart in §12 is the picture version of this sentence.
  • Capturing and documenting the specification is itself hard.
  • Identifying use cases is hard. Knowing what to test is the problem.
  • Security verification: verifying that a chip does nothing it is not supposed to do.
  • Safety verification: is the system safe when something fails?
네 번째 항목이 가장 어려운 이유Why the fourth one is the hardest

"해야 할 일을 하는가"와 "해서는 안 될 일을 안 하는가"는 검증 난이도가 근본적으로 다르다.

앞의 것은 목록이 있다. 사양에 적힌 기능을 하나씩 확인하면 된다. 뒤의 것은 목록이 없다. "이 칩이 하면 안 되는 일"을 다 적을 수가 없기 때문이다. 커버리지로 "다 했다"고 말할 수도 없다. 무엇을 다 했다는 건지 정의가 안 되기 때문이다.

이게 16절의 coverage 논의와 직결된다. functional coverage는 보고 싶은 것을 적는 도구지, 보면 안 되는 것을 적는 도구가 아니다. 그건 assertion 쪽 일이고, 그래서 security verification은 assertion에 많이 의존한다.

"Does it do what it should" and "does it avoid what it must not" are fundamentally different verification problems.

The first has a list: walk the features in the spec. The second has no list, because you cannot enumerate everything a chip must not do. Nor can coverage say you are finished, because there is nothing to define finished against.

This ties straight back to §16. Functional coverage is a tool for writing down what you want to see, not what must never appear. That belongs to assertions, which is why security verification leans on them heavily.

추상화 네 단Four levels Functional → Behavioral → Structural → Physical. RTL은 가운데 둘 사이. Verilog는 가운데 둘을 다 쓸 수 있다. Functional, behavioral, structural, physical. RTL sits between the middle two, and Verilog covers both of them.
Synthesis 입력이 셋(RTL, constraint, tech library), 출력이 둘(netlist, 리포트). 입력 하나만 바뀌어도 netlist가 달라진다. Three inputs, RTL, constraints and a tech library; two outputs, a netlist and reports. Change any input and the netlist changes.
STA 입력 벡터 없이 모든 path의 지연을 더해서 본다. slack = 요구 시각 − 도착 시각. 음수면 위반. Adds path delays with no input vectors. Slack is required time minus arrival time; negative means a violation.
트레이드오프Trade-offs 공짜 점심은 없다. Area ↔ Delay가 근본이고, testability와 reliability도 면적과 타이밍을 먹는다. No free lunch. Area against delay is the fundamental one, and testability and reliability also eat area and timing.
Rule of 10Rule of 10 버그를 한 단계 늦게 찾을 때마다 비용이 10배. 설계 1, 응용 10000. Each stage later costs ten times more. One at design, ten thousand at the application.
두 갈래Two branches Dynamic(=simulation)과 static(=formal). 대개 섞어 쓴다. formal은 이 과목의 초점이 아니다. Dynamic, meaning simulation, and static, meaning formal. Usually combined. Formal is not this course's focus.
삼각대The trifecta Stimulus · Checkers · Coverage. 자극이 없으면 아무 일도 안 나고, checker가 없으면 항상 통과하고, coverage가 없으면 끝났는지 모른다. Stimulus, checkers, coverage. Without stimulus nothing happens, without checkers everything passes, without coverage you never know when you are done.

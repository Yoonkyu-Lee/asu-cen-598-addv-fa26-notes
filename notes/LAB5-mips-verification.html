What this lab does

Lab 4 가 FIFO 에 checker 를 붙이는 Lab 이었다면, 이번에는 CPU 다. CPU 의 stimulus 는 핀 값이 아니라 프로그램이다. 그 프로그램을 random 으로 만들고, 무엇을 시험했는지 세고, 정답 모델과 맞춰 본다. Lecture 15 가 말한 세 기둥(stimulus, coverage, checking)을 우리 MIPS 에 한 번씩 세우는 과제다.

Lab 4 hung a checker on a FIFO; this time it's a CPU. A CPU's stimulus isn't pin values, it's a program. Generate that program at random, count what it exercised, and compare against a reference model. It's the three pillars of Lecture 15 (stimulus, coverage, checking), each built once on our own MIPS.

다섯 명령어만으로는 0 아닌 값을 만들 수 없다The five instructions alone can't make a non-zero value

register file 은 x 로, dmem 도 x 로 시작한다. ADD, AND, LW, SW, BEQ 는 기존 값을 섞을 뿐 상수를 만들지 못한다. $0 만 믿을 수 있는데 0 끼리 더하고 AND 하면 0 이다. 그래서 setup 이 꼭 필요하다. 우리 Lab 2 코어는 addi 를 decode 하니 setup 을 addi $1, $0, 1 같은 줄로 쓰면 된다. 다른 방법은 testbench 가 dmem 에도 $readmemh 로 초기값을 넣고 setup 이 lw 로 읽는 것이다. "명령어 다섯 개" 제한이 setup 에도 걸리는지는 설명서가 말하지 않는다. setup 은 random 부분이 아니라고 보는 쪽이 자연스럽지만 TA 에게 확인한다(13절 질문 3).

The register file starts at x, and so does dmem. ADD, AND, LW, SW and BEQ only mix existing values; none can make a constant. Only $0 is trustworthy, and adding or ANDing zeros gives zero. So setup isn't optional. Our Lab 2 core decodes addi, so setup can be lines like addi $1, $0, 1. The alternative is for the testbench to $readmemh initial values into dmem too and have setup lw them. The handout doesn't say whether the five-instruction limit applies to setup. Reading setup as outside the random part seems natural, but confirm with the TA (section 13, question 3).

Five instructions, two formats

다섯 명령어가 쓰는 MIPS 형식은 둘이다. ADD 와 AND 는 R-type(opcode 0, 연산은 funct 로 가른다), LW, SW, BEQ 는 I-type(16 bit immediate). 아래는 각 명령어 하나씩을 실제로 bit 로 바꾼 것이다. register 번호와 immediate 는 위 범위 제한 안에서 고른 예다.

The five instructions use two MIPS formats. ADD and AND are R-type (opcode 0, the operation chosen by funct); LW, SW and BEQ are I-type (a 16-bit immediate). Below, one of each is turned into actual bits. The register numbers and immediates are examples picked inside the scope limits.

그림 읽기 · field 를 bit 로Reading the picture · fields to bits

Mind the order. Assembly reads add rd, rs, rt, but the bits are laid out rs, rt, rd. The 3 in add $3,$1,$2 is written first yet lands in the third register field (15:11). ADD 줄을 한 번 따라가 본다. op 000000, rs 00001, rt 00010, rd 00011, shamt 00000, funct 100000 을 이으면 00000000001000100001100000100000. 앞에서 넷씩: 0000=0, 0000=0, 0010=2, 0010=2, 0001=1, 1000=8, 0010=2, 0000=0. 그래서 0x00221820. 둘째 묶음의 0000 은 op 의 마지막 두 bit 와 rs 의 앞 두 bit 가 섞인 것이다. 경계가 안 맞는다는 말이 이것이다.

Follow the ADD row once. Concatenating op 000000, rs 00001, rt 00010, rd 00011, shamt 00000, funct 100000 gives 00000000001000100001100000100000. Four at a time from the left: 0000=0, 0000=0, 0010=2, 0010=2, 0001=1, 1000=8, 0010=2, 0000=0. Hence 0x00221820. The second group's 0000 mixes the last two bits of op with the first two of rs; that's what "boundaries don't line up" means.

BEQ 의 2 가 뜻하는 것. beq $1,$2,2 가 PC = P 에 있으면, 같을 때 다음 PC 는 P + 4 + 2 × 4 = P + 12 다. 기준이 P 가 아니라 P + 4 이고 단위가 byte 가 아니라 word 라서, offset k 는 "바로 뒤 명령어 k 개를 건너뛴다" 와 같다. 우리 RTL 의 pcplus4D + (signimm << 2) 가 정확히 이 식이다.

What BEQ's 2 means. With beq $1,$2,2 at PC = P, if equal the next PC is P + 4 + 2 × 4 = P + 12. The base is P + 4, not P, and the unit is words, not bytes, so offset k means "skip the next k instructions". Our RTL's pcplus4D + (signimm << 2) is exactly that formula.

trickbox 줄. $5 와 0xFC 는 이 페이지가 고른 값이다. $5 는 random 부분이 쓰지 않는 register 라 setup 에서 넣은 표식 값이 끝까지 남는다. 0xFC = 252 는 dmem 의 마지막 word(252 ÷ 4 = 63)이고 random SW 의 주소 넷과 겹치지 않는다. 이 선택의 이유는 05절.

The trickbox row. $5 and 0xFC are this page's choices. $5 is a register the random part never touches, so the marker value setup puts there survives to the end. 0xFC = 252 is dmem's last word (252 ÷ 4 = 63) and doesn't collide with the four random-SW addresses. Why these, in section 05.

BEQ: taken 과 not-taken 을 둘 다

BEQ: both taken and not taken

BEQ 의 결과는 실행 순간의 register 값에 달렸다. generator 가 field 만 random 으로 고르면 결과를 정하지 못한다. 고를 수 있는 길은 셋이다.

A BEQ's outcome depends on register values at the moment it runs. If the generator just picks fields at random, it can't steer the outcome. Three ways to choose:

  • 구조로 정하기. beq $r, $r 는 항상 taken 이다. not-taken 은 setup 이 서로 다른 값을 넣은 직후처럼 값이 다른 것이 확실한 자리에만 둔다. 간단하지만 not-taken 이 적게 나온다
  • generator 안에 작은 모델. register 넷과 주소 넷의 값을 generator 가 따라가며(ADD, AND, LW, SW 의 뜻만 알면 된다) BEQ 를 만들 때 원하는 결과가 나오는 rs, rt 를 고른다. taken 이면 그 뒤 k 개는 실행되지 않으므로 모델도 건너뛴다. ISS 의 아주 작은 판을 하나 짜는 셈이다. Part 5 를 위해서도 쓸모가 있다
  • 그냥 random 으로 두고 seed 를 많이. rs 와 rt 를 넷 중에서 따로 고르면 네 번에 한 번은 같은 register 라 무조건 taken 이고, 나머지는 그때의 값에 달렸다. taken 이 아주 드물지는 않지만 비율을 정할 수 없고, offset × 결과 여덟 칸이 seed 수에 맡겨진다. coverage 가 남은 구멍을 보여 주고 그걸 보고 generator 를 고치는 것이 이 Lab 이 말하는 반복이다
  • Decide it structurally. beq $r, $r is always taken. Put not-taken ones only where values are known to differ, like right after setup loads distinct values. Simple, but not-taken stays rare
  • A small model inside the generator. The generator tracks the four registers and four addresses (it only needs the meaning of ADD, AND, LW and SW) and, when making a BEQ, picks rs and rt that give the outcome it wants. If taken, the next k don't execute, so the model skips them too. That's writing a very small ISS, which pays off again in Part 5
  • Leave it random and run many seeds. Pick rs and rt independently from four and one time in four they're the same register, always taken; otherwise it depends on the values at that moment. Taken isn't rare, but you can't set the ratio, and the eight offset × outcome bins are left to the number of seeds. Coverage showing the remaining holes, and you fixing the generator in response, is the iteration this lab is about

목적지 범위는 설명서가 따로 요구한다. index i 의 BEQ 가 offset k 로 taken 이면 다음 실행은 i + 1 + k 다. 이게 trickbox 의 index 를 넘으면 프로그램 밖(채우지 않은 imem 이나 뒤 채움)으로 간다. 그래서 BEQ 를 만들 때 randomize() with { imm <= last - i - 1; } 처럼 남은 거리로 묶는다. offset 이 1–4 로 전부 앞쪽이라 loop 는 생길 수 없다. 끝은 반드시 온다.

The target range is a separate handout requirement. A BEQ at index i, taken with offset k, continues at i + 1 + k. If that's past the trickbox's index, execution walks off the program (into unloaded imem or the padding). So bound it by the remaining distance when making the BEQ, something like randomize() with { imm <= last - i - 1; }. With offsets 1–4, all forward, no loop can form; the end always comes.

Slide 5's handwriting and the handout's example write 0xdead_beef to address 0xFFFF. On our core both are a problem. Address: with base $0 the address is the immediate, and the 16-bit immediate is sign-extended: 0xFFFF becomes −1, giving address 0xFFFFFFFF, not even a multiple of 4. A trickbox waiting for dataadr == 32'hFFFF waits forever. Value: getting the 32-bit constant 0xDEADBEEF into a register normally takes lui and ori, and our decoder has neither. So this page switched to address 0xFC (positive, word-aligned, inside dmem) and a 15-bit marker that addi can load. Ending on the address alone is fine too. The deck's values read as examples.

Part 3 · What the monitor sees

monitor 는 fetch interface 를 본다. 그런데 fetch 한 것이 곧 실행된 것은 아니다. pipeline 이 멈추면 같은 명령어가 두 번 보이고, branch 가 taken 이면 fetch 했다가 버린 명령어가 섞인다. coverage 가 무엇을 세는지는 여기서 정해진다.

The monitor watches the fetch interface. But fetched isn't the same as executed. When the pipeline stalls the same instruction shows up twice, and a taken branch mixes in an instruction that was fetched and then thrown away. This is where you decide what coverage actually counts.

  • A, c3: 0x30 fetch. 그래서 fetch 주소는 28, 2C, 30, 34 이고 retire 는 beq, and 다
  • B: 같은 자리의 beq 가 not-taken 이면 2C 를 버리지 않고 계속 간다. fetch 주소는 28, 2C, 30, 34 로 A 와 똑같다. offset 1 이 건너뛰는 명령어는 바로 다음 것 하나뿐이고, taken 이든 아니든 그것은 이미 fetch 됐다. 다른 것은 retire 줄뿐이다
  • 그래서: offset 2–4 로 taken 이면 주소가 뛰어서(예: 2C 다음 34) fetch 만 보고도 알 수 있다. offset 1 의 taken 은 fetch 주소로 구별이 안 된다. taken/not-taken bin 을 fetch 만으로 세면 offset 1 의 taken 은 영원히 not-taken 으로 잘못 세진다
  • C, c3: lw 가 E, 그 값을 쓰는 add 가 D. lwstallD = 1 이라 PC 와 F 가 멈춘다. 이 cycle 의 F 는 0x48
  • C, c4: F 에 다시 0x48. 멈춘 것은 add 인데 두 번 보이는 것은 add 다음 명령어다. fetch 는 consumer 보다 한 칸 앞서 있기 때문이다. BEQ 의 stall 도 같은 모양이고, 두 cycle 멈추면 세 번 보인다
  • 초록 줄: 그 아래가 ISS 가 보는 세상이다. Part 5 의 비교는 이 줄로 한다
  • A, c1: fetch beq $1,$1,1 at 0x28. Comparing a register with itself, it's always taken; the target is 0x28 + 4 + 1 × 4 = 0x30
  • A, c2: the beq resolves in D: takeBranchD = 1. In that very cycle F is already fetching the next address, 0x2C. At the posedge ending c2, the PC goes to 0x30 and the 0x2C about to enter D is discarded (instrD to 0, validD to 0)
  • A, c3: fetch 0x30. So the fetch addresses are 28, 2C, 30, 34, and what retires is beq, and
  • B: if the same beq isn't taken, 2C isn't discarded and execution continues. The fetch addresses are 28, 2C, 30, 34, exactly as in A. Offset 1 skips only the very next instruction, and taken or not, that one has already been fetched. Only the retire line differs
  • So: a taken branch with offset 2–4 makes the address jump (2C then 34, say), visible from fetch alone. A taken offset-1 branch can't be told apart by fetch addresses. Count taken/not-taken bins from fetch alone and an offset-1 taken branch is forever miscounted as not taken
  • C, c3: the lw is in E and the add that uses it in D. lwstallD = 1 freezes the PC and F; this cycle F holds 0x48
  • C, c4: 0x48 again in F. The add is what stalled, but what appears twice is the instruction after the add, because fetch runs one slot ahead of the consumer. A BEQ stall looks the same, and a two-cycle stall shows it three times
  • The green lines: that's the world the ISS sees. Part 5 compares on those lines

그래서 monitor 가 할 일 셋

So the monitor has three jobs

  1. 같은 fetch 를 두 번 세지 않는다. PC 가 바뀔 때만 새 transaction 을 만든다. offset 이 전부 앞쪽이라 PC 가 같은 값으로 돌아오는 일은 stall 말고는 없다. Lecture 13 15절의 "요청 시점이 아니라 받아들여진 시점에 센다" 와 같은 이야기다
  2. 버려진 fetch 를 표시한다. fetch interface 만으로는 불가능한 경우가 있다(위 B). 이 페이지의 제안은 takeBranchD 를 XMR 로 interface 에 한 줄 더 싣는 것이다. 그 cycle 의 F 명령어가 버려지는 것이다. 설명서가 interface 신호에 "등" 을 붙였으니 범위 안으로 읽히지만, 리포트에 이유를 적는다
  3. transaction 을 매번 새로 만든다. Lab 4 함정과 같다. 한 object 를 재사용하면 analysis port 뒤의 모두가 같은 handle 을 들고 있게 된다. 샘플 serialalu_monitor 는 transaction 을 forever 루프 밖에서 한 번만 만들고 계속 write 한다. 그 부분은 따라 하지 않는다
  1. Don't count one fetch twice. Make a new transaction only when the PC changes. All offsets are forward, so outside a stall the PC never returns to the same value. Same idea as Lecture 13 §15's "count when it's accepted, not when it's requested"
  2. Mark discarded fetches. Sometimes it's impossible from the fetch interface alone (case B above). This page's suggestion: carry takeBranchD into the interface by XMR as one more wire; when it's 1, that cycle's F instruction is the one discarded. The handout's interface list ends in "etc.", so this reads as within scope, but give the reason in the report
  3. Make a fresh transaction every time. Same trap as Lab 4: reuse one object and everyone behind the analysis port holds the same handle. The sample serialalu_monitor creates its transaction once outside the loop and keeps write-ing it; don't copy that part

둘째와 첫째가 부딪치는 곳이 하나 있다. BEQ 가 stall 하는 동안 F 에는 그 다음 명령어가 머물러 있고, takeBranchD 는 stall 이 풀리는 마지막 cycle 에야 1 이 된다. PC 가 바뀔 때 바로 write 하면 그 표시를 놓친다. 그래서 아래 조각은 transaction 하나를 들고 있다가 다음 PC 가 나타날 때 보낸다.

Jobs one and two collide in one spot. While a BEQ stalls, the next instruction sits in F, and takeBranchD only goes to 1 in the last cycle, when the stall releases. write the moment the PC changes and you miss that mark. So the fragment below holds one transaction and sends it when the next PC shows up.

task run_phase(uvm_phase phase);
  instruction cur;
  bit [31:0] cur_pc = '1;
  wait (vif.reset == 0);             // @(negedge reset) 는 이미 내려간 뒤면 영영 안 온다// @(negedge reset) never comes if it already fell
  forever begin
    @(posedge vif.clk);
    if (vif.pc != cur_pc) begin        // 새 fetch. stall 중 반복은 건너뛴다// a new fetch; repeats during a stall are skipped
      if (cur != null) ap.write(cur);  // 앞의 것이 이제 완성됐다// the previous one is now complete
      cur = instruction::type_id::create("tr");   // 매번 새 object// a fresh object every time
      cur.decode(vif.instr);
      cur.pc = vif.pc;  cur_pc = vif.pc;
    end
    if (vif.take_branch) cur.squashed = 1;   // XMR 로 이은 takeBranchD// takeBranchD, wired in by XMR
  end
endtask

pc, squashed 는 명령어 class 에 이 페이지가 더한 field 다(rand 아님). reset 을 wait 로 기다리는 이유는 05절의 initial 블록이 reset 을 내린 뒤에 run_test() 를 부르기 때문이다. monitor 가 시작할 때 reset 은 이미 0 이고, @(negedge vif.reset) 은 다음 하강 엣지를 기다리다 끝까지 멈춘다.

pc and squashed are fields this page adds to the instruction class (not rand). The reason to wait on reset: the initial block in section 05 calls run_test() after deasserting reset. When the monitor starts, reset is already 0, and @(negedge vif.reset) would sit waiting for a falling edge that never comes.

coverage 는 fetch 를 세나 retire 를 세나Does coverage count fetches or retirements?

설명서는 monitor 를 fetch interface 에 두라고 했다. 글자 그대로 하면 버려진 fetch 도 세지고, 그 명령어와 이어진 "의존 쌍" 과 "gap" 도 세진다. 실제로는 일어나지 않은 hazard 를 덮었다고 기록하는 셈이다. 고를 길은 셋이다. (1) fetch 를 그대로 세고, 그 한계를 리포트에 적는다. (2) 위처럼 버려진 것을 표시해 collector 가 건너뛴다. (3) monitor 를 D 나 W 단계에 둔다. 셋째는 설명서와 어긋난다. 이 페이지는 (2) 를 권한다. 어느 쪽이든 coverage 의 숫자가 무엇을 센 것인지 리포트에 한 줄 적는다. 데모에서 나오기 좋은 질문이다.

The handout puts the monitor on the fetch interface. Taken literally, discarded fetches get counted too, along with the "dependent pairs" and "gaps" they form. You'd be recording hazards as covered that never happened. Three ways out: (1) count fetches as they are and state the limitation in the report; (2) mark discarded ones as above and have the collector skip them; (3) put the monitor in D or W. The third departs from the handout. This page recommends (2). Whichever you pick, put one line in the report saying what your coverage numbers count. It's a natural demo question.

field 는 명령어 하나만 보면 센다. 순서, 의존, gap 은 앞에 무엇이 있었는지를 알아야 센다. 그리고 run 하나는 프로그램 하나라서, 100% 는 run 여럿을 합쳐야 닿는다.

Fields can be counted from one instruction. Orders, dependencies and gaps need to know what came before. And one run is one program, so 100% only comes from merging several runs.

순서와 gap 을 세는 법

How to count orders and gaps

샘플 collector 의 write() 안 주석이 "Create a queue" 다. 최근 다섯 개(버려진 것 제외)를 queue 에 담아 두고, 새 명령어가 올 때마다 뒤를 본다.

The comment inside the sample collector's write() says "Create a queue". Keep the last five (discarded ones excluded) in a queue and look back each time a new instruction arrives.

  1. 순서: 직전 것의 opcode 와 지금 opcode. transition bin (ADD, AND, LW, SW, BEQ => ADD, AND, LW, SW, BEQ) 이 25 칸을 만든다
  2. register 의존: 지금 명령어가 읽는 register($0 제외)마다 queue 를 가까운 쪽부터 훑어 그 register 를 쓴 첫 명령어를 찾는다. 찾은 위치 k(0 = 바로 앞)가 사이에 낀 수다. 더 멀리 있는 producer 는 보지 않는다. 사이에서 누가 다시 썼다면 그쪽이 진짜 producer 이기 때문이다
  3. 메모리 의존: LW 이면 같은 주소에 쓴 가장 가까운 SW 를 같은 방식으로
  4. branch 결과: BEQ 다음에 온 명령어가 버려진 것으로 표시됐으면 taken. 아니면 not-taken
  1. Order: the previous opcode and this one. The transition bin (ADD, AND, LW, SW, BEQ => ADD, AND, LW, SW, BEQ) makes 25 bins
  2. Register dependency: for each register the current instruction reads (not $0), scan the queue from the nearest end for the first instruction that wrote it. Its position k (0 = immediately before) is the in-between count. Don't look further back: if someone in between rewrote it, that's the real producer
  3. Memory dependency: for an LW, the nearest SW to the same address, the same way
  4. Branch outcome: if the instruction after a BEQ was marked discarded, taken; otherwise not taken
covergroup cg_dep with function sample(instruction::op_e p, instruction::op_e c, int gap);
  cp_p : coverpoint p   { bins b[] = {instruction::ADD, instruction::AND, instruction::LW}; }
  cp_c : coverpoint c   { bins b[] = {instruction::ADD, instruction::AND, instruction::SW, instruction::BEQ}; }
  cp_g : coverpoint gap { bins g[] = {[0:4]}; }   // 0 은 설명서 밖. 04절 함정// 0 is outside the handout; see §04's trap
  x    : cross cp_p, cp_c, cp_g;                // 3 × 4 × 5 = 60 칸// 3 × 4 × 5 = 60 bins
endgroup
"모든 coverpoint" 와 cross 의 칸 수"Every coverpoint" and the size of a cross

설명서는 모든 coverpoint 가 맞을 때까지 반복하라고 한다. cross 를 크게 걸면 칸이 곱으로 늘어 100% 가 멀어진다. 위 cross 만 60 칸이고 field 쪽에 opcode × rs × rt 를 걸면 5 × 4 × 4 = 80 칸이 더 생긴다. 그중에는 만들 수 없는 칸도 있다. 예를 들어 LW 의 rs 는 $0 으로 고정했으니 LW × rs=$1 은 영원히 빈다. 그런 칸은 ignore_bins 로 빼고(L13 15절) 리포트에 이유를 적는다. 빼지 않고 "도달 불가" 로 남겨 두면 그 숫자는 generator 의 실패가 아니라 모델의 실수다.

The handout says to iterate until every coverpoint is hit. A big cross multiplies bins and pushes 100% away. The cross above alone is 60 bins, and opcode × rs × rt on the field side adds 5 × 4 × 4 = 80 more. Some bins can't be produced at all: LW's rs is fixed at $0, so LW × rs=$1 stays empty forever. Drop such bins with ignore_bins (L13 §15) and give the reason in the report. Left in as "unreachable", that number reflects a modelling mistake, not a generator failure.

seed 하나에 run 하나, run 하나에 vdb 하나

One seed per run, one vdb per run

설명서의 순서: seed 를 +ntb_random_seed=<값> 로 바꿔 가며 돌리고, run 마다 -cm_dir 로 vdb 디렉터리를 따로 두고, 끝에 urg 로 합친다. 샘플 serialalu_uvm/Makefile 이 compile 과 run 양쪽에 -cm line+cond+fsm+branch+tgl 을, run 에 +ntb_random_seed=244 를 고정으로 넣어 두었다. 그 seed 를 변수로 바꾸는 것이 첫 일이다.

The handout's order: run with the seed varied via +ntb_random_seed=<value>, give each run its own vdb directory with -cm_dir, and combine them at the end with urg. The sample serialalu_uvm/Makefile puts -cm line+cond+fsm+branch+tgl on both compile and run, and hard-codes +ntb_random_seed=244 on the run. Turning that seed into a variable is the first job.

RTL 쪽 trace: 어디서, 어떤 순서로

The RTL trace: where, and in what order

ISS 는 pipeline 을 모른다. 그래서 비교는 cycle 이 아니라 retire 에서 한다(L15 16절). 우리 코어에서 register 쓰기가 확정되는 곳은 W, 메모리 쓰기는 M 이다. testbench 에서 XMR 로 읽으면 RTL 을 고치지 않아도 된다.

The ISS knows nothing about the pipeline, so the comparison is at retire, not per cycle (L15 §16). On our core, register writes become final in W and memory writes in M. Reading them by XMR from the testbench means the RTL stays untouched.

integer tf;
initial tf = $fopen("rtl_trace.txt", "w");
always @(posedge clk) if (!reset) begin
  // W 가 먼저다. 같은 엣지에서 W 의 명령어가 M 의 명령어보다 하나 앞선 것이다// W first: at the same edge, W holds the instruction one older than M
  if (dut.mips.dp.validW && dut.mips.dp.regwriteW && dut.mips.dp.writeregW != 0)
    $fdisplay(tf, "R %0d %08h", dut.mips.dp.writeregW, dut.mips.dp.resultW);
  if (memwrite)
    $fdisplay(tf, "M %08h %08h", dataadr, writedata);
end
  • 한 always 블록에 W 먼저. 같은 posedge 에서 W 에 있는 명령어는 M 에 있는 것보다 하나 앞선 명령어다. 둘을 다른 always 블록에서 찍으면 같은 시각의 두 블록 순서가 정해져 있지 않아 줄 순서가 바뀔 수 있다
  • BEQ 는 줄이 없다. register 도 메모리도 안 쓰기 때문이다. 그래도 검사는 된다. 틀린 쪽으로 갔다면 그 뒤에 나와야 할 쓰기가 빠지거나 없어야 할 쓰기가 생긴다. 이것이 02절의 검사 4(개수)다. 더 직접 보려면 W 까지 PC 를 실어 보내 retire 한 PC 를 줄마다 붙인다. 우리 pipeline 은 D 이후로 PC 를 들고 가지 않으니 그건 RTL 수정이다
  • SW 는 M 줄이다. 주소와 데이터 둘 다 맞아야 한다. trickbox store 도 마지막 M 줄로 찍힌다. ISS 쪽에도 같은 store 가 있다
  • $finish 와의 경주. trickbox 가 store 를 본 그 엣지에서 바로 $finish 하면 같은 엣지의 trace 출력과 순서가 정해져 있지 않다. 05절 코드가 한 clock 더 기다리는 이유다
  • One always block, W first. At the same posedge, the instruction in W is one older than the one in M. Print them from two always blocks and, since the order of two blocks at the same time is undefined, lines can come out swapped
  • A BEQ has no line, since it writes neither a register nor memory. It's still checked: go the wrong way and writes that should follow go missing, or writes that shouldn't exist appear. That's check 4 (count) in section 02. To see it directly, carry the PC down to W and stamp each line with the retired PC. Our pipeline drops the PC after D, so that's an RTL change
  • An SW is an M line, address and data both. The trickbox store shows up as the last M line; the ISS has the same store
  • Racing $finish. If the trickbox calls $finish at the very edge it sees the store, its order against that edge's trace output is undefined. That's why section 05's code waits one more clock

Three programs and a Makefile

10 개 이상짜리 셋 이상이다. 손으로 쓰면 무엇을 노렸는지 리포트에 적기 쉽다. 예를 들어 (1) 04절 표의 gap 0–4 를 ALU → ALU 로 한 줄씩, (2) LW → BEQ 를 붙여 두 cycle stall 과 taken/not-taken 둘 다, (3) 같은 주소에 SW 다음 LW 와 offset 1 의 taken. generator 의 seed 셋을 쓰는 것도 된다. Makefile 은 make check 하나로 셋을 차례로 돌리고, 프로그램마다 PASS 나 첫 불일치를 찍게 한다.

Three or more, ten instructions or more each. Hand-written ones make it easy to say in the report what each targets. For example: (1) section 04's gaps 0–4 for ALU → ALU, one line each; (2) LW → BEQ for the two-cycle stall, both taken and not taken; (3) SW then LW to the same address, plus a taken offset 1. Three generator seeds also qualify. Have the Makefile run all three in turn from a single make check, printing PASS or the first mismatch per program.

왜 이걸 배우는가

Why this is worth learning

Lab 2 에서 우리는 프로그램 넷을 손으로 쓰고 "TEST PASSED" 를 받았다. 그리고 그 기록의 마지막 절이 "코드는 있는데 확인이 없는 경로" 를 셋 남겼다. 손으로 쓴 test 는 무엇을 안 시험했는지 알려 주지 않는다. 이번 Lab 은 그 질문에 세 도구로 답한다. random generator 가 사람이 생각 못 한 조합을 만들고, coverage 가 그중 무엇이 실제로 일어났는지 세고, ISS 가 일어난 일이 맞았는지 판정한다. Lecture 15 가 말한 coverage-driven constrained random 검증을 처음으로 끝까지 한 바퀴 도는 것이다. 그리고 이 Lab 의 UVM 부분은 driver 없이 monitor 와 subscriber 만 쓴다. UVM 강의 셋이 그린 그림의 오른쪽 절반(관찰하고 세는 쪽)만 먼저 손에 익히는 셈이다.

In Lab 2 we hand-wrote four programs and got "TEST PASSED". The record's last section then left three "paths with code but no check". Hand-written tests don't tell you what they didn't test. This lab answers that with three tools: a random generator makes combinations nobody thought of, coverage counts which of them actually happened, and the ISS judges whether what happened was right. It's the first full lap of the coverage-driven constrained-random verification Lecture 15 describes. And the UVM part here uses only a monitor and a subscriber, no driver: you get hands-on with the right half of the UVM lectures' picture (the observing and counting side) first.

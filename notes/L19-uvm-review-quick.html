큰 그림: 두 나무, 모양, phase

Big picture: two trees, shape, phases

  • 2쪽 object 대 component: object 는 시뮬레이션 중에 만들어지고 버려진다(transaction). component 는 처음에 한 번 만들어져 끝까지 살고 phasing 에 참여한다(driver, monitor, agent). build 가 끝난 뒤에는 component 를 만들 수 없다
  • Slide 2, object vs component: objects are created and dropped during the run (transactions); components are built once, live to the end and take part in phasing (driver, monitor, agent). You can't create a component once build is over
  • 3쪽 class 계층과 11쪽 parent 대 super: class 나무의 위 칸이 super(extends, 컴파일 때), testbench 나무의 위 칸이 parent(create(name, this), 실행 중). super.new(name, parent) 한 줄에 둘이 다 나온다. 맨 위 뿌리는 uvm_void
  • Slide 3's class tree and slide 11's parent vs super: the box above in the class tree is super (extends, compile time); in the testbench tree, parent (create(name, this), run time). super.new(name, parent) holds both. The root is uvm_void
  • 4~7쪽 testbench 모양: Top(module) 안에 Test ⊃ Env ⊃ Agent, Scoreboard, Coverage Collector. interface 하나에 agent 하나(6, 7쪽은 둘), CFG 는 설정 object, sequence 는 env 밖 test 안. Top 은 module 이고 21쪽의 uvm_top(uvm_root), test 의 instance 이름 uvm_test_top 과 다르다
  • Slides 4 to 7, the shape: inside Top (a module), Test ⊃ Env ⊃ Agent, Scoreboard, Coverage Collector. One agent per interface (two on slides 6 and 7); CFG is a settings object; sequences sit in the test, outside the env. Top is a module, not slide 21's uvm_top (uvm_root) nor the test instance name uvm_test_top
  • 5쪽 data flow(원본은 움직이는 GIF): sequence → sequencer → driver → 핀 → monitor → scoreboard. 자세한 판에 한 칸씩 밟는 슬라이더가 있다
  • Slide 5, data flow (an animated GIF in the original): sequence → sequencer → driver → pins → monitor → scoreboard. The full version has a step-by-step slider
  • 9~10쪽: 9쪽은 L16 의 run_test 그림에 "Kind of a bad name" 한 줄을 붙였다. 10쪽 phase 그림은 check 를 포함하고 run-time phase 를 run 과 나란히 그려서 L16 노트가 짚은 두 함정을 바로잡는다. 시간을 쓰는 것은 run 쪽뿐
  • Slides 9 to 10: slide 9 is L16's run_test figure plus "Kind of a bad name". Slide 10's phasing picture includes check and draws the run-time phases beside run, settling two traps from the L16 note; only the run side takes time

이름과 db

Names and the db

함정 · transactor 는 어느 층인가Trap · which layer is a transactor?

11쪽은 VIP / Agent, BFM / Driver, Monitor, Transactor 로 줄을 나눈다. 같은 강사의 Lecture 13 4쪽은 driver + monitor 묶음을 "an Agent or a BFM or a Transactor" 라고 했다. 이 덱은 transactor 를 driver, monitor 쪽 줄에 놓아 Feldman 의 쓰임(agent 안의 낱개 부품)과 같아졌다. 뜻은 수업에서 확인할 것. UVM 에는 transactor 라는 class 가 없다. VIP 는 층이 아니라 재사용, 구매 단위의 이름이다.

Slide 11 splits the lines as VIP / Agent, BFM / Driver, Monitor, Transactor. The same instructor's Lecture 13 slide 4 called the driver + monitor bundle "an Agent or a BFM or a Transactor". This deck puts transactor on the driver/monitor line, matching Feldman's usage (an individual part inside an agent); confirm in class. UVM has no transactor class. VIP isn't a layer but a word for a reused or bought unit.

12쪽 config_db 대 resource_db. config_db 는 resource_db 위에 지은 component 용, hierarchy aware 판이다. set(this, "env.agent", "num_transactions", 100) 을 test 에서 부르면 scope 가 "uvm_test_top" + "." + "env.agent" = "uvm_test_top.env.agent" 가 되고, agent 의 get(this, "", ...) 이 자기 full name 으로 같은 scope 를 만들어 100 을 받는다. resource_db 는 set("GLOBAL", ...) / read_by_name("GLOBAL", ...) 처럼 scope 를 문자열로 직접 쓴다. "GLOBAL" 은 예약어가 아니다.

Slide 12, config_db vs resource_db. config_db is the component-oriented, hierarchy-aware layer built on resource_db. Called in the test, set(this, "env.agent", "num_transactions", 100) makes the scope "uvm_test_top" + "." + "env.agent" = "uvm_test_top.env.agent"; the agent's get(this, "", ...) builds the same scope from its full name and receives 100. resource_db takes the scope as a string you write, as in set("GLOBAL", ...) / read_by_name("GLOBAL", ...); "GLOBAL" is not a keyword.

Macro, factory, item 보내기

Macros, factory, sending items

  • 13쪽 field macro: .print(), .copy(), .compare() 를 공짜로 준다. field 를 등록하지 않으면 compare() 가 늘 같다고 나온다(UVM 1.2 보충)
  • Slide 13, field macros: .print(), .copy(), .compare() for free. Register no fields and compare() always says equal (UVM 1.2 supplement)
  • 14쪽: `uvm_object_utils + create("txn") 대 `uvm_component_utils + create("driver", this)
  • Slide 14: `uvm_object_utils + create("txn") vs `uvm_component_utils + create("driver", this)
  • 15쪽 factory: testbench 를 고치지 않고 바꿔 끼운다(예: error_injection_driver). 이 수업은 override 를 안 쓰지만 ::type_id::create() 는 쓴다
  • Slide 15, factory: swap parts without editing the testbench (e.g. error_injection_driver). This course won't use overrides, but use ::type_id::create() anyway

TLM 연결과 debug

TLM wiring and debug

  • 17쪽: port 는 부르고 싶은 쪽, export 는 넘겨주는 쪽, imp 가 구현하는 쪽. 18쪽: 보통 port 는 driver–sequencer, blocking 도 있고 1 대 1. analysis port 는 monitor–subscriber, non-blocking write(), 1 대 N
  • Slide 17: a port wants to call, an export forwards, an imp implements. Slide 18: an ordinary port links driver and sequencer, may block, one to one; an analysis port links monitor to subscribers, non-blocking write(), one to many
  • 19쪽: analysis port 에는 저장소가 없다. 나중에 처리하려면 uvm_tlm_analysis_fifo 의 analysis_export 에 잇고 get() 으로 꺼낸다(비면 기다린다)
  • Slide 19: an analysis port stores nothing; to process later, connect to a uvm_tlm_analysis_fifo's analysis_export and get() (blocks when empty)
  • 20쪽: 입구가 둘 필요하면 `uvm_analysis_imp_decl(_before), (_after) 로 imp class 를 만들고 write_before(), write_after() 를 구현한다. 늘리는 것은 port 가 아니라 imp 다. write_* 는 function 이라 그 안에서 시간을 기다릴 수 없다
  • Slide 20: for two inputs, `uvm_analysis_imp_decl(_before) and (_after) define imp classes, and you implement write_before() and write_after(). What multiplies is the imp, not the port. write_* are functions, so no waiting inside
  • 21쪽 debug: .print(), `uvm_info 등, actual.compare(expected), get_full_name()(계층 경로), get_type_name()(class 이름), uvm_top.print_topology()(end_of_elaboration 에서)
  • Slide 21, debug: .print(), `uvm_info and friends, actual.compare(expected), get_full_name() (hierarchical path), get_type_name() (class name), uvm_top.print_topology() (in end_of_elaboration)

숨김 27쪽: SV 방식은 type 검사를 받지만 class 마다 넘겨야 하고, UVM 방식은 한 번 set 해서 여럿이 get 하지만 문자열 기반이라 type 검사가 약하다. 25쪽의 resource_db "get()" 은 config_db 의 이름이다(resource_db 는 read_by_name).

Hidden slide 27: the SV way gets type checking but must hand the handle to every class; the UVM way sets once for many gets but is string-based with weaker type checking. Slide 25's resource_db "get()" is config_db's name (resource_db uses read_by_name).

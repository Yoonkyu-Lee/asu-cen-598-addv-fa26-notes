1

결론부터

The short version

이 강의는 SystemVerilog 문법을 훑는다. 그런데 문법 목록으로 외우면 실패한다. 슬라이드가 강의 시작부터 진짜 메시지를 못 박는다.

This lecture walks through SystemVerilog syntax. But memorising it as a feature list fails. The slides nail the real message from the opening.

"It's not a program, it's a design. You're not calling. You're instantiating."

HDL 은 프로그래밍 언어가 아니다. 문장이 병렬로 평가되고, subroutine 을 call 하는 게 아니라 module 을 instantiate 해서 wire 로 연결한다. 문법이 C 랑 비슷하게 생긴 게 이 과목에서 제일 비싼 함정이다.

"It's not a program, it's a design. You're not calling. You're instantiating." An HDL is not a programming language. Statements evaluate in parallel, and you do not call a subroutine, you instantiate a module and wire it up. The fact that the syntax resembles C is the most expensive trap in this course.

그래서 슬라이드가 결론을 파란 박스 두 개로 박아둔다. "Think hardware!" 와 "Draw hardware first. Then write code."

Which is why the conclusion sits in two blue boxes: "Think hardware!" and "Draw hardware first. Then write code."

용어 뜯어보기 · instantiateJargon · instantiate
한 줄In one linemodule 의 사본을 하나 실제로 만들어서 회로에 놓는 것. "부품을 한 개 사서 기판에 납땜하는 것" 에 가깝다.Making an actual copy of a module and placing it in the circuit. Closer to soldering one component onto a board than to calling a function.

2

logic 하나로 끝난 혼란

One keyword ends the confusion

슬라이드 제목이 "Ending the Wire vs. Reg Confusion" 이다. 무엇이 혼란이었냐면, Verilog 에서 reg 라고 선언해도 레지스터가 아닐 수 있었다. 이름이 거짓말을 했다.

The slide is titled "Ending the Wire vs. Reg Confusion". The confusion was that in Verilog a reg declaration might not be a register at all. The name lied.

SystemVerilog 는 logic 하나로 합쳤다. 어느 하드웨어가 되는지는 선언이 아니라 쓰는 방식이 정한다. 다만 다중 드라이버가 필요한 곳에는 여전히 wire 가 남는다.

SystemVerilog folds them into logic. What hardware you get is decided by how you use it, not by the declaration. wire still survives where you genuinely need multiple drivers.

testbench 에서는 규칙이 뒤집힌다. 합성되는 코드에서는 logic 을 쓰지만, testbench 에서는 bit 과 initial 과 지연을 쓴다. 같은 언어의 다른 부분집합이다.

The rule flips in a testbench. Synthesisable code uses logic; testbenches use bit, initial and delays. Same language, a different subset.

3

always 블록으로 의도를 말한다

Signalling intent with always blocks

슬라이드 제목의 핵심 단어가 intent 다. always_comb / always_ff 는 "내가 무엇을 만들 셈이었는지" 를 도구에게 말하는 장치다. 그냥 always 로 쓰면 도구가 알아서 짐작하고, 짐작이 어긋나도 아무도 안 알려준다.

The key word in the slide title is intent. always_comb and always_ff exist to tell the tool what you meant to build. Write a bare always and the tool guesses, and nobody warns you when the guess is wrong.

여기서 오늘 강의에서 가장 중요한 단어가 나온다.

And here is the most important word in this lecture.

용어 뜯어보기 · inference (추론)Jargon · inference
한 줄In one line합성 도구가 RTL 을 읽고 "이건 flip-flop 이겠군" 하고 판단해서 그 하드웨어를 만들어내는 것.The synthesis tool reading your RTL, deciding "that must be a flip-flop", and building it.
왜 어려운가Why it is hard추론은 명령이 아니라 짐작이다. 코드 어디에도 "flip-flop 을 만들어라" 라고 안 적혀 있다. @(posedge clk) 와 <= 라는 모양을 보고 도구가 판단한다.Inference is a guess, not a command. Nowhere does the code say "build a flip-flop". The tool reads the shape, @(posedge clk) and <=, and decides.
헷갈리는 것Easy to misread시뮬레이터는 추론하지 않는다. 코드를 그냥 실행한다. 그래서 시뮬레이션은 맞는데 합성 결과가 다른 상황이 생긴다. 이게 simulation/synthesis mismatch 다.A simulator does not infer. It just runs the code. Hence the case where simulation is right and the synthesised hardware is not: a simulation/synthesis mismatch.

latch 추론이 이 강의 최대의 함정이다. always_comb 안에서 if 나 case 의 가지를 하나라도 안 채우면, 도구는 "값을 유지해야 하나 보다" 하고 latch 를 만들어버린다. 조합 논리를 쓰려다 기억 소자가 생기는 것이다. 그리고 latch 는 STA 로 검증하기 까다롭고 테스트도 어렵다.

Latch inference is the big one. Leave any branch of an if or case unfilled inside always_comb and the tool concludes "the value must be held" and builds a latch. You wanted combinational logic and got memory. Worse, latches are awkward for STA and hard to test.

방어법은 하나다. 모든 가지를 채워라. else 를 빼먹지 말고, case 에 default 를 넣는다.

One defence: fill every branch. Never drop the else, always give a case its default.

4

의미를 붙이는 것들

Things that attach meaning

슬라이드가 typedef 를 두 줄로 설명하는데, 두 번째 줄이 이 강의 후반의 거의 전부를 설명한다. "They help attach semantic meaning to your design."

The slide explains typedef in two lines, and the second one accounts for most of the back half of this lecture: "They help attach semantic meaning to your design."

즉 이 셋은 기능을 추가하는 게 아니라 의도를 코드에 새기는 도구다. 셋 다 없어도 설계는 돌아간다. 있으면 사람이 읽을 수 있고 컴파일러가 실수를 잡아준다.

So these three add no capability; they write intent into the code. The design works without them. With them it becomes readable by humans and checkable by the compiler.

구문Construct 무엇을 말하나What it says 언제 만나나Where you meet it
typedef "이 폭과 이 뜻을 가진 타입에 이름을 준다""Name this width and this meaning" 같은 폭을 여러 곳에서 쓸 때Whenever one width repeats
enum "이 신호가 가질 수 있는 값은 이것들뿐이다""These are the only values this signal may take" FSM 을 쓰는 순간 바로. 슬라이드 넉 장이 이것만 다룬다The moment you write an FSM. Four slides go to it
struct "이 신호들은 한 덩어리다""These signals belong together" 패킷 헤더, 버스 트랜잭션Packet headers, bus transactions

한 줄로 구별하면 enum 은 "값 하나가 무엇인지", struct 는 "여러 신호가 왜 한 덩어리인지" 를 말한다.

One line to tell them apart: enum says what a single value is; struct says why several signals travel together.

배열의 packed 와 unpacked 구분도 여기 낀다. Verilog 에도 있던 것인데 이름이 없었다. SystemVerilog 가 이름을 붙이고 규칙을 정리했다. 이름을 붙였다는 게 이 절의 전부다. 선언에서 타입 이름 왼쪽에 붙은 차원이 packed, 오른쪽이 unpacked 다.

Packed versus unpacked arrays belong here too. Verilog had both but never named them. SystemVerilog gave them names and tidied the rules, and the naming is the whole point. Dimensions left of the name are packed, right of it are unpacked.

5

규모를 다루는 것들

Things that handle scale

여기부터는 문법이 아니라 설계 규모의 문제다. 신호 일곱 개짜리 버스를 module 다섯 개에 연결해본 적이 있으면 왜 이게 있는지 바로 안다.

From here it is not syntax, it is a problem of scale. Wire a seven-signal bus into five modules once and you will know exactly why these exist.

interface 는 그 신호 뭉치에 이름 하나를 주는 것이다. 신호를 추가해도 포트 목록을 다섯 군데 고칠 필요가 없다.

An interface gives that bundle a single name. Add a signal and you do not edit five port lists.

그런데 슬라이드가 스스로 묻는다. "But I didn't specify the direction of the interface ports!" 방향을 안 정하면 양쪽이 같은 신호를 동시에 구동할 수 있다. 그게 multi-drive 다.

Then the slide asks itself: "But I didn't specify the direction of the interface ports!" Without directions, both sides can drive the same signal. That is a multi-drive.

modport 가 그 답이다. 같은 interface 신호가 master 쪽에서는 output 이고 slave 쪽에서는 input 이 되도록 방향을 못 박는다. 덕분에 multi-drive 가 컴파일 시점에 막힌다. 런타임에 x 를 보고 디버깅하는 것보다 훨씬 싸다.

Modport is the answer: it pins the directions so the same signal is an output on the master side and an input on the slave side. Multi-drive is then blocked at compile time, far cheaper than chasing an x at runtime.

마지막으로 package. 슬라이드가 문제부터 말한다. "Verilog has a global namespace." 모든 이름이 한 통에 들어가니 같은 이름이 충돌한다. 그래서 `include 와 `ifdef 가드로 땜질했는데 슬라이드 표현이 "hacky" 다.

Finally package. The slide leads with the problem: "Verilog has a global namespace." Every name lands in one bucket, so identical names collide. The patch was `include plus `ifdef guards, which the slide calls "hacky".

7

시험에 나올 것

What shows up on the quiz

  • inference 가 무엇인가. 그리고 왜 "명령이 아니라 짐작" 인가
  • What inference is, and why it is "a guess, not a command"
  • latch 가 언제 생기나. always_comb 에서 가지를 안 채웠을 때
  • When a latch appears: an unfilled branch inside always_comb
  • blocking(=) vs. non-blocking(<=). 조합에는 앞, 순차에는 뒤. 섞지 않는다
  • Blocking (=) vs. non-blocking (<=). First for combinational, second for sequential, never mixed
  • logic 이 wire/reg 를 대체하는 범위. 다중 드라이버에는 여전히 wire
  • How far logic replaces wire/reg, and that multiple drivers still need wire
  • modport 가 무엇을 막나. multi-drive 를 컴파일 시점에
  • What a modport prevents: multi-drive, at compile time
  • 결정표 다섯 줄. 어떤 상황에 무엇을 쓰는가
  • The five rows of the decision table: which construct for which situation

다음 강의(4 강)는 지금까지 그냥 clk 이라고 써온 그 신호를 정면으로 다룬다. 클럭이 여러 개면 무슨 일이 생기고 리셋을 어떻게 걸어야 하는지가 나온다.

Lecture 15
Case study: CPU verification

DUT 가 CPU 가 되면 stimulus 는 프로그램이고 정답은 ISS 가 낸다. 검증은 BIU 하나에서 system 전체까지 다섯 층으로 쌓아 올리고, RTL 과 ISS 는 매 cycle 이 아니라 명령어가 retire 할 때 맞춘다.

When the DUT is a CPU, the stimulus is a program and the ISS supplies the right answers. Verification is built up in five layers, from a single BIU to the whole system, and the RTL is matched against the ISS not every cycle but when each instruction retires.

이 강의가 하는 일

What this lecture does

지금까지 검증 강의는 FIFO 같은 작은 블록을 DUT 로 놓고 이야기했다. 이 강의는 DUT 를 CPU 로 바꾼다. CPU 는 검증하기 유난히 어려운 DUT 다. 입력이 신호가 아니라 프로그램이고, 같은 프로그램이라도 pipeline 안에서는 stall, forwarding, flush, 추측 실행이 섞여 돌기 때문에 매 cycle 의 정답을 미리 적어둘 수가 없다. 그래서 질문이 셋으로 갈린다. 어디서부터 쌓아 올리나(층), 무엇을 넣나(명령어 생성기), 무엇과 비교하나(ISS).

Until now the verification lectures used small blocks like a FIFO as the DUT. This lecture swaps the DUT for a CPU, which is an unusually hard thing to verify. Its input is a program, not a signal, and inside the pipeline the same program runs with stalls, forwarding, flushes and speculation mixed in, so you cannot write down the right answer for every cycle in advance. That splits into three questions: where do you build up from (the levels), what do you feed it (instruction generators), and what do you compare against (the ISS).

If you take one thing, take retire. The CPU's RTL and the ISS run the same program in completely different ways, so you don't compare every cycle; you compare each instruction's effects when it retires (slide 49). The first half of the lecture is about how to drive the CPU; the second half heads toward this one word.

The three pillars and coverage-driven constrained random

슬라이드 3쪽의 삼각형은 Lecture 2 의 검증의 삼각대 그대로다. Stimulus(무엇을 넣나), Checking(맞았나), Coverage(어디까지 해봤나). 제목은 "The Key to Successful Verification". 2쪽 간지의 발표자 노트에는 "Tweak stimulus" 한 줄이 있는데, 5쪽의 "steer constraints" 와 같은 이야기로 읽힌다.

Slide 3's triangle is Lecture 2's verification tripod unchanged: stimulus (what goes in), checking (was it right), coverage (how much have we tried). Its title is "The Key to Successful Verification". The divider on slide 2 carries a one-line speaker note, "Tweak stimulus", which reads like the same idea as slide 5's "steer constraints".

4쪽이 세 기둥을 하나의 흐름으로 묶는다. 제목이 곧 방법론의 이름이다. Coverage-Driven Constrained Random Verification + Directed Tests.

Slide 4 ties the three pillars into one loop, and its title is the name of the method: Coverage-Driven Constrained Random Verification + Directed Tests.

그림 읽기Reading the picture
  1. 왼쪽 분홍 상자가 testbench 다. 그 안의 Random Generator 가 값을 뽑고 Constraints 가 그 값을 합법적인 범위로 묶는다. 둘이 짝이라 화살표 일곱 개가 Constraints 의 오른쪽 끝에서 나간다
  2. 오른쪽 파란 상자는 DUT 가 할 수 있는 일의 공간이다. 타원 셋이 기능 A, B, C 이고, 주황 점이 그 안에 숨은 버그다. 점선 타원 "?" 는 슬라이드에 이름 없이 그려진 영역이다. 화살표 하나가 거기 닿지만 버그는 없다. 기능 목록에 없는 곳에도 random 은 간다는 뜻으로 읽힌다
  3. 분홍 가는 화살표 일곱이 random stimulus 다. 여섯은 기능 안의 버그 하나씩에 닿고, 하나는 "?" 영역에 닿는다. 버그 일곱 중 여섯을 random 이 찾는다
  4. Feature C 오른쪽 위, 검은 테두리 점이 일곱째 버그다. 기능 C 의 가장자리 밖에 있어서 random 화살표가 하나도 안 간다. 이것은 굵은 화살표 Directed Test C1 만 닿는다. 사람이 그 시나리오를 알고 일부러 쓴 test 다
  5. 초록 점선 셋이 coverage 다. 기능 A, B, C 가 실행될 때마다 왼쪽 아래의 같은 이름 통이 찬다. 통 셋이 다 차 있지 않다(C 가 가장 낮다). 통의 높이가 다음에 무엇을 할지를 정한다. 이게 "coverage-driven" 이다

즉 기본은 constrained random 으로 넓게 찌르고, coverage 로 빈 곳을 보고, random 으로 안 닿는 모서리는 directed test 로 메운다. 이 순서가 다음 절의 coverage 표에서 숫자로 다시 나온다.

  1. The pink box on the left is the testbench. Its Random Generator draws values and its Constraints keep them within legal bounds. They work as a pair, so the seven arrows leave from the right edge of Constraints
  2. The blue box on the right is the space of what the DUT can do. The three ellipses are features A, B and C, and the amber dots are bugs hiding in them. The dashed "?" ellipse is a region the slide draws without a name; one arrow reaches it but there's no bug. Read it as random also going places the feature list doesn't name
  3. The seven thin pink arrows are random stimulus: six land on one bug each inside a feature, one lands in the "?" region. Random finds six of the seven bugs
  4. The dot with a black ring, top right of Feature C, is the seventh bug. It sits just outside C's edge, where no random arrow goes. Only the thick arrow, Directed Test C1, reaches it: a test someone wrote on purpose because they knew the scenario
  5. The three dashed green lines are coverage: each time feature A, B or C runs, the bucket with the same name, bottom left, fills. None of the three is full (C is lowest). The bucket levels decide what to do next. That is what "coverage-driven" means

So the default is to poke widely with constrained random, look for empty spots through coverage, and fill the corners random can't reach with directed tests. The next section's coverage table plays the same sequence out in numbers.

Functional coverage and "are we done?"

슬라이드 5쪽은 functional coverage 하나를 CPU 의 말로 보여준다. 명령어 종류 × destination register 의 cross 다. 명령어 여섯(ADD, SUB, MUL, AND, OR, NOT) 과 register 열(r0~r9)이라 6 × 10 = 60칸이다. 한 칸은 "그 명령어가 그 register 에 결과를 쓴 적이 있나" 다. 6쪽은 문답 셋이다.

Slide 6 is three questions and answers.

  1. "code coverage 100%, functional coverage 100% 면 끝인가?" 아니다. functional coverage 는 정의한 coverage point 만큼만 좋다. 아무도 생각하지 못한 시나리오나 기능 사이의 관계에 버그가 있으면, coverage 표에 그 칸이 없으니 100% 여도 거기는 안 가봤다
  2. "Once we hit 100% code and 100% functional coverage, are we done?" No. Functional coverage is only as good as the coverage points you define. If a bug lives in a scenario or a relationship between features nobody thought of, there's no bin for it, so 100% says nothing about it
  3. "그럼 어떻게 하나?" 완전히 끝날 수는 없지만 그것을 목표로 한다. extended soak verification 과 overlapping verification techniques, 즉 cycle 을 훨씬 더 많이 돌려서 예상 못 한 곳에서 새 버그가 안 튀어나오는지 본다
  4. "How do we solve this?" You can never be fully done, but you aim to be: extended soak verification and overlapping verification techniques, meaning many more cycles, to make sure no new bugs pop out in unexpected areas
  5. "새 버그가 나오면?" 그 시나리오가 앞으로의 run 에서 쳐졌는지 알 수 있게 functional coverage 를 보강한다. 버그 하나가 coverage 표의 새 칸이 된다

IFU 가 하는 일 (이상화한 판)What the IFU does (idealised)

25쪽은 스스로 "Idealised Example" 이라고 밝힌다. 24쪽의 진짜 블록을 다 쓰지 않고 동작만 다섯 단계로 줄였다.

Slide 25 calls itself an "Idealised Example": it skips most of slide 24's real blocks and reduces the behaviour to five steps.

  1. DPU(Data Processing Unit) 가 IFU 에 주소를 보낸다
  2. The DPU (Data Processing Unit) sends an address to the IFU
  3. IFU 는 그 주소의 명령어가 instruction cache 에 있는지, main memory 에서 가져와야 하는지 본다. main memory 에서 가져오면 다음을 위해 cache 에도 넣는다. 한 번에 cache line 하나를 가져오는데 슬라이드는 "512/32 = 16 instructions" 라고 쓴다
  4. The IFU checks whether the instruction at that address is in the instruction cache or must be fetched from main memory. If fetched from memory, it's also placed in the cache for future use. A whole cache line is fetched at a time; the slide writes "512/32 = 16 instructions"
  5. 가져온 명령어를 부분적으로 decode 해서 branch 인지 본다
  6. The instruction is partially decoded to see whether it's a branch
  7. branch 면 branch prediction 을 하고, DPU 로 나가는 명령어에 예측 결과를 붙여 고친다
  8. If so, branch prediction runs and the instruction going to the DPU is modified with the prediction
  9. 명령어는 fetch queue 에 들어가고, DPU 가 요청할 때마다 내보낸다
  10. Instructions go into the fetch queue and are delivered whenever the DPU asks

512/32 = 16 을 풀면. 슬라이드는 단위를 안 적었지만 cache line 이 512 bit(64 byte), 명령어 하나가 32 bit 라고 읽으면 512 ÷ 32 = 16 개다. 이 숫자가 10절에서 한 번 더 나오는데 거기서는 8 이다.

Unpacking 512/32 = 16. The slide gives no units, but reading the cache line as 512 bits (64 bytes) and each instruction as 32 bits gives 512 ÷ 32 = 16. The number comes up again in §10, where it's 8.

Hit and miss differ only in steps 2 and 3. A hit reads the RAM; a miss gets a generator-built line through the BFM and writes it into the RAM, which adds one more check, "is the line the same". 40쪽 간지 다음, 41쪽의 제목이 이 절의 출발점이다. "CPU Stimulus is a program." CPU 는 명령어를 먹으므로 stimulus 가 뜻이 통하는 명령어 열이어야 한다. random instruction generator 는 프로세서를 두들기는 assembly 프로그램을 만든다. random 하게 고를 수 있는 것이 넷이다.

After the divider on slide 40, slide 41's title is where this section starts: "CPU Stimulus is a program." A CPU consumes instructions, so its stimulus must be meaningful instruction sequences. A random instruction generator produces assembly programs that exercise the processor, and can randomize four things:

  • 명령어: 산술, load/store, branch, CSR 접근
  • Instructions: arithmetic, loads/stores, branches, CSR accesses
  • operand: register, immediate 값, 메모리 주소

  • 관계: 명령어 사이의 의존

그냥 random bit 를 넣으면 안 되나Why not just random bits?

42쪽의 답. random bit 는 illegal 명령어로 decode 되거나 하는 일이 거의 없는 프로그램이 된다. 명령어 하나하나가 합법이어도 엉뚱한 주소를 가리키는 등 문제가 남는다. 그래서 generator 에 constraint 가 필요하다.

Slide 42's answer: random bits decode as illegal instructions or make programs that do little work. Even individually legal instructions can go wrong, for example by referring to wrong addresses. So a generator needs constraints.

Even within the deck the role has four names (see the jargon box). The test is "what does it mimic, and how is it used?" Conversely, a reference model isn't always an ISS: a C model attached through Lecture 12's DPI is one, and so is the queue used to verify a FIFO. For a CPU, the ISS just happens to fill that role.

The top row (blue) is the RTL's cycles c1 to c14; the name in a box is the instruction that finished W and retired in that cycle. The program is lw $2,0($0), add $3,$2,$2, sub $4,$3,$2, or $5,$4,$3, beq $4,$2,+1, (the skipped add $6,$3,$3), sw $4,4($0), slt $7,$2,$3, sw $5,8($0).

  1. c1 to c4 are empty: the first instruction, lw, is still passing through F, D, E and M. With five stages, the first retire is in c5
  2. c6 is a stall: add uses lw's result ($2) immediately, so it waited one cycle in D (the load-use stall). That bubble reaches W one cycle later, in c6
  3. c7 to c10: add, sub, or and beq, one per cycle. Along the way sub got add's result forwarded from M, and or got sub's from M and add's from W. None of that is visible here: retire comparison ignores the process and looks only at results
  4. c11 is a flush: beq was taken, so the add $6 fetched behind it was discarded (flush), leaving the gap in c11
  5. c12 to c14: the sw at the target 0x18, then slt, then sw

The bottom row (violet) is the ISS's steps 1 to 8. There are no cycles, so box width means nothing, and there's no stall and no flushed slot; the skipped add $6 never exists in the ISS.

The middle row (pink =) is the comparison. Each time the RTL retires (blue line), the ISS is advanced one step (violet diagonal) and the two effects are matched. RTL c5, c7, c8, c9, c10, c12, c13, c14 pair with ISS 1 to 8. That the cycle numbers and step numbers differ is the whole point. Comparing every cycle would flag c6 and c11, where the RTL did nothing while the ISS had moved on. That's why slide 49 bothers to say "not pipeline state on every clock cycle".

  • lw-use stall 없음. 둘째 줄 add 에서 $3 = 0 으로 갈라지고, 그 뒤로 sub, or 가 연쇄로 틀리고 beq 의 방향까지 바뀐다. trace comparison 으로 돌리면 불일치 줄이 여럿 나오는데 의미가 있는 것은 첫 줄뿐이다
  • No lw-use stall. It splits at the second row with $3 = 0; sub and or go wrong in a chain after it, and even the beq flips direction. Under trace comparison many lines mismatch, but only the first one means anything
  • ISS 초기 메모리 불일치. RTL 은 멀쩡한데 첫 줄부터 갈라진다. 불일치가 곧 RTL 버그는 아니라는 51쪽의 이야기다
  • ISS initial memory mismatch. The RTL is fine, yet everything splits from the first row: slide 51's point that a mismatch is not automatically an RTL bug

이 도구가 단순화한 것. RTL 쪽은 Lab 2 의 구조(M 과 W 에서 E 로 forwarding, lw-use stall, D 에서 beq 를 판정하고 M 에서 D 로 forwarding, taken 이면 F/D 를 비움)를 흉내 낸 JavaScript 모델이지 Lab 2 의 실제 RTL 이 아니다. retire 는 W 단계로 잡았고 sw 의 메모리 쓰기도 W 에서 함께 보고한다. "M→E forwarding 없음" 은 E 단계의 경로만 끊고 D 단계의 beq 비교용 forwarding 은 남겨 두었다. 버그는 한 번에 하나만 넣는다.

What this tool simplifies. The RTL side is a JavaScript model that mimics Lab 2's structure (forwarding from M and W to E, the lw-use stall, beq resolved in D with forwarding from M to D, F/D cleared when taken); it is not Lab 2's actual RTL. Retire is taken at W, and a sw's memory write is reported at W as well. "No M→E forwarding" cuts only the E-stage path and leaves the D-stage forwarding used by the beq comparison. Only one bug at a time.

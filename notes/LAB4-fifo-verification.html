검증을 왜 함? · 문제와 해결: 정답 짝을 옆에 두고 매번 대조한다

Why verify at all? · The problem, and the fix: a trusted twin checked every time

Lab 이야기 전에, "돌려 봤더니 잘 되더라" 가 왜 답이 안 되는지부터.

Before the lab itself: why "I ran it and it looked fine" isn't an answer.

문제: 눈으로 보는 검사는 금방 무너진다

The problem: checking by eye falls apart fast

FIFO 는 편의점 계산대 줄과 같다. 먼저 선 사람이 먼저 나간다. 회로로는 한쪽 clock 으로 숫자를 넣고(winc 를 올리고 wdata 에 값), 다른 쪽 clock 으로 꺼낸다(rinc 를 올리면 rdata 에 나온다). 넣은 순서 그대로 나오면 맞은 것이다.

A FIFO is like a checkout queue: whoever lines up first leaves first. As a circuit, you push numbers in on one clock (raise winc, put a value on wdata) and take them out on another (raise rinc, and it shows up on rdata). If they come out in the order they went in, it works.

이 Lab 의 testbench 는 테스트 세 개로 숫자 48 개를 넣고 48 개를 꺼낸다(16 + 8 + 12 + 12). 파형을 열어 48 쌍을 하나씩 맞춰 보는 것은 한 번은 할 수 있다. 그런데 설계를 한 줄 고칠 때마다 다시 해야 하고, 숫자가 4 만 개가 되면 아예 못 한다. 그리고 사람은 xx 하나쯤 놓친다. 그래서 업계는 testbench 가 스스로 PASS / FAIL 을 찍게 만든다. 이걸 self-checking testbench 라고 부른다.

This lab's testbench pushes 48 numbers through in three tests and pulls 48 out (16 + 8 + 12 + 12). Opening the waveform and matching 48 pairs by hand is doable once. But you'd redo it after every one-line design change, and at 40,000 numbers you simply can't. People also miss the odd xx. So the industry makes the testbench print PASS or FAIL itself: a self-checking testbench.

해결: 같은 입력을 정답 짝에도 넣고, 나올 때마다 대조한다

The fix: feed the same input to a trusted twin, and compare at every output

방법은 간단하다. DUT 에 넣는 값을 정답이라고 믿을 수 있는 아주 단순한 모형에도 똑같이 넣는다. FIFO 라면 "넣은 것을 순서대로 적어 두는 메모장" 이면 충분하다. 이걸 reference model (golden model) 이라고 한다. DUT 에서 값이 하나 나올 때마다 메모장 맨 위 값과 대조하고, 다르면 그 자리에서 오류를 찍는다.

The method is simple. Feed whatever goes into the DUT into a very simple model you can trust as the answer. For a FIFO, "a notepad that writes down what went in, in order" is enough. That's a reference model (golden model). Each time the DUT puts a value out, compare it with the top of the notepad and flag an error right there if they differ.

그림 읽기. 이 Lab 의 Part 2 에서 bug 를 켠 실행(R2)의 첫 테스트, 처음 다섯 쓰기와 다섯 읽기다. 맨 위 줄은 testbench 가 넣은 값이다. 첫 테스트는 0 부터 15 까지를 차례로 넣으니 #1~#5 는 00 01 02 03 04 다. 둘째 줄은 모델이 적어 둔 기댓값으로, 넣은 값을 그대로 베꼈으니 같다. 셋째 줄은 DUT 가 실제로 내놓은 rdata 다. 넷째 읽기까지는 00 01 02 03 으로 같다. 다섯째 읽기에서 DUT 는 xx (한 번도 쓰인 적 없는 메모리 칸의 값, 05 절)를 내놓았고 기댓값은 04 다. 그래서 맨 아래 줄 다섯째 칸이 mismatch 다. 이 실행은 48 개 중 9 개가 이렇게 어긋나 오른쪽 상자처럼 Errors : 9 와 TEST FAILED 로 끝났다. 사람이 파형에서 xx 를 찾을 필요가 없다.

Reading the figure. The first five writes and first five reads of the first test in Part 2's bug-enabled run (R2). The top row is what the testbench pushed: the first test pushes 0 to 15 in order, so #1 to #5 are 00 01 02 03 04. The second row is the model's expected values, copied straight from the input, so they match it. The third row is the DUT's actual rdata. Through the fourth read it's 00 01 02 03, the same. On the fifth read the DUT gave xx (the value of a memory slot that was never written, section 05) where 04 was expected, so the fifth slot in the bottom row is a mismatch. In this run 9 of the 48 differ like that, and it ends with Errors : 9 and TEST FAILED, as in the box on the right. Nobody has to hunt for xx on a waveform.

여기서 의문. 모델도 사람이 짠 건데 모델이 틀리면? 그럴 수 있다. 그래서 모델은 DUT 보다 훨씬 단순하게, 그리고 RTL 이 아니라 명세에서 짠다. 이 Lab 의 C 모델에는 clock 도 gray code 도 synchronizer 도 없다. 배열 하나와 숫자 셋뿐이다. RTL 을 베껴 모델을 만들면 같은 실수가 양쪽에 들어가 서로 맞다고 나온다. 어긋나면 어느 쪽이 틀렸는지는 그때 따로 따진다.

Question. The model is code someone wrote too. What if it's wrong? It can be. That's why the model is much simpler than the DUT and written from the spec, not from the RTL. This lab's C model has no clock, no gray code, no synchronizer: one array and three numbers. Copy the RTL into a model and the same mistake lands on both sides, which then agree. On a mismatch, which side is wrong is worked out separately.

이 Lab 은 이 한 가지 생각을 세 가지 모양으로 짓는다. 모델을 C 로 짜서 부르는 모양(Part 2, 03~05 절), 모델을 SystemVerilog class 로 짜고 부품을 나누는 모양(Part 3, 06~07 절), 모델 없이 "늘 참이어야 하는 규칙" 을 매 클럭 검사하는 모양(Part 4, 08~10 절). 그리고 셋 모두 일부러 고장 낸 DUT 로 검사기가 깨어 있음을 보인다. 통과만 보여 주는 검사기는 잠든 검사기와 구별이 안 되기 때문이다.

The lab builds this one idea three ways: a model written in C and called from the testbench (Part 2, sections 03 to 05), a model written as a SystemVerilog class with the job split into parts (Part 3, sections 06 to 07), and no model at all but rules that must always hold, checked every clock (Part 4, sections 08 to 10). All three are shown awake with a deliberately broken DUT, because a checker that only ever shows passes looks exactly like one that's asleep.

Part 1 · 계획 · 무엇을 돌리고 무엇을 확인하면 끝인가

Part 1 · The plan · What to run, what to check, when you're done

Part 1 의 제출물은 코드가 아니라 문서다. 코드를 짜기 전에 "무엇이 일어나야 하고, 그걸 무엇이 잡나" 를 적는다.

Part 1's deliverable is a document, not code: before writing any, write down "what has to happen, and what catches it if it doesn't".

검증 계획(verification plan)은 세 덩어리다. 구조와 방법(testbench 를 어떤 부품으로 짜고, simulation 으로 할지 formal 로 할지, 언제 끝났다고 할지), 시나리오(어떤 상황을 만들어 볼지), 검사(그 상황에서 무엇이 참이어야 하는지). 우리 계획은 directed simulation, 즉 정해진 순서의 입력을 넣는 시뮬레이션에 self-checking testbench 를 붙이는 것으로 정했다. formal(모든 입력을 수학적으로 따지는 방법)은 이 Lab 에서 돌리지 않는다.

A verification plan has three parts: structure and method (which components the testbench has, simulation or formal, and when you call it done), scenarios (which situations to create), and checks (what must be true in them). Ours is directed simulation, feeding inputs in a fixed order, with a self-checking testbench on top. Formal (reasoning mathematically over every input) isn't run in this lab.

Part 2 · The problem: the answer in C, the testbench in SystemVerilog → DPI-C

정답 짝을 어떤 언어로 짜나. 그리고 시뮬레이터 안의 testbench 가 그걸 어떻게 부르나.

What language the trusted twin is written in, and how the testbench inside the simulator calls it.

문제: 모델은 이미 C 로 있는 경우가 많다

The problem: the model often already exists in C

실제 칩 회사에서 "이 칩이 무엇을 계산해야 하나" 는 RTL 보다 먼저 C 나 C++ 로 짜인다. 아키텍처 팀이 성능을 재려고 만든 모델이다. 검증 팀이 그 정답을 SystemVerilog 로 다시 짜면 일이 두 배가 되고, 옮기다 틀릴 수도 있다. 그래서 있는 C 함수를 testbench 에서 그대로 부르는 통로가 필요하다. 그게 DPI-C (Direct Programming Interface) 다. 비유하면 통역 없이 두 사람이 서로의 전화번호로 직접 거는 것이다. SystemVerilog 쪽에서 import "DPI-C" 로 함수 이름과 인자를 선언해 두면, 시뮬레이터(VCS)가 C 파일을 같이 컴파일해 붙여 준다.

At a real chip company, "what should this chip compute" gets written in C or C++ before the RTL, as a model the architecture team uses to measure performance. If verification rewrites that answer in SystemVerilog, the work doubles and the port can go wrong. So you want a way to call the existing C functions straight from the testbench. That's DPI-C (Direct Programming Interface). Think of it as two people dialling each other directly instead of going through an interpreter. Declare the function name and arguments on the SystemVerilog side with import "DPI-C", and the simulator (VCS) compiles the C file alongside and links it in.

주어진 샘플(dpi.c, dpi_1.sv, dpi_2.sv)은 이 통로를 8 bit 덧셈기로 보여 준다. C 쪽은 add(a, b) 한 줄짜리 함수 하나다. 덧셈은 지금 입력만 보면 답이 나오니 C 쪽에 기억할 것이 없다. FIFO 는 다르다. pop() 의 답은 지금까지 무엇이 들어갔는지에 달려 있다. 그래서 C 모델이 호출과 호출 사이에 상태를 들고 있어야 한다. 설명서가 "상태를 유지하라(2D 배열과 정수 카운터)" 를 맨 먼저 적은 이유다.

The given samples (dpi.c, dpi_1.sv, dpi_2.sv) show this path with an 8-bit adder. The C side is a single one-line function, add(a, b). An adder's answer depends only on the current inputs, so C has nothing to remember. A FIFO is different: what pop() returns depends on everything pushed so far. So the C model has to hold state between calls, which is why the handout's first instruction is to maintain state (an array and integer counters).

해결: 상태를 가진 C 모델 하나, 그걸 부르는 checker module 하나

The fix: one C model with state, one checker module that calls it

그림 읽기. 아래 줄이 DUT 와 stimulus 다. 왼쪽 stimulus 가 winc 와 wdata 를 넣고 DUT 가 wfull 을 돌려준다. 오른쪽은 rinc 를 넣고 rdata, rempty 를 받는다. 분홍은 testbench 가 모는 신호, 파랑은 DUT 가 모는 신호다. 점선 두 줄은 checker 가 그 신호선 여섯 개에 옆에서 귀만 대고 있다는 뜻이다(점이 찍힌 곳). checker 는 아무 신호도 몰지 않으므로 빼도 DUT 와 stimulus 는 똑같이 돈다. checker 상자의 둘째 줄: 쓰기는 wclk 엣지에서, 읽기는 rclk 엣지에서 따로 보고, 가끔 check_status() 로 flag 를 대조한다(04 절). 위 상자가 C 모델이다. 실제 함수 이름은 fifo_ 를 붙인 fifo_reset, fifo_push, fifo_pop, fifo_is_empty, fifo_is_full (그리고 디버그용 fifo_get_count)이다. 보라 화살표가 DPI 통로다. 부르는 방향은 SystemVerilog → C 하나(import)이고 반환값만 거꾸로 온다. 맨 아래 줄: 이 testbench 는 wclk 를 #5 마다, rclk 를 #7 마다 뒤집어서 주기가 10 과 14 다. C 모델의 핵심은 이게 전부다. 16 칸짜리 배열을 원형으로 쓰고, 넣을 자리(write_ptr)와 뺄 자리(read_ptr)와 개수(count)를 센다. 파일 범위 static 변수라 함수가 끝나도 값이 남는다.

That's all there is to the C model: a 16-slot array used as a ring, with the next slot to fill (write_ptr), the next to empty (read_ptr) and the number held (count). They're file-scope static variables, so they keep their values after each call returns.

submitted · part_2/dpi/fifo_model.c · excerpt, condensed

static int fifo_mem[FIFO_DEPTH];                /* FIFO_DEPTH = 16 */
static int write_ptr = 0, read_ptr = 0, count = 0;

void fifo_push(int data) {
    if (count >= FIFO_DEPTH) return;
    fifo_mem[write_ptr] = data & DATA_MASK;          /* 0xFF */
    write_ptr = (write_ptr + 1) % FIFO_DEPTH;
    count++;
}
int fifo_pop(void) {
    if (count <= 0) return -1;
    int data = fifo_mem[read_ptr];
    read_ptr = (read_ptr + 1) % FIFO_DEPTH;
    count--;
    return data;
}
int fifo_is_empty(void) { return (count == 0); }
int fifo_is_full(void)  { return (count == FIFO_DEPTH); }

SystemVerilog 쪽은 같은 이름을 import 로 선언한다. int 는 양쪽이 같은 32 bit 정수라 짝이 맞는다. 8 bit 데이터를 int 로 넘기면 위 24 bit 는 0 이다.

The SystemVerilog side declares the same names with import. int is the same 32-bit integer on both sides, so they pair up; 8-bit data passed as an int has its upper 24 bits zero.

Part 2 · 해결: DUT 가 실제로 받은 엣지에서만 C 를 부른다

Part 2 · The fix: call C only on the edges the DUT really acted on

Part 2 과제 3 번. C 모델은 시간이 없고 DUT 는 clock 두 개 위에서 돈다. checker 가 그 둘을 맞물려야 한다.

Part 2 task 3. The C model has no time; the DUT runs on two clocks. The checker has to mesh the two.

언제 push 하고 언제 pop 하나

When to push and when to pop

설명서는 "testbench 가 winc 를 올리면 push" 라고 적었다. 그대로 짜면 한 군데가 샌다. FIFO 가 실제로 쓰는 조건은 winc && !wfull 이다(가득 찼으면 무시한다). 가득 찬 FIFO 에 winc 가 오면 DUT 는 안 받는데 모델은 받아서, 그 뒤 모든 비교가 한 칸씩 밀린다. 그래서 checker 는 DUT 가 실제로 받은 엣지에서만 모델을 부른다. 읽기도 같아서 rinc && !rempty 일 때만 pop 한다.

The handout says "when the testbench asserts winc, push". Code that literally and one case leaks. The FIFO actually writes on winc && !wfull (a full FIFO ignores the request). If winc arrives while full, the DUT takes nothing but the model takes it, and every comparison after that is off by one. So the checker calls the model only on the edges where the DUT really acted. Reads are the same: pop only on rinc && !rempty.

submitted · part_2/tb/fifo_checker.sv · excerpt, condensed

always @(posedge wclk)
  if (wrst_n && winc && !wfull) begin
    fifo_push(wdata);  write_count++;
  end

always @(posedge rclk)
  if (rrst_n && rinc && !rempty) begin
    expected_data = fifo_pop();  read_count++;
    if (rdata !== expected_data[7:0]) begin
      $error("[CHECKER][DATA MISMATCH] time=%0t expected=0x%02h actual=0x%02h", ...);

두 가지가 숨어 있다. 첫째, rdata 를 읽는 순간. @(posedge rclk) 로 깨어난 바로 그 순간의 rdata 는 엣지 직전 값이다. DUT 의 읽기 포인터는 nonblocking 대입(<=)이라 같은 시각의 뒤쪽 단계에서야 움직이기 때문이다. 그리고 이 FIFO 의 읽기는 조합 회로(rdata = mem[raddr])라, 비어 있지 않으면 맨 앞 값이 이미 rdata 에 떠 있다. 그러니 엣지 직전의 rdata 가 바로 이 엣지에 꺼내지는 값이다. stimulus 가 신호를 하강 엣지에서 바꾸므로 상승 엣지의 checker 와 경합도 없다. 둘째, !==. 한 번도 안 쓴 메모리 칸은 x 다. rdata != expected 에서 한쪽이 x 면 결과가 x 이고 if (x) 는 거짓 쪽으로 가서 오류가 안 난다. !== 는 x 까지 값으로 보고 비교한다. 05 절의 bug 가 바로 이 x 칸을 만든다.

Two things are hiding here. First, the moment rdata is read. The rdata seen right as @(posedge rclk) wakes up is the value from just before the edge, because the DUT's read pointer uses a nonblocking assignment (<=) and moves in a later region of the same time step. And this FIFO reads combinationally (rdata = mem[raddr]), so when it isn't empty the head value is already on rdata. The rdata from just before the edge is exactly what this edge pops. The stimulus changes signals on the falling edge, so there's no race with a checker on the rising edge either. Second, !==. A memory slot never written holds x. In rdata != expected, an x on either side makes the result x, if (x) takes the false branch, and no error is raised. !== treats x as a value and compares it. The bug in section 05 makes exactly such x slots.

(4) At the three edges 21, 35 and 49 the DUT's rempty is 1 and the model's is 0. Compare them directly and a bug-free DUT raises three errors (amber diamonds). (5) The real read happens at 63, and rdata from just before the edge (A1) matches pop()'s A1 (green circle). wfull on the write side drops late in the same way.

DUT 가 틀린 게 아니다. 상대편 포인터를 두 박자 늦게 보는 것은 Cummings 설계가 일부러 받아들인 대가이고, 늦게 본 flag 는 언제나 조심하는 쪽(덜 찼는데 full, 덜 비었는데 empty)으로만 틀린다(Lab 1 정리 06 절). 제출한 checker 는 이걸 기다렸다가 비교하는 쪽으로 풀었다. 테스트의 정해진 지점(reset 직후, 가득 찬 뒤, 다 비운 뒤, 테스트 2 · 3 끝)에서 clock 엣지를 몇 개(대개 두 clock 각각 4 개) 기다려 flag 가 자리 잡은 다음 check_status() 로 wfull 과 is_full(), rempty 와 is_empty() 를 맞춘다. 코드에서 세면 그 지점은 다섯 곳, flag 비교는 열 번이다.

The DUT isn't wrong. Seeing the other side's pointer two beats late is a cost the Cummings design takes on purpose, and a late flag is only ever wrong in the cautious direction: full when not quite full, empty when not quite empty (Lab 1 write-up §06). The submitted checker handles it by waiting, then comparing. At fixed points in the tests (after reset, after filling, after draining, at the end of tests 2 and 3) it waits a few clock edges (usually four of each clock) for the flags to settle, then check_status() matches wfull against is_full() and rempty against is_empty(). Counted from the code, that's five points and ten flag comparisons.

여기서 의문. 그럼 "계속 비교하라" 는 요구는 못 지킨 건가? 반만 지켰다. 정해진 지점의 비교는 "끝내 자리를 잘못 잡은 flag" 는 잡지만, 지점 사이에 잠깐 잘못 켜진 flag 는 놓친다. 매 엣지에 비교하면서도 거짓 오류를 안 내려면 비교를 한쪽 방향으로만 하면 된다. DUT 가 rempty = 0 인데 모델이 비었으면(읽으면 안 되는데 읽게 둠) 오류, DUT 가 wfull = 0 인데 모델이 가득 찼으면 오류, 반대 방향의 늦음은 허용. 여기에 "모델이 안 빈 뒤 몇 엣지 안에 rempty 가 내려가야 한다" 는 시간 제한을 더하면 영영 안 풀리는 flag 도 잡는다. 제출본에는 없고 14 절에 남겼다.

Question. So the "compare continuously" requirement wasn't met? Half met. Comparing at fixed points catches a flag that ends up in the wrong state, but misses one that's wrong briefly between the points. To compare on every edge without false errors, compare in one direction only: the DUT says rempty = 0 while the model is empty (it lets you read when it shouldn't) is an error; the DUT says wfull = 0 while the model is full is an error; lateness in the other direction is allowed. Add a time limit, "rempty must drop within so many edges after the model goes non-empty", and a flag that never clears is caught too. The submission doesn't have this; it's in section 14.

Planting the bug: skip only the memory write

설명서의 bug 는 "N 번째 쓰기마다 데이터를 버린다" 다. 버리는 방법이 둘 있다. 포인터까지 안 움직이면 쓰기 자체가 사라져 그 뒤가 전부 한 칸씩 밀린다. 제출본은 메모리 칸에 쓰는 것만 건너뛰고 포인터는 정상으로 움직인다. 그러면 FIFO 는 "받았다" 고 생각하는데 그 칸에는 예전 값이 그대로 남는다. 메모리 module(fifo_mem.sv) 안에 넣었고 plusarg 로 켠다.

The handout's bug is "drop every Nth data written". There are two ways to drop it. If the pointer doesn't move either, the write vanishes entirely and everything after shifts by one. The submission skips only the write into the memory slot and lets the pointer move as usual. The FIFO then believes it took the value, while the slot keeps whatever was there before. It lives in the memory module (fifo_mem.sv) and a plusarg turns it on.

문제: 다 한 몸이면 하나 바꿀 때 전부 바뀐다

The problem: when it's all one piece, changing one thing changes everything

Part 2 의 checker 안에서 "winc && !wfull 이면 쓰기다" (핀 읽기)와 "fifo_push(wdata)" (정답 관리)는 같은 always 블록 안에 붙어 있다. 신호 이름이 바뀌면 checker 를 고쳐야 하고, 정답 모델을 바꿔도 checker 를 고쳐야 한다. 식당으로 치면 주문 받는 사람, 장부 쓰는 사람, 맛 보는 사람이 한 사람이다. Part 3 은 이걸 나눈다. 핀을 보는 일은 monitor, 일어난 일 하나를 담는 쪽지는 transaction, 쪽지가 모이는 우편함은 mailbox, 쪽지를 정답과 맞춰 보는 심판은 scoreboard. 이렇게 나누면 다른 FIFO 에는 monitor 만, 다른 정답에는 scoreboard 만 바꾸면 된다.

Inside Part 2's checker, "winc && !wfull means a write" (reading pins) and "fifo_push(wdata)" (keeping the answer) sit in the same always block. Rename a signal and you edit the checker; swap the model and you edit the checker. In restaurant terms, the person taking orders, the one keeping the books and the one tasting the food are all the same person. Part 3 splits them: watching pins is the monitor's job, one event goes on a slip called a transaction, slips collect in a mailbox, and a referee called the scoreboard checks each slip against the answer. Split like that, a different FIFO only needs a new monitor and a different answer only a new scoreboard.

The fix: two interfaces, two monitors, one mailbox, one scoreboard

덧셈기는 clock 이 하나지만 FIFO 는 쓰기 clock 과 읽기 clock 이 따로다. 그래서 설명서가 interface 를 둘 요구하고, 제출본은 monitor 도 둘로 나눴다. 각 monitor 가 자기 clock 만 따라가면 된다. 그리고 둘이 같은 mailbox 하나에 쪽지를 넣는다.

The adder has one clock; the FIFO has a write clock and a read clock. So the handout asks for two interfaces, and the submission splits the monitor in two as well, each following only its own clock. Both drop their slips into the same single mailbox.

그림 읽기. 맨 아래: stimulus 는 Part 2 와 같은 write_word / read_word task 이고, 이번엔 wr_if 와 rd_if 의 신호를 몬다("drives"). interface 는 신호선 다발이다. wr_if 에 wclk wrst_n winc wdata wfull, rd_if 에 rclk rrst_n rinc rdata rempty 다섯씩이고 DUT 핀에 이어진다("pins"). The transaction: one event, one slip

쪽지에 무엇을 적을지 정하는 게 설명서의 과제 2 번이다. FIFO 에서 일어나는 일은 셋이다. 비워졌다(reset), 하나 들어갔다(write), 하나 나왔다(read). 그래서 op 는 FIFO_RESET, FIFO_WRITE, FIFO_READ 셋 중 하나이고, 쓰기면 wdata, 읽기면 rdata 를 data 에 담는다. 과제 4 번이 요구한 timestamp 와, 만들어진 순서를 세는 id 를 더했다.

Deciding what goes on the slip is the handout's task 2. Three things happen to a FIFO: it's cleared (reset), one goes in (write), one comes out (read). So op is one of FIFO_RESET, FIFO_WRITE, FIFO_READ, and data holds wdata for a write or rdata for a read. Task 4's timestamp and an id counting creation order are added.

data 를 bit 가 아니라 logic 으로 둔 데 이유가 있다. bit 는 0 과 1 만 담아서 x 가 들어오면 0 으로 바뀐다. 그러면 05 절의 xx 읽기가 쪽지에 00 으로 적혀, 기댓값이 우연히 00 이면 bug 가 숨는다. logic 은 x 를 그대로 싣는다.

There's a reason data is logic rather than bit. A bit holds only 0 and 1, so an x becomes 0. Section 05's xx read would go on the slip as 00, and if the expected value happened to be 00, the bug would hide. logic carries the x through.

monitor: 엣지 직전 값을 찍는 clocking block

The monitor: a clocking block that samples just before the edge

monitor 가 쪽지를 만드는 조건은 Part 2 의 checker 와 같다. 쓰기 monitor 는 winc && !wfull, 읽기 monitor 는 rinc && !rempty. 그리고 쓰기 쪽 reset 이 걸리면 reset 한 번에 FIFO_RESET 쪽지 하나. 신호는 interface 의 clocking block(mon_cb)으로 읽는데, default input #1step 이 "엣지 바로 직전의 값" 을 찍는다. Part 2 에서 always @(posedge) 가 깨어나자마자 읽어서 얻은 것과 같은 값을, 경합 걱정 없이 문법으로 못박은 것이다.

The monitors build slips under the same conditions as Part 2's checker: winc && !wfull for the write monitor, rinc && !rempty for the read monitor, plus one FIFO_RESET slip per write-side reset. They read signals through the interface's clocking block (mon_cb), whose default input #1step samples "the value just before the edge". It's the same value Part 2 got by reading the moment always @(posedge) woke up, pinned down by syntax instead of by care about races.

Part 3 · 해결: scoreboard 가 q[$] 로 정답을 들고 쪽지마다 대조한다

Part 3 · The fix: a scoreboard keeps the answer in q[$] and checks every slip

Part 3 과제 5 번. Part 2 의 C 모델이 하던 일을 SystemVerilog queue 하나가 한다.

Part 3 task 5. One SystemVerilog queue does what Part 2's C model did.

q[$] 는 크기가 정해지지 않은 줄(queue)이다. 뒤에 붙이는 push_back, 앞에서 빼는 pop_front 가 있다. FIFO 의 정답으로 이보다 단순한 것이 없다. scoreboard 는 mailbox 에서 쪽지를 하나씩 꺼내서 쪽지 종류대로 한다. FIFO_WRITE 면 q.push_back(data), FIFO_READ 면 q.pop_front() 로 꺼낸 기댓값과 쪽지의 data 를 !== 로 비교, FIFO_RESET 이면 q.delete() 로 비운다. 모델이 이미 16 개를 들고 있는데 쓰기가 오거나, 모델이 빈데 읽기가 오면 그것도 오류다.

q[$] is a queue of no fixed size, with push_back to add at the end and pop_front to take from the front. There's no simpler answer key for a FIFO. The scoreboard pulls slips from the mailbox one at a time and acts on the kind: FIFO_WRITE does q.push_back(data); FIFO_READ compares the slip's data with the expected value from q.pop_front() using !==; FIFO_RESET empties it with q.delete(). A write while the model already holds 16, or a read while the model is empty, is an error too.

여기서 의문. 쓰기 쪽지와 읽기 쪽지가 같은 시각에 오면 순서가 꼬이지 않나? 이 stimulus 에서는 안 꼬인다. 읽기 monitor 가 읽기 쪽지를 만들려면 DUT 의 rempty 가 0 이어야 하고, 앞의 그림처럼 rempty 는 쓰기보다 몇 엣지 늦게 내려간다. 그러니 어떤 값의 읽기 쪽지가 생길 때는 그 값의 쓰기 쪽지가 이미 몇 엣지 전에 mailbox 에 들어가 있다. 같은 시각의 쓰기와 읽기는 서로 다른 값이라 순서가 바뀌어도 q 의 앞쪽은 그대로다.

Question. Can a write slip and a read slip at the same instant arrive in the wrong order? Not with this stimulus. For the read monitor to make a read slip, the DUT's rempty must be 0, and as the earlier figure shows, rempty drops a few edges after the write. So whenever a read slip for some value appears, that value's write slip went into the mailbox edges earlier. A write and a read at the same instant concern different values, so even if they swap, the front of q is unchanged.

When it says PASS

오류 0 만으로는 PASS 를 주지 않는다. 비교가 한 번도 안 일어나도 오류는 0 이기 때문이다. 제출한 passed() 는 세 조건을 다 본다. 오류 0, 비교 1 번 이상, 끝났을 때 모델에 남은 것 0. 마지막 조건은 "넣었는데 끝내 안 나온 값" 을 잡는다. 그리고 stimulus 가 wfull 이나 rempty 를 기다리다 영원히 멈추는 경우를 위해 100 µs 에 끝내는 watchdog 을 붙였다(13 절).

Zero errors alone doesn't earn a PASS, because zero comparisons also gives zero errors. The submitted passed() checks all three: zero errors, at least one comparison, and nothing left in the model at the end. The last one catches "went in but never came out". And a watchdog ends the run at 100 µs in case the stimulus waits forever on wfull or rempty (section 13).

문제: 들킨 시각과 고장 난 시각이 멀다

The problem: the moment it's caught is far from the moment it broke

05 절의 그림을 다시 보면, #5 쓰기는 255 에 버려졌는데 checker 는 693 에야 알았다. 그 사이에 438 단위가 흘렀고 쓰기가 11 번 더 있었다. 이 정도면 원인을 찾기 쉽지만, 진짜 칩에서는 수만 사이클 뒤에 엉뚱한 곳에서 드러난다. 그때 파형을 거꾸로 거슬러 올라가는 것이 디버깅 시간의 대부분이다. 마트로 치면 문 닫을 때 재고를 세는 것과, 문마다 CCTV 를 달아 두는 것의 차이다.

Look again at section 05: write #5 was dropped at 255 and the checker found out at 693. 438 units passed in between, with eleven more writes. That's still easy to trace, but on a real chip the fault surfaces tens of thousands of cycles later, somewhere unrelated, and walking the waveform back to the cause is most of the debugging time. It's the difference between counting stock at closing time and having a camera on every door.

assertion 은 그 CCTV 다. "이 회로에서 언제나 참이어야 하는 규칙" 을 하나씩 적어 두면, 시뮬레이터가 매 클럭 엣지마다 그 규칙을 검사하고, 깨지는 그 사이클에 실패를 찍는다. 정답 모델이 필요 없다. 규칙만 있으면 된다. Part 4 의 bug 실행에서 그 차이가 그대로 보인다.

An assertion is that camera. Write down, one at a time, "rules that must always be true in this circuit", and the simulator checks each rule at every clock edge and reports a failure in the very cycle it breaks. No answer model needed, only the rule. Part 4's bug run shows the difference plainly.

assertion 을 읽는 법

How to read an assertion

모양은 "조건이면 결과" 하나다. A |-> B 는 "A 가 참인 엣지에서 B 도 참이어야 한다", A |=> B 는 "A 가 참인 엣지의 다음 엣지에서 B 가 참이어야 한다" 다. 화살표 왼쪽 A 를 antecedent(조건), 오른쪽 B 를 consequent(결과)라고 부른다. 그리고 지난 엣지의 값을 꺼내는 $past(x), 지난 엣지와 같은지 보는 $stable(x) 가 자주 쓰인다. 아래는 설명서의 첫 예시(가득 찼는데 쓰려 하면 포인터가 안 움직인다)를 그렇게 적고, 엣지 일곱 개 동안 따라간 것이다.

There's one shape: "if the condition, then the result". A |-> B means "on an edge where A holds, B must hold too"; A |=> B means "B must hold on the edge after one where A holds". A on the left is the antecedent (condition), B on the right the consequent (result). Two helpers show up a lot: $past(x) for the value at the previous edge, and $stable(x) for "same as at the previous edge". Below, the handout's first example (a write attempted while full leaves the pointer alone) written that way and followed for seven edges.

(1) tick 1, 2: winc 는 1 이지만 wfull 이 0 이라 조건이 거짓이다. 쓰기가 정상으로 일어나 binary 포인터 wbin 이 15 → 16 → 17 이 된다. 읽기 포인터가 1 이라 치면 17 − 1 = 16 개로 가득 차서, tick 3 표본은 wfull = 1 이다. (2) tick 3: 조건 참(분홍 1). 검사가 시작되고 화살표가 다음 tick 으로 간다. (3) tick 4: wbin 이 그대로 17 이라 $stable 참, pass. (4) tick 5 → 6 도 같은 모양으로 pass. (6) "vacuous": 조건이 거짓인 tick 에서도 검사는 시작되고, 아무것도 확인하지 않은 채 통과로 끝난다. 일곱 중 다섯이 그렇다. 맨 아래 앰버 줄처럼 tick 4 에 18 로 움직였다면 tick 3 에서 시작한 검사가 tick 4 에서 실패했을 것이다.

Idea and purpose. Narrow what PASS means. Before the fix, PASS meant "nobody complained". After it, PASS means "every checker actually checked, all agreed, and the run reached the end". No new checkers: the existing ones were all tied into the final verdict and the half rules made whole.

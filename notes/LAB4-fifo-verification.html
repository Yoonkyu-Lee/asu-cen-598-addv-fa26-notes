Stimulus: Lab 1's two tasks

덱 3쪽이 stimulus 는 "Same Verilog style stimulus" 라고 못박았고, 설명서도 Lab 1 의 stimulus 를 다시 써도 된다고 한다. 우리 testbench 의 write_word 는 wait (!wfull) 로 자리가 날 때까지 기다린 뒤 wclk 의 하강 엣지에서 winc 를 한 사이클 올린다. read_word 도 wait (!rempty) 뒤 rclk 하강 엣지에서 rinc 를 올린다. 테스트는 plusarg 셋으로 고른다: +TEST_FILL_EMPTY, +TEST_FLAGS, +TEST_SIMULTANEOUS.

Slide 3 fixes the stimulus as "Same Verilog style stimulus", and the handout says Lab 1's stimulus can be reused. Our testbench's write_word does wait (!wfull) until there's room, then raises winc for one cycle from a falling wclk edge. read_word likewise does wait (!rempty) and raises rinc from a falling rclk edge. Three plusargs pick the test: +TEST_FILL_EMPTY, +TEST_FLAGS, +TEST_SIMULTANEOUS.

Lab 1 stimulus 는 가득 찼을 때 쓰지 않고, 비었을 때 읽지 않는다Lab 1's stimulus never writes when full or reads when empty

wait (!wfull) 와 wait (!rempty) 가 바로 그 뜻이다. 예의 바른 testbench 라 FIFO 가 무시해야 할 요청을 한 번도 안 보낸다. 그래서 그대로 쓰면 두 군데가 비어 버린다. Part 2 checker 의 "가득 찼을 때 쓰기는 무시되는가" 검사가 한 번도 안 돌고, Part 4 설명서의 예시 property(가득 찼는데 쓰려 하면 포인터가 안 바뀐다)는 조건이 영영 참이 안 돼서 매번 검사 없이 통과한다(09절). 설명서가 "조건이 안 생기면 stimulus 를 더하라" 고 적은 이유다. 가득 찬 FIFO 에 winc 를 올리는 task, 빈 FIFO 에 rinc 를 올리는 task 를 하나씩 더 만든다.

That's exactly what wait (!wfull) and wait (!rempty) mean. It's a polite testbench that never sends a request the FIFO should ignore. Reuse it as is and two things go untested. Part 2's "is a write while full ignored" check never runs, and the handout's Part 4 example property (a write attempt while full leaves the pointer alone) never has its condition true, so it passes every time without checking anything (section 09). That's why the handout says to add stimulus if the conditions never occur. Add one task that raises winc into a full FIFO and one that raises rinc on an empty one.

"논문의 FIFO" 와 우리 Lab 1 FIFO 는 조금 다르다"The paper's FIFO" and our Lab 1 FIFO differ slightly

설명서는 Parts 1–3 에 Cummings 논문의 FIFO 를, Lab 1 에서 바꾼 것 없이 쓰라고 한다. 우리 Lab 1 Part 1 은 논문 논리 그대로에 memory 쪽 interface, almost_full 과 almost_empty, DEPTH 파라미터를 얹었다(Lab 1 기록 07절). "바꾼 것 없이" 가 even-odd 회로를 빼라는 뜻인지, almost flag 까지 걷어내라는 뜻인지는 설명서만으로 갈리지 않는다. 우리 코드를 그대로 쓰고 almost flag 는 검사 대상에서 빼거나, 논문 코드를 새로 가져오거나. TA 에게 확인한다(12절 질문 3).

The handout says parts 1–3 use the FIFO from the Cummings paper, without the Lab 1 modifications. Our Lab 1 Part 1 is the paper's logic plus a memory-side interface, almost_full and almost_empty, and a DEPTH parameter (Lab 1 record §07). Whether "without modifications" means "not the even-odd circuit" or "strip the almost flags too" can't be settled from the handout. Either use our code and leave the almost flags out of the checks, or bring in the paper's code fresh. Ask the TA (section 12, question 3).

방법론과 sign-off 기준

Methodology and sign-off metrics

방법론 쪽은 덱 3쪽이 거의 다 정해 준다. simulation 으로, directed stimulus(Verilog 식)를 넣고, 검사는 checker 기반(Part 2, 3)과 assertion 기반(Part 4) 두 가지. formal 은 이 Lab 에서 돌리지 않는다. 다만 Part 4 의 SVA 는 같은 property 를 formal 도구에 넘길 수도 있는 형태라는 점은 적을 만하다(Lecture 2 15절).

Slide 3 settles nearly all of the methodology: simulation, with directed (Verilog-style) stimulus, and checking done two ways, checker based (parts 2 and 3) and assertion based (part 4). Formal isn't run in this lab, though it's worth noting that part 4's SVA is the kind of property a formal tool could take too (Lecture 2 §15).

sign-off 기준은 설명서가 정의하지 않는다. coverage 가 없으니 흔한 기준(coverage 몇 %)을 쓸 수 없다. 이 Lab 안에서 셀 수 있는 것으로 후보를 적어 둔다. 고른 것과 이유를 계획서에 쓴다.

The handout doesn't define the sign-off metrics. With no coverage, the usual metric (coverage percentage) is off the table. Here are candidates you can actually count in this lab; write down which you picked and why.

  • 계획서의 시나리오가 전부 한 번 이상 돌았다
  • checker 와 scoreboard 의 $error 가 0 개다. 끝날 때 모델이 비어 있다(남은 항목이 없다)
  • assertion 마다 조건이 실제로 참이 된 적이 있고(09절의 vacuous pass 가 아닌) 실패는 0 번이다
  • bug 를 켠 실행에서 checker 가 그것을 잡았다. 검사기가 눈을 뜨고 있다는 증거다
  • every scenario in the plan ran at least once
  • zero $errors from the checker and scoreboard, and the model ends empty (nothing left over)
  • each assertion had its condition actually true at least once (not just the vacuous passes of section 09) and never failed
  • the bug-enabled run was caught by the checker, which is evidence the checker is awake

The C model: what to decide

덱 6쪽은 두 줄로 요약한다. 상태를 유지하고(Maintain state), API 를 내놓는다(Expose APIs). 그 아래 목록이 Array (memory), Push(), Pop(), Is_empty(), Is_full() 이다. 설명서는 "등" 을 붙여 함수를 더해도 된다고 열어 둔다. 짜기 전에 네 가지를 정한다.

Slide 6 sums it up in two lines: Maintain state, Expose APIs. Below them: Array (memory), Push(), Pop(), Is_empty(), Is_full(). The handout adds "etc.", leaving room for more functions. Decide four things before you write it.

  1. 깊이와 폭을 어디서 받나. C 쪽에 16 을 적으면 DUT 파라미터를 바꿀 때 어긋난다. model_init(depth) 같은 함수로 testbench 가 넘긴다
  2. reset 은 어떻게 전하나. DUT 가 reset 되면 모델도 비워야 한다. Lab 1 testbench 는 테스트 시작마다 reset_fifo() 를 부른다. 같은 함수가 reset 용이 된다
  3. 비었는데 pop, 가득 찼는데 push 가 오면. 모델이 조용히 쓰레기를 돌려주면 안 된다. 오류 값을 돌려주거나 checker 가 먼저 is_empty() 를 확인하게 한다
  4. 상태를 어디 두나. 파일 범위의 static 변수. 함수 안 지역 변수면 호출이 끝날 때 사라진다
  1. Where do depth and width come from? Hard-code 16 in C and it drifts when the DUT parameter changes. Have the testbench pass it, with something like model_init(depth)
  2. How does reset reach it? When the DUT resets, the model must empty too. Lab 1's testbench calls reset_fifo() at the start of every test; the same init function serves as the reset
  3. What about a pop while empty or a push while full? The model mustn't quietly hand back garbage. Return an error value, or have the checker call is_empty() first
  4. Where does the state live? In file-scope static variables. Locals inside a function vanish when the call returns

Part 2 · When the checker looks

C 모델은 시간이 없다. 부르면 바로 바뀐다. DUT 는 두 clock 위에서 돌고, flag 는 synchronizer 를 건너와야 바뀐다. checker 가 할 일은 이 둘 사이의 시간 차이를 정확히 아는 것이다.

The C model has no time: call it and it changes at once. The DUT runs on two clocks, and its flags change only after crossing synchronizers. The checker's job is to know exactly the timing gap between the two.

Row by row from the top. The numbers along the top are time in ns.

  1. wclk, winc, wdata. wclk has a 10 ns period, rising at 5, 15, 25 ns and so on. At 10 ns (a falling edge) the testbench sets wdata to A1 and winc to 1. The FIFO takes A1 at the next rising edge, 15 ns, and that's when the checker calls push(A1) (the pink diamond in the bottom row). winc drops at the 20 ns falling edge
  2. wptr (gray). At 15 ns the write pointer goes from 0 to 1: 00000 → 00001 in 5-bit gray. Binary 0 → 1 happens to look the same (0 and 1 are identical in gray and binary)
  3. rclk and the numbers 1, 2, 3. rclk has a 14 ns period, rising at 7, 21, 35, 49, 63, 77 ns. After the 15 ns write, the first rclk edge is 21 ns (1), the second 35 ns (2), the third 49 ns (3)
  4. rq1_wptr, rq2_wptr. The two synchronizer stages carrying the write pointer into the read side. The name reads "wptr as captured in q1, q2 (first, second flip-flop) of the rclk domain". Stage one becomes 00001 at 21 ns (edge 1), stage two at 35 ns (edge 2) (L05 §16)
  5. rempty. rempty is computed as "next read pointer equals synchronized write pointer" and registered on an rclk edge. Only after 35 ns does rq2 hold 00001, flipping the computed value to "not empty", and that lands in the register at the next edge, 49 ns (edge 3): 34 ns after the write. Those three edges are Lab 1 Part 2's measured "3 cycles after a write"
  6. rinc. The testbench's read_word sees rempty drop and raises rinc at the next falling rclk edge, 56 ns, then lowers it at 70 ns
  7. rdata. rdata = mem[raddr] is a combinational read, so A1 appears on rdata at 15 ns, the moment it's in memory, even though rempty is still 1. So rdata alone doesn't mean anything was read. When the read happens at 63 ns and raddr moves on, rdata shows the unwritten next slot: x
  8. is_empty() (C). The C model goes "not empty (0)" the instant of the push at 15 ns and "empty (1)" the instant of the pop at 63 ns. No delay at all
  9. naive flag check. Testing rempty == is_empty() at every rclk edge fails three times, at 21, 35 and 49 ns, where the DUT says 1 and the model 0. Even at 49 ns, rempty just before the edge is still 1. The DUT isn't wrong; see the trap below
  10. checker. At 63 ns, rinc is 1 and rempty is 0, so a read happens. The checker compares rdata from just before this edge (A1) with what pop() returns (A1). A match (green circle)

The wfull side has the same shape: a read changes rptr, which crosses two wclk-side synchronizer stages, and wfull drops at the third wclk edge. Turning on has no delay, though: wfull goes to 1 at the edge of the 16th write, rempty at the edge of the last read, because both are computed from the next pointer value (wgraynext, rgraynext).

push 와 pop 의 조건

The conditions for push and pop

설명서는 "TB 가 winc 를 올리면 push" 라고 적었다. 그대로 짜면 한 군데가 샌다. FIFO 가 실제로 쓰는 조건은 winc && !wfull 이다(fifo_mem 의 if (wclken && !wfull)). 가득 찬 FIFO 에 winc 를 올리면 DUT 는 무시하는데 모델은 받는다. 그다음부터 모든 비교가 하나씩 밀린다. 그래서 checker 는 DUT 가 실제로 받은 엣지에서만 부른다.

The handout says "when the TB asserts winc, push". Code it literally and one case leaks. The FIFO actually writes on winc && !wfull (fifo_mem's if (wclken && !wfull)). Raise winc on a full FIFO and the DUT ignores it while the model accepts it, and every comparison after that is off by one. So the checker calls the model only on the edges where the DUT really took the request.

always @(posedge wclk)                         // 쓰기 domain// write domain
  if (wrst_n && winc && !wfull) model_push(wdata);

always @(posedge rclk)                         // 읽기 domain// read domain
  if (rrst_n && rinc && !rempty) begin
    exp = model_pop();                         // 엣지 직전의 rdata 와 비교// compare with rdata from just before the edge
    if (rdata !== exp[7:0]) $error("pop mismatch: exp %h got %h", exp[7:0], rdata);
  end

@(posedge rclk) 로 깨어난 순간 읽는 rdata 는 엣지 직전 값이다. DUT 의 포인터는 nonblocking 대입이라 같은 시각의 뒤쪽 단계에서야 바뀐다. Lab 1 testbench 가 신호를 하강 엣지에서 바꾸므로 상승 엣지에서 읽는 checker 와 경합이 없다. stimulus 를 상승 엣지에서 바꾸도록 고친다면 그때는 이 가정이 깨진다.

The rdata read the moment @(posedge rclk) wakes up is the value from just before the edge: the DUT's pointers use nonblocking assignments, so they change in a later region of the same time step. Lab 1's testbench changes signals on the falling edge, so there's no race with a checker reading on the rising edge. If you change the stimulus to drive on the rising edge, this assumption breaks.

flag 를 0 지연 모델과 그냥 비교하면 안 된다 (이 페이지의 추론)Don't compare flags naively with a zero-latency model (this page's reasoning)

설명서는 is_empty() 와 is_full() 을 "계속" 불러 rempty, wfull 과 비교하라고 한다. 위 그림처럼 == 로 비교하면 버그가 하나도 없는 DUT 에서 쓰기마다 오류가 세 번씩 난다. 이건 설명서의 요구를 어기라는 말이 아니라, 비교를 어떻게 짜야 뜻이 맞는지의 문제다.

왜 어긋나나. DUT 의 flag 는 상대편 포인터를 2 사이클 늦게 본다. 늦게 본 포인터는 언제나 실제보다 덜 간 값이라, 쓰기 쪽은 "아직 덜 읽혔다" 고, 읽기 쪽은 "아직 덜 쓰였다" 고 본다. 그래서 flag 는 조심하는 쪽으로만 틀린다. 가득 안 찼는데 full, 비지 않았는데 empty 는 있어도, 그 반대는 없다(Lab 1 기록 06절). 이 비관적인 지연은 Cummings 설계가 일부러 받아들인 대가다.

그러니 checker 가 잡아야 할 진짜 버그는 낙관적인 쪽이다. 비교를 두 겹으로 짠다.

  • 한쪽 방향 검사 (매 엣지). DUT 가 rempty = 0 인데 모델이 비었다 → underflow 위험, 오류. DUT 가 wfull = 0 인데 모델이 가득 찼다 → overflow 위험, 오류. 반대 방향은 허용한다. 02절의 C2, C3 다
  • 시간 제한 검사. 모델이 "안 빔" 이 된 뒤 rclk 엣지 셋 안에 rempty 가 내려가야 한다. wfull 도 같다. 비관적으로 틀린 상태가 영영 안 풀리는 버그(예: synchronizer 가 끊긴 것)는 이것만 잡는다. C4 다

이게 설명서가 뜻한 "비교" 와 같은지는 확인이 필요하다(12절 질문 6). 리포트에 왜 == 로 비교하지 않았는지를 이 추론으로 적어 두면 데모에서 바로 답이 된다. 덧붙여 모델 쪽에 synchronizer 를 흉내 내 지연을 넣는 방법도 있지만, 그러면 모델이 RTL 을 베끼게 되어 golden model 의 뜻이 흐려진다.

The handout says to call is_empty() and is_full() "continuously" and compare them with rempty and wfull. Compare with == as in the figure and a DUT with no bugs at all raises three errors per write. This isn't about ignoring the handout; it's about writing the comparison so it means what it should.

Why the mismatch? The DUT's flags see the other side's pointer two cycles late. A late pointer is always behind the real one, so the write side thinks "fewer reads than really happened" and the read side "fewer writes than really happened". Flags are therefore only ever wrong in the cautious direction: full when not quite full, empty when not quite empty, never the reverse (Lab 1 record §06). That pessimistic delay is a price the Cummings design accepts on purpose.

So the real bugs for the checker to catch are the optimistic ones. Build the comparison in two layers:

  • A one-directional check (every edge). DUT says rempty = 0 but the model is empty → underflow risk, error. DUT says wfull = 0 but the model is full → overflow risk, error. The opposite direction is allowed. These are C2 and C3 in section 02
  • A time-limit check. Once the model goes "not empty", rempty must drop within three rclk edges, and likewise for wfull. Only this catches a bug where the cautious state never clears (say, a broken synchronizer). That's C4

Whether this matches what the handout means by "compare" needs confirming (section 12, question 6). Write this reasoning in the report, why you didn't compare with ==, and you have your demo answer ready. You could instead add a mimic synchronizer delay to the model, but then the model copies the RTL and stops being much of a golden model.

!= 는 x 를 못 본다!= can't see x

한 번도 쓰지 않은 메모리 칸은 x 다. rdata != exp 에서 한쪽이 x 면 결과가 x 이고, if (x) 는 거짓 쪽으로 간다. 오류가 안 난다. 비교는 !==(4-state 비교)로 한다. 다음 절의 bug 가 바로 이 칸을 만든다. L12 11절에서 슬라이드의 (|mysig != 1'bx) 가 매번 실패하던 것과 같은 성질이 반대로 나타난 것이다.

A memory slot that was never written holds x. In rdata != exp, an x on either side makes the result x, and if (x) takes the false branch. No error. Compare with !== (the 4-state comparison). The next section's bug produces exactly such slots. It's the same property that made the slide's (|mysig != 1'bx) fail every time in L12 §11, showing up the other way round.

Part 2 · Dropping every Nth write

설명서가 정한 것은 셋이다. bug 는 설계에 넣는다. plusarg 로 켜고 끈다(강의 사이트 Tips 페이지가 plusarg 를 설명한다). bug 의 내용은 FIFO 에 쓰인 데이터를 N 번째마다 버리는 것. 그리고 make target 둘(오류 있음, 없음). "버린다" 를 RTL 로 옮기는 방법은 두 가지로 읽힌다.

The handout fixes three things: the bug goes in the design; a plusarg switches it (the course site's Tips page explains plusargs); and it drops every Nth data item written into the FIFO. Plus two make targets (with and without errors). "Drop" can be turned into RTL in two ways.

강의의 error injection 과는 목적이 반대다. Lecture 14 가 짚듯이 슬라이드의 error injection 은 올바른 DUT 에 나쁜 입력이나 상태를 넣고 DUT 가 잘 대처하는지를 본다. 검증 대상이 DUT 다. 이 Lab 의 bug 는 DUT 를 일부러 틀리게 만들고 checker 가 그걸 잡는지를 본다. 검증 대상이 testbench 다. 리포트에서 이 둘을 섞어 쓰지 않는다.

The opposite purpose from the lecture's error injection. As Lecture 14 points out, the slide's error injection feeds bad inputs or state into a correct DUT to see whether the DUT copes; the DUT is what's being checked. This lab's bug makes the DUT wrong on purpose to see whether the checker catches it; the testbench is what's being checked. Don't mix the two up in the report.

오류가 나는 시각이 bug 가 일어난 시각이 아니다. 버린 순간은 쓰기 domain 의 그 쓰기 엣지지만, 오류는 그 항목이 읽히는 순간, 읽기 domain 에서 한참 뒤에 난다. 리포트의 Verdi 화면에 이 두 시각을 둘 다 표시하면 "어떤 bug 를 넣었고 어떻게 드러났나" 가 한 장으로 설명된다.

  1. Top row (model push). The testbench writes 1 through 7. Each time winc && !wfull holds, so the checker pushes all seven. With N = 3, the 3rd and 6th (multiples of 3) are dropped in the DUT: the amber cells. The model has no idea, because it only sees the testbench's requests
  2. A: DUT memory. Only the slot write is blocked; the pointer advances as usual. The 3rd and 6th slots were never written, so they hold x. On a second lap you'd find last lap's value there instead
  3. A: read check. Reads are matched in model order. 1 = 1 and 2 = 2 match (green). The third read has 3 in the model and x from the DUT: a mismatch, caught only if you compare with !== (section 04). Then 4 and 5 match again, and 6 misses again. One error per dropped item
  4. B: DUT memory. The write disappears altogether. The pointer doesn't move, so 1, 2, 4, 5, 7 pack in with no gaps; the last two slots (dashed) stay empty
  5. B: read check. On the third read the model has 3 and the DUT gives 4; then 4 against 5, 5 against 7. Once it slips, everything after slips. After five reads the DUT is empty and the testbench stops reading (empty)
  6. Bottom line. In B the model still holds 6 and 7 at the end. The end-of-test "is the model empty" check (C5) catches that. In A nothing is left over

The error doesn't happen when the bug does. The drop happens in the write domain, but the error only appears when that item is read, in the read domain, much later. Mark both times on the Verdi screenshot in the report and one picture explains which bug you injected and how it surfaced.

Part 3 · The scoreboard and q[$]

C 모델이 하던 일을 SV queue 한 줄로 한다. FIFO 를 FIFO 로 검사하는 셈이라 모델 자체는 짧다. 생각할 것은 순서와 끝맺음이다.

mailbox 하나로 순서가 맞나

Does one mailbox keep the order right?

monitor 둘이 서로 다른 clock 에서 한 mailbox 에 넣는다. 걱정할 것은 하나다. 어떤 값의 READ 가 그 값의 WRITE 보다 먼저 mailbox 에 들어갈 수 있나? 없다. 04절 그림에서 보듯 쓴 값은 rempty 가 내려가야 읽히고, 그건 쓰기 뒤 rclk 엣지 셋이 지나야 한다. 그러니 WRITE 가 늘 먼저 들어가 있다. 35 ns 처럼 두 엣지가 같은 시각이어도, 그때 읽히는 값은 적어도 세 엣지 전에 쓰인 값이다. mailbox 를 둘로 나눌 수도 있지만 그러면 scoreboard 가 두 줄의 순서를 맞춰야 한다. 하나가 단순하다.

Two monitors on different clocks put into one mailbox. Only one worry: can a value's READ get into the mailbox before its WRITE? No. As the section 04 figure shows, a written value can only be read once rempty drops, which takes three rclk edges after the write, so the WRITE is always in first. Even when edges coincide, as at 35 ns, whatever is read then was written at least three edges earlier. You could split into two mailboxes, but then the scoreboard has to line up two streams. One is simpler.

끝맺음

Wrapping up

scoreboard 의 forever 는 끝나지 않는다. 테스트가 $finish 로 끝날 때 모델에 남은 것이 없는지를 final 블록에서 본다(L12 17절). 남은 개수와 비교 횟수, 오류 수를 한 줄로 찍어 두면 터미널 스크린샷이 그대로 요약이 된다. 비교 횟수가 0 이면 통과가 아니라 아무것도 안 본 것이다.

The scoreboard's forever never ends. When the test ends with $finish, check in a final block that nothing is left in the model (L12 §17). Print the leftover count, number of comparisons and number of errors on one line, and the terminal screenshot becomes the summary. Zero comparisons isn't a pass; it means nothing was looked at.

설명서는 Part 3 에서 bug 실행을 요구하지 않는다. +DROP_N 을 그대로 켜서 scoreboard 도 잡는지 확인해 보는 것은 좋은 시험이지만, 리포트에 새 절을 만들 일은 아니다.

    5 · 이름이 같은데 가리키는 것이 다른 짝5 · Same word, different thing

    •

    •

    • 
      
  • Checker and scoreboard. In this lab, Part 2's checker is a module watching pins directly; Part 3's scoreboard is a class taking transactions. By L12 §11's classification both are behavioral checking
    • 
      
  • Interface and virtual interface. One is the signal bundle itself, the other a class's handle to it (L12 §08)
    • 
      
  • Queue (SV's q[$]) and FIFO (the DUT). Same job, but one is a timeless data structure and the other a circuit on two clocks. That difference is the whole of section 04

왜 이걸 배우는가

  
Why this is worth learning

  
Lab 1 에서 우리는 FIFO 를 만들고, testbench 안에 기댓값을 손으로 적어 검사했다. 이번 Lab 은 그 testbench 를 부품으로 쪼개는 법을 세 번 보여 준다. 정답을 다른 언어의 모델로 떼어 내고(Part 2), 핀을 읽는 부품과 판정하는 부품을 떼어 내고(Part 3), 규칙을 시간 위의 선언으로 떼어 낸다(Part 4). 덱 8–9쪽이 반복해서 말하는 "재사용" 이 그 이유다. 남은 Lab 둘이 이 위에 쌓인다. Lab 5 는 Randomization 과 Coverage 칸을, Lab 6 는 APB 쪽 driver 와 monitor, assertion 을 다시 쓴다. 그리고 바로 다음 강의들이 UVM 이다. UVM 은 이 Lab 의 monitor, mailbox, scoreboard 를 표준 class 로 정해 둔 것이다.

  
In Lab 1 we built the FIFO and checked it with expected values hand-written into the testbench. This lab shows, three times, how to break that testbench into components: pull the answer out into a model in another language (Part 2), separate the part that reads pins from the part that judges (Part 3), and turn the rules into declarations over time (Part 4). "Reuse", which slides 8–9 keep coming back to, is why. The last two labs build on this: Lab 5 fills in the randomisation and coverage boxes, and Lab 6 uses driver, monitor and assertions again on the APB side. And the very next lectures are UVM, which fixes this lab's monitor, mailbox and scoreboard as standard classes.

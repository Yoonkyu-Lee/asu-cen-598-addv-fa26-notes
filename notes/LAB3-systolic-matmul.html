행렬곱 가속기를 왜 만듬? · 문제: 곱하고 더하기가 512 번

Why build a matmul accelerator? · The problem: 512 multiply-adds

Lab 이야기 전에, 이 하드웨어가 대신해 주는 계산이 얼마나 되는지부터.

Before the lab itself: how much arithmetic this hardware takes over.

행렬곱이 뭔지부터. 8×8 행렬 둘을 곱하면 8×8 행렬 C 가 나온다. C 의 칸 하나는 A 의 한 줄과 B 의 한 칸 기둥을 짝지어 곱한 뒤 다 더한 값이다. 짝이 여덟이라 곱하기 여덟 번, 더하기 여덟 번이다(처음 0 에 더하는 것까지 센다).

First, what a matrix product is. Multiply two 8×8 matrices and you get an 8×8 matrix C. One element of C is a row of A and a column of B, multiplied pair by pair and summed. Eight pairs, so eight multiplies and eight adds (counting the first add onto 0).

그림 읽기. C[2][5] 는 A 의 2 번 줄(가로)과 B 의 5 번 기둥(세로)에서 나온다. 두 줄에서 같은 순번끼리 짝을 짓는다: A[2][0] 과 B[0][5], A[2][1] 과 B[1][5], …, A[2][7] 과 B[7][5]. 짝마다 곱해서 여덟 개를 다 더한다. C 는 칸이 8 × 8 = 64 개이고 칸마다 이 일을 하니 곱하고 더하기가 64 × 8 = 512 번이다. 이 숫자가 Part 3 리포트 질문 "MAC 이 몇 번인가" 의 답이다(15 절).

Reading the figure. C[2][5] comes from row 2 of A (across) and column 5 of B (down). Pair them up by position: A[2][0] with B[0][5], A[2][1] with B[1][5], …, A[2][7] with B[7][5]. Multiply each pair and add all eight. C has 8 × 8 = 64 elements, each needing this, so that's 64 × 8 = 512 multiply-adds. That number answers the Part 3 report question "how many MACs?" (section 15).

한 번의 "곱하고 더하기" 를 업계에서는 MAC(multiply-accumulate)이라 부른다. 누적값(accumulator)에 곱을 하나씩 더해 간다는 뜻이다. 이 Lab 의 하드웨어는 결국 MAC 을 격자로 깐 것이다.

One "multiply and add" is called a MAC (multiply-accumulate) in the industry: keep adding products onto a running sum, the accumulator. The hardware in this lab is, in the end, MACs laid out in a grid.

해결 1 · systolic array: 숫자를 격자에 흘려보낸다

Fix 1 · A systolic array: stream the numbers through a grid

주어진 4×4 가 이미 하는 일이다. 이 Lab 은 그 위에서 시작한다.

This is what the given 4×4 already does. The lab starts on top of it.

MAC 을 4×4 로 16 개 깐다. 하나하나를 PE(processing element)라 부른다. PE 는 자기 누적값을 하나 갖고, 박자(클럭)마다 왼쪽에서 받은 a 와 위에서 받은 b 를 곱해 누적값에 더한다. 그리고 a 는 오른쪽 이웃에게, b 는 아래 이웃에게 그대로 넘긴다. PE(i,j) 가 끝에 들고 있는 누적값이 C[i][j] 다.

Lay out 16 MACs as a 4×4 grid. Each one is a PE (processing element). A PE keeps one accumulator, and on every beat (clock) it multiplies the a it got from the left by the b it got from above and adds the product in. Then it passes a on to its right neighbour and b to the one below. The accumulator PE(i,j) ends up holding is C[i][j].

이름의 systolic 은 심장 수축기(systole)에서 왔다. 심장이 박동마다 피를 한 번씩 밀어내듯, 박자마다 숫자가 한 칸씩 밀려 들어간다. 장점은 숫자를 메모리에서 한 번만 읽고 PE 끼리 돌려쓴다는 것이다. A 의 원소 하나가 같은 줄 PE 넷을 차례로 지나며 네 번 쓰인다.

The name comes from systole, the heart's contraction: just as each heartbeat pushes blood along once, each clock pushes the numbers one PE further. The win is that each number is read from memory once and then reused PE to PE: one element of A walks through the four PEs in its row and gets used four times.

그림 읽기. 첫 클럭을 0 번이라 하자. 0 번 클럭에 줄마다 PE 에 가장 가까운 칸이 첫 PE 로 들어가고, 박자마다 한 칸씩 당겨진다. 보라색 둘을 따라간다. a10 (= A[1][0]) 은 1 번 줄에서 PE 쪽으로부터 둘째 칸이다(앞에 · 하나). 그래서 1 번 클럭에 PE10 에 들어가고, 오른쪽으로 두 번(PE11, PE12) 옮겨 3 번 클럭에 PE12 에 닿는다. 칸 번호 i + k = 1 + 0 = 1 에 이동 j = 2 를 더한 3 이다. b02 (= B[0][2]) 는 2 번 기둥에서 셋째 칸이다(앞에 · 둘). 2 번 클럭에 PE02 에 들어가고 아래로 한 번(PE12) 옮겨 3 번 클럭에 닿는다. 칸 번호 j + k = 2 에 이동 i = 1 을 더해 역시 3. 둘이 PE12 에서 만나 곱해진다. 이 짝은 C[1][2] = A[1][0]·B[0][2] + A[1][1]·B[1][2] + … 의 첫 항이다. 다음 항 a11 과 b12 는 각각 한 칸씩 뒤에 서 있어 4 번 클럭에 만난다. 어느 PE 든 a 의 도착은 i + k + j, b 의 도착은 j + k + i 로 같아서, 늘 같은 k 끼리 만난다.

Reading the figure. Call the first clock number 0. On clock 0 the slot nearest the grid in each queue enters the first PE, and every beat the queue moves up one slot. Follow the two purple labels. a10 (= A[1][0]) is the second slot from the grid in row 1 (one · ahead), so it enters PE10 on clock 1, then moves right twice (PE11, PE12) and reaches PE12 on clock 3: slot number i + k = 1 + 0 = 1, plus j = 2 moves, is 3. b02 (= B[0][2]) is the third slot in column 2 (two · ahead), so it enters PE02 on clock 2 and moves down once (PE12), arriving on clock 3: slot j + k = 2, plus i = 1 move, also 3. They meet in PE12 and get multiplied. That pair is the first term of C[1][2] = A[1][0]·B[0][2] + A[1][1]·B[1][2] + …. The next term, a11 and b12, each stand one slot further back and meet on clock 4. For any PE, a arrives at i + k + j and b at j + k + i, the same, so the same k always meet.

주어진 matmul.v 가 이 4×4 를 이미 다 해 놓았다. RAM 에서 읽을 주소를 만드는 부분(systolic_data_setup), PE 격자(systolic_pe_matrix), 끝난 C 를 한 기둥씩 RAM 에 쓰는 부분(output_logic), 그리고 PE 안의 MAC(seq_mac)이다. RAM 의 한 칸(주소 하나)은 32 비트이고 원소 넷이 들어간다. A 는 기둥 하나, B 는 줄 하나가 한 칸이다.

The given matmul.v already does all of this for 4×4: address generation for the RAM reads (systolic_data_setup), the PE grid (systolic_pe_matrix), writing finished columns of C back to RAM (output_logic), and the MAC inside each PE (seq_mac). One RAM word (one address) is 32 bits and holds four elements: one column of A, or one row of B.

문제 2 · 정수 8 비트로는 모자라다 → FP8 E3M4

Problem 2 · 8-bit integers aren't enough → FP8 E3M4

Part 1. 같은 8 비트를 다르게 읽는다.

Part 1. The same 8 bits, read differently.

주어진 MAC 은 넘치면 조용히 버린다

The given MAC quietly drops what overflows

주어진 것 · matmul.v · seq_mac · excerpt
given · matmul.v · seq_mac · excerpt
reg [`DWIDTH-1:0] a_flop, b_flop, mult;   // DWIDTH = 8// DWIDTH = 8
...
mult <= a_flop * b_flop;   // 8 비트 × 8 비트를 8 비트에 담는다// 8 bits × 8 bits stored in 8 bits

8 비트 곱하기 8 비트는 16 비트까지 나오는데 mult 가 8 비트라 위쪽 8 비트가 그냥 잘린다. 16 × 16 = 256 은 2 진수로 1_0000_0000 이라 아래 8 비트가 전부 0, 즉 0 이 된다. 경고도 없다. 그리고 정수라서 0.25 같은 소수는 아예 못 담는다.

8 bits times 8 bits can need 16 bits, but mult is 8 bits wide, so the top 8 are just cut off. 16 × 16 = 256 is 1_0000_0000 in binary; the low 8 bits are all 0, so the result is 0, with no warning. And being integers, they can't hold a fraction like 0.25 at all.

해결: 비트를 셋으로 나눠 과학적 표기법처럼 쓴다

The fix: split the bits three ways, like scientific notation

Part 1 은 같은 8 비트를 FP8 E3M4 로 읽게 한다. 1.5 × 23 같은 과학적 표기법의 2 진판이다. 맨 앞 1 비트는 부호(sign), 다음 3 비트(E3)는 2 의 몇 제곱인지(exponent), 나머지 4 비트(M4)는 1.xxxx 의 소수점 아래(mantissa)다. exponent 는 음수도 필요해서 저장값에서 3 을 빼고 읽는다. 이 3 을 bias 라 부른다(설명서가 23−1 − 1 = 3 으로 준다). 맨 앞 1 은 늘 1 이라 저장하지 않는다(hidden bit).

Part 1 has the same 8 bits read as FP8 E3M4, a binary version of scientific notation like 1.5 × 23. The first bit is the sign, the next 3 bits (E3) say which power of two (the exponent), and the last 4 bits (M4) are the digits after the point in 1.xxxx (the mantissa). The exponent needs negative values too, so you subtract 3 from the stored value; that 3 is the bias (the handout gives it as 23−1 − 1 = 3). The leading 1 is always 1, so it isn't stored (the hidden bit).

그림 읽기. 0x38 은 2 진수로 0011 1000 이다. 앞에서부터 자르면 sign 0, exponent 011, mantissa 1000. sign 0 이라 양수. exponent 011 은 3 이고 bias 3 을 빼면 20. mantissa 앞에 숨은 1 을 붙이면 1.1000(2 진) = 1 + 1/2 = 1.5. 그래서 +1.5 × 1 = 1.5. 같은 비트 0011 1000 을 int8 로 읽으면 56 이다. 비트는 같고 읽는 규칙만 다르다.

Reading the figure. 0x38 is 0011 1000 in binary. Cut it from the left: sign 0, exponent 011, mantissa 1000. Sign 0, so positive. Exponent 011 is 3; subtract the bias 3 and it's 20. Put the hidden 1 in front of the mantissa: 1.1000 in binary = 1 + 1/2 = 1.5. So +1.5 × 1 = 1.5. The same bits 0011 1000 read as int8 are 56. Same bits, different reading rule.

대가: 칸 사이가 고르지 않다

The catch: the steps aren't even

그림 읽기. mantissa 가 4 비트라 한 exponent 안에 코드가 24 = 16 개다. exponent 가 0 (저장값 011)이면 1 부터 2 까지를 16 칸으로 나누니 간격 1/16 = 0.0625. exponent 가 3 (저장값 110)이면 8 부터 16 까지를 16 칸으로 나누니 간격 8/16 = 0.5. 그 줄의 마지막 코드는 mantissa 1111, 즉 1.9375 × 8 = 15.5 이고 이게 FP8 의 가장 큰 수다. 저장값 111 은 숫자가 아니라 ∞ 와 NaN(숫자가 아님)에 쓴다. 제출본도 그렇게 읽는다(아래 표). 그래서 16 은 담을 수 없고, 15.5 를 넘게 반올림되는 결과는 ∞ 가 된다.

Reading the figure. With a 4-bit mantissa there are 24 = 16 codes per exponent. At exponent 0 (stored 011), 1 to 2 is split into 16 steps of 1/16 = 0.0625. At exponent 3 (stored 110), 8 to 16 is split into 16 steps of 8/16 = 0.5. The last code on that row is mantissa 1111, 1.9375 × 8 = 15.5, the largest FP8 number. Stored 111 isn't a number: it's used for ∞ and NaN (not a number), and the submission reads it that way (table below). So 16 can't be stored, and any result that rounds past 15.5 becomes ∞.

판정 · 반올림이 매번 일어나서 계산기와 갈린다

The verdict · Rounding happens every step, so a calculator disagrees

Part 1. 결과를 맞다고 판정하려면 기준이 하드웨어와 같은 순서로 반올림해야 한다.

Part 1. To call a result right, the reference has to round in the same order as the hardware.

FP8 은 칸이 듬성듬성해서 거의 모든 결과가 칸 사이에 떨어진다. 그러면 가장 가까운 칸으로 옮긴다(반올림). 문제는 이게 곱하기 한 번, 더하기 한 번마다 일어난다는 것이다.

FP8's codes are sparse, so almost every result lands between two codes and gets moved to the nearest one (rounding). The catch is that this happens after every single multiply and every single add.

그림 읽기. 8 바로 아래는 exponent 2 줄이라 간격이 1/4, 8 부터는 exponent 3 줄이라 간격이 1/2 다. 8 + 0.25 = 8.25 는 FP8 에 없고 8.0 과 8.5 의 정확히 가운데다. 딱 중간이면 mantissa 가 짝수인 쪽으로 간다. 8.0 은 0 110 0000(mantissa 0000, 짝수), 8.5 는 0 110 0001(0001, 홀수)이라 8.0 이 된다. 그래서 8 에 0.25 를 두 번 더하면 두 번 다 8.0 에 머문다. 0.25 + 0.25 = 0.5 를 먼저 하면 8 + 0.5 = 8.5 로 정확히 담긴다. 이 8 + 0.25 는 Part 1 덧셈기 테스트의 넷째 경우이고, 기대값 0x60 (8.0), flag 00001 (inexact) 이 그대로 나왔다(R1).

Reading the figure. Just below 8 is the exponent-2 row, a quarter apart; from 8 up it's the exponent-3 row, a half apart. 8 + 0.25 = 8.25 isn't an FP8 code; it's exactly halfway between 8.0 and 8.5. An exact half goes to the even mantissa: 8.0 is 0 110 0000 (mantissa 0000, even) and 8.5 is 0 110 0001 (0001, odd), so it becomes 8.0. Add 0.25 to 8 twice and it stays at 8.0 both times. Do 0.25 + 0.25 = 0.5 first and 8 + 0.5 = 8.5 is stored exactly. That 8 + 0.25 is the fourth case of the Part 1 adder test; it gave the expected 0x60 (8.0) with flags 00001 (inexact) (R1).

그래서 기대값을 계산기로 낼 수 없다. 설명서는 "보통 계산기로" 기대값을 내라고 했지만, 계산기는 마지막에 한 번만 반올림한다. 하드웨어는 PE 안에서 곱마다, 누적마다 반올림하고 더하는 순서도 정해져 있다(k = 0, 1, 2, … 순). 제출본 testbench 는 그래서 기준 모델 fp8_ref_model.vh 를 따로 두고, 하드웨어와 같은 순서로 곱 하나·덧셈 하나마다 반올림한다(13 절). 행렬이 전부 1 이면 칸마다 1 을 여덟 번 더해 8.0 이라 순서가 상관없지만, 무작위 행렬에서는 계산기와 어긋날 수 있다.

So a calculator can't give you the expected values. The handout says to get them "using a regular calculator", but a calculator rounds once, at the end. The hardware rounds after every product and every accumulation inside the PE, in a fixed order (k = 0, 1, 2, …). That's why the submitted testbenches use a separate reference model, fp8_ref_model.vh, that rounds after each product and each add, in the same order as the hardware (section 13). With all-ones matrices each element is 1 added eight times, 8.0, and the order doesn't matter; with random matrices a calculator can land elsewhere.

Part 1 과제 2-2 와 Part 2 과제 2-1, 2-3. 누적 고리가 있으면 덧셈은 한 사이클에 끝나야 한다.

Part 1 task 2-2, Part 2 tasks 2-1 and 2-3. With an accumulation loop, the add has to finish in one cycle.

Part 2 는 PE 의 * 와 + 를 Part 1 의 FP8 곱셈기와 덧셈기로 바꾼다. 그런데 설명서가 가리킨 참고 코드(fbrosser/DSP48E1-FP 의 FP32 FPMult, FP_AddSub)는 단계 사이에 레지스터가 있는 pipeline 이고, 설명서는 이걸 걷어내 조합회로로, 즉 한 사이클 안에 답이 나오게 만들라고 한다(Part 1 과제 2-2).

Part 2 swaps the PE's * and + for Part 1's FP8 multiplier and adder. But the reference code the handout points to (FPMult and FP_AddSub, FP32, in fbrosser/DSP48E1-FP) is pipelined, with registers between stages, and the handout says to strip them out and make the units combinational, so the answer comes out within one cycle (Part 1 task 2-2).

그림 읽기. a, b 가 들어오면 클럭 1 에 a_flop, b_flop 에 잡힌다(stage 1). 같은 클럭 주기 안에 FP8_Mult 가 곱을 내고 클럭 2 에 mult 에 잡힌다(stage 2). 다시 같은 주기 안에 FP8_AddSub 가 mult + out 을 내고 클럭 3 에 out 에 잡힌다(stage 3). out 은 다음 클럭에 다시 덧셈기 입력이 된다(보라 고리). 레지스터 셋은 주어진 int8 MAC 과 똑같고, 바뀐 것은 그 사이의 회로 둘뿐이다. 두 연산기의 flag 는 OR 해서 PE 의 flags 로 나간다. 덧셈기의 operation 입력은 1'b0(덧셈)으로 묶었다.

Part 3 · 문제 4 · 4×4 넷으로 8×8 을 만든다

Part 3 · Problem 4 · Four 4×4s make an 8×8

Part 3 과제. 주어진 4×4 는 이웃과 이어질 포트를 이미 갖고 있다.

Part 3. The given 4×4 already has the ports for neighbours.

8×8 PE 격자를 새로 짜지 않고, 4×4 블록(타일) 넷을 2×2 로 붙인다. 설명서가 MAT_MUL_SIZE 는 4 그대로 두고 matmul.v 도 건드리지 말라고 한다. 주어진 4×4 에 이미 그 준비가 되어 있다. a_data_in / a_data_out, b_data_in / b_data_out, c_data_in 포트로 이웃 타일과 숫자를 주고받고, a_loc, b_loc 로 "나는 큰 격자의 어디에 있다" 를 알려 준다.

Rather than writing an 8×8 PE grid from scratch, put four 4×4 blocks (tiles) together as 2×2. The handout says to keep MAT_MUL_SIZE at 4 and leave matmul.v alone, and the given 4×4 is already built for this: the a_data_in / a_data_out, b_data_in / b_data_out and c_data_in ports pass numbers to and from neighbouring tiles, and a_loc, b_loc tell a tile where it sits in the bigger grid.

그림 읽기. a_loc 는 몇 번째 타일 줄인지(위 0, 아래 1), b_loc 는 몇 번째 타일 기둥인지(왼쪽 0, 오른쪽 1)다. 주어진 코드에서 b_loc 가 0 인 타일(TL, BL)은 A 를 RAM 에서 받고, 아니면(TR, BR) 왼쪽 이웃의 a_data_out 에서 받는다. 같은 식으로 a_loc 가 0 인 타일(TL, TR)은 B 를 RAM 에서, 아니면(BL, BR) 위 이웃에서 받는다. RAM 은 행렬마다 둘이다. A0 에 A 의 0~3 번 줄, A1 에 4~7 번 줄, B0 에 B 의 0~3 번 기둥, B1 에 4~7 번 기둥, C 도 C0 (0~3 번 줄), C1 (4~7 번 줄). RAM 한 칸이 원소 넷(32 비트)이라 4×4 타일 하나의 입구 폭과 같다. 네 타일 모두 final_mat_mul_size = 8 을 받는다. 주소와 stride 는 넷이 같고, 주소를 실제로 내는 것은 RAM 에 붙은 타일뿐이다(TL 이 A0·B0, BL 이 A1, TR 이 B1). 나머지 주소 출력은 비워 둔다.

Reading the figure. a_loc is which row of tiles (top 0, bottom 1) and b_loc which column of tiles (left 0, right 1). In the given code, a tile with b_loc 0 (TL, BL) takes A from RAM, and otherwise (TR, BR) from its left neighbour's a_data_out. Likewise a tile with a_loc 0 (TL, TR) takes B from RAM, otherwise (BL, BR) from the neighbour above. Each matrix gets two RAMs: A0 holds rows 0 to 3 of A and A1 rows 4 to 7; B0 holds columns 0 to 3 of B and B1 columns 4 to 7; C0 rows 0 to 3 of C and C1 rows 4 to 7. One RAM word is four elements (32 bits), the input width of one 4×4 tile. All four tiles get final_mat_mul_size = 8. Addresses and strides are the same for all four, and only the tiles attached to a RAM actually drive addresses (TL for A0 and B0, BL for A1, TR for B1); the other address outputs are left open.

타일 사이에도 02 절의 "늦게 넣기" 가 한 단계 위에서 다시 일어난다. TR 은 TL 을 가로질러 온 A 를 쓰니 B1 을 4 사이클 늦게 읽어야 짝이 맞는다. 주어진 주소 생성기가 이걸 a_loc, b_loc 로 한다. 읽기를 시작하는 사이클이 a_loc << 2 (= 4 × a_loc) 또는 b_loc << 2 다. 그 결과 TL 은 0~7 번 사이클에, BL 과 TR 은 4~11 번 사이클에 읽는다(다음 절 그림).

Section 02's staggering happens again one level up, between tiles. TR uses A that came across TL, so it has to read B1 four cycles later for the pairs to line up. The given address generator does this with a_loc and b_loc: reading starts on cycle a_loc << 2 (= 4 × a_loc) or b_loc << 2. So TL reads on cycles 0 to 7, and BL and TR on 4 to 11 (figure in the next section).

Part 4 · 문제 5 · CPU 는 핀을 못 흔든다 → APB 레지스터

Part 4 · Problem 5 · A CPU can't wiggle pins → APB registers

Part 4. 가속기를 SoC 에 붙일 수 있게, 제어를 레지스터 쓰기·읽기로 바꾼다.

Part 4. Turn control into register writes and reads, so the accelerator can sit in an SoC.

지금까지 8×8 을 움직인 것은 testbench 가 직접 흔드는 핀이었다. start 를 올리고, 주소 셋과 stride 셋을 핀에 걸고, done 핀을 지켜본다. 실제 칩(SoC)에서는 이 가속기를 부리는 것이 CPU 이고, CPU 는 핀을 흔들지 못한다. CPU 가 할 줄 아는 것은 "이 주소에 이 값을 쓴다", "이 주소의 값을 읽는다" 뿐이다.

So far the 8×8 has been driven by pins the testbench wiggles directly: raise start, put three addresses and three strides on pins, watch the done pin. On a real chip (an SoC), the one running this accelerator is a CPU, and a CPU can't wiggle pins. All it knows how to do is "write this value to this address" and "read the value at this address".

그래서 가속기 앞에 번호 붙은 서랍을 둔다. CPU 가 서랍 4 번에 A 의 주소를 넣고, 1 번에 1 을 넣으면 시작하고, 2 번을 열어 보면 끝났는지 알 수 있다. 이 서랍들이 CSR(control and status register)이고, 몇 번 서랍에 무엇이 있는지 적은 표가 register map 이다. CPU 와 서랍 사이의 약속(어떤 핀을 어떤 순서로)이 ARM 의 APB 다. APB 는 AMBA 버스 가운데 가장 단순한 것이라 이런 느린 설정용 레지스터에 쓴다(Lecture 10 의 12절).

So you put numbered drawers in front of the accelerator. The CPU puts A's address into drawer 4, puts a 1 into drawer 1 to start, and opens drawer 2 to see whether it's done. Those drawers are CSRs (control and status registers), and the table of which drawer holds what is the register map. The agreement between CPU and drawers (which pins, in what order) is ARM's APB, the simplest AMBA bus, used for slow configuration registers like these (Lecture 10, §12).

그림 읽기. 왼쪽 분홍 CPU 는 실제로는 testbench 다. testbench 가 APB 로 서랍(가운데 apb_slave)을 쓰고 읽는다. 서랍 번호는 1 START, 2 DONE, 3 FLAGS, 4~6 ADDR_A/B/C, 7~9 STRIDE_A/B/C 다(다음 절 표). apb_slave 는 서랍 값을 오른쪽 8×8 에 핀으로 내보내고(start_mat_mul, 주소, stride), 8×8 의 done 과 flags 를 받아 서랍 2, 3 에 담는다. 8×8 은 Part 3 의 것을 한 줄도 안 바꿨다. 아래 점선이 행렬 데이터 길이다. APB 를 거치지 않는다.

The drawers are 1 START, 2 DONE, 3 FLAGS, 4 to 6 ADDR_A/B/C, 7 to 9 STRIDE_A/B/C (table in the next section). apb_slave puts the drawer values on pins into the 8×8 on the right (start_mat_mul, addresses, strides) and takes the 8×8's done and flags into drawers 2 and 3. 읽은 값은 언제 PRDATA 에 있어야 하나

When PRDATA has to hold the read value

APB 전송 하나는 두 사이클이다. 첫 사이클(setup)에 PSEL = 1, PENABLE = 0 으로 주소를 걸고, 둘째 사이클(access)에 PENABLE = 1 이 된다. PREADY 가 1 이면 access 를 끝내는 상승 엣지에서 전송이 끝나고, 읽기라면 CPU 는 그 엣지에서 PRDATA 를 읽어 간다.

One APB transfer is two cycles. In the first (setup) PSEL = 1 and PENABLE = 0 with the address on the bus; in the second (access) PENABLE = 1. With PREADY = 1, the transfer ends on the rising edge that closes the access cycle, and for a read the CPU samples PRDATA on that edge.

그림 읽기. 맨 위 갈색이 클럭이고 칸 넷이 idle, setup, access, idle 이다. 분홍 PSEL 은 setup 과 access 두 칸 동안 1, PENABLE 은 access 한 칸만 1 이다. 앞의 셋은 커밋에 남은 사건이 아니라, 주어진 것을 제출본과 대조하다 드러난 곳이다. 뒤의 둘은 커밋 날짜 순이다.

The first three aren't events in the commit log; they turned up while comparing what was given with the submission. The last two follow commit dates.

1. 스펙에 두 군데 앞뒤가 안 맞는 줄

1. Two lines of the spec that disagree with themselves

설명서 Part 2 과제 2 의 제목이 "8x8 systolic matrix multiplier 의 int MAC 을 FP8 MAC 으로" 다. Part 2 는 4×4 이고 8×8 은 Part 3 이다. 그리고 Part 1 과제는 denormal 을 안 해도 된다고 하면서 Part 1 제출물 표는 "양·음 denormal" 줄을 요구한다. 제출본은 앞의 것은 4×4 로 읽고, 뒤의 것은 연산기가 subnormal 을 다루게 해서 둘 다 만족시켰다.

Part 2 task 2's heading says to replace the int MAC with an FP8 MAC "in the 8x8 systolic matrix multiplier", but Part 2 is the 4×4 and the 8×8 is Part 3. And Part 1's tasks make denormals optional while Part 1's deliverable table asks for a "positive and negative denormalized values" row. The submission read the first as the 4×4, and satisfied both sides of the second by having the units handle subnormals.

2. 주어진 뼈대의 폭이 서로 다르다

2. The skeleton's widths disagree

주어진 apb_slave.v 는 `define REG_DATAWIDTH 5 로 PRDATA 를 5 비트로 선언해 놓고, 바로 아래에서 PRDATA <= {done, 15'b0}, 16 비트를 넣는다. 설명서는 16 비트라고 한다. 5 비트대로 두면 done 이 잘려 나가 polling 이 영원히 끝나지 않는다. 제출본은 16 으로 바꿨다(12 절 표).

The given apb_slave.v declares PRDATA as 5 bits with `define REG_DATAWIDTH 5, then a few lines later assigns PRDATA <= {done, 15'b0}, 16 bits. The handout says 16. Left at 5, done would be cut off and polling would never end. The submission changed it to 16 (table in section 12).

3. 주석과 코드가 반대를 말한다

3. A comment and its code say opposite things

// If b_loc is 0, that means this matmul block is on the top-row ...// If b_loc is 0, that means this matmul block is on the top-row ...

주석은 "b_loc 가 0 이면 맨 윗줄이고 b 를 메모리에서 받는다" 인데 바로 아래 코드는 b_loc 로 a 를 고른다. 코드대로라면 b_loc 는 타일 기둥 번호이고, 0 이면 왼쪽 끝이라 A 를 메모리에서 받는다. 8×8 연결은 주석이 아니라 코드를 따라야 맞는다(08 절 그림의 a_loc, b_loc). 이걸 거꾸로 읽으면 TR 과 BL 의 a_loc, b_loc 가 뒤바뀌고 A 와 B 가 엉뚱한 이웃에서 온다. ones 테스트는 A 와 B 가 전부 1 이라 이런 뒤바뀜을 못 잡을 수 있다. random 이 잡는다.

The comment says "if b_loc is 0 the block is on the top row and b comes from memory", but the code right below uses b_loc to choose a. Going by the code, b_loc is the tile column, and 0 means the left edge, which takes A from memory. The 8×8 wiring has to follow the code, not the comment (a_loc, b_loc in the section 08 figure). Read it the other way round and TR's and BL's a_loc, b_loc swap, so A and B come from the wrong neighbours. The ones test may not catch that, since A and B are all ones; random does.

4. 연달아 돌리면 앞 결과가 섞인다 (10/20 → 10/21)

4. Back-to-back runs mix in the previous result (10/20 → 10/21)

Part 3 첫 판(10/20 업로드)은 PE 누적값을 pe_reset 핀으로만 비웠다. 행렬을 하나 곱하고 리셋 없이 다음 행렬을 곱하면 PE 의 out 에 앞 결과가 남은 채 새 곱이 더해진다. 다음 날 커밋 0da678c "bug fix on part 3" 가 시작할 때마다 비우는 줄을 넣었다.

The first Part 3 version (uploaded 10/20) cleared the PE accumulators only through the pe_reset pin. Multiply one matrix, then the next without a reset, and the new products are added onto the previous result still sitting in each PE's out. The next day, commit 0da678c "bug fix on part 3" added a clear at every start.

submitted · part_3/matmul_8x8.sv · excerpt
submitted · part_3/matmul_8x8.sv · excerpt
// 새 연산이 시작될 때 PE 누적값을 비운다. 그 사이클엔 피연산자를 안 쓴다// clear PE accumulators when a new operation starts; no operands are consumed that cycle
assign pe_clear = pe_reset | (start_mat_mul & ~running_d);

running_d 는 한 사이클 전의 start_mat_mul 이라, start_mat_mul & ~running_d 는 start 가 0 에서 1 로 바뀐 첫 사이클에만 1 이다. 같은 커밋이 flag 도 고쳤다. 고치기 전에는 시작 사이클의 flag 를 그대로 담았고, 고친 뒤에는 시작 사이클에 0 으로 비우고 그다음부터 OR 해 쌓는다. 이 수정을 확인하려고 Part 3 의 random 이 10 쌍을 리셋 없이 연달아 돌린다(R3, 불일치 0). 11 절의 "도는 중에 START 에 1 을 또 써도 무시" 도 이 0 → 1 검출 때문이다.

running_d is start_mat_mul one cycle earlier, so start_mat_mul & ~running_d is 1 only on the first cycle after start goes from 0 to 1. The same commit fixed the flags as well: before, the start cycle's flags were loaded as they were; after, they're cleared on the start cycle and ORed in from then on. To check the fix, Part 3's random runs its 10 pairs back to back with no reset (R3, 0 mismatches). Section 11's "writing 1 to START mid-run is ignored" also comes from this 0 → 1 detection.

5. 두 합성 표를 같은 잣대로 다시 낼 수 없었다 (10/22)

5. The two synthesis tables couldn't be redone on one ruler (10/22)

리포트를 정리하면서 15 절의 이상한 점이 드러났다. 같은 PE 인데 8×8 의 가장 긴 길이 더 짧고, 두 최고 주파수의 계산법이 다르다. 8×8 은 스크립트(run_dc.tcl)와 보고서가 저장소에 있지만, 4×4 정수판과 FP8 판의 보고서와 스크립트는 없다. 숫자는 리포트 표에만 있다. 같은 스크립트로 4×4 를 다시 합성하지 않아서 차이의 원인(스크립트 옵션, 경로 제약, 다른 날의 다른 설정)을 가리지 못했다.

Putting the report together exposed the oddities in section 15: the same PE, yet a shorter longest path in the 8×8, and two maximum frequencies computed two ways. The 8×8's script (run_dc.tcl) and reports are in the repository, but the 4×4 integer and FP8 reports and script aren't; their numbers exist only in the report table. The 4×4s weren't re-synthesised with the same script, so the cause (script options, path constraints, different settings on a different day) wasn't pinned down.

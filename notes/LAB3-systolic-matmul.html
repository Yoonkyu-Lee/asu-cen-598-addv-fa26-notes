The bias and how to read the bits

Lecture 8 05절의 규칙이 exponent 가 q bit 이면 bias = 2q−1 − 1 이다. q = 3 을 넣으면 bias = 22 − 1 = 3. exponent 칸의 3 bit 를 부호 없는 정수 X 로 읽고 3 을 빼면 실제 지수 E 다. mantissa 4 bit 앞에는 hidden bit 1 이 붙어 1.mmmm 이 된다. 아래 그림의 다섯 줄은 이 규칙만으로 읽힌다. 여섯째 줄은 규칙이 하나 더 있어야 읽힌다.

The rule from Lecture 8 section 05: with a q-bit exponent, bias = 2q−1 − 1. Put in q = 3 and bias = 22 − 1 = 3. 덱이 정하지 않은 것

What the deck leaves open

ExMy 라는 이름은 bit 수만 정한다. 아래는 설계와 testbench 가 같은 답을 가져야 하는 질문이다. 샘플 FP 코드가 이미 답을 갖고 있을 가능성이 크다. 그 코드를 먼저 읽고, 코드도 정하지 않은 것만 조 안에서 정한다.

The name ExMy fixes only bit counts. These are questions the design and the testbench must answer the same way. The sample FP code very likely answers some already. Read it first, and decide as a group only what it leaves open.

  1. exponent 111: ∞ 와 NaN 인가, 숫자인가. 최댓값이 15.5 와 31 로 갈린다(숫자로 쓰면 1.9375 × 24 = 31)
  2. exponent 000: subnormal 을 지원하나, 0 으로 버리나(flush to zero). 0.25 보다 작은 곱이 0 이 되는지가 갈린다
  3. rounding: Lecture 8 09절의 기본값 RTE 인가, 잘라내기(RTZ)인가. mantissa 가 4 bit 뿐이라 거의 모든 곱이 반올림된다
  4. 누적 정밀도: PE 의 누적 register 가 FP8 인가, 더 넓은가. int8 판은 누적 register 가 입력보다 넓었을 것이다(L09 08절의 폭 이야기). FP8 로 누적하면 합이 커질수록 작은 항이 묻힌다
  5. 넘침: 15.5 를 넘으면 ∞ 인가, 최댓값에 붙나(saturate). flags 와 직결된다(06절)
  1. Exponent 111: ∞ and NaN, or numbers? The maximum is 15.5 one way and 31 the other (as numbers, 1.9375 × 24 = 31)
  2. Exponent 000: are subnormals supported, or flushed to zero? It decides whether products below 0.25 become 0
  3. Rounding: RTE, the default from Lecture 8 section 09, or truncation (RTZ)? With only four mantissa bits, nearly every product gets rounded
  4. Accumulation precision: is the PE's accumulator FP8, or wider? The int8 version's accumulator was presumably wider than its inputs (the width discussion in L09 §08). Accumulate in FP8 and small terms vanish as the sum grows
  5. Overflow: above 15.5, ∞ or clamp to the maximum (saturate)? This ties straight into flags (section 06)

int8 에서는 testbench 가 정수 곱셈으로 기댓값을 바로 계산했을 것이다. FP8 에서는 그게 안 된다. 곱 하나마다, 덧셈 하나마다 반올림이 일어나고, FP 덧셈은 결합법칙이 성립하지 않아서(Lecture 8 10절) 더하는 순서까지 같아야 비트가 같다. PE 는 k = 0, 1, 2, 3 순서로 누적한다. 첫 테스트는 반올림이 아예 안 일어나는 값으로 골라라. 0.5, 1, 1.5, 2 같은 수는 곱과 합이 전부 정확히 담긴다. 예: 1.5 × 2.5 = 3.75 = 1.111b × 21 은 mantissa 1110 으로 정확하다. 그다음에 반올림이 일어나는 경우를 같은 규칙의 reference model(스크립트나 testbench 함수)로 계산해 비교한다. 이 판단은 슬라이드에 없는 보충이다.

For int8, the testbench presumably computed expected values with plain integer maths. That won't work for FP8: every product and every addition rounds, and FP addition isn't associative (Lecture 8 section 10), so the bits only match if the order matches too. The PE accumulates k = 0, 1, 2, 3 in that order. Pick first tests whose values never round at all: numbers like 0.5, 1, 1.5 and 2 keep every product and sum exact. For instance 1.5 × 2.5 = 3.75 = 1.111b × 21, exact with mantissa 1110. After that, compute rounding cases with a reference model under the same rules (a script or a testbench function) and compare. This advice is supplementary, not from the slides.

왜 걷어내나: 누적이 자기 자신을 기다린다

Why: the accumulator waits on itself

덱은 이유를 적지 않는다. 아래는 이 노트의 읽기다. Lecture 9 08절의 PE 는 매 사이클 acc ← acc + a × b 를 한다. a 와 b 는 한 사이클에 한 PE 씩 이웃으로 넘어가므로, PE 는 매 사이클 새 a, b 짝을 받는다. 07절의 규칙 "PE(i, j) 는 k 번째 항을 T = i + j + k + 1 에 받는다" 가 그 뜻이다. 그러면 k 번째 항을 더하려면 k − 1 번째까지의 합이 다음 사이클에 이미 나와 있어야 한다. 덧셈기가 두 사이클 걸리면 그 합이 아직 없다. Lecture 8 11절의 현장 감각 문제(내적을 pipeline 덧셈기 하나로 누적하면 의존 때문에 한 번에 하나밖에 못 넣는다)와 같은 문제다.

The deck doesn't give the reason; what follows is this note's reading. The PE in Lecture 9 section 08 does acc ← acc + a × b every cycle. a and b hop one PE per cycle, so a PE gets a fresh a, b pair every cycle; that's what section 07's rule "PE(i, j) receives term k at T = i + j + k + 1" means. To add term k, the sum through term k − 1 must already be there the next cycle. With a two-cycle adder it isn't. It's the same problem as the field exercise in Lecture 8 section 11: accumulating a dot product through one pipelined adder lets only one addition in at a time, because each depends on the last.

그림 읽기Reading the picture
  • 왼쪽: a 는 왼쪽 이웃에서, b 는 위 이웃에서 온다. F* 가 곱하고 F+ 가 지금까지의 합(acc)에 더한다. acc 의 출력이 아래로 돌아 F+ 의 둘째 입력이 된다. 이 고리가 문제의 자리다. 오른쪽 c 가 누적 결과다
  • 주황 점선: 샘플 코드처럼 F* 와 F+ 안에 pipeline register 가 있으면 고리 안에 사이클이 늘어난다
  • 오른쪽 첫 줄 (a, b arrive): 사이클 1, 2, 3, 4 에 항 k0, k1, k2, k3 의 a, b 짝이 하나씩 도착한다. 이 PE 의 위치가 (0, 0) 이라고 치면 T = 0 + 0 + k + 1 이라 k 번째가 사이클 k + 1 이다
  • 둘째 줄 (de-pipelined, 초록): 연산기가 한 사이클이면 도착한 사이클에 바로 더한다. 4 사이클이면 네 항이 다 들어간다
  • 셋째 줄 (2-cycle F+): +k0 가 사이클 1 과 2 를 차지한다. k1 은 사이클 2 에 도착했지만 k0 까지의 합은 사이클 2 가 끝나야 나온다. 그래서 +k1 은 사이클 3 에야 시작한다. 주황 글씨가 그 자리다. 그사이 a, b 는 다음 PE 로 넘어가 버리므로 기다릴 수도 없다. 결과적으로 항 하나를 두 사이클에 하나씩밖에 못 받는다

곱셈기만 pipeline 이면 사정이 다르다. 곱셈은 고리 밖에 있다. k 번째 곱이 몇 사이클 늦게 나와도 매 사이클 하나씩 나오면 덧셈기는 매 사이클 하나씩 더할 수 있다. 전체가 그만큼 늦어질 뿐이다. Lecture 9 09절의 "4N − 2 (+ MAC 안의 사이클 수)" 의 괄호가 그 늦어짐이다. 15쪽 그림은 어느 연산기인지 가리지 않으므로 둘 다 걷어내라는 뜻인지, 덧셈기만인지는 덱에 없다. 둘 다 걷어내는 것이 가장 단순하고 일정 계산도 int8 판과 같아진다.

  • Left: a comes from the left neighbour, b from above. F* multiplies and F+ adds the product to the sum so far (acc). acc's output loops back down to F+'s second input; that loop is where the trouble is. c on the right is the running result
  • Amber dashed lines: with pipeline registers inside F* and F+, as in the sample code, the loop gets extra cycles
  • Right, first row (a, b arrive): the a, b pairs for terms k0, k1, k2, k3 arrive one per cycle in cycles 1, 2, 3, 4. Take this PE to be at (0, 0): T = 0 + 0 + k + 1, so term k arrives in cycle k + 1
  • Second row (de-pipelined, green): with one-cycle units, each term is added in the cycle it arrives. All four are in after 4 cycles
  • Third row (2-cycle F+): +k0 takes cycles 1 and 2. k1 arrives in cycle 2, but the sum through k0 isn't out until cycle 2 ends, so +k1 can't start until cycle 3 (the amber note). Meanwhile a and b have already moved on to the next PE, so it can't wait either. The PE ends up taking a term only every other cycle

A pipelined multiplier alone is a different story. Multiplication sits outside the loop. If product k comes out a few cycles late but one still comes out every cycle, the adder can add one per cycle; everything just finishes that much later. That delay is the bracket in Lecture 9 section 09's "4N − 2 (+ cycles inside the MAC)". Slide 15's picture doesn't say which unit, so whether to de-pipeline both or only the adder isn't in the deck. Doing both is simplest and keeps the timing identical to the int8 version.

대가: 한 사이클이 길어진다

The price: a longer cycle

pipeline 을 걷어내면 공짜로 빨라지는 게 아니다. FP 곱셈 전체와 FP 덧셈 전체(정렬, 더하기, 정규화, 반올림)가 한 clock 주기 안에 들어가야 한다. critical path 가 길어져 최대 클럭이 내려간다. Lecture 7 04절이 pipelining 을 timing 을 버는 기법으로 소개했는데, 여기서는 그 반대 방향으로 간다. latency 를 사이클 수로 맞추는 대신 주기를 내준다. 합성이 이 Lab 의 요구에 들어 있는지는 덱에 없지만, 데모에서 "왜 걷어냈나, 대가는 무엇인가" 는 물어볼 만한 질문이다.

Removing the pipelining isn't a free speed-up. A whole FP multiply and a whole FP add (align, add, normalise, round) now have to fit in one clock period. The critical path grows and the maximum clock drops. Lecture 7 section 04 introduced pipelining as a way to win timing; this goes the other way, giving up clock period to keep the cycle counts. The deck doesn't say whether synthesis is part of this lab, but "why de-pipeline, and what did it cost" is a fair demo question.

Two things the deck leaves open

첫째, 4 bit 의 뜻. 슬라이드에는 flag(3:0) 라는 폭만 있다. 샘플 FP 코드의 출력일 가능성이 크니 그 코드에서 확인한다. 참고로 IEEE 754 는 예외를 다섯 가지 둔다: invalid operation, division by zero, overflow, underflow, inexact. 곱셈기와 덧셈기에는 나눗셈이 없으니 남는 것이 넷이다. 4 bit 가 이 넷이라는 것은 이 노트의 추측일 뿐이다.

First, what the 4 bits mean. The slides give only the width, flag(3:0). They're most likely the sample FP code's outputs, so check there. For reference, IEEE 754 defines five exceptions: invalid operation, division by zero, overflow, underflow and inexact. A multiplier and an adder never divide, which leaves four. That the 4 bits are those four is only this note's guess.

둘째, 언제의 flag 인가. 16쪽 그림에서 OR 의 출력은 register 를 거치지 않고 PE 밖으로 나간다. 그대로면 flags 는 그 사이클의 연산에 대한 것이다. 그런데 testbench 는 done 을 본 뒤에 APB 로 읽는다. 그때 PE 는 이미 계산을 마쳤으니 조합 회로 flags 는 마지막 사이클의 값이거나 0 이다. "이번 행렬곱 중에 한 번이라도 넘쳤나" 를 읽으려면 flag 를 register 에 OR 로 쌓아 두고(한 번 1 이면 계속 1) start 때 지우는 장치가 필요하다. 그리고 쌓을 때는 진짜 데이터가 지나가는 사이클만 쌓아야 한다. 계단 앞뒤의 빈 사이클에 들어오는 값(0 이나 시뮬레이션의 x)이 flag 를 오염시킬 수 있다. 21쪽 목록의 Validity masks 가 이 판단과 닿아 있을 수 있다(07절).

Second, flags from when? On slide 16 the OR's output leaves the PE without passing a register. As drawn, flags describe that cycle's operation. But the testbench reads them over APB after seeing done, when the PEs have finished, so combinational flags show the last cycle or nothing. To read "did anything overflow during this matmul", you need to OR each cycle's flags into a register (once 1, stays 1) and clear it on start. And only accumulate on cycles where real data is passing: values in the empty cycles around the staircase (zeros, or x in simulation) can pollute the flags. Slide 21's Validity masks may connect to this (section 07).

CSR 을 고르는 법 (24쪽)

Choosing CSRs (slide 24)

24쪽(CSR Registers)의 지시는 셋이다. 레지스터 크기를 고른다: 신호 하나를 레지스터 하나에 둘 수도, 여러 신호를 레지스터 하나에 묶을 수도 있다. 레지스터 주소를 고른다: register map 을 만든다. testbench 에서 맞는 주소에 쓴다: start 를 주소 1 에 두었으면 start 를 켜려고 주소 1 에 쓴다. 실제 회사에서는 이 표가 spec 문서에 들어간다.

Slide 24 (CSR Registers) gives three instructions. Choose register sizes: one signal per register, or several signals packed into one. Choose register addresses: create a register map. Write to the correct address from the testbench: if start is mapped to address 1, write address 1 to assert start. In real life the map lives in the specification document.

묶을지 말지에는 대가가 있다. 이 부분은 슬라이드 밖 보충이다. 신호 여럿을 한 레지스터에 묶으면 주소를 아끼지만, apb_write 는 레지스터 한 칸을 통째로 쓴다. start 와 stride 가 같은 칸에 있으면 start 만 켜려 해도 stride 값을 같이 다시 써야 한다(먼저 읽어서 고쳐 쓰거나, testbench 가 값을 기억하거나). 쓰는 신호와 읽는 신호를 다른 칸에 두면 이 문제가 줄고, testbench 의 실수도 줄어든다.

Packing has a price (this is supplementary, not from the slides). Packing several signals into one register saves addresses, but apb_write writes a whole register. If start and a stride share one, turning on start means rewriting the stride as well (read it first and modify, or have the testbench remember it). Keeping written signals and read signals in separate registers shrinks the problem and the testbench's room for mistakes.

Two cycles per transfer (one SETUP, one ACCESS). This slave holds PREADY at 1, so there are no wait states. A slave that drops PREADY stretches ACCESS by that much, and the task has to wait for an edge with PREADY at 1.

The task and the slave in code (a sketch for understanding)

아래는 위 파형을 그대로 코드로 옮긴 이 노트의 스케치다. 실제로는 example_tb.v 와 apb_slave.v 의 초기 코드에서 출발한다. 신호 이름과 폭은 그 파일을 따른다.

Below is this note's sketch of the waveform above in code. In practice you start from the starter code in example_tb.v and apb_slave.v, and follow their signal names and widths.

task apb_write(input [7:0] addr, input [31:0] data);
  @(posedge pclk);
  psel <= 1; pwrite <= 1; paddr <= addr; pwdata <= data; penable <= 0;
  @(posedge pclk);
  penable <= 1;
  @(posedge pclk);
  while (!pready) @(posedge pclk);
  psel <= 0; penable <= 0;
endtask

task apb_read(input [7:0] addr, output [31:0] data);
  @(posedge pclk);
  psel <= 1; pwrite <= 0; paddr <= addr; penable <= 0;
  @(posedge pclk);
  penable <= 1;
  @(posedge pclk);
  while (!pready) @(posedge pclk);
  data = prdata;
  psel <= 0; penable <= 0;
endtask

task 안의 @(posedge pclk) 셋이 파형의 T1, T2, T3 이다. 첫 엣지 뒤에 SETUP 값을 내놓고, 둘째 엣지 뒤에 PENABLE 을 올리고, 셋째 엣지에서 PREADY 를 확인한다. 그 엣지에서 PREADY 가 1 이면 전송이 끝난 것이고, 읽기라면 바로 그때 PRDATA 를 담는다. 0 이면 다음 엣지까지 기다린다. done 기다리기(4 단계)는 이 task 를 되풀이해 부르는 것이다.

The three @(posedge pclk) in each task are T1, T2 and T3 in the waveform: after the first edge put out the SETUP values, after the second raise PENABLE, and at the third check PREADY. If PREADY is 1 there, the transfer is done, and a read captures PRDATA right then; if 0, wait for the next edge. Waiting for done (step 4) is just calling this task repeatedly.

고친 곳 하나, PSEL. 26쪽은 Penable && Pwrite 만 본다. slave 가 하나뿐이면 같은 결과지만, APB 의 규칙은 PSEL 과 PENABLE 이 둘 다 1 인 엣지가 전송이다(Lecture 10 12절). slave 가 둘 이상인 SoC 에 붙이면 남의 전송에 반응하게 된다. 고친 곳 둘, 읽기 타이밍. 26쪽은 읽기도 prdata <= flags 처럼 <= 로 적었다. 이 대입이 PENABLE = 1 인 엣지(T6)에서 일어나면 PRDATA 는 T6 직후에 바뀐다. 그런데 testbench 는 바로 그 T6 에서 PRDATA 를 담으므로 바뀌기 전 값을 읽는다. 고치는 방법은 셋이다. 위처럼 PADDR 로 조합 회로 읽기를 하거나, SETUP 엣지(PSEL = 1, PENABLE = 0)에서 미리 register 에 담거나, PREADY 를 한 사이클 내려 wait state 를 하나 넣는다. 주어진 apb_slave.v 가 어느 방식인지 먼저 본다. 이 둘은 슬라이드에 없는 보충이다.

Fix one, PSEL. Slide 26 checks only Penable && Pwrite. With a single slave the result is the same, but APB's rule is that a transfer is an edge where PSEL and PENABLE are both 1 (Lecture 10 section 12); dropped into an SoC with several slaves, this one would react to other slaves' transfers. Fix two, read timing. Slide 26 writes reads with <= too, as in prdata <= flags. If that assignment happens at the edge with PENABLE = 1 (T6), PRDATA changes just after T6, while the testbench captures PRDATA at T6 itself, so it reads the old value. Three ways out: a combinational read off PADDR as above, capture into a register at the SETUP edge (PSEL = 1, PENABLE = 0), or drop PREADY for one cycle to insert a wait state. Check which approach the given apb_slave.v takes first. Both fixes are supplementary, not from the slides.

start 와 done 이 레지스터가 되면 생기는 일

What happens when start and done become registers

선이었을 때는 testbench 가 start 를 한 사이클만 올렸다 내릴 수 있었다. 레지스터가 되면 1 을 쓴 뒤 0 을 쓰기 전까지 계속 1 이다. state machine 이 start 를 "1 인 동안 계속 시작" 으로 읽으면 끝나자마자 다시 시작한다. 길은 셋이다: testbench 가 곧바로 0 을 쓴다, slave 가 한 사이클 뒤 스스로 0 으로 되돌린다, state machine 이 start 의 0 → 1 변화만 본다. 어느 쪽이든 register map 에 적어 둔다. done 은 반대 문제다. matmul 의 done 이 한 사이클짜리 펄스라면, 전송 하나에 두 사이클 걸리는 APB 읽기로는 그 한 사이클을 놓칠 수 있다. 그래서 위 예는 done_reg 에 담아 다음 start 까지 들고 있게 했다. 이 판단도 슬라이드 밖 보충이다.

As a wire, start could be raised for just one cycle. As a register, once you write 1 it stays 1 until you write 0. If the state machine treats start as "keep starting while it's 1", it starts again the moment it finishes. Three ways out: the testbench writes 0 straight after, the slave returns it to 0 by itself a cycle later, or the state machine reacts only to start going 0 → 1. Whichever you pick, write it into the register map. done has the opposite problem: if the matmul's done is a one-cycle pulse, APB reads that take two cycles each can miss it, which is why the example above latches it into done_reg until the next start. Lecture 9 07절의 규칙은 PE(i, j) 가 k 번째 항을 T = i + j + k + 1 에 받는 것이다. 8×8 전체로 보면 #1 의 첫 열은 j = 4 라서, 같은 k 의 b 값이 #0 의 첫 열보다 4 사이클 늦게 와야 한다. a 값은 #0 의 PE 네 칸을 지나느라 저절로 4 사이클 늦게 #1 에 닿는다. 그런데 #1 이 RAM B 에서 b 를 #0 과 같은 사이클에 읽기 시작하면 b 가 4 사이클 빨리 도착해 a 와 짝이 어긋난다. 그래서 #1 쪽 RAM B 읽기를 4 사이클 늦게 시작하거나 b 를 4 단 늦춰야 한다. #2 의 a 도 같은 이유로 4 사이클(i = 4) 늦어야 한다. #3 은 a 와 b 를 둘 다 이웃에서 받으므로 따로 할 일이 없다. 31쪽은 이 늦춤을 그리지 않았다. 주어진 4×4 가 이걸 어떻게 처리하는지 확인한다.

The amber "+4 cycles" is this note's derivation. Lecture 9 section 07's rule is that PE(i, j) receives term k at T = i + j + k + 1. In the full 8×8, #1's first column is j = 4, so its b value for a given k must arrive 4 cycles after #0's first column gets its own. The a values reach #1 4 cycles late automatically, having crossed #0's four PEs. But if #1 starts reading RAM B in the same cycle as #0, its b values arrive 4 cycles early and pair with the wrong a. So #1's RAM B reads must start 4 cycles later, or its b must go through 4 extra delay stages. #2's a needs the same 4 cycles (i = 4). #3 gets both a and b from neighbours and needs nothing extra. Slide 31 doesn't draw this delay; check how the given 4×4 handles it.

This lab's wrapper and APB tasks don't end here. Lab 6 in this course is an APB agent with assertions. And this is exactly the order in which an accelerator goes into a real SoC: get the arithmetic right, settle the number format, wrap it in CSRs, scale it up.

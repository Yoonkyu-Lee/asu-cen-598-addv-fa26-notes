Case study: CPU verification

CPU 를 검증할 때 stimulus 는 프로그램, 정답은 ISS 다. 다섯 층으로 쌓아 올리고, RTL 과 ISS 는 명령어가 retire 할 때 맞춘다.

When verifying a CPU, the stimulus is a program and the answers come from an ISS. Build up in five layers, and match the RTL against the ISS when each instruction retires.

결론부터

The short version

검증의 일반론을 CPU 하나에 적용한 case study 다. 슬라이드 1쪽이 밝히듯 많은 쪽이 Hitesh Mishra 의 Arm 프로세서 검증 자료에서 왔고, 뒤쪽은 공개 RISC-V 프로젝트(CORE-V, Ibex, riscv-dv)의 예다. CPU 는 입력이 프로그램이고 pipeline 안에서 stall, forwarding, flush 가 섞여 돌기 때문에 매 cycle 의 정답을 적어둘 수 없다. 그래서 세 질문으로 갈린다.

A case study applying general verification ideas to one CPU. As slide 1 says, many slides come from Hitesh Mishra's processor verification material at Arm; the later ones are examples from open RISC-V projects (CORE-V, Ibex, riscv-dv). A CPU's input is a program, and inside the pipeline stalls, forwarding and flushes mix together, so you can't write down the right answer for every cycle. That splits into three questions.

세 기둥, coverage, checking

Three pillars, coverage, checking

슬라이드 3~8쪽. 방법론의 이름이 4쪽 제목이다. Coverage-Driven Constrained Random Verification + Directed Tests. constrained random 으로 넓게 찌르고, coverage 로 빈 곳을 보고, random 이 안 닿는 모서리는 directed test 로 메운다.

Slides 3 to 8. The method's name is slide 4's title: Coverage-Driven Constrained Random Verification + Directed Tests. Poke widely with constrained random, find empty spots through coverage, fill the corners random can't reach with directed tests.

  • 5쪽의 coverage 표: 명령어 6 × destination register 10 = 60칸. random 만으로 3칸(5%)에서 59칸(98.3%)까지 오르고 AND→r8 한 칸이 남는다. "steer constraints or directed test" 로 100%. 슬라이드의 21.1% 는 13칸(21.7%)의 오타로 보인다
  • Slide 5's coverage table: 6 instructions × 10 destination registers = 60 bins. Random alone climbs from 3 bins (5%) to 59 (98.3%), leaving AND→r8. "Steer constraints or directed test" gets 100%. The slide's 21.1% looks like a typo for 13 bins (21.7%)
  • 6쪽: 100% 면 끝인가? 아니다. functional coverage 는 정의한 칸만큼만 좋다. soak 로 cycle 을 훨씬 더 돌리고, 새 버그는 새 칸이 된다
  • Slide 6: done at 100%? No. Functional coverage is only as good as the bins defined. Soak with many more cycles; each new bug becomes a new bin
  • 7쪽 grey box checking: DUT 의 출력만이 아니라 안쪽 상태를 probe 해서 하는 check. 입력으로 기대값을 계산하는 result modelling 이 같이 필요하고, model 이 정확해야 한다
  • Slide 7, grey box checking: a check that probes internal state, not just outputs. It needs result modelling (computing the expected values from the inputs), and the model must be accurate

Top-level testbench 와 test 세 종류

The top-level testbench and three kinds of test

18쪽의 부품 여섯: program loader, memory models, bus agents, coverage collectors, protocol checkers, arch state checkers. 33쪽 Arm 그림에서는 Test Programs 와 Memory Model, AXI BFM 둘, ACE Snoop Generator, Trickbox, ISS (Arch Model)가 그것이다. trickbox 는 test 프로그램이 testbench 에게 인터럽트, reset, 메모리 지연과 오류, snoop, pass/fail 을 요청하는 창구다(34쪽).

Slide 18's six components: program loader, memory models, bus agents, coverage collectors, protocol checkers, arch state checkers. In slide 33's Arm picture they're Test Programs and the Memory Model, two AXI BFMs, the ACE Snoop Generator, the Trickbox, and the ISS (Arch Model). A trickbox is how a test program asks the testbench for interrupts, resets, memory delays and errors, snoops, or pass/fail (slide 34).

Stimulus 는 프로그램이다

The stimulus is a program

슬라이드 41~45쪽. random bit 는 illegal 명령어나 하는 일 없는 프로그램이 된다. generator 의 constraint 다섯: supported ISA, register initialization, memory map, control flow, execution environment. illegal 명령어는 exception 시험용으로 일부러 넣기도 한다.

Slides 41 to 45. Random bits give illegal instructions or programs that do nothing. A generator's five constraints: supported ISA, register initialization, memory map, control flow, execution environment. Illegal instructions are sometimes generated on purpose to test exceptions.

  • 관계를 randomize(43쪽): destination 을 source 로 다시 쓸 확률, producer–consumer 거리, load/store/branch/long-latency 빈도, 같은 주소 확률. hazard 를 치려면 이게 필요하다
  • Randomize relationships (slide 43): the probability of reusing a destination as a source, producer–consumer distance, the mix of loads/stores/branches/long-latency ops, the probability of hitting the same address. Hitting hazards needs these
  • directed template + random 세부(44쪽): 같은 주소에 store 다음 load, long-latency 다음 의존 명령어, taken branch 와 flush 될 명령어, 진행 중 연산 근처의 exception
  • Directed templates + random details (slide 44): store then load to the same address, a long-latency op then a dependent instruction, a taken branch with younger instructions to flush, an exception near in-flight operations
  • riscv-dv(45쪽): 구글의 RISC-V generator. SystemVerilog class 로 짰다
  • riscv-dv (slide 45): Google's RISC-V generator, written as SystemVerilog classes

Lab 5 의 출발점. Lab 2 기록의 18절이 확인 못 한 경로 셋(branchstallD, not-taken beq, lw 바로 뒤 beq)을 남겼다. 각각이 44쪽 표의 손잡이 하나다.

ISS 와 retire 비교

The ISS and retire comparison

슬라이드 47~52쪽. ISS 는 프로세서의 architectural 동작만 흉내 내는 소프트웨어 모델이다. PC, register, 메모리, CSR 과 privilege, exception 을 갱신하지만 pipeline 과 cycle 은 모른다. RTL 은 forwarding, stall, flush, 추측 실행을 하고 구현마다 cycle 수가 다르다. 그래서 49쪽: 같은 프로그램, 같은 초기 상태로 돌리고, 매 cycle 이 아니라 retire 할 때 비교한다. retire 는 명령어의 효과가 architectural 하게 확정되는 순간이다.

Slides 47 to 52. An ISS is a software model of only the processor's architectural behaviour: it updates the PC, registers, memory, CSRs and privilege, and exceptions, but knows nothing about pipelines or cycles. The RTL does forwarding, stalls, flushes and speculation, in implementation-dependent cycles. Hence slide 49: run the same program from the same initial state, and compare at retire, not every cycle. Retirement is when an instruction's effects become architecturally committed.

그림 읽기Reading the picture

위 줄이 RTL 의 cycle 이다. 다섯 단계라 c1~c4 는 pipeline 이 차는 중이고 첫 retire 는 c5 의 lw 다. c6 은 stall(add 가 lw 결과를 바로 써서 한 cycle 멈춘 빈자리), c11 은 flush(beq 가 taken 이라 버린 add 의 빈자리)다. 아래 줄은 ISS 의 step 1~8 로, cycle 도 빈자리도 없다. 분홍 선이 짝이다. RTL 의 c5, c7, c8, c9, c10, c12, c13, c14 가 ISS 의 1~8 과 맞춰진다. 매 cycle 을 비교했다면 c6 와 c11 에서 틀렸다고 했을 것이다.

The top row is the RTL's cycles. With five stages, c1 to c4 fill the pipeline and the first retire is the lw in c5. c6 is a stall (the gap left when add waited a cycle for lw's result) and c11 a flush (the gap left by the add discarded after the taken beq). The bottom row is the ISS's steps 1 to 8, with no cycles and no gaps. The pink lines pair them: RTL c5, c7, c8, c9, c10, c12, c13, c14 match ISS 1 to 8. Comparing every cycle would have flagged c6 and c11.

51쪽: 초기 상태, ISA 구성, 인터럽트와 debug 요청의 시점, cycle counter 와 timer, MMIO, 구현 정의 동작이 맞지 않으면 RTL 이 멀쩡해도 불일치가 난다. 자세한 판 17절에서 버그를 심어 직접 돌려볼 수 있다.

Slide 51: if initial state, ISA configuration, the timing of interrupts and debug requests, cycle counters and timers, MMIO, or implementation-defined behaviour don't agree, you get mismatches even with correct RTL. §17 of the full note lets you plant bugs and try it.

UVM 1

UVM 은 testbench 를 걸어 둘 뼈대다. run_test() 한 줄이 시뮬레이션을 넘겨받고, test 가 감독이 되어 component 를 짓고, 모든 component 가 같은 phase 순서를 밟으며, run 은 objection 이 다 내려가야 끝난다. 핀을 만지는 것은 맨 아래 transactor(driver, monitor)뿐이다.

UVM is a frame to hang your testbench on. One run_test() call takes over the simulation, the test directs it by building the components, every component walks the same phase order, and the run ends only when every objection is dropped. Only the transactors at the bottom (driver, monitor) touch pins.

UVM 코드 안에 든 것What's inside UVM's code

5쪽은 UVM 을 열어보면 무엇이 있는지를 적는다. SystemVerilog 로 쓴 package 하나(class 와 type 의 모음), 그리고 macro 다. macro 는 두 종류로, 메시지를 찍는 것(Lecture 14 · 06 의 `uvm_info, `uvm_error)과 class 의 field 를 한꺼번에 처리하는 것(슬라이드 표현으로 "large code shortcuts")이다. 그 밖에 이런 장치가 들어 있다. component 관리, 통합된 runtime phase 관리, 자원 공유 database, 시뮬레이션 event 관리, register abstraction/access layer, template class(parameterized class) 정의, transaction 처리(queue 에 넣고, 주고받고, TLM 구현).

Slide 5 lists what you find when you open UVM up: a single package written in SystemVerilog (classes and types), and macros, of two kinds: message reporting (Lecture 14 · 06's `uvm_info, `uvm_error) and class field automation (in the slide's words, "large code shortcuts"). Beyond those, mechanisms for: component management, unified run-time phase management, a resource sharing database, simulation event management, a register abstraction/access layer, template (parameterized) class definitions, and transaction handling (queuing, exchanging, TLM implementations).

운전을 배우는 법Learning to drive

6쪽은 비유 한 장이다. 차의 사용 설명서를 읽는다고 운전을 배우지 않는다. 마찬가지로 UVM 의 NaturalDocs 페이지(UVM class reference 를 자동 생성한 문서)나 class 소스를 읽어서는 UVM 을 쓰는 법을 배우지 못하고, UVM 책을 읽어서는 design verification 을 배우지 못한다. 도로에 나가기 전에 도로의 규칙, 곧 다른 운전자와 어떻게 지내는지를 먼저 이해하라는 것이다. 이 노트가 03~06절에서 phase 와 objection 을 길게 다루는 이유가 이 "도로의 규칙" 이다. 모든 component 가 같은 규칙을 지키기 때문에 남이 만든 부품과 함께 달릴 수 있다.

Slide 6 is a single analogy. You don't learn to drive by reading your car's owner's manual. Likewise, reading UVM's NaturalDocs pages (the auto-generated class reference) or its class sources won't teach you to use UVM, and reading a UVM book won't teach you design verification. Before getting on the road, understand the rules of the road: how you deal with the other drivers. That's why §03 to §06 spend so long on phases and objections. They are the rules of the road, and because every component follows them, your parts can share the road with parts someone else built.

02

옛 방식과 새 방식 (DV Paradigm Shift)

Old way, new way (the DV paradigm shift)

7쪽은 같은 DUT 를 두 방식으로 시험하는 코드를 나란히 놓는다. DUT 는 입력 셋(signalA 1비트, signalB 16비트, signalC 32비트)과 출력 둘(ack 1비트, dout 32비트)을 가진 module 이고, tb_top 안에 dut 라는 이름으로 놓여 있다.

Slide 7 sets two ways of testing the same DUT side by side. The DUT is a module with three inputs (signalA, 1 bit; signalB, 16 bits; signalC, 32 bits) and two outputs (ack, 1 bit; dout, 32 bits), instantiated as dut inside tb_top.

Test 가 지휘한다

The UVM test takes charge

8쪽의 오른쪽 위에 슬레이트를 든 영화감독 사진이 있다. 슬라이드의 말로 test 가 시뮬레이션의 감독(director)이다. 세 줄로 정리된다. UVM 이 시뮬레이션의 처음부터 $finish 까지 사건의 순서를 쥔다. 코드는 class 로 짜고, class 안에 function 과 task 가 있다. 기본 동작은 test class 하나하나가 관리한다.

At the top right of slide 8 is a film director holding a clapperboard. In the slide's words, the test acts as the director of the simulation. Three points: UVM controls the order of events from the start of the simulation to $finish; code is organised into classes containing functions and tasks; and basic behaviour is managed by each test class.

아래쪽 화살표 셋이 흐름이다. run_test 는 고른 test class 의 object 를 만들고 시뮬레이션을 끝까지($finish) 끌고 간다. my_test 는 UVM component 의 표준 virtual method(task 와 function)를 구현하고, UVM 의 test controller 가 phase 를 실행시키면 그 안에서 TB environment 를 설정하고 짓고 stimulus sequence(task)를 띄운다. my_environment 는 같은 표준 virtual method 를 구현해서 testbench environment 를 설정한다.

The three arrows at the bottom are the flow. run_test constructs the selected test class object and carries the simulation to completion ($finish). my_test implements the UVM component standard virtual methods (tasks and functions); as the UVM test controller executes the phases, it configures and constructs the TB environment and launches stimulus sequences (tasks). my_environment implements the same standard virtual methods to configure the testbench environment.

Lecture 12 의 virtual method 가 여기서 일한다. "표준 virtual method 를 구현한다" 는 말은 Lecture 12 · 05 의 polymorphism 그대로다. UVM 의 base class 가 build_phase, run_phase 같은 이름의 virtual method 를 비워 두고, 우리가 그것을 override 한다. UVM 은 base class handle 로 그 method 를 부르는데, 실제로는 우리 것이 돈다. UVM 이 우리 코드를 부르는 것이지 우리가 UVM 을 부르는 것이 아니다. 감독 비유가 가리키는 방향이 이것이다.

Lecture 12's virtual methods at work. "Implements the standard virtual methods" is Lecture 12 · 05's polymorphism, unchanged. UVM's base classes leave virtual methods named build_phase, run_phase and so on empty, and we override them. UVM calls them through a base-class handle, and ours is what runs. UVM calls our code, not the other way round; that's the direction the director analogy points.

  my_env env;

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  function void build_phase(uvm_phase phase);   // 시간 0, function// time 0, a function
    super.build_phase(phase);
    env = my_env::type_id::create("env", this);   // 내 아래에 env 를 짓는다// build the env below me
  endfunction

  task run_phase(uvm_phase phase);              // 시간이 흐른다, task// time passes, a task
    my_seq seq;

  endtask

줄마다 무엇인지. extends uvm_test 는 UVM 의 test base class 를 물려받는다. `uvm_component_utils 는 이 class 를 UVM 의 factory 에 등록하는 macro 다. factory 에 등록되어 있어야 run_test 가 문자열 "smoke_test" 만 보고 object 를 만들 수 있고, type_id::create 로 만들 수 있다. 생성자의 인자 둘(name, parent)은 component 만 갖는 모양이다(07절). build_phase 는 function, run_phase 는 task 다(04~05절). raise/drop 은 06절. 슬라이드는 factory 와 macro 의 이름을 이 강의에서 다루지 않는다. 이 문단은 UVM class reference 를 기준으로 한 보충이고, 자세한 것은 다음 강의에서 나올 것으로 본다.

Line by line. extends uvm_test inherits UVM's test base class. `uvm_component_utils is a macro that registers the class with UVM's factory; that registration is what lets run_test build an object from nothing but the string "smoke_test", and what makes type_id::create work. The constructor's two arguments (name, parent) are the shape only components have (§07). build_phase is a function and run_phase a task (§04 to §05). Raise and drop are §06. The slides don't cover the factory or these macros in this lecture; this paragraph is a supplement based on the UVM class reference, and the details presumably come next time.

Function 과 task: 시간을 쓰나

Functions and tasks: does it take time?

phase 로 들어가기 전에 덱이 SV 의 기초 하나를 다시 짚는다. 9쪽은 같은 비교(기댓값과 실제 값이 같으면 "Correct value", 아니면 "Incorrect value" 를 찍는다)를 task 하나와 function 하나로 짜서 나란히 놓는다. 차이는 task 쪽이 @(actual) 로 값이 바뀌기를 기다린 뒤 비교한다는 것뿐이다. 이 차이를 구별 기준 한 줄로 줄이면 Lecture 3 · 14 와 같다. 시간을 쓰나.

Before phases, the deck revisits one piece of SV basics. Slide 9 writes the same comparison (print "Correct value" if expected equals actual, "Incorrect value" otherwise) as a task and as a function, side by side. The only difference is that the task first waits for the value to change with @(actual). Reduced to one deciding question, it's the same as Lecture 3 · 14: does it take time?

  • task 는 function 처럼 쓸 수도 있고(9쪽은 "필요하면 값을 돌려줄 수도 있다" 고 쓴다), 시뮬레이션 시간을 쓸 수도 있다. 신호 변화나 event 를 기다리기(wait, @), 절대 시간만큼 지연하기(#), 다른 process 에 막혀 기다리기, 시간을 쓰는 다른 task 부르기
  • A task can act like a function (slide 9 says it can even return a value if necessary), and it can also consume simulation time: waiting on a signal change or event (wait, @), delaying an absolute time (#), blocking on another process, or calling other tasks that take time
  • function 은 시간을 쓰면 안 된다. 부른 그 순간에 끝난다
  • A function may NOT consume time; it finishes at the instant it's called

한 가지 정밀하게. SV 의 task 에는 function 같은 반환값(return expr;)이 없다. "값을 돌려준다" 는 말은 output 이나 ref 인자로 내보낸다는 뜻으로 읽는다(IEEE 1800 기준 보충).

One precision: an SV task has no function-style return value (return expr;). Read "can return a value" as passing results out through output or ref arguments (a supplement per IEEE 1800).

function bit same(bit [7:0] exp, bit [7:0] act);
  return exp == act;                  // 시간이 안 흐른다// no time passes
endfunction

task wait_ack(virtual dut_if vif);
  @(posedge vif.clk iff vif.ack);     // 여기서 시간이 흐른다// time passes here
endtask

1. check_phase is missing

11쪽과 12쪽은 끝 묶음을 extract, report, final 셋으로 적는다. UVM 1.2 와 IEEE 1800.2 의 common phase 는 extract, check, report, final 넷이다. scoreboard 가 "남은 것 없이 다 맞았나" 를 판정하기 좋은 자리가 check_phase 다. 시험에서 phase 의 순서를 쓰라고 하면 슬라이드 표현이 기준이겠지만, 실제 코드를 읽을 때는 check_phase 가 있다고 알고 있어야 한다.

Slides 11 and 12 list the end group as extract, report, final. In UVM 1.2 and IEEE 1800.2 the common phases end with four: extract, check, report, final. check_phase is the natural place for a scoreboard to decide "did everything match with nothing left over". On a quiz the slides are probably the reference, but when reading real code, know that check_phase exists.

2. run-time phase 는 run_phase "안" 이 아니라 "옆" 이다

2. The run-time phases run beside run_phase, not inside it

Objections: when does it end?

13쪽 제목은 Phase Control 이다. 앞 절의 sub-phase 순서(reset, configure, main, shutdown, 각각 pre_와 post_ 포함)를 적은 뒤 핵심 한 줄이 온다. 각 component 의 phase 는, 자기가 바쁜 동안 phase 가 일찍 끝나 버리지 않도록 objection 을 써야 한다. 쓰는 법은 두 줄이다.

Slide 13 is titled Phase Control. After listing the sub-phase order from the previous section (reset, configure, main, shutdown, each with pre_ and post_), it gives the key line: each component's phase or sub-phase should use an objection to prevent early termination of its phase while it is busy. Two calls do it.

phase.raise_objection(this);   // 손을 든다: "나 아직 일하는 중"// hand up: "I'm still working"
// ... 시간이 흐르는 일 ...// ... work that takes time ...
phase.drop_objection(this);    // 손을 내린다: "나는 끝났다"// hand down: "I'm done"

슬라이드의 예는 monitor 다. monitor 가 transaction 하나를 지켜보는 중이고, 그 transaction 이 끝났다는 event 를 기다려야 한다면, 그동안 objection 을 들고 있어야 run 단계가 그 transaction 을 반쯤 본 채로 끝나지 않는다.

The slide's example is a monitor: if it's watching a transaction and has to wait for an event marking its completion, it should hold an objection meanwhile, so the run doesn't end with that transaction half-observed.

Deciding question: when does the count reach zero? Both come from a single objection mistake. Forget the raise and the count is zero from the start: run_phase ends as soon as it begins, no stimulus goes out, and the log prints only the report, with no errors. Zero errors looking like a pass is what makes it dangerous. Forget the drop (say, raising inside a forever loop that never exits) and the count never reaches zero, so it runs to the timeout. In UVM 1.2 the default is the `UVM_DEFAULT_TIMEOUT macro's 9200s, ending in a UVM_FATAL (a supplement from the UVM 1.2 source). §14 lets you produce both.

(c). Time 0 ns, zero comparisons, and no errors means run_phase ended as soon as it began. (a) A DUT bug would let time pass and the scoreboard would count mismatches. (b) A null vif would crash on a null access the moment the driver writes a pin, or, written §11's way, raise a UVM_FATAL in build_phase. Of the three, only a missing objection leaves no trace. So it pays to add a separate check treating "zero comparisons" as a failure in itself (the same idea as Lab 4 · 07's "zero comparisons isn't a pass; it means nothing was checked").

Components and objects

14쪽은 UVM 의 class 를 두 부류로 가른다. SV testbench 에서는 모든 class 가 object 다(Lecture 12 · 04). UVM 은 그중 특별한 부분집합을 component 라고 부른다. component 는 testbench 의 표준 틀(슬라이드 표현으로 runtime infrastructure)이 되는 부품이고, 모든 UVM testbench 에 공통의 바탕(슬라이드는 이젤과 팔레트 그림을 붙였다)을 준다. 그리고 셋을 더 한다. simulation phase 흐름을 강제하고, 제 목적에 맞는 기본 장치와 virtual method(task, function)를 깔아 두고, 시간 0 에만 만들어지며 시뮬레이션 내내 살아 있다.

Slide 14 splits UVM's classes into two kinds. In an SV testbench every class is an object (Lecture 12 · 04); UVM calls a special subset of them components. Components are the standard template building blocks (in the slide's words, the runtime infrastructure) and give every UVM testbench a common framework (the slide adds an easel-and-palette picture). They also enforce the simulation phase flow, lay down basic mechanics and virtual methods (tasks, functions) for their purpose, and are constructed only at time 0 and stay alive for the whole simulation.

Transaction 과 transactor

Transactions and transactors

16쪽 제목은 Magic of Abstraction Layers 다. 두 층으로 나눈다. 위층은 transaction 이다. 자료형으로 쓴 높은 수준의 서술이라 design 과 하드웨어 신호 interface 의 구현 세부에서 떨어져 있고, field 와 operand 를 묶은 struct 나 class 로 선언한다. 아래층은 interface 신호에 실제로 닿는 일(신호를 assert 하거나 지켜보기)이고, 이건 낮은 층의 component 인 transactor 가 한다. transactor 는 둘이다. driver 는 입력 신호 값을 능동적으로 움직이고, monitor 는 입출력 신호 값을 수동적으로 지켜본다. 이 층 나눔 덕분에 test 를 쓰는 사람은 물리적인 신호에 직접 연결하지 않아도 된다.

Slide 16 is titled Magic of Abstraction Layers, and it splits things into two layers. The upper layer is transactions: high-level descriptions in data types, abstracted away from the implementation details of the design and its hardware signal interfaces, declared as a struct or class bundling fields and operands. The lower layer is actually touching interface signals (asserting or watching them), done by lower-level components called transactors. There are two: the driver actively controls input signal values; the monitor passively watches I/O signal values. The layering insulates the test writer from connecting directly to physical signals.

17쪽이 UVM 의 이름을 붙인다. transaction 은 uvm_sequence_item 으로 선언하고, 이건 특별한 종류의 object 일 뿐이다. sequence 는 sequence item 하나 이상의 모음이다. sequencer 는 정해진 한 가지 sequence_item type 의 sequence 만 풀어낸다. driver 는 자기 sequencer 에게서 sequence_item 요청을 하나씩 받고, 원하면 같은 type 이나 다른 type 의 sequence_item 으로 응답(response)을 돌려줄 수 있다. monitor 는 신호의 움직임을 관찰해 transaction(sequence_item)으로 옮겨 적는다.

Slide 17 attaches UVM's names. Transactions are declared as uvm_sequence_items, just a special type of object. A sequence is a collection of one or more sequence items. A sequencer only unpacks sequences of one given sequence_item type. The driver receives each sequence_item request from its sequencer and may optionally return a response of the same or a different sequence_item type. A monitor observes signal activity and transcribes it into a transaction (sequence_item).

  • The two headings and the dashed line: "transaction level (objects)" on the left is the world of handles; "signal level (pins)" on the right is the world of 0s and 1s moving with the clock. Slide 16's abstraction boundary is that dashed line
  • The uvm_sequence box on the left: the three stacked cards are sequence items (only the front one is labelled). A sequence is "a collection of items" (slide 17)

  • 2. "get_next_item": the driver asks the sequencer for the next item. It matters that the driver asks: the sequencer doesn't push, the driver pulls. The grey dashed arrow below, "response (optional)", is slide 17's optional response

class bus_item extends uvm_sequence_item;
  `uvm_object_utils(bus_item)
  rand bit [15:0] addr;
  rand bit [31:0] data;
  function new(string name = "bus_item");
    super.new(name);
  endfunction
endclass

class bus_driver extends uvm_driver #(bus_item);   // 받을 item type 을 못박는다// fixes the item type it accepts
  `uvm_component_utils(bus_driver)
  virtual dut_if vif;                              // 11절// §11
  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction
  task run_phase(uvm_phase phase);
    forever begin
      seq_item_port.get_next_item(req);    // 당겨 온다. 없으면 기다린다// pull one; wait if none
      @(posedge vif.clk);
      vif.addr <= req.addr;               // 핀을 만지는 곳은 여기뿐// the only place pins are touched
      vif.data <= req.data;
      seq_item_port.item_done();           // 이 item 은 끝났다// this item is done
    end
  endtask
endclass

uvm_driver #(bus_item) 의 괄호가 17쪽의 "한 가지 type" 이다. driver 와 그 sequencer 는 같은 item type 으로 parameterize 해야 연결된다. req 는 uvm_driver 가 미리 선언해 둔 그 type 의 handle 이다. forever 는 끝나지 않지만 괜찮다. run_phase 가 objection 으로 끝나면 UVM 이 이 task 를 끊는다(06절).

The parameter in uvm_driver #(bus_item) is slide 17's "given type": a driver and its sequencer must be parameterized with the same item type to connect. req is a handle of that type that uvm_driver declares for you. The forever never ends, and that's fine: when run_phase ends by objection, UVM kills this task (§06).

TLM: port, export, analysis port

TLM: ports, exports, analysis ports

20쪽은 TLM (Transaction Level Model) 을 이렇게 정의한다. 높은 수준의 transaction object 와 낮은 수준의 transactor component 사이에 오가는 요청과 응답에 abstraction layer 의 규칙을 씌우는 것. transactor component(uvm_sequencer 와 uvm_driver)는 안에 TLM port, export, FIFO 를 구현해 두고 그것으로 uvm_sequence_item 요청(과 원하면 응답)을 옮긴다.

Slide 20 defines TLM (Transaction Level Model) as imposing the abstraction layer's rules on requests and responses between high-level transaction objects and low-level transactor components. The transactor components (uvm_sequencer and uvm_driver) implement TLM ports, exports and FIFOs internally and move uvm_sequence_item requests (and optionally responses) through them.

21쪽이 부품 넷을 정의한다.

Slide 21 defines four pieces.

  • port: transaction 이 바깥에 무언가를 요청하는 통로. port 는 요청만 내고, 반대편에 누가 붙어 있는지 몰라도 된다. 예: driver 가 transaction 을 요청한다
  • Port: the way a transaction requests something external. A port only issues the request and doesn't need to know what's on the other side. Example: the driver requests a transaction
  • analysis port: port 와 비슷하지만 구독자를 여럿 붙일 수 있다. 예: monitor 가 analysis port 로 transaction 을 scoreboard 와 coverage collector 에 동시에 뿌린다(multicast)
  • Analysis port: like a port, but allows multiple subscribers. Example: a monitor multicasts transactions to both the scoreboard and the coverage collector
  • export: port 가 요청한 method 를 구현하는 쪽. 예: port 와 export 가 연결되어 있으면 sequencer 가 driver 의 요청에 응해 transaction 을 내준다
  • Export: the element that implements the method the port requests. Example: the sequencer services the driver's request for a transaction, provided port and export are connected
  • FIFO: transaction 을 넣었다 꺼내는 queue
  • FIFO: a queue to store and retrieve transactions

오른쪽 단의 요점은 한 줄이다. UVM 이 TLM 기능을 전부 속에서 구현해 두었으니, 사용자는 알맞은 component 와 object 를 만들고 connect() 를 불러 port 와 export 를 묶기만 하면 된다.

The right-hand column's point is one line: UVM implements all the TLM machinery under the hood; you just instantiate the right components and objects and call connect() to bind ports to exports.

Lab 4's mailbox is the pre-UVM version of an analysis port. In §06 and §07 of Lab 4 the monitor put transactions into a mailbox and the scoreboard get them (Lecture 12 · 17). And mailbox wiring means handing handles around by hand in the top, while an analysis port is one connect() line in connect_phase. Adding coverage in Lab 4 would have meant a second mailbox and a second put in the monitor; here it's one more connect().

Lecture 2 · 17 의 TLM 은 Transaction Level Modeling, 곧 하드웨어를 RTL 보다 높은 수준에서 모델링하는 것이었다(약어 사전의 TLM 항목도 이 뜻). 20쪽의 TLM 은 Transaction Level Model 이라고 풀지만, 실제로 가리키는 것은 UVM component 끼리 transaction 을 주고받는 연결 API(port, export, FIFO)다. 바탕의 생각("신호 다발 대신 함수 호출로 잇는다")은 같고, 쓰이는 자리가 다르다. UVM 문서에서 "TLM port" 라고 하면 뒤쪽이다.

Deciding question: is it about writing a model, or about connecting? Lecture 2 · 17's TLM was Transaction Level Modeling: modelling hardware above RTL (the glossary's TLM entry has this meaning). Slide 20 expands TLM as Transaction Level Model, but what it actually points at is the connection API (ports, exports, FIFOs) UVM components use to pass transactions. The underlying idea ("connect with function calls, not bundles of wires") is the same; the place it's used differs. In UVM documents, "TLM port" means the latter.

Transactor 가 RTL 신호에 닿는 법

How transactors reach the RTL signals

08절에서 driver 만 핀을 만진다고 했다. 그런데 driver 는 class 의 object 이고 DUT 는 module 이다. object 가 어떻게 module 안의 핀을 잡나. 22~25쪽 네 장이 같은 제목(Abstraction: How Transactors Access the RTL Signals)으로 이 질문 하나를 푼다.

§08 said only the driver touches pins. But the driver is a class object and the DUT is a module. How does an object get hold of pins inside a module? Slides 22 to 25 share one title (Abstraction: How Transactors Access the RTL Signals) and answer this one question.

22쪽: 컴파일된 모델과 실행 중의 세계Slide 22: the compiled model and the run-time world

왼쪽은 elaborate 된 시뮬레이션 모델이다. RTL, interface, TB 파일, uvm_pkg, testbench package, 지원 package 가 모두 들어가 한 번 컴파일된 바이너리 실행 파일이 된다(Lecture 14 · 07 의 simv 가 그것이다). 오른쪽은 runtime environment 다. 프로그램 메모리 안에 있고, 시뮬레이션마다 동적으로 만들어진다. 슬라이드는 그 아래에 "OS RAM" 이라는 별 모양을 붙였다. 그리고 실행 중의 세계에서는 PLI 같은 특별한 장치 없이는 시뮬레이션 모델 안을 직접 들여다볼 수 없다고 쓴다. 예로 든 것이 빨간 글씨 force top.DUT.ack = 1'b1; 와 엄지를 내린 손이다. 슬라이드는 이것을 illegal cross-module reference 라고 부른다.

On the left is the elaborated simulation model: RTL, interfaces, TB files, uvm_pkg, the testbench package and support packages all go in and are compiled once into a binary executable (Lecture 14 · 07's simv). On the right is the runtime environment: it lives in program memory and is created dynamically with each simulation; the slide tags it with a starburst reading "OS RAM". From that run-time world, the slide says, you can't look directly inside the simulation model without special mechanisms (PLIs). Its example is a red force top.DUT.ack = 1'b1; next to a thumbs-down, labelled an illegal cross-module reference.

이 설명은 강의의 그림 언어다. SV 표준으로 말하면 이유가 이렇다(IEEE 1800 기준 보충). package 안의 항목은 계층 참조를 쓸 수 없다. UVM 의 driver 같은 class 는 재사용을 위해 package 안에 정의하므로, 그 안에서 top.DUT.ack 같은 경로를 쓸 수 없다. package 는 어느 testbench 에 끼워질지 모르는 채로 따로 컴파일되기 때문이다. module 안에 정의한 class 라면 계층 경로를 쓸 수 있지만, 그러면 그 class 는 그 testbench 에 묶여 재사용할 수 없다. Lecture 14 · 04 의 XMR 함정("인스턴스 이름에 묶인다")이 class 쪽에서 더 강하게 나타나는 셈이다.

That's the lecture's picture language. In terms of the SV standard, the reason is this (a supplement per IEEE 1800): items inside a package may not use hierarchical references. A UVM class like a driver is defined in a package for reuse, so it can't contain a path like top.DUT.ack; the package is compiled separately without knowing which testbench it will end up in. A class defined inside a module could use hierarchical paths, but then it's tied to that testbench and can't be reused. It's Lecture 14 · 04's XMR trap ("tied to instance names") in a stronger form on the class side.

답 보기Show answer

(1) 이름: set 과 read_by_name 의 문자열이 한 글자라도 다르면("dut_if_ptr" 와 "dutif_ptr") 못 찾는다. 문자열이라 컴파일러가 잡아 주지 않는다. (2) type: resource_db 는 parameterized class 라 #(virtual dut_if) 로 넣고 #(virtual dut_signals) 로 꺼내면 다른 사전을 뒤지는 셈이다. 양쪽 #(...) 의 type 이 같아야 한다. (3) 순서: set 이 run_test() 뒤에 있거나 다른 initial 에 있어서 driver 의 build_phase 보다 늦게 실행되면, 읽는 순간에는 아직 없다. 11절 예제에서 set 을 run_test() 바로 앞에 둔 이유다. 범위("*" 대 특정 경로)가 맞는지도 본다.

(1) The name: if the strings in set and read_by_name differ by one character ("dut_if_ptr" vs "dutif_ptr"), the lookup fails, and being strings, the compiler won't catch it. (2) The type: resource_db is a parameterized class, so storing with #(virtual dut_if) and reading with #(virtual dut_signals) searches a different dictionary; the types in both #(...) must match. (3) The order: if set sits after run_test(), or in a different initial that runs after the driver's build_phase, it isn't there yet when read. That's why §11's example puts set right before run_test(). Also check the scope ("*" vs a specific path).

UVM 은 어디서 왔나

Where UVM came from

29쪽은 backup 의 목차 같은 질문 넷이다. 어떻게 여기까지 왔나, 정말 universal 인가(그런 게 있기는 한가), UVM 의 목적과 진짜 가치는 무엇인가, UVM 배우기. 28쪽이 둘째 질문에 답했고, 30~31쪽이 첫째에 답한다.

Slide 29 poses four questions, a table of contents for the backup: how did we get here; is it really universal (is that even a thing); what's the purpose and real value of UVM; learning UVM. Slide 28 answered the second; slides 30 and 31 answer the first.

30쪽: 설계자가 직접 검증하던 시절에서 벤더 방법론까지Slide 30: from designers verifying their own work to vendor methodologies

"아주 오래전" 에는 RTL 설계자가 자기 검증을 주로 맡았다. testbench 는 DUT 하나를 instance 로 놓는 지루하고 융통성 없는 것이었고, 프로젝트를 넘나드는 재사용을 목표로 하지 않아 사람마다 "예술적 표현" 이 되었다. test 는 대부분 directed 였고, "random" stimulus 와 사후 검사는 Verilog/VHDL 밖의 프로그램이 했다. 판정은 로그와 파형을 눈으로 보는 것이었고, RTL code coverage(line, toggle, condition)를 목표로 삼았다. 슬라이드는 여기에 100% code coverage != functional coverage 를 적는다(Lecture 13 · 14~15). 그 뒤 EDA 벤더가 자기 시뮬레이터에 묶인 독자 방법론과 도구를 팔기 시작했다. 동기는 대체로 같았지만 벤더끼리 전혀 호환되지 않았고, 슬라이드의 말로 EDA 의 목표는 license 를 (더) 팔고 고객을 묶어 두는 것이라 업계 전체가 협력할 동기가 별로 없었다.

"Long, long ago", RTL designers mostly did their own verification. Testbenches that instantiated a DUT were tedious and inflexible, and without any goal of cross-project reuse they became "artistic expression". Tests were mostly directed, with "random" stimulus and post-processing checks done by programs outside Verilog/VHDL. Checking meant eyeballing logs and waveforms, and the target was RTL code coverage (line, toggle, condition). Here the slide notes 100% code coverage != functional coverage (Lecture 13 · 14 to 15). Then EDA vendors began packaging proprietary methodologies and tools tied to their own simulators. The motivations were broadly the same but the solutions were completely incompatible across vendors, and, in the slide's words, the goal in EDA is to (up)sell licenses and lock in customers, so there was little incentive to collaborate across the industry.

직접 해보기: phase 와 objection

Try it: phases and objections

슬라이드는 phase 의 순서(11~12쪽)와 objection 의 쓰임(13쪽)을 말로만 설명한다. 여기서는 05절 계층 그림의 testbench(test, env, agent 안의 driver, monitor, sequencer, 그리고 scoreboard)를 phase 하나씩 밟아 본다. test 와 monitor 가 objection 을 어떻게 다루는지만 골라 두고, run_phase 가 언제 끝나고 scoreboard 가 몇 개를 비교하는지를 본다.

The slides describe the phase order (slides 11 to 12) and the use of objections (slide 13) only in words. Here you step phase by phase through §05's testbench (test, env, an agent with driver, monitor and sequencer, plus a scoreboard). Choose only how the test and the monitor handle objections, and watch when run_phase ends and how many transactions the scoreboard compares.

상황은 고정이다. test 의 sequence 가 item 다섯 개를 보내고, driver 는 item 하나에 20 ns 를 써서 0 ns 부터 100 ns 까지 보낸다. monitor 는 item k 를 (k−1)×20+5 ns 에 보기 시작해서, DUT 의 응답을 받으면 끝낸다. 1~4 번은 응답이 10 ns 뒤라 30, 50, 70, 90 ns 에 끝나고, 5 번만 응답이 늦어 130 ns 에 끝난다. 끝난 transaction 은 analysis port 로 scoreboard 에 간다.

The situation is fixed. The test's sequence sends five items; the driver spends 20 ns on each, from 0 ns to 100 ns. The monitor starts watching item k at (k−1)×20+5 ns and finishes when the DUT responds. Items 1 to 4 get a response 10 ns later, finishing at 30, 50, 70 and 90 ns; only item 5's response is slow, finishing at 130 ns. Each finished transaction goes to the scoreboard through the analysis port.

Things to try.

  • test: sequence 앞뒤로 올리고 내림, monitor: 안 씀. 가장 흔한 예제 모양이다. run 은 100 ns 에 끝나고 scoreboard 는 4/5 를 비교한다. 에러는 0 개다. 5 번은 130 ns 에 끝날 예정이었는데 run 이 먼저 닫혔다. 13쪽의 monitor 예가 막으려는 바로 그 경우다
  • Test: raise and drop around the sequence; monitor: none. The most common example shape. The run ends at 100 ns and the scoreboard compares 4/5, with zero errors. Item 5 was due to finish at 130 ns, but the run closed first: exactly the case slide 13's monitor example guards against
  • 같은 test 에 monitor: transaction 을 보는 동안 올림. 수가 100 ns 에 0 이 되지 않고 130 ns 까지 이어져 5/5 가 된다. 표의 objection 열에서 test 가 내린 뒤에도 1 이 남는 줄을 찾아본다
  • Same test with monitor: raise while watching a transaction. The count doesn't hit zero at 100 ns but holds until 130, giving 5/5. Find the row in the objection column where 1 remains after the test drops

What this tool simplifies. It doesn't run real UVM; it's JavaScript that mimics only the phase order and the objection count. Events at the same time share one row, and there's nothing like a drain time. The build and connect rows show only the "parent first" and "children first" rules and don't fix the order among siblings (say, driver and monitor). The testbench doesn't use the run-time phases (reset to shutdown). check_phase is not on the slides but is in UVM, so it gets a row. The timeout uses UVM 1.2's default, 9200s.

01

Object 와 component

Objects and components

2쪽은 Lecture 16 의 14~15쪽을 두 줄로 줄인다. object 는 시뮬레이션 중에 만들어지고 버려진다(예: transaction). component 는 시뮬레이션 처음에 한 번 만들어지고 버려지지 않으며, phasing 에 참여한다(예: driver, monitor, agent). 그리고 component 아래에 "Active vs. Passive components" 한 줄이 붙어 있다. 구별 자체와 생성자 모양(new(name) 대 new(name, parent))은 Lecture 16 의 07절이 다 했다.

Slide 2 squeezes Lecture 16's slides 14 and 15 into two lines. Objects are created and destroyed during the simulation (e.g. transactions). Components are created once at the start, never destroyed, and take part in phasing (e.g. driver, monitor, agent). Under components sits one more line, "Active vs. Passive components". The distinction itself and the constructor shapes (new(name) vs new(name, parent)) are all in Lecture 16, §07.

강사의 정리에서 새로 볼 것은 "Participate in phasing" 이 정의 안에 들어갔다는 점이다. 수명(언제 만들고 언제 버리나)과 phase 가 같은 말의 두 얼굴이다. 처음에 한 번 만들어져 끝까지 사니까 모두가 같은 순서표를 밟을 수 있고, 계속 생겼다 사라지는 transaction 에게는 밟을 순서표가 없다. "Active vs. Passive" 가 component 쪽에 붙은 것도 같은 이유다. active 와 passive 는 agent 가 무엇을 짓느냐(driver 와 sequencer 를 짓나)의 문제라서 build 가 있는 component 에만 뜻이 있다(Lecture 17 의 07~08절).

What's new in the instructor's version is that "participate in phasing" is part of the definition. Lifetime (when it's built and when it's dropped) and phasing are two faces of the same thing: because a component is built once and lives to the end, everyone can walk the same timetable; a transaction that keeps appearing and vanishing has no timetable to walk. "Active vs. Passive" sits under components for the same reason: active and passive are about what an agent builds (does it build a driver and sequencer?), which only means something for a component that has a build (Lecture 17, §07 to §08).

함정 · "Never destroyed" 는 "언제든 만들 수 있다" 가 아니다Trap · "never destroyed" doesn't mean "create any time"

구별 기준: build 가 끝났나. 슬라이드는 component 가 "처음에" 만들어진다고만 쓴다. UVM 1.2 는 이것을 규칙으로 강제한다. build 단계가 끝난 뒤(예: run_phase 안)에서 component 를 만들려 하면 uvm_component 의 생성자가 UVM_FATAL 로 멈춘다(UVM 1.2 소스 기준 보충). 그래서 "test 중간에 monitor 하나 더 붙이자" 는 안 된다. 필요하면 처음부터 지어 두고 is_active 나 config 로 켜고 끈다. object 는 반대로 언제든 만든다. run_phase 의 forever loop 안에서 transaction 을 매번 새로 만드는 것이 정상이다(Lecture 17 의 06절).

The test: has build finished? The slide only says components are created "in the beginning". UVM 1.2 enforces it: try to create a component after the build phase is over (say inside run_phase) and uvm_component's constructor stops with a UVM_FATAL (supplement, from the UVM 1.2 source). So "let's attach one more monitor mid-test" doesn't work; build it up front and switch it with is_active or config. Objects are the opposite: create them whenever. Building a fresh transaction on every pass of a run_phase forever loop is normal (Lecture 17, §06).

두 나무: super 와 parent

Two trees: super and parent

3쪽은 ChipVerify 의 UVM class 계보 그림 한 장이다. Lecture 16 의 15쪽(그 노트 07절 그림)과 같은 계보인데 세 가지가 더 보인다. 맨 위의 uvm_void, component 쪽의 uvm_scoreboard, uvm_env, uvm_test, object 쪽의 uvm_sequence_base 다. 그리고 이 그림은 4~7쪽의 testbench 계층 그림과 짝이다. 11쪽의 마지막 줄 "Parent (tb hierarchy) vs. Super (class hierarchy)" 가 그 둘에 이름을 붙인다. 그래서 두 나무를 한 그림에 놓았다.

Slide 3 is a single ChipVerify picture of the UVM class lineage. It's the same lineage as Lecture 16's slide 15 (that note's §07 figure), with three extras: uvm_void at the very top, uvm_scoreboard, uvm_env and uvm_test on the component side, and uvm_sequence_base on the object side. It pairs with the testbench hierarchy pictures on slides 4 to 7, and the last line of slide 11, "Parent (tb hierarchy) vs. Super (class hierarchy)", names the two. So here both trees share one picture.

그림 읽기Reading the picture

왼쪽, class 계층. 화살표는 "extends" 이고 자식이 부모 class 를 가리킨다. 속이 빈 삼각형이 UML 의 상속 표시다.

  1. uvm_void: 3쪽 맨 위 칸. 멤버도 method 도 없는 빈 class 로, 모든 UVM class 의 공통 조상 노릇만 한다(UVM 1.2 클래스 레퍼런스). Lecture 16 그림은 uvm_object 에서 시작했으니 한 칸 위가 더 있는 셈이다
  2. uvm_object → uvm_report_object → uvm_component: component 는 object 의 자손이다. 사이의 report_object 가 `uvm_info 같은 메시지 기능을 준다(L16 07절)
  3. uvm_driver #(T) → my_driver: 분홍 화살표 옆 super. my_driver 안에서 super. 라고 쓰면 이 화살표 끝, 곧 uvm_driver #(T) 의 것을 부른다
  4. 옆 갈래 uvm_transaction → uvm_sequence_item → my_txn: object 쪽이다. my_txn 의 점선 테두리가 "만들어졌다 버려진다" 는 표시다. 3쪽 그림은 이 갈래 아래에 uvm_sequence_base 와 uvm_sequence 까지 이어 그린다. sequence 도 object 라는 뜻이다(L16 07절)

3쪽 그림은 uvm_sequencer 를 uvm_component 바로 아래 그렸지만 UVM 1.2 에서는 그 사이에 uvm_sequencer_base, uvm_sequencer_param_base 가 끼어 있다. 그림이 줄인 것이고, 읽는 데 지장은 없다(보충).

오른쪽, testbench 계층. 선은 "안에 담는다" 이고 위 칸이 아래 칸의 parent 다.

  1. uvm_top(class 는 uvm_root): UVM 이 하나 만들어 두는 꼭대기. 21쪽의 uvm_top.print_topology() 가 이것이다(10절)
  2. uvm_test_top: run_test() 가 만든 test 에 붙이는 instance 이름. class 는 my_test 다. 칸마다 굵은 글씨가 instance 이름, 작은 회색이 class 이름이다
  3. env → agt → seqr, drv, mon: 부모가 자기 build_phase 에서 create("drv", this) 처럼 만든다. 둘째 인자 this 가 그대로 parent 가 된다. 분홍 선 옆 parent = agt 가 그 결과다

같은 my_driver 의 위 칸이 두 개다. 왼쪽 나무에서는 uvm_driver #(T)(super), 오른쪽 나무에서는 agt(parent). 하나는 class 의 이름이고 다른 하나는 instance 의 이름이다. 그래서 같은 질문 "driver 위에 뭐가 있나" 에 답이 둘이다.

Left, the class tree. Arrows mean "extends", child pointing at parent class; the hollow triangle is UML's inheritance mark.

  1. uvm_void: the top box on slide 3. An empty class with no members or methods, there only as the common ancestor of every UVM class (UVM 1.2 class reference). Lecture 16's picture started at uvm_object, so this is one level higher
  2. uvm_object → uvm_report_object → uvm_component: components descend from objects; report_object in between supplies messaging such as `uvm_info (L16 §07)
  3. uvm_driver #(T) → my_driver: the pink arrow labelled super. Inside my_driver, super. calls whatever is at the tip of this arrow, i.e. uvm_driver #(T)'s version
  4. Side branch uvm_transaction → uvm_sequence_item → my_txn: the object side. my_txn's dashed border means "created and discarded". Slide 3 continues this branch down to uvm_sequence_base and uvm_sequence: sequences are objects too (L16 §07)

Slide 3 draws uvm_sequencer directly under uvm_component; in UVM 1.2 there are uvm_sequencer_base and uvm_sequencer_param_base in between. The picture simplifies, harmlessly (supplement).

Right, the testbench tree. Lines mean "contains", and the box above is the parent.

  1. uvm_top (class uvm_root): the top UVM builds for you; slide 21's uvm_top.print_topology() is this (§10)
  2. uvm_test_top: the instance name run_test() gives the test it builds; its class is my_test. In each box the bold text is the instance name and the small grey text the class
  3. env → agt → seqr, drv, mon: each parent builds its children in its own build_phase with something like create("drv", this); that second argument this becomes the parent. The pink line's parent = agt is the result

The same my_driver has two "boxes above". In the left tree it's uvm_driver #(T) (super); in the right tree it's agt (parent). One is a class name, the other an instance name, which is why "what's above the driver?" has two answers.

두 단어가 한 줄에 같이 나오는 곳이 있다. 모든 component 의 생성자다.

There's one line where both words appear together: every component's constructor.

class my_driver extends uvm_driver #(my_txn);
  function new(string name, uvm_component parent);  // parent: 나를 담는 instance (agt)// parent: the instance that contains me (agt)
    super.new(name, parent);                       // super: uvm_driver 의 생성자를 부른다// super: calls uvm_driver's constructor
  endfunction
endclass

super.new(name, parent) 는 "class 계층의 부모(super)에게 testbench 계층의 부모(parent)를 넘겨준다" 는 한 줄이다. 받아서 계층 안에 자리를 잡는 일은 uvm_component 의 생성자가 한다. 이름 짓기의 함정은 05절에서 다시 본다.

super.new(name, parent) reads as "hand the testbench parent to the class parent". It's uvm_component's constructor that actually takes it and slots the component into the tree. §05 returns to the naming trap.

The second argument "env.agent" is a path relative to it (the inst_name). Joined with a dot, "uvm_test_top" + "." + "env.agent" = "uvm_test_top.env.agent" becomes the value's scope. The third argument "num_transactions" is the name, the fourth, 100, the value
  2. Row 2, get. Here this is the agent, whose full name is already "uvm_test_top.env.agent". The inst_name is the empty string "", so nothing is added and the scope is the full name as is. It means "look for values meant for me", which is why config_db's get is so often written (this, "", ...)

  4. Row 3, resource_db. No this; the scope argument is just the string "GLOBAL". "GLOBAL" isn't a keyword, only characters. A reader asking for the same characters "GLOBAL" and the same name "timeout" gets 1000 in timeout. As the bottom line says, the call itself carries nothing about who made it or where

What each macro expands to is taken from UVM 1.2's uvm_sequence_defines.svh: `uvm_do calls create, start_item, randomize() and finish_item in that order, and `uvm_send calls only start_item and finish_item, no randomize (supplement).

Option 3 을 sequence 하나로 짜면 이렇다. 이 노트의 예다. req 는 uvm_sequence #(my_txn) 이 미리 선언해 둔 handle 이라 Option 1, 2 에서는 따로 선언하지 않는다.

Here's Option 3 as a whole sequence, this note's example. req is a handle that uvm_sequence #(my_txn) declares for you, which is why Options 1 and 2 don't declare it.

  function new(string name = "my_seq");
    super.new(name);
  endfunction

    repeat (10) begin
      my_txn txn = my_txn::type_id::create("txn");

      if (!txn.randomize())

FIFO 에 쓰기만 하는 sequence 가 있다. 제약은 "FIFO 가 거의 찼으면 쓰기 길이를 줄인다" 이고, 그 "거의 찼나" 는 monitor 가 갱신하는 변수(현재 점유량)를 읽는다. Option 2 와 Option 3 중 무엇으로 짜야 하나.

A sequence only writes to a FIFO. Its constraint is "if the FIFO is nearly full, shorten the write", and "nearly full" reads a variable the monitor keeps updated (current occupancy). Should it use Option 2 or Option 3?

답 보기Show answer

Option 3. Option 2 는 `uvm_send 앞에서 randomize 하므로, 값을 정한 시점과 driver 가 실제로 그 item 을 받는 시점 사이에 시간이 흐를 수 있다. driver 가 앞 item 을 처리하는 동안 FIFO 상태가 바뀌면 이미 정한 값은 낡은 상태에 맞춘 값이다. Option 3 은 start_item 이 돌아온 뒤, 곧 driver 가 다음 item 을 달라고 한 그 순간에 randomize 하므로 가장 최근 상태를 본다. L17 05절 그림의 "set fields" 가 grant 뒤에 있는 이유가 이것이다(이 판단은 슬라이드 밖 보충). 상태와 무관한 순수 random 이면 셋 중 무엇을 써도 결과는 같다.

Option 3. Option 2 randomizes before `uvm_send, so time can pass between choosing the values and the driver actually taking the item; if the FIFO's state changes while the driver works on the previous item, the values were chosen for a stale state. That's why "set fields" comes after the grant in L17 §05's figure (this judgement is a supplement, not from the slides). For pure randomness that ignores state, all three give the same result.

write_before 는 function 이라 시간을 쓸 수 없다. @ 를 넣으면 컴파일이 안 된다(L16 04절의 function 대 task). 18쪽의 "non-blocking" 이 이 뜻이다. 흔한 모양은 기대값을 쌓아 두고, 실제값이 올 때 꺼내 비교하는 것이다. write_before 에서 참조 모델로 기대 출력을 계산해 queue 에 push_back 하고, write_after 에서 pop_front 해서 비교한다. 시간은 아무도 안 기다린다. 출력이 입력 순서대로 나온다면 이것으로 충분하다. Lab 4 의 scoreboard 가 쓰기 transaction 이면 q.push_back, 읽기 transaction 이면 q.pop_front 로 비교한 것(Lab 4 07절)과 같은 생각이다. 시간을 기다리며 처리하고 싶으면 imp 대신 19쪽의 analysis FIFO 둘을 두고 run_phase(task)에서 get 한다.

write_before is a function, so it can't consume time; an @ inside won't compile (L16 §04, function vs task). That's what slide 18's "non-blocking" means. The usual shape is store the expected values, and compare when the actual ones arrive: in write_before, compute the expected output with a reference model and push_back it onto a queue; in write_after, pop_front and compare. Nobody waits on time. If outputs come out in input order, that's enough. It's the same idea as Lab 4's scoreboard, which did q.push_back on write transactions and compared against q.pop_front on reads (Lab 4 §07). If you do want to process with time passing, use two of slide 19's analysis FIFOs instead of imps and get from them in run_phase (a task).

The subscriber. Put the covergroup in a coverage collector that extends uvm_subscriber #(T) and sample it from the received transaction's fields inside write(T t).

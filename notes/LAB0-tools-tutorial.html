이 Lab이 하는 일

What this lab does

설계를 새로 하지 않는다. 이미 있는 설계 하나를 세 도구에 차례로 통과시키면서, 각 도구가 무엇을 받아 무엇을 내놓는지 손으로 익히는 게 전부다.

You design nothing here. You push one existing design through three tools in order, and learn by hand what each one takes in and what it hands back.

Lab 0은 두 부분이다. Part I은 Synopsys 사이트에서 온라인 트레이닝을 듣는 것이고, Part II는 Apporto 서버에 접속해서 제공된 설계로 세 도구를 실제로 돌리는 것이다. 이 페이지는 그 사이를 메운다. 트레이닝이 설명 없이 지나가는 용어들을 먼저 풀어두면 Part II에서 명령을 칠 때 무슨 일이 벌어지는지 보인다.

Lab 0 has two parts. Part I is a set of online trainings on the Synopsys site. Part II is logging into the Apporto server and actually running the three tools on a design that is handed to you. This page fills the gap between them. If the vocabulary the trainings skip past is unpacked first, you can see what is happening when you type the commands in Part II.

이 Lab이 특이한 점 셋. 혼자 한다. 이 과목의 다른 Lab은 2인 1조인데 Lab 0만 개인 과제다. 데모가 없다. 코드를 내지 않는다. 리포트만 낸다. 셋 다 다른 Lab의 습관을 그대로 가져오면 틀리는 지점이다.

Three things make this lab unusual. You do it alone. Every other lab in this course is done in pairs; Lab 0 is individual. There is no demo. You submit no code. Just a report. All three are places where carrying over habits from the other labs will cost you.

01

세 도구는 지도의 어디인가

Where the three tools sit

도구 이름을 외우기 전에 자리부터 잡는다. 셋은 나란히 놓인 대안이 아니라 서로 다른 일을 한다.

Before memorising names, place them. These three are not alternatives sitting side by side; they do different jobs.

Lecture 1의 Design Flow 그림이 이 과목 전체의 지도였다. 이 Lab은 그 지도에서 RTL Design 다음의 두 갈래를 처음으로 손에 쥐는 시간이다. 한 갈래는 검증(맞게 동작하나), 다른 갈래는 합성(gate로 내릴 수 있나)이다.

The design flow diagram in Lecture 1 was the map for this whole course. This lab is where you first get your hands on the two branches that leave RTL Design: one is verification (does it behave), the other is synthesis (can it be taken down to gates).

그림 읽기Reading the picture

왼쪽의 RTL 상자에서 시작해 화살표를 따라간다. 상자 밑의 .v / .sv 는 파일 확장자다. .v 는 Verilog, .sv 는 SystemVerilog 소스다.

  • 위쪽 갈래 ("맞게 도나?"): VCS 가 RTL 을 시뮬레이션한다 (simulate). VCS 와 Verdi 사이 화살표 위의 FSDB 는 둘 사이를 건너가는 파일이다. 시뮬레이션 중 신호 값이 어떻게 바뀌었는지 기록한 파형 파일이고, 08 절에서 다룬다. Verdi 가 그 파일을 열어 디버그한다 (debug). 버그를 찾으면 오른쪽 "버그를 고친다" 로 가고, 분홍 점선이 RTL 로 되돌아가는 길이다 (back to RTL). 고치고 다시 돌리는 이 고리가 검증의 일상이다
  • 아래쪽 갈래 ("gate로 내려가나?"): Design Compiler 가 RTL 을 합성한다 (synthesize). 결과가 netlist 이고, 밑의 gate-level 은 그 netlist 가 AND, OR, flip-flop 같은 실제 gate 를 이어 붙인 목록이라는 뜻이다
  • netlist 다음의 점선 화살표와 P&R, fab 은 이 과목이 다루지 않는 다음 단계다. P&R 은 Place and Route, 칩 위에 gate 를 놓고(place) 선을 잇는(route) 단계다. fab 은 fabrication, 공장에서 실제로 칩을 만드는 것이다. 점선과 회색이 "이 과목 밖" 표시다

색에도 뜻이 있다. 파랑은 설계(RTL), 보라는 도구(VCS, Verdi, Design Compiler), 분홍은 검증 쪽 일(버그 고치기), 갈색은 물리 쪽 산출물(netlist), 회색은 범위 밖이다. 이 노트의 그림은 모두 같은 규칙을 쓴다.

Start at the RTL box on the left and follow the arrows. The .v / .sv under it are file extensions: .v is Verilog source, .sv is SystemVerilog.

  • Upper branch ("does it behave?"): VCS simulates the RTL. The FSDB on the arrow between VCS and Verdi is a file handed from one to the other: a waveform file recording how signal values changed during simulation (section 08). Verdi opens it to debug. When you find a bug you go to "fix the bug", and the pink dashed line is the road back to RTL. Fix, rerun, repeat: that loop is everyday verification
  • Lower branch ("can it become gates?"): Design Compiler synthesises the RTL. The result is a netlist, and gate-level means that netlist is a list of real gates, AND, OR, flip-flops, wired together
  • The dashed arrow after the netlist and P&R, fab are next steps this course doesn't cover. P&R is Place and Route: placing gates on the chip and routing the wires between them. fab is fabrication, the factory actually making the chip. Dashed and grey mark "outside this course"

The colours mean something too. Blue is design (RTL), violet is tools (VCS, Verdi, Design Compiler), pink is verification work (fixing bugs), brown is physical output (the netlist), grey is out of scope. Every picture in these notes uses the same rule.

시뮬레이션과 합성은 같은 RTL을 읽지만 목적이 반대다. 시뮬레이터는 "이 코드가 시간에 따라 어떻게 동작하나"를 묻고, 합성기는 "이 코드를 어떤 하드웨어로 만들 수 있나"를 묻는다. 그래서 시뮬레이션은 되는데 합성은 안 되는 코드가 존재한다. #10 같은 지연이나 $display가 그렇다. 이 간극이 Lecture 3에서 배운 합성 가능한 코드 이야기와 정확히 같은 이야기다.

02

"컴파일"이 한 단어가 아니다

Compile is not one word

여기가 이 Lab에서 처음 막히는 자리다. C를 컴파일하듯 한 방에 되는 게 아니라, 도구가 단계를 나눠 부른다.

This is the first place people get stuck. It is not one shot the way compiling C is; the tool splits it into named stages.

C에서는 gcc main.c 하면 실행 파일이 나온다. VCS도 겉보기에는 비슷한데, 안에서는 세 가지 서로 다른 일이 일어나고 그 셋이 각각 이름을 가지고 있다. 트레이닝이 이 이름들을 설명 없이 던지기 때문에 먼저 못 박아둔다.

In C, gcc main.c gives you an executable. VCS looks similar from outside, but three different things happen inside and each of them has a name. The training throws those names at you without introduction, so pin them down first.

세 단계Three stages

Analysis는 소스 파일을 하나씩 읽어서 문법을 검사하고, 그 결과를 library라는 곳에 넣어둔다. Elaboration은 top module을 정해서 계층 전체를 조립하고 parameter를 실제 값으로 확정한다. Simulation은 그렇게 조립된 것을 시간축 위에서 실제로 돌린다.

Analysis reads the source files one at a time, checks their syntax, and files the result into something called a library. Elaboration picks a top module, assembles the whole hierarchy, and freezes parameters to real values. Simulation takes that assembled thing and actually runs it along a time axis.

여기서 결정적인 사실 하나. Verilog와 SystemVerilog만 쓰면 analysis 단계를 따로 부를 필요가 없다. 그래서 명령이 두 개로 끝난다. VHDL이 섞이면 analysis를 따로 불러야 해서 세 개가 된다. 이게 다음 두 절의 전부다.

One fact decides everything that follows. If you only use Verilog and SystemVerilog, you never have to invoke analysis separately. So the flow is two commands. Mix in VHDL and analysis has to be called on its own, making it three. That is the whole content of the next two sections.

왜 VHDL만 다른가. VHDL은 아래에서 위로 분석해야 하는 언어다. 어떤 entity를 쓰려면 그 entity가 이미 분석되어 library에 들어가 있어야 한다. 그래서 파일 순서가 중요하고, 분석 결과를 담아둘 장소가 필요하다. Verilog에는 그런 제약이 없어서 .v 파일을 아무 순서로나 던져도 된다.

Why VHDL is the odd one out: it is a language that has to be analysed bottom up. To use an entity, that entity must already have been analysed and filed into a library. So file order matters, and you need somewhere to keep the analysed results. Verilog has no such constraint, so you can throw .v files at it in any order.

03

2-step flow

The 2-step flow

순수 Verilog/SystemVerilog일 때. Lab 0에서 실제로 쓰는 게 이쪽이다.

For pure Verilog and SystemVerilog. This is the one you actually use in Lab 0.

그림 읽기Reading the picture
  • 소스 파일 밑의 design.v tb.sv 는 예시 이름이다. 설계 파일 하나와 testbench 파일 하나라는 뜻이고, Lab 0 의 실제 이름은 18_19_Slice.v 와 18_19_Slice_tb.v 다 (아래 명령 참고)
  • 첫 화살표 위의 vcs 가 1 단계 명령이다. 화살표 밑의 elaborate + compile 은 이 한 명령이 하는 두 가지 일이다. elaborate 는 모듈들을 이어 붙여 설계 전체의 구조(어느 모듈이 어느 모듈을 인스턴스로 품는지)를 만드는 것이고, compile 은 그것을 컴퓨터가 실행할 수 있는 프로그램으로 바꾸는 것이다
  • 그 결과가 simv 라는 실행 파일이다. 설계와 testbench 가 한 프로그램 안에 들어 있다
  • 둘째 화살표 위의 ./simv 가 2 단계 명령이다. 앞의 ./ 는 "지금 이 디렉토리에 있는" 이라는 Unix 표기다. 실행하면 시뮬레이션이 돈다 (simulate)
  • 결과는 log (실행 중 찍히는 메시지) 와 FSDB (파형 파일) 다. FSDB 는 testbench 가 dump 를 요청했을 때만 생긴다 (08 절)
  • 오른쪽의 "setup 파일 없음 / library 매핑 없음" 은 다음 04 절의 3-step flow 와 견준 말이다. 2-step 에는 그 준비가 필요 없다
  • The design.v tb.sv under source files are placeholder names for one design file and one testbench file. In Lab 0 they're really 18_19_Slice.v and 18_19_Slice_tb.v (see the commands below)
  • The vcs over the first arrow is the step-one command, and elaborate + compile under it are the two jobs that one command does. Elaborate means stitching the modules together into the structure of the whole design (which module instantiates which); compile means turning that into a program the computer can run
  • The result is an executable called simv, with the design and testbench inside one program
  • The ./simv over the second arrow is the step-two command. The leading ./ is Unix for "the one in this directory". Running it runs the simulation
  • Out come a log (the messages printed while it runs) and an FSDB (the waveform file). The FSDB only appears if the testbench asks for a dump (section 08)
  • "no setup file / no library mapping" on the right is a comparison with the 3-step flow in section 04. The 2-step flow needs none of that
# 1단계: elaborate + compile. simv 라는 실행 파일이 생긴다
%> vcs -sverilog 18_19_Slice.v 18_19_Slice_tb.v

# 2단계: 그 실행 파일을 돌린다
%> ./simv
# step 1: elaborate and compile. this produces an executable named simv
%> vcs -sverilog 18_19_Slice.v 18_19_Slice_tb.v

# step 2: run that executable
%> ./simv

-sverilog는 SystemVerilog 구문을 켜는 스위치다. 안 켜면 logic이나 always_ff 같은 Lecture 3에서 배운 문법이 문법 오류로 잡힌다. Lab 0의 testbench가 SystemVerilog이므로 이 스위치가 필요하다.

-sverilog is the switch that turns SystemVerilog constructs on. Without it, the syntax you learned in Lecture 3 such as logic or always_ff comes back as a syntax error. The Lab 0 testbench is SystemVerilog, so you need this switch.

Lab 0에서는 이 명령을 직접 치지 않는다. sim/Makefile에 타겟으로 들어 있다. 그래도 Makefile을 열어서 어느 타겟이 어느 명령을 부르는지 읽어라. Lab 0 문서가 명시적으로 시키는 일이기도 하고, Lab 1부터는 Makefile을 직접 고쳐야 한다.

You will not type this command yourself in Lab 0; it is sitting in sim/Makefile as a target. Open the Makefile anyway and read which target invokes which command. Lab 0 explicitly tells you to, and from Lab 1 on you will be editing those Makefiles yourself.

The 3-step flow and logical libraries

  2. elaborate: 가운데 logical library 는 분석 결과가 쌓이는 곳의 이름이다 (05 절 예시의 WORK 같은). 다음 화살표의 vcs 가 그 조각들을 top 모듈부터 이어 붙여 simv 실행 파일을 만든다. 2-step 에서는 vcs 가 소스 읽기부터 한꺼번에 했지만 여기서는 이 단계만 맡는다

아래 주황 점선 상자 synopsys_sim.setup 에서 위로 올라가는 점선 화살표는 "이 파일이 logical library 이름이 실제로 어느 디렉토리인지 정한다" 는 뜻이다. 상자 안의 "logical 이름 → 실제 디렉토리" 가 그 말이다. 05 절의 WORK : ./work 한 줄이 예다. WORK 라는 이름이 지금 디렉토리 밑의 work 폴더를 가리킨다는 뜻이다.

The numbers 1, 2, 3 are the stages.

  1. analysis: the three boxes on the left are source languages, and each has its own analysis command. vlogan is for Verilog / SystemVerilog, vhdlan for VHDL, syscan for SystemC. All three end in "an", so tie them to the "an" in analysis and they stick. Analysis checks the source's syntax and turns it into intermediate results; all three arrows land in the one box in the middle
  2. elaborate: the logical library in the middle is the name of the place analysed results pile up in (like WORK in the section 05 example). The vcs on the next arrow stitches those pieces together from the top module down and builds the simv executable. In the 2-step flow vcs also read the source; here it only does this stage
  3. simulate: run simv and get results, same as the 2-step flow

The dashed arrow rising from the amber dashed box synopsys_sim.setup means "this file decides which real directory a logical library name points at", which is what "logical name to real directory" inside the box says. The line WORK : ./work from section 05 is an example: the name WORK points at the work folder under the current directory.

synopsys_sim.setup

3-step flow가 필요로 하는 설정 파일. 두 줄만 읽을 줄 알면 된다.

The configuration file the 3-step flow needs. You only have to be able to read two kinds of line.

이 파일이 하는 일은 딱 두 가지다. logical 이름을 실제 디렉토리에 붙이는 것과 도구 환경 변수를 켜는 것. 문법도 단순하다. --로 시작하면 주석이고, 이름 : 값이 한 줄이다.

The file does exactly two things: it ties logical names to real directories, and it sets tool environment variables. The syntax is just as small. A line starting with -- is a comment; everything else is name : value.

-- 이 파일에서 주석은 대시 두 개로 시작한다. # 이 아니다
WORK   : ./work
TB_LIB : /home/yk/proj/libs/tb_lib

-- 콜론 왼쪽이 logical 이름, 오른쪽이 진짜 Unix 경로다
-- 같은 문법으로 도구 변수도 켠다
TIMEBASE : ns
-- comments in this file start with two dashes, not with #
WORK   : ./work
TB_LIB : /home/yk/proj/libs/tb_lib

-- left of the colon is the logical name, right of it is the real Unix path
-- tool variables are set with the same syntax
TIMEBASE : ns

읽는 요령 하나. 콜론 왼쪽은 설계가 부르는 이름, 오른쪽은 파일 시스템의 사실. 설계 코드는 TB_LIB이라고만 부르고 그게 디스크 어디인지는 모른다. 그 연결을 이 파일이 혼자 알고 있다. 그래서 이 파일 한 줄만 고치면 설계를 안 건드리고도 다른 라이브러리를 물릴 수 있다.

One reading trick: left of the colon is what the design calls it, right of it is a fact about the filesystem. The design code only ever says TB_LIB and has no idea where on disk that is. This file is the only thing that knows. That is why editing one line here swaps in a different library without touching the design at all.

환경 설정 쪽도 짚어둔다. VCS를 쓰려면 VCS_HOME이 설치 경로를 가리켜야 하고 PATH에 $VCS_HOME/bin이 들어가야 한다. 라이선스는 SNPSLMD_LICENSE_FILE이나 LM_LICENSE_FILE에 포트@호스트 형태로 준다. 제대로 잡혔는지는 show_setup으로 확인하고, library 매핑만 보려면 show_setup -lib을 쓴다.

A word on environment setup too. To use VCS, VCS_HOME has to point at the install directory and $VCS_HOME/bin has to be on PATH. Licences come from SNPSLMD_LICENSE_FILE or LM_LICENSE_FILE in port@host form. To check that any of it took, run show_setup; to see just the library mappings, show_setup -lib.

Lab 0에서 진짜 물리는 지점Where this actually bites in Lab 0

Lab 0에서는 이 설정을 직접 쓰지 않는다. env.cshrc가 대신 해준다. 그런데 그 스크립트는 tcsh용이고 bash에서는 안 돈다. Lab 0 문서가 명시적으로 경고하는 지점이다. bash에서 source env.cshrc를 하면 문법 오류가 쏟아지거나, 더 나쁘게는 조용히 절반만 먹고 나중에 "명령을 찾을 수 없음"으로 나타난다. 먼저 tcsh로 들어간 다음 source 한다.

You do not write this setup yourself in Lab 0; env.cshrc does it for you. But that script is for tcsh and will not run under bash. Lab 0 warns about this explicitly. Sourcing it from bash either throws a pile of syntax errors or, worse, silently takes half and shows up later as command not found. Get into tcsh first, then source it.

simv: 한 번 굽고 여러 번 돌린다

simv: compile once, run many

elaboration이 왜 따로 있는지에 대한 실질적인 답.

The practical answer to why elaboration is a separate stage at all.

elaboration의 결과물인 simv는 보통의 실행 파일이다. 한 번 만들어두면 옵션만 바꿔서 몇 번이고 다시 돌릴 수 있다. 시드를 바꿔 랜덤 테스트를 100번 돌리는 상황을 생각하면, 매번 다시 컴파일하는 것과 실행 파일을 재사용하는 것의 차이가 시간 단위로 벌어진다. 트레이닝이 이걸 compile once, run multiple times라고 부른다.

simv, the product of elaboration, is an ordinary executable. Build it once and you can rerun it as often as you like with different options. Picture running a random test a hundred times with different seeds: the gap between recompiling every time and reusing the executable is measured in hours. The training calls this compile once, run multiple times.

runtime 옵션 중 상당수는 compile time에 짝이 켜져 있어야 동작한다. 예를 들어 coverage를 simv에서 요청해도, vcs 단계에서 coverage 계측을 넣어두지 않았으면 아무것도 안 나온다. 그런데 에러가 안 난다. 그냥 결과가 비어 있다. 초보가 여기서 몇 시간을 태운다. "옵션을 줬는데 아무 일도 안 일어난다"면 제일 먼저 의심할 것은 오타가 아니라 compile 단계에 짝이 빠졌는지다.

Many runtime options only work if their counterpart was enabled at compile time. Ask simv for coverage, and if the vcs step never instrumented for coverage, you get nothing. And it does not error. The result is simply empty. This is where beginners burn an afternoon. If an option seems to do nothing, the first suspect is not a typo, it is a missing counterpart at compile time.

Verdi가 푸는 문제

The problem Verdi solves

도구를 배우기 전에 그 도구가 없던 시절의 고통을 먼저 안다. 그래야 옵션 이름이 외워진다.

Learn the pain that existed before the tool, and its option names stop being arbitrary.

예전에는 시뮬레이터와 디버거가 서로 다른 도구였다. 그래서 같은 설계를 두 번 컴파일해야 했다. 한 번은 시뮬레이션용, 한 번은 디버그 데이터베이스용. 문제가 셋 생긴다. 시간이 두 배로 든다. 시뮬레이션 스크립트의 옵션을 디버거 쪽으로 옮기는 게 쉽지 않다. 그리고 최악은, 두 도구가 소스를 다르게 해석해서 데이터가 어긋나는 경우가 생긴다는 것이다. 표준을 살짝 벗어난 코드에서 특히 그렇다.

The simulator and the debugger used to be different tools. So you compiled the same design twice: once for simulation, once to build a debug database. Three problems follow. It takes twice as long. Porting the options from your simulation script to the debugger side is not easy. And worst of all, the two tools can read the source differently and the data ends up inconsistent, especially for code that strays slightly outside the standard.

그래서 나온 게 Unified Front-End다. 한 번만 컴파일하고, 그 결과를 시뮬레이터와 디버거가 같이 쓴다. 사용자 입장에서는 -kdb 옵션 하나를 붙이는 것으로 끝난다. 이 한 줄이 위 세 문제를 다 없앤다.

The answer is the Unified Front-End: compile once, and let the simulator and the debugger share the result. From where you sit it comes down to adding one option, -kdb. That single flag removes all three problems above.

# 2-step flow: vcs 에 붙이면 끝
%> vcs -sverilog -kdb -debug_access+all design.v tb.sv

# 3-step flow: 분석기마다 다 붙여야 한다. 하나라도 빠지면 그 언어만 디버그가 안 된다
%> vlogan -kdb ...
%> vhdlan -kdb ...
%> vcs -kdb top
# 2-step flow: put it on vcs and you are done
%> vcs -sverilog -kdb -debug_access+all design.v tb.sv

# 3-step flow: every analyser needs it. miss one and that language alone loses debug
%> vlogan -kdb ...
%> vhdlan -kdb ...
%> vcs -kdb top
충돌하는 옛날 옵션The old options that clash

스크립트에 -P, -debug, -debug_all, -debug_pp가 남아 있으면 빼야 한다. -debug_access와 충돌하고, 게다가 옛날 옵션이 우선권을 가져간다. 그래서 새 옵션을 붙여놓고도 옛날 동작을 하는 상태가 된다. 인터넷에서 퍼온 스크립트를 쓸 때 정확히 이 함정에 빠진다. 오래된 블로그일수록 저 옵션들이 들어 있다.

If -P, -debug, -debug_all or -debug_pp are still in your script, take them out. They clash with -debug_access, and the old ones win. So you end up with the new flag present and the old behaviour running. This is exactly what happens when you paste a script off the internet, and the older the blog post, the more likely those flags are in it.

08

KDB vs. FSDB

Verdi를 이해하는 데 이 구분 하나면 절반은 끝난다. 이름이 비슷해서 계속 섞인다.

Half of understanding Verdi is this one distinction. The names look alike and people keep mixing them.

그림 읽기Reading the picture
  • KDB 는 Knowledge Database 다. 설계의 구조를 담는다. 어느 모듈이 어느 신호로 이어지는지, 소스 몇 번째 줄에 무엇이 있는지. "정적" 은 시간에 따라 변하지 않는다는 뜻이다. 오른쪽 위의 vcs -kdb 가 만드는 방법이다. compile 할 때 -kdb 옵션을 붙인다
  • FSDB 는 Fast Signal Database 다. 시뮬레이션 동안 신호 값이 언제 무엇으로 바뀌었는지의 기록, 곧 파형이다. "동적" 은 시간에 따라 변하는 값이라는 뜻이다. 오른쪽 아래의 simv + dump 는 simv 를 돌리면서 dump(값을 파일로 쏟아내기)를 요청해야 생긴다는 뜻이다. Lab 0 에서 생기는 novas.fsdb 가 이 파일이다
  • 두 화살표가 Verdi 로 모인다. Verdi 가 둘을 겹쳐 읽어야 오른쪽 상자처럼 "파형의 이 지점이 소스의 이 줄" 이라고 이어줄 수 있다

이름이 헷갈리면 가운데 글자로 기억한다. Knowledge 는 아는 것(설계가 어떻게 생겼나), Signal 은 신호 값(무슨 일이 일어났나).

  • KDB is the Knowledge Database. It holds the design's structure: which module connects to which through which signal, what's on which source line. "Static" means it doesn't change over time. The vcs -kdb at top right is how you get one: add -kdb when you compile
  • FSDB is the Fast Signal Database: a record of when each signal changed and to what during simulation, in other words the waveform. "Dynamic" means values that change over time. The simv + dump at bottom right means it only appears if you run simv and ask for a dump (pouring values out into a file). The novas.fsdb you get in Lab 0 is this file
  • Both arrows meet at Verdi. Only by reading the two together can it tell you, as the box on the right says, "this point on the waveform is this line of source"

If the names blur, go by the letter that differs: Knowledge is what's known (what the design looks like), Signal is signal values (what happened).

가장 흔한 초보 증상: 옵션을 다 줬는데 .fsdb 파일이 안 생긴다. 이유는 거의 항상 하나다. dump를 요청한 코드가 없다. -debug_access는 "덤프할 수 있게 해줘"이지 "덤프해"가 아니다. 실제 덤프는 testbench 안의 $fsdbDumpvars 같은 호출이 하거나, UCLI 프롬프트에서 덤프 명령을 쳐서 한다. 권한과 실행은 다른 것이다.

The most common beginner symptom: every flag is in place and no .fsdb file appears. The reason is almost always the same. Nothing asked for a dump. -debug_access means make dumping possible, not do the dumping. The actual dump comes from a call such as $fsdbDumpvars in the testbench, or from typing a dump command at the UCLI prompt. Permission and action are different things.

두 가지 디버그 모드

Two debug modes

시뮬레이션과 같이 살아 있을 것인가, 끝난 뒤 기록을 볼 것인가. 이 선택이 옵션을 가른다.

Do you live alongside the simulation, or read the record after it finished? That choice decides your options.

Interactive · 살아 있는 채로Interactive, while it lives

시뮬레이터와 Verdi가 같이 떠 있다. 세워놓고 값을 보고, 다시 진행시키고, 다시 세운다. simv에 -verdi를 붙여서 띄운다.

The simulator and Verdi are up at the same time. Halt, inspect, step on, halt again. You get this by adding -verdi to the simv run.

버그를 재현하는 데 오래 걸릴 때 유리하다. 한 번 세워놓고 계속 캐물을 수 있다.

Good when the bug takes a long time to reach: get there once, then keep asking questions.

Post-process · 끝난 뒤에Post-process, after the fact

시뮬레이션은 이미 끝났고 FSDB만 남았다. 그걸 -ssf로 연다. 이때 그 FSDB를 만든 KDB가 자동으로 같이 로드된다.

The simulation is over and only the FSDB remains. You open it with -ssf, and the KDB that produced it loads automatically alongside.

회귀 테스트를 밤새 돌리고 아침에 실패한 것만 열어보는 방식. 실무에서 훨씬 흔하다.

Run regressions overnight, open only the failures in the morning. Far more common in practice.

# interactive: 시뮬레이터를 띄우면서 Verdi 를 같이 연다
%> ./simv -verdi

# post-process: 남아 있는 FSDB 를 연다. KDB 는 알아서 따라온다
%> verdi -ssf novas.fsdb
# interactive: bring the simulator up with Verdi attached
%> ./simv -verdi

# post-process: open the FSDB that was left behind. the KDB follows on its own

Design Compiler와 합성

Design Compiler and synthesis

RTL을 gate로 내리는 도구. VCS와 성격이 완전히 달라서, 옵션이 아니라 변수와 스크립트로 몬다.

The tool that takes RTL down to gates. It behaves nothing like VCS: you steer it with variables and scripts, not options.

합성은 RTL을 gate-level netlist로 번역하는 일이다. 번역이라고 부르는 이유는 의미를 보존하기 때문이고, 컴파일과 다른 이유는 목표 하드웨어의 부품 목록을 보고 고른다는 점이다. 그 부품 목록이 technology library다. 같은 RTL이라도 어느 library를 주느냐에 따라 전혀 다른 netlist가 나온다.

Synthesis is translating RTL into a gate-level netlist. It is a translation because meaning is preserved; it differs from compilation because it picks parts from a catalogue of what the target process actually offers. That catalogue is the technology library. The same RTL against a different library produces a completely different netlist.

Timing report 읽는 법

Reading a timing report

합성이 끝나면 리포트가 나온다. report_timing의 기본 출력은 네 구역으로 되어 있고, 이 구조만 알면 어디를 봐야 할지가 정해진다.

Synthesis produces reports. The default report_timing output has four sections, and knowing the structure tells you where to look.

그림 읽기Reading the picture
  • 번호 1 부터 4 는 리포트에 위에서 아래로 나오는 순서다
  • 1. Path Information: 어느 경로를 쟀는지(출발점과 도착점), 어느 library 의 값을 썼는지. 계산 재료가 아니라 이름표다
  • 2. Path Delay 밑의 data arrival time: 신호가 출발점에서 도착점까지 실제로 도착하는 시각. 지나는 gate 와 선의 지연을 차례로 더한 값이다
  • 3. Path Required 밑의 data required time: 신호가 늦어도 이때까지는 도착해야 하는 시각. 대개 clock 주기에서 받는 flip-flop 이 요구하는 준비 시간(setup)을 뺀 값이다
  • 두 화살표가 4. Summary 로 모여 required - arrival = slack 을 계산한다
  • 오른쪽: slack 이 + 면 (MET), 조건을 만족했다. - 면 (VIOLATED), 위반이다

숫자로 한 번. required 가 2.00 ns, arrival 이 1.63 ns 라면 slack = 2.00 − 1.63 = +0.37 ns, (MET) 이다. 신호가 0.37 ns 여유를 두고 도착했다. arrival 이 2.10 ns 라면 2.00 − 2.10 = −0.10 ns, (VIOLATED) 다. 0.10 ns 늦었다. 이 숫자들은 설명을 위해 지어낸 예다.

  • The numbers 1 to 4 are the order the sections appear in the report, top to bottom
  • 1. Path Information: which path was measured (start and end point) and which library's values were used. It's a label, not an ingredient
  • data arrival time under 2. Path Delay: the time the signal actually arrives at the end point, found by adding up the delays of every gate and wire along the way
  • data required time under 3. Path Required: the time the signal must arrive by at the latest. Usually that's the clock period minus the setup time the receiving flip-flop needs
  • Both arrows meet in 4. Summary, which computes required - arrival = slack
  • On the right: slack with a + is (MET), the requirement is satisfied; with a - it's (VIOLATED)

Once with numbers. Required 2.00 ns and arrival 1.63 ns give slack = 2.00 − 1.63 = +0.37 ns, (MET): the signal made it with 0.37 ns to spare. Arrival 2.10 ns gives 2.00 − 2.10 = −0.10 ns, (VIOLATED): 0.10 ns late. These numbers are made up for illustration.

slack이라는 단어가 여기서 처음 나온다. 여유 시간이다. 신호가 도착해야 하는 시각(required)에서 실제로 도착한 시각(arrival)을 뺀 값이고, 양수면 (MET), 음수면 (VIOLATED)가 붙는다. 이 수업 후반의 타이밍 이야기가 전부 이 한 줄에서 출발한다.

This is where the word slack first appears. It is spare time: the time the signal was required by minus the time it actually arrived, marked (MET) when positive and (VIOLATED) when negative. Every timing discussion later in this course starts from that single line.

report_timing의 기본 동작을 알아둘 것. path group마다 가장 나쁜 경로 하나만 보여주고, setup(최대 지연)만 본다. hold도 area도 DRC도 안 나온다. 더 보려면 -max_paths로 경로 수를 늘리거나 -nworst로 endpoint당 개수를 늘린다. 지연이 cell 출력 핀 기준으로만 찍히는 게 답답하면 -input_pins를 붙인다. 그러면 net delay가 보인다.

Know what report_timing does by default: it shows only the single worst path per path group and looks at setup, the maximum delay, only. No hold, no area, no DRC. To see more, raise the path count with -max_paths or the per-endpoint count with -nworst. If it frustrates you that delays are reported only to cell output pins, add -input_pins and the net delays appear.

$finish가 불렸다는 건 testbench가 중간에 죽은 게 아니라 자기가 끝났다고 선언했다는 뜻이다. 시뮬레이션이 끝까지 갔다는 증거가 이거다. 에러로 죽었으면 $finish 없이 다른 메시지가 뜬다.

$finish being called means the testbench declared itself done rather than dying partway. That is your proof the simulation ran to completion. If it had crashed you would see something else and no $finish.

그리고 novas.fsdb가 생겼다. 이게 파형 파일이다. Task 2에서 이걸 열 거다. ls -A 다시 쳐보면 novas.fsdb, novas_dump.log, ucli.key 세 개가 더 늘어 있을 거다. compile 단계 네 개 / sim 단계 세 개, 이렇게 나눠서 리포트에 적으면 된다.

And novas.fsdb showed up. That is the waveform file, and Task 2 opens it. Run ls -A once more and you have three new entries: novas.fsdb, novas_dump.log and ucli.key. Four from the compile step, three from the sim step. That is your written list.

4. Task 2 · Verdi로 파형 보기

4. Task 2 · Waveforms in Verdi

자, 아까 compile이랑 compile_verdi가 따로 있다고 했던 거 기억나나. 여기서 그게 걸린다.

Remember how there was both a compile and a compile_verdi? Here is where that matters.

방금 만든 걸로 Verdi를 열면 파형은 보이는데 설계 계층이 안 보인다. Verdi가 설계 구조를 읽으려면 -kdb라는 옵션으로 만든 knowledge database가 필요한데, 그게 compile_verdi에만 붙어 있기 때문이다. 그냥 다시 컴파일해야 한다.

Open Verdi against what you just built and the waveform shows up but the design hierarchy does not. For Verdi to read the structure it needs a knowledge database, built by the -kdb switch, and that switch only lives in compile_verdi. So you recompile.

make clean
make compile_verdi
make sim
make waves_verdi
make clean
make compile_verdi
make sim
make waves_verdi

compile_verdi 로그 끝에 이 줄이 뜨면 제대로 된 거다. 일반 compile에는 안 나오는 줄이다.

If the tail of the compile_verdi log shows this line, it worked. A plain compile never prints it.

Verdi KDB elaboration done and the database successfully generated

그리고 make waves_verdi를 치면 Verdi 창이 뜬다. 좀 걸리니까 기다려라.

Then make waves_verdi opens Verdi. Give it a moment.

창이 뜨면 왼쪽에 Hierarchy 패널이 있다. 거기 tb_dsp_slice 밑에 slice_me가 있고, 그 밑에 pre_adder, multiplier, adder_subtractor 같은 게 주르륵 나온다. 이게 첫 번째 제출용 스크린샷이다. 삼각형 눌러서 다 펼쳐놓고 찍어라.

When it opens there is a Hierarchy pane on the left. Under tb_dsp_slice you will find slice_me, and under that a row of things like pre_adder, multiplier, adder_subtractor. That is your first screenshot. Expand the triangles so it is all visible, then capture it.

그 다음이 파형인데, 여기가 요령이 좀 필요하다. 제출물이 "설계 신호와 testbench 신호가 둘 다" 있어야 한다고 못박아놨다. 한쪽만 찍으면 미달이다.

The waveform is next, and this one has a knack to it. The deliverable explicitly wants signals from the design and from the testbench. One side only does not count.

신호를 하나씩 골라 넣을 필요 없다. Hierarchy에서 스코프를 우클릭 → Add to Waveform → Add to Wave2 하면 그 스코프 신호가 통째로 들어간다. testbench 쪽(tb_dsp_slice)에 한 번, DUT 쪽(slice_me)에 한 번 해라. 그러면 요구사항이 자동으로 충족된다.

You do not pick signals one at a time. Right-click a scope in the Hierarchy pane → Add to Waveform → Add to Wave2 and the whole scope goes in. Do it once on the testbench (tb_dsp_slice) and once on the DUT (slice_me) and the requirement takes care of itself.

다 넣고 나면 화면이 좀 답답할 거다. 두 가지만 손보면 된다.

It will look cramped once everything is in. Two fixes.

  • F를 눌러라. Zoom All이다. 처음엔 앞쪽 100ns 정도만 확대돼 있어서 신호가 거의 안 변하는 것처럼 보이는데, 전체를 맞춰놓으면 값이 계속 바뀌는 게 보인다. 채점자 입장에서도 "제대로 돌았구나"가 훨씬 잘 보인다.
  • Press F for Zoom All. By default you are zoomed into the first 100 ns or so, where the signals look nearly static. Fit the whole run and you can see values changing throughout. It reads much more convincingly as "this actually ran".
  • 이름 칸 경계를 오른쪽으로 끌어라. 기본값이 좁아서 chainout[63:0] 같은 긴 이름이 잘린다. 잘린 채로 내면 무슨 신호인지 알아보기 힘들다
  • Drag the name column wider. The default is narrow and clips longer names like chainout[63:0]. Submit it clipped and nobody can tell which signal is which

5. Task 3 · Synthesis in DC

마지막이다. 여태까지는 설계가 맞게 도는지를 봤다면, 합성은 그걸 진짜 게이트로 바꿨을 때 얼마나 크고, 얼마나 먹고, 얼마나 빠른지를 본다.

Last one. Up to now we checked whether the design behaves. Synthesis asks how big, how hungry and how fast it gets once it is turned into real gates.

돌리기 전에 compile_dc.tcl을 한 번 열어봐라. 리포트 질문 1번과 2번 답이 그냥 적혀 있다.

Before running it, open compile_dc.tcl. The answers to report questions 1 and 2 are literally written in there.

cd ~/lab0/work/synth
cat -n compile_dc.tcl
cd ~/lab0/work/synth
cat -n compile_dc.tcl

target_library랑 link_library가 나오는 줄을 찾아봐라. 어떤 std cell library를 쓰는지, 그걸 어떤 명령으로 넘기는지가 거기 있다. 참고로 이 둘은 역할이 다르다. target_library는 "이 셀들로 만들어라"는 거고 link_library는 "참조를 풀 때 여기서 찾아라"는 거다. 같은 값을 넣는 경우가 많아서 헷갈리는데 의미는 다르다.

Find the lines with target_library and link_library. Which std cell library is used and what command hands it over are both right there. Worth knowing that the two differ: target_library says "build out of these cells", link_library says "resolve references against these". They are often set to the same thing, which is why people conflate them, but they mean different things.

그리고 돌린다.

Then run it.

make synth
make synth

10초쯤 걸리고, 끝나면 Thank you...라고 인사하고 나간다. 리포트 파일 네 개가 생긴다: timing.rep, cell.rep, power.rep, area.rep.

Takes about ten seconds, then it says Thank you... and exits. Four report files appear: timing.rep, cell.rep, power.rep and area.rep.

로그에 Error: unknown command 'set_ultra_optimization'이 두 번 뜰 거다. 놀라지 마라. 무시해도 된다. 이건 DC Ultra 라이선스가 있어야 쓰는 명령인데 우리 라이선스엔 없어서 "그런 명령 모른다"고 한 것뿐이다. 스크립트는 그냥 다음 줄로 넘어갔고 합성은 끝까지 갔다. "에러가 있다"와 "실패했다"는 다르다. 리포트 네 개가 다 생겼으면 성공한 거다.

The log will print Error: unknown command 'set_ultra_optimization' twice. Do not panic. Ignore it. That command needs a DC Ultra licence, which this install does not have, so DC simply does not recognise it. The script carried on to the next line and synthesis finished. "There are errors" and "it failed" are not the same thing. If all four reports exist, you are fine.

이제 리포트를 열어서 필요한 숫자를 뽑는다. 제출물이 power, area, timing 세 개를 따로 요구한다.

Now open the reports and pull the numbers. The deliverable wants power, area and timing as three separate things.

tail -20 area.rep
tail -25 power.rep
tail -20 timing.rep
tail -20 area.rep
tail -25 power.rep
tail -20 timing.rep

timing이 제일 중요한데, 맨 아래 slack 줄만 보면 된다.

Timing is the one that matters most, and you only really need the slack line at the very bottom.

slack (MET)                                   0.11

(MET)이면 요구한 클럭에서 이 설계가 돈다는 뜻이고 (VIOLATED)면 못 돈다는 뜻이다. 위에 있는 복잡한 표들은 전부 그 한 줄이 왜 그 값인지를 설명하는 재료다. 처음엔 아래부터 보는 게 맞다.

(MET) means the design runs at the clock you asked for; (VIOLATED) means it does not. All the dense tables above it are just the workings behind that one number. Reading bottom-up is the right instinct here.

power 쪽도 하나 짚고 가자. 보면 clock network가 전력의 대부분을 먹는다. 이상해 보이는데 당연한 거다. 클럭은 모든 플립플롭에 매 사이클 토글하면서 들어가니까 설계에서 제일 바쁜 신호다. 실무에서 clock gating을 그렇게 열심히 하는 이유가 이거다. 이걸 알아두면 나중에 "전력이 왜 이렇게 높지?" 할 때 클럭부터 의심하게 된다.

One note on power: the clock network eats most of it. Looks odd, makes sense. The clock is the busiest net in the design, toggling into every single flip-flop every cycle. This is exactly why clock gating gets so much attention in industry. Worth remembering, so that next time power looks high you look at the clock first.

5번 힌트를 하나 주면, 조합 논리인지 순차 논리인지부터 갈라라. assign이면 클럭이 없으니 게이트만 나오고, always @(posedge clk)면 플립플롭이 나온다. 그리고 if (clr)가 always 블록 안에 있는지 sensitivity list에 있는지가 동기 리셋이냐 비동기 리셋이냐를 가른다. 이거 11절에서 다룬 내용이다.

A hint for 5: start by splitting combinational from sequential. An assign has no clock, so you get gates only; an always @(posedge clk) gives you flip-flops. And whether if (clr) sits inside the always block or in the sensitivity list is what makes the reset synchronous or asynchronous. That is the section 11 material.

함정

Traps

앞 절에 흩어져 있던 것 중 실제로 시간을 잡아먹는 것만 모았다.

The ones scattered through the sections above that actually cost you hours, gathered in one place.

1 · 조용한 실패가 기본이다1 · Silent failure is the default

이 도구들은 옵션을 잘못 붙여도 대개 에러를 안 낸다. coverage를 요청했는데 리포트가 비어 있고, 디버그를 켰는데 파형이 없고, FSDB를 열었는데 신호가 안 보인다. 소프트웨어 컴파일러에 익숙한 사람이 제일 크게 데는 지점이다. "에러가 없다"를 "잘 됐다"로 읽지 마라. 결과물이 실제로 생겼는지를 눈으로 확인하는 습관이 이 판의 기본기다.

These tools mostly do not error when an option is on the wrong stage. You asked for coverage and the report is empty; you enabled debug and there is no waveform; you opened the FSDB and no signals appear. This is what burns people who come from software compilers. Do not read "no errors" as "it worked." Checking that the artefact actually exists is the basic hygiene of this trade.

2 · 권한과 실행은 다르다2 · Permission is not action

-debug_access는 덤프할 수 있게 해주는 옵션이지 덤프하는 옵션이 아니다. 실제 덤프는 설계 안의 호출이나 UCLI 명령이 한다. 같은 모양의 함정이 coverage에도 있다. 계측을 켜는 것과 수집을 요청하는 것이 다른 단계에 있다.

-debug_access is the option that makes dumping possible, not the option that dumps. The dump itself comes from a call in the design or a UCLI command. Coverage has a trap of the same shape: instrumenting and requesting collection live on different stages.

3 · library 라는 단어가 다섯 가지를 가리킨다3 · The word library means five things

이 Lab 하나를 지나는 동안 같은 단어가 다섯 번, 서로 아무 관계 없는 뜻으로 나온다. 문서에서 library를 만나면 뜻을 짐작하지 말고 어느 도구의 어느 단계인지부터 확인해라.

Inside this one lab the same word turns up five times meaning five unrelated things. When you meet it in a document, do not guess: work out which tool and which stage first.

무엇Which도구·단계Tool and stage담는 것Holds
logical library VCS, analysis (04절)VCS, analysis (§04) 분석된 소스analysed source
technology library DC, 합성 (11절)DC, synthesis (§11) 공정이 제공하는 gate 카탈로그the gate catalogue the process offers
-y library directory VCS, 파일 탐색VCS, file lookup module 정의를 찾아볼 디렉토리a directory to hunt module definitions in

뒤의 둘이 제일 위험하다. 둘 다 DC이고 둘 다 .db를 가리킨다. 갈리는 기준 하나만 잡아라. 만들 때 쓰면 target, 읽을 때 쓰면 link.

The last two are the dangerous pair: same tool, and both point at .db files. Hold on to one rule. Building uses target, reading uses link.

4 · 인터넷 스크립트의 옛날 옵션4 · Old flags from copied scripts

-P, -debug, -debug_all, -debug_pp는 -debug_access와 충돌하고 우선권까지 가져간다. 새 옵션이 무시되는 게 아니라, 새 옵션을 쓰고 있다고 믿는 상태로 옛날 동작을 하게 된다. 증상이 헷갈리는 이유다.

-P, -debug, -debug_all and -debug_pp clash with -debug_access and take priority over it. The new flag is not merely ignored: you get the old behaviour while believing you are on the new one. That is why the symptoms are confusing.

5 · 이 Lab만 규칙이 다르다5 · This lab plays by different rules

Lab 0은 개인 과제다. 다른 Lab의 2인 1조를 그대로 가져오면 학문적 정직성 문제가 된다. 그리고 데모도 코드 제출도 없다. 리포트만 낸다. 반대로 다른 Lab의 습관대로 코드를 정성껏 정리하고 리포트를 대충 쓰면 배점을 통째로 놓친다.

Lab 0 is individual work. Carrying over the pair setup from the other labs turns into an academic integrity problem. And there is no demo and no code submission, only a report. Conversely, polishing the code the way the other labs reward while writing the report carelessly throws away the whole score.

왜 이걸 배우는가

Why any of this is worth learning

이 Lab에는 설계가 없다. 그래서 시시해 보이는데, 남은 다섯 Lab이 전부 이 위에서 돌아간다. Lab 1의 FIFO도, Lab 2의 pipelined MIPS도, Lab 6의 APB agent도 결국 vcs로 굽고 simv로 돌리고 Verdi로 들여다본다. 지금 조용한 실패를 알아보는 눈을 만들어두면 앞으로 다섯 번 아낀다. 못 만들어두면 다섯 번 다 같은 자리에서 막힌다.

There is no design work in this lab, which makes it look trivial. But all five remaining labs run on top of it. The FIFO in Lab 1, the pipelined MIPS in Lab 2, the APB agent in Lab 6 all end up baked by vcs, run by simv and inspected in Verdi. Build the eye for silent failure now and you save it five times over. Skip it and you get stuck in the same spot five times.

SystemVerilog 와 UVM

SystemVerilog and UVM

슬라이드 4쪽의 첫 줄. System Verilog is an HDVL. 그 아래 두 줄이 이 약어를 스스로 푼다. Hardware description language meets… High level parallel programming language. Verilog 는 하드웨어를 기술하는 언어였고, 거기에 C++ 같은 고급 언어의 기능이 붙어서 하드웨어를 검증하는 코드까지 한 언어로 쓰게 됐다는 뜻이다.

The first line of slide 4: System Verilog is an HDVL. The next two lines unpack it themselves: hardware description language meets… high level parallel programming language. Verilog was a language for describing hardware; bolting on the features of a high level language like C++ lets the same language carry the code that verifies hardware too.

슬라이드 6쪽이 UVM 을 한 장으로 소개한다. A methodology and a library written in System Verilog. 언어가 아니라 SV 로 짠 class 라이브러리와 그것을 쓰는 관행이다. Accellera(슬라이드에는 Acellera 로 오타)가 시작했고 지금은 IEEE 표준이며 모든 EDA 벤더가 지원한다. 계보는 VMM, OVM, eRM 을 거쳐 UVM 으로 모였다. 존재 이유는 표준화와 재사용이고, 그 결과물이 Verification IP(VIP)다.

Slide 6 introduces UVM in one page: a methodology and a library written in System Verilog. Not a language, but a class library written in SV plus the conventions for using it. Accellera (misspelled Acellera on the slide) started it, it is now an IEEE standard, and every EDA vendor supports it. The lineage runs VMM, OVM, eRM, and finally UVM. Its reason to exist is standardization and reuse, and the product of that is Verification IP (VIP).

UVM 은 Lecture 15~17 이다. 10/28, 11/2, 11/4 세 번을 외부 강사 Joel Feldman 이 맡는다. 오늘 배우는 class, inheritance, virtual method, virtual interface, randomize, covergroup 가 UVM 이 그대로 깔고 앉는 바닥이다. UVM 의 factory 같은 것은 오늘 덱에 나오지 않는다. 약어 사전의 UVM, OVM · VMM, VIP 항목은 Lecture 2 의 22절에서 들어갔다.

The running example: one DUT and an old-style testbench

강의 전체가 하나의 DUT 를 두고 진행된다. 슬라이드 8쪽이 그 DUT 의 포트를 그리고, 옆에 손으로 그린 파형을 붙였다. 요청(req)을 주소와 데이터와 함께 넣으면 DUT 가 ready 를 한 번 올리고 끝나면 done 을 올리는 단순한 읽기/쓰기 장치다.

The whole lecture works around one DUT. Slide 8 draws its ports and pastes a hand-drawn waveform beside it. It is a simple read/write device: raise a request (req) with an address and data, and the DUT raises ready once and then done when it finishes.

슬라이드 8쪽의 DUT 오른쪽에도 이름 없는 화살표가 넷 나가고 둘 들어온다. 슬라이드가 이름을 붙이지 않아서 그림에서 뺐다. Backup 64쪽의 checker 가 dut_in_if 와 dut_out_if 라는 interface 를 두 개 쓰는 것으로 봐서 입력 쪽과 출력 쪽 interface 가 따로 있는 DUT 로 그린 것이다.

오른쪽, 파형. 세로 점선 E0~E5 가 clk 의 상승 엣지다. 분홍 점선 셋이 testbench 코드의 세 줄이 깨어나는 시점이다.

  1. E0 과 E1 사이, rst 가 0 에서 1 로. testbench 가 @(posedge rst) 에서 기다리다 여기서 깨어나 "Starting writing.." 을 찍는다. 손그림에서도 rst 는 0 에서 1 로 올라간다. 이 DUT 의 reset 은 0 일 때 걸리는(active-low) 것이고, 1 로 올라가는 순간이 reset 이 풀리는 순간이다
  2. E1. @(posedge clk) 로 다음 상승 엣지까지 기다린 뒤 req = 1, rw = 1, addr = 32'h0202_0404, wdata = 32'hffff 를 한꺼번에 준다. 그 전까지 addr 과 wdata 는 아무도 안 몰아서 x 다

함정 · @ 는 앞으로 올 엣지만 본다Trap · @ only sees edges still to come

발표자 노트가 묻는다. "What does the @(posedge done) do?" 답: done 이 0 에서 1 로 바뀌는 다음 순간까지 이 process 를 멈춰 세운다. 핵심은 "다음" 이다. testbench 가 이 줄에 닿기 전에 done 이 이미 올라가 있었다면 그 엣지는 지나갔고, 다음 엣지가 영영 안 오면 testbench 는 영원히 멈춘다. 이미 1 인지를 보려면 레벨을 기다리는 wait (done); 을 쓴다. 이건 슬라이드가 아니라 LRM 의 event control 규칙에서 나오는 이야기다.

The speaker notes ask: "What does the @(posedge done) do?" Answer: it blocks this process until the next moment done changes from 0 to 1. The key word is "next". If done had already risen before the testbench reached this line, that edge is gone, and if no further edge ever comes, the testbench hangs forever. To check whether it is already 1, wait on the level with wait (done);. This comes from the LRM's event control rules, not from the slides.

이 방식이 왜 부족한가. 슬라이드가 말로 적지는 않지만, 이 강의의 나머지가 전부 그 답이다. 쓰기 한 번이 신호 단위 문장 열 줄이다. 다른 주소로 한 번 더 쓰려면 열 줄을 복사한다. 결과가 맞는지는 사람이 파형을 눈으로 보고 판단한다(발표자 노트에 "Can eye ball waves. But that doesn't give continuous checking" 이라는 줄이 있다). 무엇을 시험했는지 세는 장치도 없다. 다음 절부터 SV 가 이 셋을 하나씩 고친다.

Why this falls short. The slides do not spell it out, but the rest of the lecture is the answer. One write is ten signal-level statements; another write to another address means copying all ten. Correctness is judged by a person eyeballing the waveform (the speaker notes have the line "Can eye ball waves. But that doesn't give continuous checking"). Nothing counts what has been tested. 슬라이드 18쪽. Classes can be extended to create derived classes. 이유는 둘째 줄이다. Allows for customization without breaking/rewriting known-good functionality of the base classes. 이미 검증된 Packet 은 그대로 두고, 일부러 틀린 명령을 싣는 오류 packet 을 따로 만든다.

Slide 18: classes can be extended to create derived classes. The reason is the second line: allows for customization without breaking/rewriting known-good functionality of the base classes. Leave the proven Packet alone and build a separate error packet that deliberately carries a bad command.

class ErrPkt extends Packet;          // Packet 의 property 와 method 를 다 물려받는다// inherits all of Packet's properties and methods

슬라이드의 Command = ~cmd; 는 그대로는 컴파일되지 않는다. enum 에 ~ 를 걸면 결과가 int 가 되고, enum 변수에는 같은 enum 값이나 명시적 cast 만 넣을 수 있다. 그래서 cmd_t'( ) 로 감쌌다. 값을 따라가 보면 WRITE(=2)의 비트를 뒤집은 ~2 는 -3 이고, 이건 IDLE, READ, WRITE 어느 이름에도 해당하지 않는 값이다. 오류 packet 이 DUT 가 모르는 명령을 싣게 하려는 의도로 읽힌다.

The slide's Command = ~cmd; does not compile as written. Applying ~ to an enum yields an int, and an enum variable only accepts a value of the same enum or an explicit cast, hence the cmd_t'( ) wrapper. Follow the value: flipping the bits of WRITE (=2) gives ~2 = -3, which matches none of IDLE, READ or WRITE. The intent reads as making the error packet carry a command the DUT does not know.

발표자 노트(한 쪽 어긋나 붙어 있다)가 하나를 덧붙인다. "Inheriting from multiple classes is not supported." extends 뒤에는 부모 class 가 하나만 온다.

The speaker notes (attached to a neighbouring slide) add one more point: "Inheriting from multiple classes is not supported." Only one parent class follows extends.

constraint 세 줄 읽기Reading the three constraint lines
  1. Addr >= 32'h0000_ffff: 65535 이상
  2. Addr <= 32'hffff_0000: 4294901760 이하
  3. Addr[1:0] == 2'b00: 아래 두 비트가 0, 즉 4 의 배수(4 바이트 정렬된 주소)

셋을 한꺼번에 만족해야 한다. 그러면 가장 작은 값은 32'h0000_ffff 가 아니다. ffff 의 아래 두 비트는 11 이라 3 번 조건에 걸린다. 그 위로 처음 오는 4 의 배수가 32'h0001_0000 이다. 가장 큰 값은 32'hffff_0000 그대로다(아래 두 비트가 00). 가능한 값의 개수는 (ffff_0000 − 0001_0000) ÷ 4 + 1 = (4294901760 − 65536) ÷ 4 + 1 = 1,073,709,057 개이고, randomize() 는 이 중 하나를 고른다.

  1. Addr >= 32'h0000_ffff: at least 65535
  2. Addr <= 32'hffff_0000: at most 4294901760
  3. Addr[1:0] == 2'b00: the bottom two bits are 0, i.e. a multiple of 4 (a 4-byte aligned address)

All three must hold at once. So the smallest value is not 32'h0000_ffff: its bottom two bits are 11, which fails line 3. The first multiple of 4 above it is 32'h0001_0000. The largest is 32'hffff_0000 itself (bottom bits 00). The number of legal values is (ffff_0000 − 0001_0000) ÷ 4 + 1 = (4294901760 − 65536) ÷ 4 + 1 = 1,073,709,057, and randomize() picks one of them.

반환값을 확인하는 이유. constraint 끼리 모순이면 풀 수 있는 값이 없고, randomize() 는 0 을 돌려주고 변수는 이전 값을 그대로 둔다. 확인하지 않으면 testbench 는 지난번 값을 또 보내면서 정상적으로 돈 줄 안다. 슬라이드가 if 로 감싼 것은 그래서다. 이게 Lecture 2 의 constrained random 을 실제로 쓰는 모양이다.

Why check the return value. If the constraints contradict each other there is no solution, and randomize() returns 0 and leaves the variables at their previous values. Without the check, the testbench sends the last value again and believes all is well. That is why the slide wraps it in an if. This is what Lecture 2's constrained random looks like in practice.

함정 · implication 은 확률을 기울인다Trap · implications skew the odds

슬라이드 34쪽의 implication 을 rand cmd_t Command; 와 rand bit [31:0] Addr; 에 그대로 걸어 보자. LRM 의 solver 는 (Command, Addr) 쌍 중 가능한 것 전체에서 고르게 고른다. WRITE 일 때 가능한 Addr 는 32'h8000 보다 큰 값 전부, 232 − 32769 = 4,294,934,527 개다. IDLE 과 READ 일 때는 32'hffff_0000 한 개씩뿐이다. 그러면 Command 가 WRITE 가 아닐 확률은 2 / (4,294,934,527 + 2), 사실상 0 이다. READ 는 영원히 안 나온다. 처방은 Backup 62쪽의 solve Command before Addr; 다(19절). Command 를 먼저 고르게 하면 셋이 1/3 씩 나온다. 슬라이드는 이 문제를 직접 말하지 않는다. LRM 의 solve...before 설명이 바로 이 예다.

Apply slide 34's implication as is to rand cmd_t Command; and rand bit [31:0] Addr;. The LRM's solver picks uniformly over all legal (Command, Addr) pairs. With WRITE, every Addr above 32'h8000 is legal: 232 − 32769 = 4,294,934,527 values. With IDLE or READ, only 32'hffff_0000, one each. So the chance that Command is not WRITE is 2 / (4,294,934,527 + 2), effectively zero; READ never appears. assert property (@(posedge Clk) $rose(Req) |-> ##[2:20] Ready);
그림 읽기Reading the picture

assertion 은 Clk 의 상승 엣지마다 신호 값을 표본으로 찍어 판단한다. 엣지 사이에서 바뀐 값은 다음 엣지에서야 보인다.

  1. Req 는 tick 0 과 1 사이에 올라간다. tick 0 의 표본은 0, tick 1 의 표본은 1 이다. $rose(Req) 는 "직전 표본이 0 이고 이번 표본이 1" 이라는 뜻이므로 tick 1 에서 참이다(분홍 점선)
  2. |-> 는 "왼쪽이 참인 바로 그 tick 에서 오른쪽 검사를 시작한다" 는 뜻이다. 오른쪽의 ##[2:20] 은 거기서 2 tick 뒤부터 20 tick 뒤까지다. 1 + 2 = 3, 1 + 20 = 21. 그래서 초록 띠가 tick 3 에서 시작해 그림 밖 tick 21 까지 간다
  3. Ready 는 tick 4 와 5 사이에 올라가므로 tick 5 의 표본이 1 이다. 창 안이다. tick 5 에서 통과(초록 점선)하고 이 시도는 끝난다
  4. Ready 가 tick 21 까지 한 번도 1 이 아니었다면 tick 21 에서 실패가 보고된다. Ready 가 tick 2 에 1 이었다면? 창이 tick 3 부터라 그건 세지 않는다

Req 와 Ready 를 파랑으로 칠한 것은 둘 다 설계 쪽 신호이기 때문이다. assertion 은 검증 장치지만 설계의 신호를 직접 본다.

An assertion samples signal values at each Clk rising edge and judges on those samples. A change between edges is only seen at the next edge.

  1. Req rises between tick 0 and tick 1. The sample at tick 0 is 0, at tick 1 it is 1. $rose(Req) means "previous sample 0, this sample 1", so it is true at tick 1 (pink dotted line)
  2. |-> means "start checking the right side at the very tick the left side is true". The right side's ##[2:20] runs from 2 ticks later to 20 ticks later: 1 + 2 = 3, 1 + 20 = 21. Hence the green band starts at tick 3 and runs off the picture to tick 21
  3. Ready rises between ticks 4 and 5, so the tick 5 sample is 1, inside the window. It passes at tick 5 (green dotted line) and this attempt is done
  4. Had Ready never been 1 by tick 21, a failure at tick 21 would be reported. What if Ready were 1 at tick 2? The window starts at tick 3, so that would not count

Req and Ready are blue because both are design-side signals. An assertion is a verification device, but it looks straight at the design's signals.

무엇을 재나What it measures

슬라이드 43쪽의 정의. Quantitative measure of how well the stimulus exercised the DUT. 테스트를 다 돌리고 coverage 결과를 합쳐(merge) 보고서를 만든다. 목표는 DUT 가 가능한 모든 (슬라이드 표현으로 "read, interesting") 시나리오를 겪었다고 말할 수 있게 되는 것이다. 종류는 둘, code coverage 와 functional coverage 다. 정의와 code coverage 의 한계는 Lecture 2 의 16절이 이미 풀었고, code coverage 의 네 종류는 Backup 66쪽(21절)에 있다.

Slide 43's definition: a quantitative measure of how well the stimulus exercised the DUT. Run all tests, merge the coverage results, and generate a report. The goal is to be able to say the DUT was exposed to all possible (in the slide's words, "read, interesting") scenarios. There are two kinds, code coverage and functional coverage. The definitions and the limits of code coverage were covered in Lecture 2, §16; the four kinds of code coverage are on backup slide 66 (§21).

함정 · code coverage 100% 는 끝났다는 뜻이 아니다Trap · 100% code coverage does not mean done

구별 기준: 무엇을 셌는가. code coverage 는 설계 코드의 줄과 분기를 지나갔는지를 센다. 코드를 안 짜도 컴파일러 옵션만으로 나온다(66쪽). functional coverage 는 검증 엔지니어가 보고 싶다고 적어둔 상황이 일어났는지를 센다. 코드를 짜야 한다(44쪽: "Need to write code to express what you intend to cover"). 설계에서 빠뜨린 기능은 코드에 줄이 없으니 code coverage 로는 영원히 안 보인다. 반대로 functional coverage 는 사람이 적어둔 것만 센다. 둘은 서로를 대신하지 못한다. 13절의 도구에서 code coverage 같은 숫자는 없지만, 값이 고르게 들어가도 bin 이 비는 경우를 직접 만들어 볼 수 있다.

The criterion: what was counted. Code coverage counts whether lines and branches of the design code were passed through, and needs no coding, just compiler switches (slide 66). Functional coverage counts whether the situations a verification engineer wrote down actually happened, and has to be coded (slide 44: "Need to write code to express what you intend to cover"). A feature the design forgot has no lines, so code coverage can never see it missing; functional coverage only counts what someone wrote down. Neither replaces the other. §13's tool has no code coverage number, but you can make bins stay empty even while values flow in with your own hands.

Per slide 45, a covergroup expresses combinations and coverage at the transaction level, and can live in a module, an interface or a class.

module testbench;
  bit [3:0] data;
  cmd_t     cmd;

  covergroup mycg;                     // 무엇을 셀지 적는 틀// the template of what to count
    coverpoint data;                   // data 의 값을 센다// count values of data
    coverpoint cmd;                    // cmd 의 값을 센다// count values of cmd
  endgroup

  initial begin
    mycg cg;
    cg = new();                         // covergroup 도 new 로 만든다// a covergroup is also built with new
    randomize(data);
    randomize(cmd);
    cg.sample();                        // 이 순간의 data, cmd 를 한 번 센다// count data and cmd once, right now
  end
endmodule

randomize(data) 는 class 밖에서 쓰는 형태로, 지금 scope 의 변수를 무작위로 채운다(LRM 은 std::randomize 라고 부른다). 그리고 sample() 이 불리는 순간에만 센다. 이 코드는 딱 한 번 부른다.

randomize(data) is the form used outside a class; it fills variables in the current scope (the LRM calls it std::randomize). And counting only happens when sample() is called. This code calls it exactly once.

함정 · sample() 을 안 부르면 0% 다Trap · no sample(), no coverage

45쪽 코드는 sample() 을 딱 한 번 부른다. 그래서 46쪽 보고서가 15.62% 다. 시뮬레이션이 몇 시간을 돌아도 sample() 이 그 사이에 안 불리면 coverage 는 그대로다. class 안의 covergroup 은 반대로 생성자에서 new 를 빠뜨리면 handle 이 null 이라 sample() 에서 멈춘다. 어디서 sample 하느냐가 곧 무엇을 세느냐다. driver 가 보내기 전에 sample 하면 "보내려 한 것" 을, monitor 가 본 뒤에 sample 하면 "DUT 에 실제로 들어간 것" 을 센다.

Slide 45's code calls sample() exactly once, which is why slide 46's report shows 15.62%. Simulate for hours and coverage will not move if sample() is not called meanwhile. Conversely, a covergroup in a class whose constructor forgets the new leaves a null handle and dies at sample(). Where you sample decides what you count: sampling in the driver before sending counts "what we meant to send"; sampling after the monitor sees it counts "what actually reached the DUT".

final blockThe final block

  
initial 은 시뮬레이션이 시작될 때, final 은 끝날 때 한 번 돈다. 둘 다 여러 개면 도는 순서는 보장되지 않는다. testbench 가 끝나면서 scoreboard 의 남은 항목 수나 통계를 찍는 자리가 final 이다.

  
initial runs once when simulation starts, final once when it ends. With several of either, their order is not guaranteed. final is where a testbench prints leftover scoreboard entries or statistics on the way out.

  

  함정 · 슬라이드 58쪽의 마지막 줄은 오타다Trap · the last line of slide 58 is a typo
  
슬라이드는 "You are now allowed to consume time in a final block" 이라고 적었다. LRM 은 반대다. final 은 시간을 쓰지 않고 실행되어야 하고, 안에 #, @, wait 같은 기다림을 둘 수 없다. 시뮬레이션은 이미 끝나는 중이라 기다릴 시간이 없다. now 가 아니라 not 으로 읽는다.

  
The slide reads "You are now allowed to consume time in a final block". The LRM says the opposite: final must execute without consuming time, with no #, @ or wait inside. Simulation is already ending; there is no time left to wait for. Read not, not now.

It boils down to one rule: with try_ it never blocks and returns whether it succeeded; without, it waits until it can. This table is why §07 calls a mailbox "FIFO + Event": it keeps order like a FIFO, and waiting while it is empty is like waiting on an event. In §14's testbench picture, it is the usual way to pass objects from stimulus to driver and from monitor to checker.

  ##[2:20] (ready == 1) ##[50:100] !$isunknown(rdata);   // 슬라이드: (rdata != 'x)// slide: (rdata != 'x)
endsequence
sequence data_write;
  ##[2:20] (ready == 1) ##0 !$isunknown(wdata);          // 슬라이드: (wdata != 'x)// slide: (wdata != 'x)
endsequence

property read_prop;
  @(posedge clk) cmd_req(0) |-> data_read |-> done;
endproperty
property write_prop;
  @(posedge clk) cmd_req(1) |-> data_write |-> done;
endproperty

write_prop 를 말로 풀면: rw 가 1(쓰기)인 채로 req 가 올라가면, 2~20 tick 안에 ready 가 1 이 되고, 그 같은 tick 에(##0) wdata 에 x 가 없어야 하며, 그 tick 에 done 도 1 이어야 한다. read_prop 는 rw 가 0 일 때, ready 뒤 50~100 tick 안에 rdata 가 x 가 아니게 되는 것을 본다. 02절의 손그림처럼 done 이 ready 보다 한 cycle 늦게 오는 DUT 라면 이 |-> done 은 맞지 않는다. 그때는 |=> done 이 맞다. assert 앞의 read_assert: 는 label 이고, 실패 메시지와 파형 창(11절의 41쪽)에 이 이름으로 나온다. 슬라이드의 != 'x 는 11절의 != 1'bx 와 같은 문제라 $isunknown 으로 바꿨다.

  
write_prop in words: if req rises with rw at 1 (write), then within 2 to 20 ticks ready becomes 1, at that same tick (##0) wdata has no x, and done is also 1 at that tick. read_prop, for rw at 0, checks that rdata stops being x within 50 to 100 ticks after ready. For a DUT whose done arrives one cycle after ready, as in §02's sketch, this |-> done does not fit; |=> done would. The read_assert: before assert is a label, the name that shows in failure messages and in the waveform viewer (slide 41 in §11). class mychecker;
  virtual dut_in_if  ivif;                    // 입력 쪽 interface// input-side interface
  virtual dut_out_if ovif;                    // 출력 쪽 interface// output-side interface
  Packet in_queue[$], out_queue[$];

  task main();

      reset_checker();                        // queue 와 상태를 비운다// clear queues and state
      @(negedge ivif.rst);                    // 슬라이드가 고른 reset 엣지// the reset edge the slide chose
      fork
        detect_reset();                       // reset 이 다시 오면 끝난다// returns when reset comes again
        track_inputs();
        track_outputs();
        do_comparisons();
      join_any
      disable fork;                           // 나머지 셋을 죽이고 처음부터// kill the other three and start over
    end
  endtask

  task track_inputs();
    Packet pkt;
    forever begin
      @(posedge ivif.done);
      create_inp_pkt(pkt);                    // 신호를 읽어 packet 으로 묶는다// read the signals into a packet
      in_queue.push_back(pkt);
    end
  endtask

  task track_outputs();
    Packet pkt;
    forever begin
      @(posedge ovif.done);
      create_out_pkt(pkt);
      out_queue.push_back(pkt);
    end
  endtask

  task do_comparisons();

    forever begin
      wait (in_queue.size() > 0 && out_queue.size() > 0);   // 슬라이드: if (...) 만 있다// slide: only an if (...)

      oup = out_queue.pop_front();

        $error("Mismatching packets found");
    end
  endtask
endclass

// done 이 오르고 몇 cycle 뒤 req 가 내려가는 경우 (슬라이드 주석의 fom_req 는 오타)// done rising a few cycles before req drops (the slide comment's fom_req is a typo)
property expiry_case;
  @(posedge clk) disable iff (!reset)
  $rose(done) |-> ##[1:5] ($fell(req) && (done == 1'b0));
endproperty
expiry_case_cprop: cover property (expiry_case);

  
assert 와 cover 의 차이는 "틀리면 어떻게 하나" 다. assert 는 성질이 깨지면 오류를 낸다. cover 는 성질이 성립한 횟수를 센다. 이 예라면 "done 이 오른 뒤 1~5 cycle 안에 req 가 내려가고 done 도 0 으로 돌아온" 상황을 시뮬레이션이 몇 번 겪었는지를 보고서에 올린다. 0 번이면 그 경우를 아직 시험하지 않은 것이다.

  
The difference between assert and cover is what happens on a mismatch. assert raises an error when the property breaks; cover counts how many times it held. Here, the report shows how often the simulation saw "within 1 to 5 cycles after done rose, req fell and done was back to 0". Zero means that case has not been tested yet.

Slide 69: a model is an artifact that stands in for a physical entity so you can analyse it; it abstracts the entity and includes only the details that analysis needs. Three examples: a counter's behavioral RTL model captures functionality only, an IP's black-box model only the interface, and an ALU's transistor level model timing and power too. And a model you cannot execute (simulate) is no good; some models can also be implemented (synthesized).

Slide 70: going down the design flow (Algorithm → RTL → Gates → Transistors), the level of abstraction drops and detail grows, so simulation takes too long.

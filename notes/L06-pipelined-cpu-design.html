01

Single cycle 을 다시 본다

Single cycle, revisited

파이프라인 이야기를 하려면 먼저 쪼갤 대상이 있어야 한다. 그게 single cycle CPU 다. 명령어 하나를 한 클럭 안에 통째로 끝내는 설계다.

Before you can talk about pipelining you need something to cut up. That is the single cycle CPU: one instruction finishes entirely within one clock period.

명령어 하나가 하는 일을 다섯 덩어리로 나눈 것이 IF, ID/RF, EX, MEM, WB 다. single cycle 설계에서 이 다섯은 단계가 아니라 그냥 순서다. 한 클럭 안에서 신호가 이 순서로 흘러갈 뿐, 사이에 register 가 없다.

The work of one instruction splits into five chunks: IF, ID/RF, EX, MEM, WB. In a single cycle design these five are an order, not stages. The signal flows through them within one clock period, with no registers in between.

Slide 5 walks lw $s3, 8($s0) through all five. It forms the address as sign_ext(8) + $s0, reads memory at that address, and writes the value into $s3. Alongside it, the slide draws the control path and the data path in different colours. That split matters later, because when you pipeline the machine you have to pipeline the two separately.

슬라이드 6쪽이 던지는 질문이고, 답은 아니다. 이게 single cycle 설계에서 제일 헷갈리는 지점이라 슬라이드가 세 장(6, 7, 8)을 들여 푼다.

Slide 6 asks it and the answer is no. This is the most confusing point in a single cycle design, and the deck spends three slides (6, 7, 8) on it.

즉 읽기는 전부 조합 회로다. 주소를 주면 값이 나온다. clock 을 기다리지 않는다. 클럭에 걸리는 것은 쓰기뿐이다. 그래서 한 클럭 안에 다섯 덩어리가 전부 들어간다.

So every read is combinational. Give it an address and the value comes out, no clock involved. Only the writes are clocked. That is how all five chunks fit inside one clock period.

블록도에서 clock 표시를 보고 사이클을 하나 먹는다고 읽으면 안 된다. register file 과 data memory 에 clock 이 그려져 있는 것은 쓰기 포트 때문이다. 읽기 포트는 조합 회로다. 이걸 잘못 읽으면 single cycle 설계가 3 사이클짜리로 보이고, 뒤에 나오는 파이프라인 단계 수도 안 맞게 센다.

A clock symbol on a block diagram does not mean this costs a cycle. The register file and data memory are drawn clocked because of their write ports. The read ports are combinational. Misread this and a single cycle design looks like a three cycle one, and your stage count for the pipeline comes out wrong too.

02

무엇이 문제였나

What was wrong with it

single cycle 은 이해하기 쉽고 정확하다. 그런데 슬라이드 9쪽이 세 가지 문제를 든다. 성능, 전력, 면적. 칩 설계에서 늘 같이 따라다니는 세 축이다.

A single cycle machine is easy to understand and it is correct. Slide 9 lists three problems with it: performance, power, area. The three axes that follow you around in chip design.

성능

Performance

클럭 주기가 가장 긴 명령어에 맞춰진다. lw 하나 때문에 모든 명령어가 느려진다. add 는 메모리를 안 쓰는데도 lw 가 끝날 만큼 기다린다.

The clock period is set by the longest instruction. One lw slows every instruction down. An add never touches memory but still waits as long as lw needs.

전력

Power

모든 datapath 요소가 항상 켜져 있다. 안 쓰는 단계를 꺼둘 방법이 없다. 슬라이드 표현으로 clock gating 이 불가능하다.

Every datapath element is always active. There is no way to switch off a stage you are not using. In the slide's words, no clock gating is possible.

면적

Area

하드웨어 활용률이 낮다. ALU 는 한 주기에 아주 잠깐만 일하고 나머지 시간은 논다. 그걸 위해 면적을 다 내주고 있다.

Hardware utilisation is poor. The ALU works for a sliver of each period and idles the rest. You paid full area for that.

성능을 재는 네 가지 말

슬라이드 10쪽이 네 개를 나열한다. throughput, latency, IPC, CPI. 이름만 나오고 정의는 안 나온다. 그런데 이 강의 나머지가 전부 이 네 개로 이야기하므로 여기서 정리하고 간다.

Slide 10 lists four: throughput, latency, IPC, CPI. It gives the names without definitions. The rest of the lecture argues in these terms, so it is worth pinning them down here.

03

Pipelining 이란 무엇인가

What pipelining is

슬라이드 13쪽의 정의는 temporal parallelism 이다. 명령어 하나를 여러 단계로 쪼개고, 서로 다른 명령어가 서로 다른 단계에 동시에 올라가 있게 하는 것. 공간을 늘려 병렬로 만드는 게 아니라, 시간 축에서 겹치게 만든다.

Slide 13 defines it as temporal parallelism: break each instruction into a series of steps and let different instructions occupy different steps at the same time. You are not duplicating hardware to go parallel. You are overlapping in time.

슬라이드는 파이프라인이 도는 모습을 세 구간으로 부른다.

The slide names three phases of a running pipeline.

control path 도 같이 쪼개야 한다

The control path has to be cut up too

슬라이드 15쪽이 짧게 지나가는데 놓치면 안 되는 대목이다. datapath 만 쪼개면 안 된다. control signal 도 제 단계에 도착해야 한다. MemWrite 는 MEM 단계에서, RegWrite 는 WB 단계에서 필요하다. 그런데 둘 다 ID 단계에서 명령어를 해석할 때 만들어진다.

Slide 15 goes by quickly but it matters. Cutting the datapath is not enough. Control signals have to arrive at the right stage too. MemWrite is needed in MEM and RegWrite in WB, yet both are produced back in ID when the instruction is decoded.

슬라이드는 두 가지 방법을 적는다. control signal 을 pipeline register 에 같이 실어 나르거나, 명령어 워드 자체를 각 단계까지 들고 가서 거기서 필요한 신호를 만들거나. 뒤에 나오는 실제 설계(슬라이드 23쪽)는 앞쪽을 쓴다.

The slide gives two options: carry the control signals along in the pipeline registers, or carry the instruction word itself into each stage and generate what that stage needs there. The actual design later on (slide 23) takes the first route.

100 ns 짜리 셋 중 하나다. 50 ns 짜리를 아무리 쪼개도 클럭 주기는 여전히 100 ns 에 묶인다. 클럭은 가장 느린 단계가 정하기 때문이다. 100 ns 를 둘로 쪼개 50 씩 만들어도 나머지 두 개가 100 이라 여전히 100 이다. 셋을 다 쪼개야 비로소 50 으로 내려간다. 이게 파이프라인 단수를 늘려도 기대만큼 안 빨라지는 이유고, 슬라이드 17쪽이 말하는 균형 문제다.

One of the three 100 ns stages. Splitting a 50 ns stage changes nothing, because the period is set by the slowest stage. And splitting one 100 ns stage into two 50s still leaves two other 100s, so the period stays at 100. You have to split all three before it drops to 50. This is why adding stages does not pay off the way you expect, and it is the balance problem slide 17 raises.

전력과 면적도 슬라이드가 같이 짚는다. 전력은 단계별로 gating 이 가능해진다. ADD 명령어는 MEM 단계를 안 쓰므로 그 단계를 꺼둘 수 있다. single cycle 에서는 불가능했던 일이다. 면적은 늘어나지만 활용률이 좋아진다.

The slide covers power and area too. Power improves because you can now gate per stage. An ADD does not use MEM, so that stage can be switched off, which was impossible in the single cycle design. Area grows, but utilisation gets better.

Slide 17 asks the best question in the lecture. Can you keep adding pipeline stages to keep raising the clock?

슬라이드가 기호 네 개로 답한다. G 는 조합 논리의 게이트 수, T 는 그 조합 논리의 지연, R 은 register 하나의 비용, S 는 register 의 지연이다.

The slide answers with four symbols. G is the gate count of the combinational logic, T its delay, R the cost of a register, and S a register's delay.

여기서 읽어야 할 것은 두 식의 비대칭이다. 비용은 G + R*k 로 k 에 정직하게 비례해 늘어난다. 반면 throughput 은 1/(T/k + S) 라서 k 를 키울수록 이득이 줄어든다. 처음 몇 단은 크게 벌지만 나중에는 register 지연 S 만 남는다. 돈은 계속 내는데 성능은 안 오르는 구간이 생긴다.

The thing to read here is the asymmetry between the two formulas. Cost is G + R*k, growing honestly in proportion to k. Throughput is 1/(T/k + S), so each extra stage buys less than the one before. The first few stages win a lot, then all that is left is the register delay S. You reach a region where you keep paying and stop gaining.

2. One thing turns out to be broken

WriteReg must arrive at same time as Result. This is the most famous first bug in pipeline design.

무슨 일이 일어나냐면 이렇다. 결과를 어느 register 에 적을지를 정하는 번호는 명령어 안에 들어 있고, 그건 ID 단계에서 뽑힌다. 그런데 실제로 적는 것은 WB 단계다. 그 사이에 세 사이클이 있다. 번호를 같이 안 실어 나르면, WB 단계에 도착했을 때 register file 은 그 시점에 ID 단계에 있는 다른 명령어의 번호를 보고 있다. 엉뚱한 register 에 적는다.

Here is what goes wrong. The number saying which register to write lives inside the instruction and is extracted in ID. The write itself happens in WB, three cycles later. If you do not carry the number along, then by the time WB runs, the register file is looking at the number belonging to whatever instruction is in ID right now. You write to the wrong register.

고치는 방법은 단순하다. register 번호도 데이터와 함께 pipeline register 를 타고 내려가게 한다. 그러면 결과와 번호가 같은 사이클에 WB 에 도착한다.

The fix is simple: send the register number down the pipeline registers alongside the data. Then the result and its destination arrive at WB in the same cycle.

일반화하면 이렇다. 어떤 단계에서 필요한 정보는, 그 단계까지 명시적으로 실어 날라야 한다. single cycle 에서는 전부 한 사이클 안이라 그냥 선을 이으면 됐다. 파이프라인에서는 선을 잇는 것만으로는 안 되고 시간을 맞춰야 한다.

Generalised: any information a stage needs has to be carried to that stage explicitly. In a single cycle design everything was inside one period, so a wire was enough. In a pipeline a wire is not enough. The timing has to line up too.

3. Control has the same problem

슬라이드 23쪽이 두 줄로 정리한다. control unit 은 single cycle 때 쓰던 것과 같은 것이고, control 이 제 단계에 도착하도록 늦춰진다.

즉 control 로직을 새로 설계하지 않는다. ID 에서 한 번 만들고, 그 신호들을 데이터와 똑같이 pipeline register 에 태워서 각자 필요한 단계까지 내려보낸다. RegWrite 는 WB 까지 네 칸을 간다.

So you do not redesign the control logic. You generate it once in ID and then ride the signals down the pipeline registers exactly like data, each one getting off at the stage that needs it. RegWrite travels all four hops to WB.

Handling data hazards

슬라이드 30쪽이 그림 하나로 문제를 보여주고, 32쪽과 33쪽이 같은 그림에 해법을 얹는다. 코드는 이렇다.

Slide 30 shows the problem in one figure, and slides 32 and 33 put the fixes onto that same figure. The code is this.

add $s0, $s2, $s3
and $t0, $s0, $s1
or  $t1, $s4, $s0
sub $t2, $s0, $s5

네 줄 전부 $s0 에 걸려 있다. add 가 $s0 를 만들고 나머지 셋이 그걸 읽는다. 그런데 add 가 $s0 를 register file 에 적는 것은 5 사이클째(WB)이고, and 는 3 사이클째(ID)에 그걸 읽으려 한다. 그림에서 화살표가 시간을 거슬러 올라간다. 그게 hazard 의 시각적 정의다.

All four hang on $s0. The add produces it and the other three read it. But add writes $s0 into the register file in cycle 5 (WB), while and tries to read it in cycle 3 (ID). In the figure the arrows point backwards in time. That is what a hazard looks like on a diagram.

화살표가 뒤로 가면 hazard 다. 이 한 문장이 슬라이드 30, 33, 37, 41쪽을 다 읽는 열쇠다. 해법이란 전부 화살표를 앞으로 돌려놓는 방법이다. 값을 일찍 꺼내 오거나(forwarding), 읽는 쪽을 늦추거나(stall), 애초에 그 자리에 다른 걸 놓거나(nop, 재배치).

An arrow pointing backwards is a hazard. That one sentence unlocks slides 30, 33, 37 and 41. Every fix is a way of making the arrow point forward again: get the value out earlier (forwarding), make the reader later (stall), or put something else in that slot (nops, reordering).

Forwarding 으로 못 막는 경우

The case forwarding cannot cover

lw 바로 뒤에서 그 값을 쓰면 forwarding 만으로는 안 된다. 이 강의에서 제일 중요한 함정이고, quiz 에 나오기 딱 좋은 모양이다.

A use immediately after an lw cannot be fixed by forwarding alone. The most important trap in this lecture, and exactly the shape a quiz question takes.

lw  $s0, 40($0)
and $t0, $s0, $s1

이유는 타이밍이 아니라 물리다. add 의 결과는 EX 끝(3 사이클)에 이미 존재했다. 그래서 4 사이클의 EX 로 앞당겨 줄 수 있었다. 그런데 lw 의 결과는 메모리를 읽어야 나오므로 MEM 끝(4 사이클)에야 존재한다. and 는 그 값을 4 사이클의 EX 에서 원한다. 아직 세상에 없는 값을 당겨올 수는 없다.

The reason is physics, not timing bookkeeping. The result of add already existed at the end of EX in cycle 3, so it could be pulled into EX in cycle 4. The result of lw only exists at the end of MEM in cycle 4, because memory has to be read first. And and wants it in EX during cycle 4. You cannot forward a value that does not exist yet.

그래서 한 사이클을 반드시 버려야 한다. 멈춰 세운 다음, 그 뒤에 forwarding 한다. 슬라이드 37쪽 그림에서 and 의 RF 가 두 번 그려지고 or 의 IM 이 두 번 그려진 것이 그 한 사이클이다.

So one cycle has to be thrown away. Stall, then forward after it. In the figure on slide 37 that lost cycle is why and has its RF drawn twice and or has its IM drawn twice.

이 패턴을 load-use hazard 라고 부른다. 슬라이드에는 그 이름이 안 나오지만 업계와 교과서에서 쓰는 표준 표현이다. 컴파일러가 lw 다음 자리에 의존 없는 명령어를 넣어주면 이 한 사이클도 안 버릴 수 있다. 컴파일 타임 해법이 여기서 다시 쓸모가 생긴다.

The pattern is called a load-use hazard. The slide does not use the name, but it is the standard term in textbooks and in industry. A compiler that slots an independent instruction after the lw saves even that one cycle, which is where the compile time fixes earn their keep again.

MemtoRegE 가 지금 EX 에 있는 게 load 명령어라는 뜻이다. 그리고 rtE 는 그 load 의 목적지 register 다. Decode 에 있는 명령어의 두 피연산자 중 하나라도 거기 걸리면 멈춘다.

The MemtoRegE term means the instruction now in EX is a load, and rtE is that load's destination register. If either operand of the instruction in Decode matches it, stall.

마지막 줄이 섹션 06 의 함정에서 말한 그것이다. 앞의 두 단계를 붙들고(StallF, StallD), 그 때문에 EX 에 생기는 빈자리를 지운다(FlushE). 멈추기만 하면 EX 에는 직전 명령어가 그대로 남아 두 번 실행된다. 그래서 flush 가 반드시 같이 간다.

That last line is the point from the trap in section 06. Hold the two front stages (StallF, StallD) and erase the hole that leaves in EX (FlushE). If you only stall, the previous instruction stays sitting in EX and executes twice. That is why the flush always rides along.

Control hazard 를 어떻게 막나

Handling control hazards

Data hazard 는 값이 안 준비된 문제였다. Control hazard 는 어느 명령어를 가져와야 하는지 자체를 모르는 문제다. 더 나쁘다.

A data hazard is a value that is not ready. A control hazard is not knowing which instruction to fetch at all. That is worse.

슬라이드 41쪽 그림이 대가를 보여준다. beq 가 주소 20 에 있고, 분기 판정은 MEM 단계(4 사이클)에서야 난다. 그때까지 주소 24, 28, 2C 의 명령어 세 개가 이미 파이프라인에 들어와 있다. 분기가 성립하면 셋 다 지워야 한다.

Slide 41 shows the price. The beq sits at address 20 and the branch is not resolved until MEM, in cycle 4. By then the instructions at 24, 28 and 2C are already in the pipeline, all three of them. If the branch is taken, all three have to be discarded.

Early branch resolution: 판정을 앞으로 당긴다

Early branch resolution: decide sooner

슬라이드 42쪽부터 45쪽까지가 이 이야기다. 분기 판정에 필요한 것은 두 register 값을 비교하는 것뿐이다. ALU 를 통째로 기다릴 이유가 없다. 비교기를 Decode 단계에 두면 2 사이클째에 판정할 수 있고, 버리는 명령어가 셋에서 하나로 준다.

Slides 42 through 45 cover this. All the branch needs is a comparison of two register values. There is no reason to wait for the full ALU. Put a comparator in Decode and the branch resolves in cycle 2, dropping the flush count from three to one.

하나를 고치면 다른 게 생긴다. 슬라이드 43쪽이 그걸 직접 말한다.

Fixing one thing creates another. Slide 43 says so directly.

Introduced another data hazard in Decode stage. 분기의 피연산자가 바로 앞 명령어가 계산한 값이면, 그 값은 아직 register file 에 없다. 원래는 분기가 MEM 까지 가는 동안 시간이 벌렸는데, Decode 로 당기면서 그 여유가 사라진 것이다.

Introduced another data hazard in Decode stage. If a branch operand was computed by the immediately preceding instruction, it is not in the register file yet. The old design bought time by letting the branch travel to MEM. Moving it to Decode spent that slack.

해법은 같은 도구를 다시 쓰는 것이다. 쓸 수 있으면 forwarding 하고, 아니면 stall 한다. 슬라이드 43쪽이 그렇게 적는다. 파이프라인 설계가 왜 복잡해지는지 이 한 장이 보여준다. 대가를 옮길 수는 있어도 없앨 수는 없다.

The fix is the same toolbox again: forward the value if it is available, otherwise stall. That is what slide 43 says. This one slide is a good picture of why pipeline design gets complicated. You can move the cost around. You cannot delete it.

Branch prediction: 아예 찍는다

Branch prediction: just guess

판정을 아무리 앞으로 당겨도 벌점은 남는다. 그래서 마지막 수단은 판정을 기다리지 않고 찍어서 계속 fetch 하는 것이다. 맞으면 벌점이 0 이고, 틀리면 원래 내던 벌점을 낸다.

However early you resolve, some penalty remains. So the last move is to guess and keep fetching instead of waiting. Right guess costs nothing. Wrong guess costs what you were paying anyway.

Two things on the scale. The gain is that the misprediction rate halves, 8% down to 4%. The loss is delay on the Decode path. If that makes Decode the slowest stage, the clock period rises and every instruction gets slower. Why memory became a hierarchy


  
슬라이드 49쪽은 계층 그림 하나다. 축이 latency 와 area 가 같이 커지는 방향이다. 이 강의에서는 MEM 단계가 한 사이클에 끝나는 것으로 가정했다. 현실에서는 그게 성립하지 않는다. main memory 는 수백 사이클이 걸린다.

  
Slide 49 is a single hierarchy picture, with the axis running in the direction where latency and area grow together. This lecture assumed MEM finishes in one cycle. In reality it does not. Main memory takes hundreds of cycles.


  
그래서 캐시가 있고, 캐시가 빗나가면 파이프라인이 수백 사이클 stall 한다. 우리가 본 lwstall 은 한 사이클짜리 귀여운 경우다. 캐시 이야기는 이 과목의 범위를 넘고, Design Flow 에서 보면 SoC 강의(10 강, 11 강)에서 memory 와 interconnect 로 다시 나온다.

  
Hence caches, and when a cache misses the pipeline stalls for hundreds of cycles. The lwstall we studied is the cute one cycle version. Caches themselves are out of scope here, and looking at the design flow, memory comes back in the SoC lectures (10 and 11) as memory and interconnect.

What to read in this table is not the list but the structure. A modern CPU did not abandon the five stage pipeline. It refilled each stage with more pipeline. The hazard machinery is the same family too: a scheduler that "checks operands are ready before dispatching" is the same kind of thing as the stall condition on slide 39, and register renaming removes the data hazards that come purely from reusing register names.

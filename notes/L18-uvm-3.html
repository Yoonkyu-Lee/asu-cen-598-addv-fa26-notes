Sequence item 에 randomization 을 붙인다

Making the sequence item flexible

4쪽의 말은 두 줄이다. 입력 쪽 field 를 random 으로 선언하고, randomization 에 영향을 줄 constraint 를 더한다. 오른쪽 코드는 Lecture 17 의 transaction class 에 이 둘을 얹은 것이다. 보내는 쪽 field 셋(reset, 8 bit address, 32 bit data_in)에 rand 가 붙었고, DUT 의 출력에서 채워지는 field(data_out)에는 안 붙었다. constraint 는 둘이다. 하나는 address 의 아래 3 bit 가 0 이어야 한다는 것(8 의 배수), 다른 하나는 reset 이 0 이면 address 가 0 보다 커야 한다는 implication 과, address 를 reset 보다 먼저 풀라는 solve ... before 다.

Slide 4 says two things: declare the input fields as random, and add constraints to affect randomization. The code on the right is Lecture 17's transaction class with both added. The three fields that are sent (reset, an 8-bit address, a 32-bit data_in) get rand; the field filled from the DUT's output (data_out) doesn't. There are two constraints: the address's low 3 bits must be zero (a multiple of 8), and an implication that when reset is 0 the address must be greater than 0, together with a solve ... before that solves address before reset.

문법 자체는 Lecture 12 의 10절(constraint, implication)과 19절(solve ... before, inline constraint)에서 다 봤다. 새로운 것은 그것을 uvm_sequence_item 에 단다는 것뿐이다. 그러면 다음 절의 sequence 가 이 item 을 만들 때마다 randomize() 로 새 값을 뽑는다. 이 노트의 예는 64 칸짜리 작은 memory 에 읽고 쓰는 요청이다.

The syntax itself is all from Lecture 12, §10 (constraints, implication) and §19 (solve ... before, inline constraints). The only new thing is hanging it on a uvm_sequence_item, so that each time the next section's sequence makes this item it draws fresh values with randomize(). This note's example is a read or write request to a small 64-slot memory.

class mem_req extends uvm_sequence_item;
  rand bit        rst;        // 1 이면 "reset 펄스를 보내라"// 1 means "send a reset pulse"
  rand bit        is_write;
  rand bit [5:0]  slot;       // 0..63 칸 중 하나// one of slots 0..63
  rand bit [15:0] wdata;
       bit [15:0] rdata;      // DUT 가 돌려준 값. rand 가 아니다// what the DUT returned; not rand

  constraint c_rst   { soft rst == 0; }               // 보통은 reset 이 아니다// normally not a reset
  constraint c_align { slot[1:0] == 2'b00; }         // 4 칸 단위: 0, 4, ..., 60// steps of 4: 0, 4, ..., 60
  constraint c_rd    { (!is_write) -> (slot < 16); } // 읽기는 앞쪽 칸에서만// reads only from the low slots
  constraint c_order { solve is_write before slot; }

  `uvm_object_utils_begin(mem_req)
    `uvm_field_int(rst,      UVM_ALL_ON)
    `uvm_field_int(is_write, UVM_ALL_ON)
    `uvm_field_int(slot,     UVM_ALL_ON)
    `uvm_field_int(wdata,    UVM_ALL_ON)
    `uvm_field_int(rdata,    UVM_ALL_ON)
  `uvm_object_utils_end

  function new(string name = "mem_req");
    super.new(name);
  endfunction
endclass

슬라이드 class 와 다른 곳이 하나 있다. rst 에 soft constraint 를 걸어 평소에는 0 이 되게 했다. 슬라이드의 item 은 reset field 가 그냥 rand 라서, 아래에서 계산하듯 아무 constraint 없이 randomize 하면 거의 절반이 reset 요청이 된다. soft 는 SV 2012 문법으로, 다른 constraint(예를 들어 03절의 inline constraint rst == 1)와 부딪히면 조용히 물러나는 constraint 다. 그래서 reset 이 필요한 sequence 만 rst == 1 을 요구하면 된다. 이 줄은 슬라이드 밖 보충이다.

One difference from the slide's class: rst gets a soft constraint so it's normally 0. In the slide's item the reset field is plain rand, so, as computed below, randomizing with no other constraint makes almost half of all items reset requests. soft (SV 2012) marks a constraint that quietly gives way when another one conflicts with it, such as §03's inline rst == 1, so only a sequence that wants a reset has to ask for one. This is a supplement, not from the slides.

그림 읽기Reading the picture

칸 하나가 randomize 가 고를 수 있는 (is_write, slot) 쌍 하나다. 칸 위 작은 숫자가 slot, 아래 숫자가 그 쌍이 나올 확률이다. 어떤 칸이 있고 없는지는 constraint 둘이 정한다.

  1. c_align(slot[1:0] == 2'b00): slot 의 아래 2 bit 가 00 이어야 하니 4 의 배수만 남는다. 6 bit 라 0~63 중 0, 4, 8, ..., 60 의 16 개다(64 ÷ 4 = 16). 그래서 write 줄이 16 칸이다
  2. c_rd((!is_write) -> (slot < 16)): is_write 가 0(읽기)이면 slot 이 16 보다 작아야 한다. 16 개 중 0, 4, 8, 12 의 4 개만 남는다. 그래서 read 줄이 4 칸이고, 오른쪽 회색 글처럼 16~60 은 읽기로는 못 간다. is_write 가 1 이면 implication 의 왼쪽이 거짓이라 아무 제한이 없다
  3. A, solve 없음: LRM 의 기본 규칙대로 solver 는 가능한 쌍 전체에서 고르게 고른다. 쌍은 4 + 16 = 20 개라 칸마다 1/20 = 5%. 읽기는 4 × 5% = 20%, 쓰기는 16 × 5% = 80%. is_write 는 1 bit 인데도 50 대 50 이 아니다. 쓰기 쪽에 가능한 slot 이 네 배 많기 때문이다(Lecture 12 의 10절 함정과 같은 현상, 거기는 2 대 약 43억이었다)
  4. B, solve is_write before slot: is_write 를 먼저 고른다. 먼저 고르는 변수는 자기 값들 사이에서 고르게 나오므로 읽기 50%, 쓰기 50%. 그다음 slot 을 그 조건 안에서 고르게 고른다. 읽기면 4 칸에 50% ÷ 4 = 12.5% 씩, 쓰기면 16 칸에 50% ÷ 16 = 3.125%, 반올림해서 3.1% 씩
  5. A 와 B 의 칸의 모양은 같다. 20 칸 그대로이고 사라지거나 생긴 칸이 없다. solve ... before 는 풀 수 있는 답의 집합은 그대로 두고 확률만 옮긴다. 그래서 constraint 와 모순이 생길 일이 없다

슬라이드의 constraint 에 같은 셈을 해 보면 이렇다. address 는 8 bit 이고 아래 3 bit 가 0 이므로 0, 8, ..., 248 의 32 개. reset 이 0 이면 address 가 0 이 아니어야 하므로 31 개, reset 이 1 이면 32 개 전부. solve 가 없으면 쌍이 31 + 32 = 63 개라 address 가 0 일 확률은 1/63(약 1.6%), reset 이 1 일 확률은 32/63(약 50.8%)이다. 슬라이드처럼 address 를 먼저 풀면 address 가 32 개 중 고르게 나와 0 일 확률이 1/32(약 3.1%)로 오르고, reset 이 1 일 확률은 1/32 × 1 + 31/32 × 1/2 = 33/64(약 51.6%)가 된다. 즉 슬라이드의 solve 는 address 0 을 두 배쯤 자주 보게 하는 효과이고, reset 쪽은 거의 바꾸지 않는다. 그리고 어느 쪽이든 randomize 한 item 의 절반가량이 reset 이다. 위 코드가 soft rst == 0 을 둔 이유다.

Each cell is one (is_write, slot) pair randomize can pick. The small number on top is the slot; the number below is that pair's probability. Which cells exist is decided by two constraints.

  1. c_align (slot[1:0] == 2'b00): the low 2 bits must be 00, leaving multiples of 4. Slot is 6 bits, so of 0 to 63 that's 0, 4, 8, ..., 60: 16 values (64 ÷ 4). Hence 16 cells in the write row
  2. c_rd ((!is_write) -> (slot < 16)): when is_write is 0 (a read), slot must be below 16, leaving only 4 of the 16: 0, 4, 8, 12. Hence 4 cells in the read row, and, as the grey note says, slots 16 to 60 can't be read. With is_write = 1 the left side of the implication is false, so there's no limit
  3. A, no solve: by the LRM's default rule, the solver picks uniformly over all legal pairs. There are 4 + 16 = 20, so each cell is 1/20 = 5%: reads 4 × 5% = 20%, writes 16 × 5% = 80%. is_write is one bit, yet it isn't 50/50, because writes have four times as many legal slots (the same effect as the trap in Lecture 12, §10, where it was 2 against about 4.3 billion)
  4. B, solve is_write before slot: is_write is picked first. A variable solved first comes out uniform over its own values, so reads 50%, writes 50%. Then slot is picked uniformly within that. Reads: 50% ÷ 4 = 12.5% per cell; writes: 50% ÷ 16 = 3.125%, shown rounded as 3.1%
  5. A and B have the same cells. All 20 are still there; none vanished or appeared. solve ... before leaves the set of solutions alone and moves only the probabilities, so it can never create a contradiction

The same arithmetic on the slide's constraints: address is 8 bits with its low 3 bits zero, so 32 values (0, 8, ..., 248). With reset = 0 the address can't be 0, leaving 31; with reset = 1 all 32. Without a solve there are 31 + 32 = 63 pairs, so address is 0 with probability 1/63 (about 1.6%) and reset is 1 with 32/63 (about 50.8%). Solving address first, as the slide does, makes address uniform over its 32 values, raising address 0 to 1/32 (about 3.1%), while reset = 1 becomes 1/32 × 1 + 31/32 × 1/2 = 33/64 (about 51.6%). So the slide's solve mainly makes address 0 show up about twice as often and barely moves reset. Either way about half of all randomized items are resets, which is why the code above has soft rst == 0.

함정 · rand 를 어디에 붙이나Trap · where rand goes

구별 기준은 "이 field 를 누가 채우나" 하나다. sequence 가 정해서 driver 가 핀으로 내보낼 값(is_write, slot, wdata)은 rand. DUT 가 돌려주고 monitor 가 핀에서 읽어 채울 값(rdata, 슬라이드의 data_out)은 rand 가 아니다. 출력 field 에 rand 를 붙여도 컴파일은 되지만, 보내는 쪽에서는 의미 없는 값이 들어가고 그 값이 로그에 찍혀 "DUT 가 이 값을 냈나?" 하는 헷갈림만 남는다. rand 가 없는 field 는 randomize() 가 건드리지 않으니 새로 만든 item 에서는 0 이다.

The one test is who fills the field. Values the sequence decides and the driver puts on pins (is_write, slot, wdata) get rand. Values the DUT returns and the monitor reads off the pins (rdata, the slide's data_out) don't. A rand on an output field compiles fine, but the sending side fills it with a meaningless value that then shows up in logs and leaves you wondering whether the DUT produced it. A field without rand is untouched by randomize(), so it's 0 in a freshly created item.

Lecture 13 의 손잡이가 여기 달린다. Lecture 13 의 05절이 constraint 를 "어디로 random 을 몰아갈지" 정하는 손잡이로 설명했다. UVM 에서는 그 손잡이가 두 층에 갈린다. item class 안의 constraint(여기)는 "이 프로토콜에서 합법인 값" 처럼 언제나 지킬 규칙이고, sequence 가 거는 inline constraint(03절)는 "이번 시나리오에서는 쓰기만" 처럼 그때그때 바꿀 의도다. 앞의 것을 item 에, 뒤의 것을 sequence 에 두면 item 을 고치지 않고 sequence 만 늘려 시나리오를 늘린다.

Lecture 13's knobs get mounted here. Lecture 13, §05 described constraints as knobs for steering randomness. In UVM those knobs split over two layers: constraints inside the item class (here) are rules that always hold, like "legal for this protocol", and inline constraints a sequence adds (§03) are intent that changes per scenario, like "writes only this time". Put the first in the item and the second in sequences, and you grow scenarios by adding sequences without touching the item.

rst == 0(class)과 rst == 1(inline)은 함께 만족할 수 없으니 randomize() 가 실패하고 0 을 돌려준다. SV 규칙상 실패한 randomize 는 변수를 하나도 바꾸지 않는다. item 은 방금 factory 로 만든 것이라 모든 field 가 기본값 0 이다. 그러니 driver 는 rst = 0, is_write = 0, slot = 0, 즉 slot 0 에서 읽기 하나를 받는다. reset 대신 평범한 읽기가 나간 것이다. 로그에는 `uvm_do_with 가 찍은 UVM_WARNING(RNDFLD, "Randomization failed in uvm_do_with action") 하나뿐이고, UVM_ERROR 는 0 이라 report 만 보면 통과다. 고치는 법은 soft 를 되살리는 것이고, 재발을 막으려면 위 손으로 쓴 판처럼 실패를 `uvm_error 로 올리거나 RNDFLD warning 을 error 로 격상하는 설정을 둔다. 01절에서 soft 를 쓴 이유가 이것이다.

rst == 0 (class) and rst == 1 (inline) can't both hold, so randomize() fails and returns 0. By SV's rules a failed randomize changes no variables, and the item was just built by the factory, so every field is its default 0. The driver therefore gets rst = 0, is_write = 0, slot = 0: a read of slot 0, an ordinary read instead of a reset. The log has only the UVM_WARNING from `uvm_do_with (RNDFLD, "Randomization failed in uvm_do_with action"), and UVM_ERROR is 0, so the report reads as a pass. The fix is to restore soft; to stop it recurring, promote failures to `uvm_error as in the hand-written version above, or configure the RNDFLD warning to be upgraded to an error. That's why §01 uses soft.

8쪽의 말도 두 줄이다. sequence 안에서 sequence 를 만든다. 그리고 `uvm_do* macro 는 item 뿐 아니라 안에 넣은 다른 sequence 에도 쓸 수 있다. 작은 상자의 자식 sequence 는 주소 하나를 rand 변수로 갖고, 그 값으로 item 의 address 를 묶어 item 하나를 보낸다. 큰 상자의 부모 sequence 는 자식 sequence handle 셋을 rand 로 선언하고, body() 에서 첫째는 `uvm_do 로, 둘째와 셋째는 `uvm_do_with 로 자식의 주소 변수에 서로 다른 조건(한쪽은 8'h80 보다 작게, 한쪽은 8'hFF 로)을 걸어 차례로 돌린다.

함정 · inline constraint 안의 이름은 누구의 것인가Trap · whose name is it inside an inline constraint?

randomize() with { ... } 안의 이름은 먼저 randomize 되는 object 안에서 찾고, 거기 없을 때만 그 호출을 적은 쪽(지금 sequence)에서 찾는다(IEEE 1800 의 randomize with 이름 규칙, Lecture 12 의 19절 보충). 위 rd_at_seq 에서 slot 은 item 의 것이고, base 는 item 에 없으니 sequence 의 것으로 찾아진다. 그런데 item 에도 같은 이름의 field 가 있으면 item 쪽이 이겨서 slot == base 가 "item 의 slot 이 item 의 base 와 같다" 가 되어 버린다. 그래서 sequence 쪽 변수라는 것을 못 박는 local:: 을 붙였다.

Names inside randomize() with { ... } are looked up first in the object being randomized, and only if not found there, in the scope that wrote the call (the current sequence): IEEE 1800's name rule for randomize with, a supplement to Lecture 12, §19. In rd_at_seq above, slot is the item's, and base, not being in the item, is found in the sequence. But if the item had a field of the same name, the item's would win, and slot == base would mean "the item's slot equals the item's base". Hence the local::, which pins it to the sequence's variable.

8쪽의 자식 sequence 는 이 자리에 this. 를 붙여 sequence 의 주소 변수를 가리키려 한다. Verification Academy 포럼의 답변들은 with 블록 안의 this 도 randomize 되는 object(여기서는 item)를 가리킨다고 설명한다. 그렇다면 this. 뒤의 이름을 item class 에서 찾게 되는데, 슬라이드의 item 에는 그 이름(addr)이 없고 address 만 있다. 이 노트는 시뮬레이터로 돌려 보지 않았으므로 확인이 필요한 지점으로 남기되, 의도대로 쓰려면 local::addr 로 적는 것이 안전하다. 부모 쪽 `uvm_do_with(subseqB, { subseqB.addr < ... }) 는 문제가 없다. subseqB 라는 이름이 자식 class 안에 없으니 부모 쪽에서 찾아지고, 그 handle 이 마침 randomize 되는 바로 그 object 다.

Slide 8's child sequence puts this. in that spot to point at the sequence's address variable. Answers on the Verification Academy forum explain that this inside a with block also refers to the object being randomized (the item here). If so, the name after this. is looked up in the item class, and the slide's item has no such name (addr), only address. This note hasn't run it on a simulator, so it's left as a point to check; to get the intended meaning, writing local::addr is the safe form. The parent's `uvm_do_with(subseqB, { subseqB.addr < ... }) is fine: the name subseqB doesn't exist inside the child class, so it's found in the parent, and that handle happens to be the very object being randomized.

하나 더. 8쪽의 부모 sequence 는 자식 handle 셋에 rand 를 붙였다. 이 흐름에서는 하는 일이 없다. `uvm_do 가 자식을 새로 만들고 그 자리에서 randomize 하기 때문이다. handle 의 rand 는 부모 자신이 randomize 될 때 이미 만들어져 있는 자식 object 까지 같이 randomize 하라는 뜻이다.

One more thing: slide 8's parent marks its three child handles rand. In this flow that does nothing, because `uvm_do builds each child fresh and randomizes it on the spot. rand on a handle means "when the parent itself is randomized, also randomize the child object it already holds".

함정 · import 와 `include 는 다른 일을 한다Trap · import and `include do different jobs

구별 기준은 "이름을 빌려 보나, 글자를 복사해 넣나" 다. import 는 이미 컴파일된 package 안의 이름을 보이게만 한다. `include 는 전처리 단계에서 파일의 글자를 그 자리에 붙여 넣는다. 그래서 같은 class 파일을 두 package 에 각각 `include 하면 글자는 같아도 서로 다른 두 type(mem_env_pkg::mem_req 와 mem_test_pkg::mem_req)이 생기고, 한쪽 handle 을 다른 쪽에 넣으려는 순간 type 이 안 맞는다는 컴파일 오류가 난다. SV 에서 class 의 type 은 이름만이 아니라 선언된 자리(scope)로 정해지기 때문이다. class 파일은 package 한 곳에만 include 하고 나머지는 import 로 빌려 쓰는 것이 11쪽 구조의 숨은 규칙이다(슬라이드 밖 보충).

The deciding question is "borrowing names, or pasting text?" import only makes visible names inside an already-compiled package; `include pastes a file's text in place at preprocessing time. So `include the same class file into two packages and, despite identical text, you get two different types (mem_env_pkg::mem_req and mem_test_pkg::mem_req); the moment you assign a handle of one to the other, compilation fails on a type mismatch. In SV a class's type is set not only by its name but by the scope it's declared in. Include each class file into exactly one package and borrow it everywhere else with import: that's the unwritten rule behind slide 11's structure (supplement, not from the slides).

함정 · 선언 안 한 net 은 1 bit 다Trap · an undeclared net is 1 bit

13쪽은 DUT 를 sigA, sigB, sigC, ack, dout 라는 이름에 잇고 assign 으로 interface 와 연결하는데, 이 다섯을 선언하는 줄이 보이지 않는다. Verilog 와 SV 는 port 연결이나 assign 의 왼쪽에 선언 안 된 이름이 나오면 1 bit 짜리 implicit net 을 만들어 준다. 그러면 signalB(16 bit), signalC 와 dout(32 bit)이 1 bit 선을 지나며 최하위 bit 하나만 남는다. 예를 들어 interface 의 signalB 가 16'h00A5 여도 DUT 에는 16'h0001 이 들어간다(A5 의 최하위 bit 1 만 살고 나머지 15 bit 는 0). 컴파일은 경고만 내고 통과하므로 "UVM 이 값을 이상하게 보낸다" 로 오해하기 쉽다. 슬라이드가 지면 때문에 선언을 뺐을 가능성이 크지만, 그대로 옮기면 이렇게 된다. 막는 법은 둘이다. 위 노트판처럼 DUT port 를 interface 신호에 바로 잇거나, 파일 맨 위에 `default_nettype none 을 두어 선언 안 된 이름을 컴파일 오류로 만든다.

Slide 13 connects the DUT to names sigA, sigB, sigC, ack and dout and ties them to the interface with assigns, but no line declares those five. Verilog and SV create a 1-bit implicit net for an undeclared name in a port connection or on the left of an assign. Then signalB (16 bits) and signalC and dout (32 bits) pass through a 1-bit wire and only their LSB survives. If the interface's signalB is 16'h00A5, the DUT gets 16'h0001 (A5's LSB, 1, survives; the other 15 bits are 0). Compilation passes with only warnings, so it's easy to misread as "UVM is sending odd values". The slide most likely dropped the declarations for space, but copied as is, this is what happens. Two defences: connect DUT ports straight to interface signals, as in the version above, or put `default_nettype none at the top of the file so undeclared names become compile errors.

위 네 줄은 phase(보라 이름)와 그 안에서 도는 sequence(분홍 막대), 맨 아래 줄은 driver 가 실제로 처리한 item 의 순서다. 칸 하나가 10 ns 이고 아래 눈금이 ns 다.

  3. configure, 0 ns long: 아무도 objection 을 올리지 않은 phase 는 시작하자마자 끝난다. 20 ns 의 세로선이 그 자리다. pre_, post_ phase 들도 같은 이유로 길이가 0 이라 그리지 않았다
  4. main_phase, burst_seq 20..80: 20 ns 에 main 이 시작해 burst 를 띄운다. 그런데 mix 가 아직 둘 남아 있다. 두 sequence 가 sequencer 에서 번갈아 grant 를 받아 driver 줄이 mix 2, burst 1, mix 3, burst 2 로 섞인다. 옅은 amber 의 mix 2, mix 3 이 main 의 트래픽 사이에 끼어든 item 이다. mix 3 이 50 ns 에 끝나 run_phase 쪽 objection 이 내려가고, 그 뒤는 burst 3, 4 만 간다
  5. 끝, 80 ns: main_phase 가 80 ns 에 내린다. run_phase 와 run-time phase 가 둘 다 내려갔으므로 그때 extract 이후로 넘어간다

그래서 16쪽의 test 는 "reset 하고 나서 트래픽" 을 의도했지만 실제로는 reset 전에 트래픽이 하나 나갈 수 있고, reset 뒤의 트래픽도 부모의 sequence 와 섞인다. 위 노트판 코드처럼 빈 run_phase 를 두면 run_phase 줄이 비고, driver 줄은 rst(0~10), burst 1~4(10~50) 로 깨끗하게 끝난다. 12절 도구에서 둘을 바꿔 가며 볼 수 있다.

The top four rows are phases (violet names) with the sequences running in them (pink bars); the bottom row is the order the driver actually handled items. Each cell is 10 ns; the ticks below are ns.

  1. run_phase, inherited, mix_seq 0..50: the parent test's run_phase raises an objection at time 0 and launches §04's mix_seq (three items). It starts at the same moment as, and alongside, the run-time phases. Its third item finishes at 50 ns and it drops
  2. reset_phase, rst_seq 0..20: at the same time 0 the reset sequence starts too. Two sequences queue on the same sequencer at once, so the sequencer decides the order (arbitration). Here mix wins the first grant, so the driver row's first cell, mix 1 (0 to 10 ns), reaches the DUT before the reset: dark amber. Then rst (10 to 20 ns) goes, rst_seq finishes and drops, and reset_phase ends at 20 ns
  3. configure, 0 ns long: a phase in which nobody raises an objection ends as soon as it starts; the vertical line at 20 ns is where it sits. The pre_ and post_ phases are zero-length for the same reason and aren't drawn
  4. main_phase, burst_seq 20..80: main starts at 20 ns and launches burst, but mix still has two items left. The two sequences take turns getting grants, so the driver row interleaves mix 2, burst 1, mix 3, burst 2; the lighter-amber mix 2 and mix 3 are items wedged into main's traffic. mix 3 ends at 50 ns and the run_phase side drops; after that only burst 3 and 4 go
  5. The end, 80 ns: main_phase drops at 80 ns. Now both run_phase and the run-time phases have dropped, so things move on to extract and beyond

So slide 16's test means "reset, then traffic", but in fact one traffic item can go out before the reset, and the traffic after it mixes with the parent's sequence. With an empty run_phase as in this note's code, the run_phase row is empty and the driver row is a clean rst (0 to 10) then burst 1 to 4 (10 to 50). §12's tool lets you flip between the two.

The parent test's run_phase. 답 보기Show answer

full name 에서 sequencer 부분(uvm_test_top.env.agt.sqr)을 떼면 top.cfg.wr2 가 남는다. 이것이 sequence 의 사슬이다. test 가 sequencer 위에서 직접 띄운 것이 top(depth 1), top 의 body() 가 `uvm_do(cfg) 로 돌린 것이 cfg(depth 2), cfg 의 body() 가 `uvm_do(wr2) 로 돌린 것이 wr2(depth 3), 그리고 wr2 의 body() 가 보낸 item 이라 depth 4 다. 그러니 이 item 을 만든 코드는 wr2 의 class 의 body() 이고, 그 위로 sequence 가 셋(top, cfg, wr2)이다. 이름이 변수 이름에서 오므로(03절 그림 1 번) cfg 의 class 안에서 wr2 라는 변수를 찾으면 그 class 가 나온다.

Strip the sequencer part (uvm_test_top.env.agt.sqr) from the full name and top.cfg.wr2 is left: the chain of sequences. top (depth 1) is what the test started directly on the sequencer; cfg (depth 2) is what top's body() ran with `uvm_do(cfg); wr2 (depth 3) is what cfg's body() ran with `uvm_do(wr2); and the item, sent by wr2's body(), is depth 4. So the code that made it is the body() of wr2's class, with three sequences above it (top, cfg, wr2). Since names come from variable names (step 1 in §03's picture), find the variable wr2 inside cfg's class and you have the class.

What this tool simplifies. It doesn't run real UVM; it's JavaScript mimicking only phase starts and ends and the sequencer's queue.

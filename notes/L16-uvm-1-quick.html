Lecture 16
UVM 1

run_test() 한 줄이 시뮬레이션을 넘겨받고, test 가 component 를 짓고, 모두가 같은 phase 를 밟고, run 은 objection 이 다 내려가야 끝난다. 핀은 driver 와 monitor 만 만진다.

One run_test() call takes over the simulation, the test builds the components, everyone walks the same phases, and the run ends only when every objection is dropped. Only the driver and monitor touch pins.

run_test 와 test

run_test and the test

슬라이드 4~8쪽. UVM 은 testbench 를 걸어 둘 framework 다. 어느 testbench 든 같은 모양(코드 배치, configuration database, 메시지, component 계층)이고, 한 번 컴파일하고 여러 번 돌린다. 7쪽의 대비가 요점이다.

Slides 4 to 8. UVM is a framework to hang your testbench on: every testbench has the same shape (code layout, configuration database, messaging, component hierarchy), and you compile once, simulate many times. Slide 7's contrast is the point.

  • 옛 방식: test module 이 tb_top.dut.signalA 같은 계층 경로로 핀을 직접 건드리고, 기다리고, 비교하고, $finish 한다. 다 한 블록에 엉켜 있다
  • Old way: a test module pokes pins through hierarchical paths like tb_top.dut.signalA, waits, compares and calls $finish, all tangled in one block
  • 새 방식: top 의 initial 에서 run_test("my_test") 한 줄. 나머지는 UVM 이 한다. 실행 명령줄의 +UVM_TESTNAME=... 가 인자보다 이긴다(보충)
  • New way: one line, run_test("my_test"), in the top's initial; UVM does the rest. +UVM_TESTNAME=... on the command line beats the argument (supplement)
  • 8쪽: test 가 감독이다. run_test 가 test object 를 만들고 끝까지 끌고 가고, test 는 phase 마다 env 를 짓고 설정하고 sequence 를 띄운다. env 는 같은 virtual method 로 testbench 를 설정한다
  • Slide 8: the test is the director. run_test creates the test object and carries the run to the end; the test builds and configures the env and launches sequences phase by phase; the env configures the testbench through the same virtual methods
함정 · 시나리오 차이는 test 에Trap · scenario differences go in the test

env 는 블록마다 한 번 짜서 여러 test 가 공유한다. test 마다 달라지는 것을 env 에 분기로 넣지 않는다. 4쪽 "each test describes the intent".

An env is written once per block and shared by many tests. Don't put per-test differences into the env as branches; slide 4's "each test describes the intent".

Phase 와 objection

Phases and objections

슬라이드 9~13쪽. 구별 기준은 시간을 쓰나다. function 은 시간을 못 쓰고(짓기, 설정, 확인), task 는 쓸 수 있다(reset, stimulus, 기다리기, 샘플링).

Slides 9 to 13. The deciding question is does it take time? Functions can't (building, configuring, checking); tasks can (reset, stimulus, waiting, sampling).

시점Whenphase종류Kind
t = 0build, connect, end_of_elaboration, start_of_simulationfunction
t ≥ 0run (와 나란히 reset, configure, main, shutdown, 각각 pre_/post_)run (alongside it reset, configure, main, shutdown, each with pre_/post_)task
t = Nextract, (check), report, finalextract, (check), report, finalfunction
  • 12쪽: build_phase 는 top-down(부모가 있어야 자식을 만든다), 나머지는 bottom-up. 보충: final_phase 는 top-down 이고, run_phase 는 모든 component 가 동시에 시작한다
  • Slide 12: build_phase runs top-down (a parent must exist to create its children), the others bottom-up. Supplement: final_phase is top-down, and every component's run_phase starts at once
  • 13쪽: 바쁜 component 는 phase.raise_objection(this) 로 손을 들고 끝나면 phase.drop_objection(this). 수가 0 이 되면 task phase 가 끝난다. 예: transaction 이 끝나기를 기다리는 monitor
  • Slide 13: a busy component raises its hand with phase.raise_objection(this) and drops it with phase.drop_objection(this); when the count hits zero, the task phase ends. Example: a monitor waiting for a transaction to finish
함정 · 0 ns 에 끝나는 testTrap · the test that ends at 0 ns

아무도 raise 하지 않으면 run_phase 는 시작하자마자 끝나고, stimulus 0 개, 에러 0 개로 통과처럼 보인다. 반대로 drop 을 빠뜨리면 timeout 까지 돈다. 그리고 슬라이드는 check_phase 를 빠뜨렸다. UVM 의 끝 묶음은 extract, check, report, final 넷이다.

If nobody raises, run_phase ends as soon as it starts, with zero stimulus and zero errors: it looks like a pass. Forget a drop and it runs to the timeout. Also, the slides omit check_phase; UVM's closing group is extract, check, report, final.

Component 와 object

Components and objects

슬라이드 14~15쪽. 모든 class 는 object 이고, 그중 특별한 부분집합이 component 다. component 는 phase 를 밟고, 시간 0 에만 만들어져 끝까지 산다(uvm_test, uvm_env, uvm_agent, uvm_driver, uvm_monitor, uvm_sequencer, uvm_scoreboard). uvm_sequence_item, uvm_transaction 의 object 는 계속 생겼다 사라진다. 생성자로 구별한다: new(name, parent) 는 component, new(name) 은 object.

Slides 14 to 15. Every class is an object; a special subset are components, which walk the phases and are built only at time 0 and live to the end (uvm_test, uvm_env, uvm_agent, uvm_driver, uvm_monitor, uvm_sequencer, uvm_scoreboard). Objects of uvm_sequence_item and uvm_transaction keep coming and going. Tell them apart by the constructor: new(name, parent) for components, new(name) for objects.

함정 · hierarchy 가 둘Trap · two hierarchies

15쪽의 class hierarchy 는 상속(무엇을 extends 하나), 12쪽의 component hierarchy 는 포함(무엇 안에 있나)이다. class 로는 uvm_agent 와 uvm_driver 가 형제지만, testbench 안에서는 agent 가 driver 를 담는다. 보충: uvm_sequence 도 uvm_sequence_item 의 자손, 곧 object 다.

Slide 15's class hierarchy is inheritance (what extends what); slide 12's component hierarchy is containment (what's inside what). As classes, uvm_agent and uvm_driver are siblings; in a testbench the agent contains the driver. Supplement: uvm_sequence also descends from uvm_sequence_item, so it's an object.

Transaction 과 agent

Transactions and agents

슬라이드 16~19쪽. transaction 은 핀의 세부에서 떨어진 높은 수준의 데이터(uvm_sequence_item)이고, transactor 는 핀에 닿는 낮은 층의 component 다. driver 는 능동적으로 입력을 움직이고, monitor 는 수동적으로 지켜본다. sequence 는 item 의 모음, sequencer 는 한 가지 item type 의 sequence 만 풀어 driver 에게 넘기고, driver 는 item 을 하나씩 당겨 간다(응답은 선택).

Slides 16 to 19. A transaction is high-level data abstracted from pin details (uvm_sequence_item); a transactor is a low-level component that touches pins. The driver actively drives inputs; the monitor passively watches. A sequence is a collection of items; a sequencer unpacks sequences of one item type for the driver, which pulls items one at a time (responses optional).

TLM 과 resource_db

TLM and resource_db

슬라이드 20~25쪽. TLM 은 component 끼리 transaction 을 주고받는 연결이다. port 는 요청만 하고(driver), export 는 그 요청을 구현해 응하고(sequencer), analysis port 는 여러 구독자에게 뿌리고(monitor → scoreboard, coverage), FIFO 는 담아 두는 queue 다. 사용자는 connect_phase 에서 connect() 만 부른다. Lab 4 의 monitor → mailbox → scoreboard 가 그 이전 판이다.

Slides 20 to 25. TLM is how components pass transactions. A port only requests (driver), an export implements and answers (sequencer), an analysis port broadcasts to many subscribers (monitor → scoreboard, coverage), a FIFO is a queue. You just call connect() in connect_phase. Lab 4's monitor → mailbox → scoreboard is the earlier version.

class 는 계층 경로로 DUT 에 닿을 수 없다(22쪽 "illegal cross-module reference". 보충: package 안의 항목은 계층 참조를 못 쓴다). 그래서 top module 이 interface instance 의 handle 을 uvm_resource_db#(virtual ...)::set 으로 넣고, driver 가 read_by_name 으로 받아 virtual interface 로 핀을 움직인다(24~25쪽). UVM 코드에서는 그 위에 얹은 uvm_config_db 를 더 자주 본다(보충).

A class can't reach the DUT through a hierarchical path (slide 22's "illegal cross-module reference"; supplement: items in a package can't use hierarchical references). So the top module stores the interface instance's handle with uvm_resource_db#(virtual ...)::set, and the driver fetches it with read_by_name and drives pins through the virtual interface (slides 24 to 25). In UVM code you'll more often see uvm_config_db, layered on top (supplement).

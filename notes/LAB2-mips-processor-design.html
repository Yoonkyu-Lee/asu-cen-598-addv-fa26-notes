이 Lab 이 하는 일

What this lab does

설계를 백지에서 시작하지 않는다. 돌아가는 single-cycle 프로세서를 받아서, 같은 명령어를 내면서 다섯 배 겹쳐 돌게 고친다. 겹치는 순간 생기는 문제를 막는 것이 이 Lab 의 본체다.

You don't start from a blank page. You get a working single-cycle processor and rework it so that it runs the same instructions with five of them overlapping. Handling what breaks the moment they overlap is the real body of this lab.

Lab 2 는 두 부분이다. Part 1 (60점)은 강의 서버 Apporto 의 /usr/local2/COURSES/ADDV/LAB2 에 있는 non-pipelined MIPS 를 5단 pipeline 으로 바꾸고, hazard 를 막고, 검증하고, 합성해서 성능을 비교하는 것이다. Part 2 (40점)는 그 pipeline 에 명령어 두 개, MULADD 와 perfmon 을 새로 넣는 것이다. 지원하는 명령어는 처음부터 여덟 개뿐이다: add, sub, and, or, slt, lw, sw, beq.

Lab 2 has two parts. Part 1 (60 points) takes the non-pipelined MIPS in /usr/local2/COURSES/ADDV/LAB2 on the Apporto server, turns it into a 5-stage pipeline, handles the hazards, verifies it, and synthesises it to compare performance. Part 2 (40 points) adds two new instructions to that pipeline, MULADD and perfmon. The instruction set is small from the start, just eight: add, sub, and, or, slt, lw, sw, beq.

Lecture 6 이 이 Lab 의 이론 전부다. 이 페이지는 개념을 다시 설명하지 않고 L06 노트의 해당 절로 보낸다. 특히 세 곳: forwarding 조건식(07절, 슬라이드 35쪽), load-use stall 조건식(같은 절, 슬라이드 39쪽), 분기 판정을 Decode 로 당기는 이야기(08절, 슬라이드 42~46쪽). L06 노트도 "그 조건식이 그대로 RTL 이 된다" 고 적어뒀다. 이 페이지가 하는 일은 그 이론을 이 과제의 규칙(ADD 만 forwarding, BEQ 만 flush, 나머지는 stall) 위에 올려놓는 것이다.

Lecture 6 is the whole theory for this lab. This page doesn't re-teach it; it points into the matching sections of the L06 notes. Three places in particular: the forwarding condition (section 07, slide 35), the load-use stall condition (same section, slide 39), and moving branch resolution into Decode (section 08, slides 42 to 46). The L06 notes already say those conditions become RTL more or less verbatim. What this page adds is laying that theory over this lab's specific rules: forward only for ADD, flush only for BEQ, stall for the rest.

Read with five questions in hand. Every one of them feeds a decision you'll make from Task 2 onward.

  1. 정말 single-cycle 인가? imem 과 dmem 이 따로 있다는 것은 single-cycle 구조와 맞는다 (명령어와 데이터를 같은 사이클에 읽어야 하니까). 그러면 CPI 는 1 이다. 코드로 확인해라. 성능 표(11절)의 기준선이 이 숫자다.
  2. register file 은 clock 의 어느 쪽에서 쓰나? WB 에서 쓰는 사이클에 ID 가 같은 register 를 읽을 수 있는지가 여기서 갈린다. stall 사이클 수가 하나 달라진다 (07절).
  3. 분기 주소와 분기 조건은 어디서 계산되나? beq 를 몇 번째 단계에서 판정할지 정하는 재료다 (06절).
  4. controller 는 무엇을 입력으로 받나? single-cycle 에서는 opcode, funct 와 함께 ALU 의 zero 같은 것을 받아 분기를 정하는 경우가 많다. pipeline 에서는 zero 가 나오는 단계와 opcode 가 있는 단계가 달라진다.
  5. top 의 포트는 무엇이고 testbench 는 그중 무엇을 보나? top 의 interface 는 바꾸면 안 된다 (02절). testbench 가 보는 신호가 곧 검증할 수 있는 전부다 (09절).
  1. Is it really single-cycle? Separate imem and dmem fit a single-cycle design (it has to read an instruction and data in the same cycle). If so, CPI is 1. Confirm it in the code: that number is the baseline in the performance table (section 11).
  2. On which clock edge does the register file write? That decides whether ID can read a register in the same cycle WB writes it, which changes stall counts by one (section 07).
  3. Where are the branch target and branch condition computed? That's the raw material for deciding which stage resolves beq (section 06).
  4. What are the controller's inputs? In single-cycle designs it often takes something like the ALU's zero flag along with opcode and funct to decide a branch. In a pipeline, the stage that has zero and the stage that has the opcode are no longer the same.
  5. What are top's ports, and which does the testbench watch? The top interface must not change (section 02). Whatever the testbench watches is the whole of what you can check (section 09).

두 번째 제약이 특이하다. datapath 파일 안에서 코드가 나오는 순서를 정해준다. Fetch 로직, Fetch→Decode register, Decode 로직(register file 인스턴스 등), Decode→Execute register, Execute 로직(ALU 인스턴스 등), Execute→Memory register, Memory 로직(있다면), Memory→Writeback register, Writeback 로직. 채점자가 파일을 위에서 아래로 읽으면서 pipeline 을 왼쪽에서 오른쪽으로 따라갈 수 있게 하려는 것으로 보인다.

The second constraint is unusual: it fixes the order code appears in inside the datapath file. Fetch logic, Fetch-to-Decode registers, Decode logic (register file instance and so on), Decode-to-Execute registers, Execute logic (ALU instance and so on), Execute-to-Memory registers, Memory logic (if any), Memory-to-Writeback registers, Writeback logic. The point seems to be that a grader reading the file top to bottom can follow the pipeline left to right.

The circled numbers are the order in the file. Odd (1, 3, 5, 7, 9) are stage logic, even (2, 4, 6, 8) are pipeline registers. Five stages have four boundaries, hence four register banks.

The blue arrow along the top is the only line running right to left. Region 9 writes what region 3 reads: the register file is instantiated in the Decode region but written from Writeback, so the write port of an instance in region 3 connects to signals from region 9. If you declare those signals down in region 9, using them in region 3 comes before the declaration and the compiler may complain. Declare all signals at the top of the file and keep only the logic in order, and the problem disappears.

The grey arrow at the bottom is the direction you read the file, not the direction data flows.

You also have to decide where the control signals' pipeline registers go. If the controller produces control in Decode and you carry those signals in the datapath's pipeline registers, everything fits inside the nine regions the lab asks for. Designs that keep separate registers inside the controller are common too. The lab only speaks to the datapath's order, not the controller's insides. Either way, say where you put them in one line of the report's code-change summary.

pipeline register 의 네 동작

Four things a pipeline register does

Task 4 로 가기 전에 어휘부터 맞춘다. Lab 2 릴리스 덱 4쪽이 표 하나로 정리했고, 여기서 제일 헷갈리는 것이 bubble 과 flush 의 차이다.

Before Task 4, line up the vocabulary. Slide 4 of the Lab 2 release deck puts it in one table, and the part that trips people is the difference between a bubble and a flush.

덱은 pipeline register 한 단이 매 사이클 할 수 있는 일을 넷으로 나눈다. 각 단에 valid 비트가 있다고 놓고, 그 비트와 데이터가 어떻게 되는지로 정의한다.

The deck splits what one pipeline register bank can do in a cycle into four operations. It assumes each bank has a valid bit and defines each operation by what happens to that bit and the data.

동작Operation뜻Meaningregister 에 일어나는 일What the register does
Advance 다음 명령어를 받는다take the next instruction data ← next_data, valid ← next_valid
Stall / Hold 지금 명령어를 여기 붙들어 둔다keep the current instruction here 아무것도 안 바뀐다nothing changes
Bubble 이 단계로 아무 명령어도 들어오지 않는다no instruction enters this stage valid ← 0
Flush / Kill 이미 있던 명령어를 실행하면 안 된다the instruction already here must not execute valid ← 0

마지막 두 줄을 봐라. register 에 하는 일은 똑같이 valid ← 0 이다. 덱이 둘을 가르는 기준은 동작이 아니라 원인이다. 덱의 문장을 줄여 옮기면: bubble 은 어떤 명령어가 그 단계로 못 넘어와서 생긴 빈자리이고, flush 는 멀쩡히 들어와 있던 명령어를 더는 실행하면 안 돼서 없애는 것이다.

Look at the last two rows. The register does exactly the same thing in both: valid ← 0. The deck separates them by cause, not by action. Paraphrasing its wording: a bubble is an empty slot that appears because an instruction could not advance into that stage; a flush destroys an instruction that was validly there because it is no longer allowed to execute.

덱 5쪽이 한 단(ID/EX)을 코드로 보여준다. 우선순위가 reset, flush, stall 순서라는 것이 요점이다.

Slide 5 of the deck shows one bank (ID/EX) as code. The point is the priority: reset, then flush, then stall.

always_ff @(posedge clk) begin
  if (reset)
    ex_valid <= 1'b0;
  else if (flush)
    ex_valid <= 1'b0;
  else if (!stall) begin
    ex_valid <= id_valid;
    ex_data  <= id_data;
  end
end

세 갈래를 표와 맞춰 읽으면 이렇다. flush 면 valid 만 0 으로 내리고 데이터는 그냥 둔다(valid 가 0 이면 데이터는 아무도 안 본다). stall 이면 어느 대입도 안 일어나니 그대로 붙들린다. 둘 다 아니면 advance 다. bubble 은 이 코드에 따로 없다. 앞 단계가 멈췄는데 이 단이 advance 하면, 앞에서 넘어오는 id_valid 가 0 이어서 저절로 bubble 이 된다.

Reading the three branches against the table: on flush, only valid drops to 0 and the data is left alone (nobody looks at data whose valid is 0). On stall, no assignment fires, so it holds. Otherwise it advances. There's no separate bubble branch: if the stage in front stalls while this bank advances, the incoming id_valid is 0 and a bubble appears on its own.

  • add $5, $6, $7 (주황): beq 바로 다음 주소(PC+4)의 명령어. 2 사이클에 이미 F 에 들어왔다. 그때는 분기 결과를 몰랐으니 다음 주소를 가져오는 게 맞았다. 2 사이클 끝에 taken 이 확정되자 이 명령어는 실행되면 안 된다. 3 사이클에 D 로 넘어가는 대신 지워진다(×). 이게 flush 다
  • L: and $8, $5, $6: 분기 목적지. 3 사이클에 F, 이후 정상 진행

범례의 네 칸이 04절 표의 네 줄이다. 파란 칸은 advance, 점선 파란 칸은 stall, 점선 회색 칸은 bubble, 주황 칸은 flush. A 의 bubble 은 "못 넘어와서 생긴 빈자리" 이고, B 의 주황은 "들어와 있던 것을 지운 자리" 다. 둘 다 valid 를 0 으로 만드는 것은 같다.

Across is cycle number 1 to 8, down is instructions. The letter in a cell is the stage (F, D, E, M, W) the instruction is in that cycle. Cells come in four styles, per the legend at the bottom.

A, row by row.

  • lw $1, 0($0): load memory at address $0+0 = 0 into $1. F D E M W in cycles 1 to 5. The value comes out of memory only at the end of cycle 4 (M)
  • add $4, $1, $5: needs $1. F in cycle 2, D in 3. It would normally be in E in cycle 4, but $1 doesn't exist yet at the start of that cycle (lw is still in M). So it is held in D for cycle 4 as well (dashed blue cell, a stall). In cycle 5's E it takes lw's value from MEM/WB by forwarding. M in 6, W in 7
  • bubble: because add couldn't move into E in cycle 4, E is empty in cycle 4. That empty slot flows on through M in 5 and W in 6 (dashed grey). It does nothing, which is why the row is labelled bubble rather than an instruction
  • sw $4, 8($0): the instruction after add. F in cycle 3. Since add won't leave D, it is held in F in cycle 4 (a stall). D in 5, and in E in 6 it takes add's $4 from EX/MEM. In M in 7 it writes $4 to address $0+8 = 8. W in 8

"ADD 만" 은 무슨 뜻인가

What "ADD only" means

과제 문장은 forwarding 이 ADD 에 대해서만 필수라는 것이다. 금지가 아니라 최소선이다. 그리고 L06 의 조건식에는 opcode 가 안 들어간다. RegWriteM 과 register 번호만 본다. 그 식을 그대로 쓰면 add 뿐 아니라 sub, and, or, slt 결과도 같은 회로로 forwarding 된다. 오히려 "add 일 때만" 으로 좁히려면 opcode 검사를 일부러 더 넣어야 한다. 어느 쪽을 택하든 상관없지만, 무엇을 택했는지 리포트에 한 줄 적고 그에 맞게 나머지를 stall 로 막아야 한다.

The lab's wording is that forwarding is required only for ADD. That's a floor, not a ban. And L06's condition has no opcode in it: it looks only at RegWriteM and register numbers. Use it as written and sub, and, or and slt results get forwarded by the same circuit as add. Narrowing it to "only when it's an add" would actually mean adding an opcode check on purpose. Either choice is fine, but say which you chose in one line of the report and make sure everything outside it stalls.

lw 가 MEM 에 있을 때 ALUOutM 은 주소다When lw is in MEM, ALUOutM is an address

L06 식을 그대로 쓰면 lw 도 RegWriteM 이 1 이라 MEM 단계 조건에 걸린다. 그런데 lw 가 MEM 에 있을 때 ALUOutM 은 계산한 메모리 주소이지 읽어온 값이 아니다. 그 사이클에 forwarding 이 일어나면 다음 명령어가 주소를 데이터로 받아서 조용히 틀린다. 슬라이드 39쪽의 lwstall 이 이걸 막는다. 한 사이클 멈춰서 lw 가 WB 로 간 다음에야 ResultW(메모리 값)를 받게 한다. forwarding 을 L06 식 그대로 넣었다면 lwstall 도 반드시 같이 넣어라. 둘은 한 벌이다.

Using L06's condition as written, lw also has RegWriteM = 1, so it matches the MEM condition. But while lw is in MEM, ALUOutM holds the computed memory address, not the loaded value. If forwarding fires that cycle, the next instruction silently takes the address as data. flush 가 실제로 지워야 하는 것

What a flush actually has to wipe

지운 명령어는 아무 상태도 바꾸면 안 된다. 바꿀 수 있는 상태는 두 개다. register file(RegWrite)과 dmem(MemWrite). 그러니 flush 의 최소 조건은 지워진 칸의 RegWrite 와 MemWrite 가 0 이 되는 것이다. 덱 5쪽처럼 단마다 valid 를 두고 쓰기 신호를 valid 와 AND 하든, register 를 통째로 0 으로 비우든(모든 control 이 0 인 칸은 아무것도 안 쓴다) 둘 다 이 조건을 만족한다. Part 2 의 instruction counter 를 생각하면 valid 비트를 두는 쪽이 나중에 편하다(14절).

A flushed instruction must not change any state. There are two pieces of state it could touch: the register file (RegWrite) and dmem (MemWrite). So the minimum for a flush is that the wiped slot's RegWrite and MemWrite end up 0. Keeping a valid bit per bank as on slide 5 and ANDing the write enables with it works, and so does clearing the whole register to zero (a slot whose control is all 0 writes nothing). With Part 2's instruction counter in mind, the valid bit is the more convenient choice later (section 14).

flush 로 IPC 가 오르는 것은 not-taken 일 때뿐이다Flushing only raises IPC on not-taken branches

리포트는 "BEQ flushing 으로 IPC 가 얼마나 올랐나" 를 따로 묻는다. 무엇과 비교해서 올랐는지가 과제에 없다. 자연스러운 기준선은 "분기를 만나면 판정이 날 때까지 fetch 를 멈추는(stall) 판" 이다. 그 둘을 비교하면 이렇게 된다. Decode 판정 기준으로, stall 판은 beq 마다 항상 1 사이클을 잃는다. flush 판은 not-taken 이면 0, taken 이면 1 을 잃는다. taken 일 때는 둘이 똑같다. 시험 프로그램의 beq 가 전부 taken 이면 IPC 차이가 0 으로 나온다. not-taken beq 를 섞어야 개선이 보인다. 비교 기준선을 무엇으로 잡았는지 리포트에 명시하고, 애매하면 TA 에게 물어라. 08절에서 직접 확인할 수 있다.

The report asks separately how much IPC rose thanks to BEQ flushing, but the lab doesn't say compared with what. The natural baseline is a version that stops fetching (stalls) on every branch until it's resolved. Compare the two with Decode resolution: the stall version always loses 1 cycle per beq; the flush version loses 0 when not taken and 1 when taken. When taken, they're identical. If every beq in your test program is taken, the IPC difference comes out zero. Mix in not-taken beqs to see the gain. Say in the report which baseline you used, and ask the TA if it's unclear. You can check this in section 08.

stall 만으로도 맞는 판을 먼저 만든다

Build a version that is correct with stalls alone, first

여기에 이 Lab 전체의 전략이 하나 들어 있다. "앞의 어떤 명령어가 아직 register file 에 안 쓴 register 를 Decode 가 읽으려 하면 멈춘다" 는 규칙 하나만 있으면, forwarding 이 하나도 없어도 모든 data hazard 가 맞게 처리된다. 느리지만 틀리지 않는다. 그 판을 먼저 통과시키고 커밋한 다음, forwarding 은 그 위에 얹는 최적화로 넣는다. 그러면 세 가지를 얻는다.

This is where one strategy for the whole lab lives. With one rule, "stall if Decode wants to read a register that some earlier instruction hasn't written to the register file yet", every data hazard is handled correctly without a single forwarding path. Slow, but never wrong. Pass and commit that version first, then add forwarding on top as an optimisation. You get three things:

  1. 시험하지 않은 조합도 안전하다. forwarding 조건이 어떤 경우를 놓쳐도 stall 규칙이 잡는다. 과제가 "그 밖은 stall" 이라고 한 것이 정확히 이 구조다
  2. IPC 비교의 기준선이 생긴다. 같은 프로그램을 두 판에서 돌린 사이클 수가 "forwarding 으로 오른 IPC" 다
  3. forwarding 이 맞으면 사이클 수만 줄어야 한다. forwarding 을 넣고 결과가 달라졌다면 forwarding 이 틀린 것이다
  1. Untested combinations stay safe. If the forwarding condition misses a case, the stall rule catches it. That's exactly the shape of the lab's "stall for anything else"
  2. You get a baseline for IPC. The cycle counts of the same program on the two versions are "the IPC gained from forwarding"
  3. Correct forwarding only lowers cycle counts. If results change when you add it, the forwarding is wrong
register file 이 같은 사이클에 쓰고 읽을 수 있나Can the register file write and read in the same cycle

stall 사이클 수는 register file 하나로 하나씩 달라진다. WB 가 $1 을 쓰는 바로 그 사이클에 Decode 가 $1 을 읽는다고 하자. register file 이 clock 의 앞 반에 쓰고 뒤 반에 읽도록 되어 있거나(예: falling edge 에 쓰기), 쓰는 값을 같은 사이클 읽기 출력으로 바로 돌려주도록 되어 있으면 새 값을 읽는다. 그냥 rising edge 에 쓰는 register file 이면 옛 값을 읽는다. 그러면 그 사이클도 멈춰야 하고, 위의 "아직 안 쓴" 은 "아직 쓰는 중이거나 안 쓴" 으로 바뀐다. 01절의 질문 2 가 이것이다. 제공된 register file 이 어느 쪽인지 확인하고, 바꾼다면 리포트에 적어라.

The register file alone shifts stall counts by one. Say WB writes $1 in the very cycle Decode reads $1. If the register file writes in the first half of the clock and reads in the second (for example, writing on the falling edge), or passes the value being written straight to the read output in the same cycle, Decode sees the new value. A plain rising-edge-write register file returns the old value; then that cycle must stall too, and "not written yet" above becomes "not written yet or being written this cycle". This is question 2 from section 01. Check which kind the provided register file is, and if you change it, say so in the report.

왜 이걸 배우는가

  
Why this is worth learning

  
이 MIPS 는 여기서 끝나지 않는다. 이 과목의 Lab 5 가 MIPS 에 random stimulus 와 coverage 를 붙이는 검증 Lab 이다. 이번에 만든 pipeline 이 그때 검증 대상(DUT)이 될 가능성이 크다. 그때 random 으로 쏟아지는 명령어 조합이 지금 시험하지 않은 hazard 를 찾아낼 것이다. "그 밖은 stall" 로 모든 조합을 맞게 만들어 둔 설계와 시험한 경우만 맞는 설계의 차이가 거기서 드러난다.

  
This MIPS doesn't end here. Lab 5 in this course is a verification lab that puts random stimulus and coverage on a MIPS, and the pipeline you build now is likely to be the DUT then. The random instruction mixes it throws will find the hazards you didn't test this time. That's where a design made correct for every combination by "stall for everything else" separates from one that's correct only on the cases you tried.

그림 읽기Reading the picture

이름 읽는 법. 신호 이름의 첫 글자가 그 신호가 사는 clock 영역이다. w 로 시작하면 쓰기 쪽, r 로 시작하면 읽기 쪽.

  • winc · rinc: 쓰기 요청 · 읽기 요청 (increment, 포인터를 한 칸 올려 달라는 뜻)
  • wptr · rptr: 쓰기 · 읽기 포인터의 gray code 사본. 경계를 넘는 것이 이 둘이다
  • rq2_wptr: 읽기 영역(r) 에서 동기화 2 단째(q2) 를 지나 도착한 쓰기 포인터(wptr). wq2_rptr 은 그 반대
  • waddr · raddr: 메모리 주소. 포인터에서 바퀴 비트를 뗀 칸 번호다 (아래 1 번 그림)
  • wfull · rempty: 가득 참 · 비었음 플래그. 각각 자기 영역에서 만들어진다

쓰기 한 번이 읽는 쪽에 알려지는 길. winc → wptr_full 이 waddr 칸에 wdata 를 쓰고 포인터를 한 칸 올린다 → 올라간 포인터의 gray 사본 wptr 이 경계를 넘는다 → sync_w2r 의 flip-flop 두 개를 지나 rq2_wptr 이 된다 → rptr_empty 가 자기 포인터와 비교해 rempty 를 내린다. 읽기의 길은 이 거울상이다.

Reading the names. A signal's first letter is the clock domain it lives in: w for the write side, r for the read side.

  • winc / rinc: write request / read request (increment: move the pointer on by one)
  • wptr / rptr: the gray-coded copies of the write and read pointers. These two are what cross
  • rq2_wptr: the write pointer (wptr) as it arrives in the read domain (r) after synchroniser stage two (q2). wq2_rptr is the reverse
  • waddr / raddr: memory addresses, the pointer minus its lap bit (picture 1 below)
  • wfull / rempty: the full and empty flags, each made in its own domain

How one write reaches the reader. winc → wptr_full writes wdata into slot waddr and moves its pointer on → the gray copy wptr crosses the boundary → it passes the two flip-flops of sync_w2r and becomes rq2_wptr → rptr_empty compares it with its own pointer and drops rempty. A read travels the mirror image.

1. FIFO 는 원형으로 도는 칸과 손가락 두 개다

1. A FIFO is a ring of slots and two fingers

FIFO 는 먼저 들어온 것이 먼저 나가는 줄이다. 하드웨어에서는 메모리 칸을 원형으로 쓰고, 손가락 둘로 위치를 가리킨다. W 는 "다음에 쓸 칸", R 은 "다음에 읽을 칸"이다. 쓸 때마다 W 가 한 칸, 읽을 때마다 R 이 한 칸 시계 방향으로 간다. 끝에 닿으면 처음으로 돌아온다. 이 손가락이 코드의 포인터다.

A FIFO is a queue: first in, first out. In hardware you use a block of memory as a ring and keep two fingers on it. W is "the next slot to write", R is "the next slot to read". Each write moves W one slot clockwise, each read moves R one slot. At the end they wrap back to the start. Those fingers are the pointers in the code.

그림 읽기Reading the picture

각 링 밑의 W 0 000 은 포인터 네 비트다. 맨 앞의 보라색 한 비트가 바퀴 비트, 뒤의 세 비트가 칸 번호(binary)다. 칸이 8 개라 칸 번호는 세 비트면 된다 (23 = 8).

  • empty: W = 0 000 (0 바퀴째, 0 번 칸), R = 0 000. 네 비트가 전부 같다. 그래서 비었다
  • 3 entries: W = 0 100 (0 바퀴째, 4 번 칸), R = 0 001 (0 바퀴째, 1 번 칸). 1, 2, 3 번 칸이 차 있다. 개수는 4 − 1 = 3
  • full: W = 1 010 (1 바퀴째, 2 번 칸), R = 0 010 (0 바퀴째, 2 번 칸). 칸 번호 010 은 같고 바퀴 비트만 다르다. W 가 한 바퀴를 더 돌았다는 뜻이고, 그래서 가득 찼다. 네 비트를 통째로 숫자로 읽어 빼면 1010 − 0010 = 10 − 2 = 8, 칸 수와 같다

바퀴 비트가 없으면 empty 와 full 의 포인터가 둘 다 "같은 칸" 이라 구별이 안 된다. 이 한 비트 때문에 코드의 포인터가 주소보다 한 비트 넓다.

The W 0 000 under each ring is the pointer's four bits. The first bit, in purple, is the lap bit; the other three are the slot number in binary. Eight slots need three bits (23 = 8).

  • empty: W = 0 000 (lap 0, slot 0), R = 0 000. All four bits match, so it's empty
  • 3 entries: W = 0 100 (lap 0, slot 4), R = 0 001 (lap 0, slot 1). Slots 1, 2 and 3 are full. The count is 4 − 1 = 3
  • full: W = 1 010 (lap 1, slot 2), R = 0 010 (lap 0, slot 2). Slot 010 matches and only the lap bit differs: W has gone round once more, so it's full. Read all four bits as a number and subtract: 1010 − 0010 = 10 − 2 = 8, the number of slots

Without the lap bit, empty and full would both be "same slot" and you couldn't tell them apart. That one bit is why the pointers in the code are one bit wider than the address.

여기까지는 clock 이 하나인 FIFO 와 같다. 비었는지는 R 을 W 와 비교해서, 찼는지는 W 를 R 과 비교해서 안다. 문제는 그 비교에서 생긴다.

So far this is no different from a single-clock FIFO. Empty is decided by comparing R with W, full by comparing W with R. The trouble starts in that comparison.

2. 문제: 두 손가락이 서로 다른 시계를 본다

2. The problem: the two fingers watch different clocks

이 FIFO 는 쓰는 쪽과 읽는 쪽의 clock 이 다르다. W 는 wclk 에 맞춰 움직이고 R 은 rclk 에 맞춰 움직인다. 두 clock 사이에는 아무 약속이 없다. 그래서 읽는 쪽이 "비었나?" 를 판단하려고 W 를 볼 때, W 가 마침 바뀌는 중일 수 있다.

In this FIFO the writer and the reader run on different clocks. W moves on wclk, R on rclk, and the two clocks have no agreement at all. So when the reader looks at W to decide "am I empty?", W may be in the middle of changing.

자동차 주행거리계를 떠올리면 된다. 0799 에서 0800 으로 넘어갈 때는 세 자리가 같이 돈다. 도는 도중에 사진을 찍으면 0899 나 0700 처럼 있었던 적 없는 숫자가 찍힐 수 있다. 여러 비트짜리 포인터도 똑같다. 비트들이 정확히 같은 순간에 바뀌지 않기 때문이다. 선마다 길이가 조금씩 달라서 몇십 ps 씩 어긋난다.

Think of a car odometer rolling from 0799 to 0800. Three digits turn together, and a photo taken mid-roll can show 0899 or 0700, numbers that were never on the dial. A multi-bit pointer is the same, because its bits never flip at exactly the same instant; each wire is a slightly different length, so they drift apart by tens of picoseconds.

  • b3 가 아직 안 바뀌었으면 0100, 곧 7 (옛 값)
  • b3 가 이미 바뀌었으면 1100, 곧 8 (새 값)

"7 아니면 8 만 가능하다" 는 이 뜻이다. 잡히는 값은 항상 진짜 있었던 값이다. 7 이 잡히면 조금 옛날 값을 본 것일 뿐이고, 5 번에서 보듯 그건 안전한 쪽으로만 틀린다.

Left (binary). 7 is 0111 and 8 is 1000. One step, and all four bits change. In a real circuit they don't change at exactly the same instant; wires differ slightly in length and the flips drift apart by a tiny amount. The picture has them flip in the order b3, b2, b1, b0. The dashed line is the moment rclk samples, and at that moment the bits are:

So 1011 is captured, which is 11 in decimal: neither 7 nor 8, a value the pointer never had. The reader believes the writer has reached slot 11 and goes on to read slots 8, 9 and 10, which were never written: garbage goes out. Sample a moment earlier or later and you get other nonsense like 1111 (15) or 1001 (9). Each of the four bits can be old or new, so any of the 16 combinations is possible.

Right (gray). Gray code is a way of writing numbers so that neighbours differ in exactly one bit. In it, 7 is 0100 and 8 is 1100. Compare them: only b3 changes, and b2, b1, b0 stay 1, 0, 0. So whenever you sample, b3 is the only bit that can be caught either way:

  • b3 not flipped yet: 0100, which is 7 (the old value)
  • b3 already flipped: 1100, which is 8 (the new value)

That's what "only 7 or 8 possible" means: whatever is captured is a value that really existed. If it's 7, the reader is just looking at a slightly old value, and as point 5 shows, that only ever errs on the safe side.

Converting. Binary to gray: XOR the number with itself shifted right by one. For 8, 1000 XOR 0100 = 1100. The code's (rbinnext>>1) ^ rbinnext is exactly this. 3. 해결 하나: 한 번에 한 비트만 바뀌게 센다

3. Fix one: count so that only one bit changes at a time

gray code 는 이웃한 두 수가 항상 한 비트만 다르게 만든 숫자 표기다. 0, 1, 2, 3 을 000, 001, 011, 010 으로 쓰는 식이다. 한 비트만 바뀌면 "바뀌는 중" 에 찍어도 그 비트가 옛 값이거나 새 값일 뿐이라, 찍힌 숫자는 반드시 옛 포인터거나 새 포인터다. 있었던 적 없는 숫자는 나올 수 없다.

Gray code is a way of writing numbers so that neighbours always differ in exactly one bit: 0, 1, 2, 3 become 000, 001, 011, 010. With only one bit moving, a capture taken mid-change sees that bit either old or new, so the number captured is always the old pointer or the new one. A value that never existed can't appear.

그래서 논문은 포인터를 두 벌 들고 있다. 더하기와 메모리 주소에는 보통 binary 를 쓰고, 경계를 넘길 때만 gray 로 바꾼 사본을 보낸다. 02 절 블록도의 굵은 파란 선 둘이 그 사본이다. 한 걸음씩만 움직여야 한다는 조건도 여기서 나온다. 포인터는 한 번에 한 칸씩만 가므로 딱 맞는다.

That's why the paper keeps two copies of each pointer: ordinary binary for incrementing and addressing, and a gray-coded copy only for sending across the boundary. Those copies are the two thick blue lines in the section 02 diagram. The trick needs the value to move one step at a time, which a FIFO pointer does anyway.

4. 해결 둘: 그 한 비트에도 가라앉을 시간을 준다

4. Fix two: give even that one bit time to settle

gray code 로 바뀌는 비트가 하나로 줄었어도, 그 한 비트가 flip-flop 의 입력에서 바뀌는 순간과 clock 엣지가 정확히 겹치는 일은 여전히 생긴다. 그러면 flip-flop 은 잠깐 0 도 1 도 아닌 어중간한 상태에 머물 수 있다. 이것을 metastability 라고 한다. 대부분은 금방 한쪽으로 떨어지지만, 그 어중간한 값을 곧바로 비교기에 넣으면 비교기가 엉뚱하게 반응한다.

Gray code cuts the moving bits down to one, but that one bit can still change exactly as the flip-flop's clock edge arrives. When that happens the flip-flop can hang for a moment somewhere between 0 and 1. That's metastability. It almost always falls to one side quickly, but feed that in-between value straight into a comparator and the comparator can do something daft.

그림 읽기Reading the picture
  • 위 그림: 쓰는 쪽에서 건너온 gray 포인터의 한 비트가 sync1 → sync2 → 비교기 순서로 간다. 두 flip-flop 은 모두 rclk 로 돈다
  • 첫 rclk 상승 엣지: 마침 그 순간 sync1 의 입력이 0 에서 1 로 바뀌고 있었다고 하자. sync1 은 깔끔하게 1 로 못 가고 잠깐 흔들린다 (주황 구간). 이것이 metastability 다
  • 다음 엣지까지: 한 주기가 통째로 남아 있고, 그 사이에 sync1 은 한쪽으로 자리잡는다. 그림에서는 1 로 자리잡았다
  • 둘째 엣지: sync2 가 sync1 을 찍는다. 이미 깨끗한 1 이므로 sync2 도 깨끗한 1 이 된다. 비교기는 sync2 만 보므로 흔들림을 한 번도 보지 않는다
  • 만약 0 으로 자리잡았다면: 둘째 엣지에 sync2 는 0 을 받고, 새 값 1 은 한 엣지 더 늦게 도착한다. 이것도 "옛 값이거나 새 값" 이라 문제가 없다. 늦어질 뿐이다

한 주기 안에 가라앉지 못할 확률이 아주 조금은 남는다. 두 단이면 그 확률이 실용적으로 무시할 만큼 작아진다는 것이 업계의 표준 관행이다. 대가는 값이 받는 쪽에 한두 엣지 늦게 닿는 것이다.

  • Top: one bit of the gray pointer, arriving from the write side, goes sync1 → sync2 → comparator. Both flip-flops run on rclk
  • First rclk rising edge: suppose that at that very moment sync1's input is changing from 0 to 1. sync1 doesn't go cleanly to 1; it wavers for a moment (the amber stretch). That's metastability
  • Until the next edge: there's a whole period left, and in that time sync1 settles one way. Here it settled at 1
  • Second edge: sync2 samples sync1, which is a clean 1 by now, so sync2 becomes a clean 1. The comparator only looks at sync2, so it never sees the wavering
  • Had it settled at 0: sync2 takes 0 on the second edge and the new value 1 arrives one edge later. That's still "old or new", so nothing breaks; it's just later

A tiny chance remains that it doesn't settle within a period. With two stages that chance becomes small enough to ignore in practice, which is why two stages are the standard. The cost is the value reaching the receiver an edge or two late.

5. 늦게 보는 것은 안전한 쪽으로만 틀린다

5. Seeing late only ever errs on the safe side

두 해결의 결과로 읽는 쪽이 보는 W 는 늘 조금 옛날 값이다. 동기화기 두 단을 지나오는 동안 W 는 더 앞으로 갔을 수 있다. 이게 괜찮은 이유가 이 설계의 핵심이다. 늦게 본 값은 틀리더라도 항상 조심스러운 방향으로 틀린다.

After both fixes, the W the reader sees is always a little out of date: while it crawled through the two synchroniser stages, the real W may have moved on. Why that's fine is the heart of the design: a late value, when it's wrong, is always wrong in the cautious direction.

그림 읽기Reading the picture

읽는 쪽. 칸 8 개, 읽기 포인터 R 은 0 번 칸이라고 하자. 쓰는 쪽은 이미 5 개를 써서 실제 W 는 5 다 (0~4 번 칸). 그런데 읽는 쪽에 도착해 있는 W 는 동기화기 두 단을 지나오느라 두 사이클 전의 값 3 이다. 읽는 쪽이 계산하는 개수는 3 − 0 = 3. 그래서 많아야 3 개를 읽는다. 0, 1, 2 번 칸은 실제로 다 써져 있으니 읽는 것은 전부 진짜 데이터다. 3, 4 번 칸은 다음에 W 가 도착하면 읽는다.

쓰는 쪽. 쓰는 쪽은 6 개를 썼고, 읽는 쪽은 그중 2 개를 이미 꺼내 갔다. 실제로는 4 개가 남아 빈 칸이 4 개다. 그런데 쓰는 쪽에 도착해 있는 R 은 꺼내 가기 전의 값 0 이다. 쓰는 쪽 계산으로는 6 − 0 = 6 개가 들어 있고 빈 칸은 2 개다. 그래서 2 개만 더 쓰고 멈춘다. 실제로는 4 개를 쓸 수 있었으니 2 칸 일찍 멈춘 것이다. 반대로 아직 안 읽힌 칸을 빈 칸으로 착각하는 일은 없다. 늦게 본 R 은 실제 R 보다 뒤에 있지 앞에 있을 수 없기 때문이다.

Read side. Say there are 8 slots and the read pointer R is at slot 0. The writer has already written five, so the real W is 5 (slots 0 to 4). But the W sitting on the read side came through two synchroniser stages and is the value from two cycles ago, 3. The reader computes 3 − 0 = 3 entries and takes at most three. Slots 0, 1 and 2 really are written, so everything it reads is real data. Slots 3 and 4 get read once the newer W arrives.

Write side. The writer has written six and the reader has already taken two, so four remain and four slots are free. But the R sitting on the write side is the value from before those reads, 0. The writer computes 6 − 0 = 6 in the FIFO and 2 free, writes two more and stops. It could have written four, so it stopped two early. What it never does is mistake an unread slot for a free one, because a late R can only be behind the real R, never ahead of it.

그래서 늦게 풀리는 rempty 는 버그가 아니다. "데이터가 있는데 없다고 말하는" 쪽으로만 틀리기 때문이다. CDC 회로가 틀리는 방향을 이렇게 한쪽으로 몰아두는 것이 설계의 요령이고, Cummings 논문이 하는 일이 바로 그것이다. 반대 방향, 곧 없는데 있다고 말하는 일은 구조상 일어날 수 없다.

So a late rempty isn't a bug. It only ever errs as "there's data but I say there isn't". Herding a CDC circuit's mistakes into one direction like this is the craft, and it's exactly what the Cummings paper does. The other direction, saying there's data when there isn't, can't happen by construction.

6. 그 안전의 값: 레지스터 넷, 쓰기 뒤 세 엣지

6. The price of that safety: four registers, three edges after the write

얼마나 늦는지는 쓰기가 읽는 쪽 플래그에 닿기까지 지나는 레지스터 개수로 정해진다. 쓰기 포인터 자신, 동기화기 두 단, 그리고 rempty 자체도 등록된 출력이라 한 번 더. 넷이다. 첫째는 쓰기 엣지 그 자체에서 잡으므로 쓰기 뒤로 세면 세 엣지다.

How late is decided by how many registers a write passes before it reaches the read-side flag: the write pointer itself, the two synchroniser stages, and one more because rempty is a registered output. Four. The first captures on the write edge itself, so counted after the write it's three edges.

아래는 그 레지스터 넷을 1 비트로 줄인 모형이다. 실물은 포인터가 여러 비트이고 비교기도 더 복잡하지만, 지연을 만드는 것은 레지스터의 개수라서 1 비트로 줄여도 그 수는 그대로다. 반 클럭씩 밟아보자.

Below is a one-bit model of those four registers. The real pointers are several bits wide and the comparison is more involved, but what creates the delay is the number of registers, and that survives the reduction. Step through it half a clock at a time.

한 줄 정리. 여러 비트를 다른 clock 으로 넘기면 있지도 않은 숫자가 잡힌다. gray code 로 바뀌는 비트를 하나로 줄이고, 동기화기 두 단으로 그 비트에 가라앉을 시간을 준다. 그러면 받는 쪽은 늘 조금 옛날 값을 보는데, 그 오차는 항상 안전한 쪽이다. 대가는 쓰기 뒤 세 엣지의 지연이다. Part 2 가 이걸 실제로 쟀고, 거기까지 가는 데 두 번 틀렸다 (14 절).

In one line. Send several bits to another clock and you can catch a number that never existed. Gray code cuts the moving bits to one, and a two-stage synchroniser gives that bit time to settle. The receiver then always sees a slightly old value, and that error is always on the safe side. The price is a three-edge delay after each write. Part 2 measured it, and got it wrong twice on the way (section 14).

So the design was made to compute the occupancy. The snag is that the pointers are in gray code, and you cannot subtract those. Gray code does not do arithmetic. It has to go back to binary first.

코드로는 세 줄이다.

gray2bin 은 bin[i] = bin[i+1] ^ gray[i] 를 MSB 부터 훑는 function automatic 이다. ALMOST_FULL_LEVEL 은 (3 * DEPTH) / 4 로 깊이에서 유도한다. 깊이를 바꾸면 문턱도 같이 따라간다.

gray2bin is a function automatic that sweeps bin[i] = bin[i+1] ^ gray[i] down from the MSB. ALMOST_FULL_LEVEL is derived from the depth as (3 * DEPTH) / 4, so changing the depth moves the threshold with it.

이 계산은 공짜가 아니다. 뺄셈기 하나와 비교기 하나가 wclk 의 임계 경로에 붙는다. 논문이 굳이 비교만으로 wfull 을 만든 이유가 여기 있다. 비교는 싸고 뺄셈은 비싸다. 요구사항이 3/4 플래그를 요구하지 않았다면 이 로직은 안 넣는 게 맞다.

This calculation is not free. A subtractor and a comparator join the critical path on wclk. That is exactly why the paper builds wfull out of a comparison alone: comparison is cheap, subtraction is not. Without a requirement for 3/4 flags, this logic should not be there.

1. Test 3 never finished

동시 읽기·쓰기 테스트가 멈춘 채로 안 끝났다. 에러도 안 나고 그냥 돌기만 했다.

The simultaneous read/write test hung. No error, it just kept running.

원인은 시작 조건이었다. 읽기 프로세스와 쓰기 프로세스를 동시에 띄웠는데, 그 순간 FIFO 가 비어 있었다. read_word 는 rempty 가 내려가기를 기다리는데, 첫 데이터가 들어와서 동기화기 두 단을 건너오기 전까지는 rempty 가 안 내려간다. 읽기가 먼저 기다리기 시작하면 그 기다림 안에서 영영 나오지 못한다.

The cause was the starting condition. The read and write processes were launched together, and at that instant the FIFO was empty. read_word waits for rempty to fall, but rempty does not fall until the first item has been written and has crossed both synchroniser stages. If the reader starts waiting first, it never gets out of that wait.

고친 방법은 동시 구간에 들어가기 전에 FIFO 에 몇 개를 미리 넣어두는 것이다. 그러면 읽기가 첫 사이클부터 꺼낼 것이 있다.

The fix is to preload a few entries before entering the simultaneous phase, so the reader has something to take from the first cycle.

이게 설계 버그가 아니라 testbench 버그라는 게 중요하다. 설계는 맞게 동작했다. "비었으니 읽지 마라" 라고 정확히 말하고 있었다. testbench 가 그 말을 듣고도 포기할 줄 몰랐던 것이다. 실물 consumer 라면 rempty 를 보고 그 사이클을 건너뛰지 무한정 기다리지 않는다.

It matters that this is a testbench bug, not a design bug. The design behaved correctly; it was saying "empty, do not read" exactly as it should. The testbench heard that and did not know how to give up. A real consumer would look at rempty and skip the cycle rather than wait forever.

2. 테스트가 통과하는데 설계가 틀려 있어도 통과했다

2. The test passed even with the design broken

05 절에 적은 그것이다. wait (almost_full) 과 상수 문자열. 찾은 방법은 설계를 일부러 틀리게 만들어 보는 것이었다. 테스트를 의심할 때 제일 빠른 수단이다. 틀린 설계를 잡아내지 못하는 테스트는 테스트가 아니다.

The one in section 05: wait (almost_full) and a constant string. We found it by deliberately breaking the design. That is the fastest move available when you suspect a test. A test that cannot catch a broken design is not a test.

3. 고치는 쪽이 같은 실수를 반복했다

3. The fix repeated the very flaw it was fixing

이게 제일 볼 만하다. 상수 문자열을 비판해놓고, 고친 첫 판이 똑같은 짓을 했다.

This is the good one. Having criticised the constant string, the first cut of the fix did exactly the same thing.

검사 둘은 제대로 들어갔는데, 그 밑의 $display("almost_full correct: ...") 가 조건 없이 찍혔다. 05 절 커밋 뷰어의 755a20f 에서 그 줄을 볼 수 있다.

Both checks went in properly, but the $display("almost_full correct: ...") under them printed unconditionally. The line is in 755a20f in section 05's commit viewer.

검사는 제대로 들어갔으니 실패는 잡힌다. 그런데 로그에는 실패 줄 바로 밑에 "correct" 가 찍힌다. 읽는 사람이 헷갈린다. 발견은 돌려봐서 했다. 눈으로 코드를 보면 검사가 다 있으니 맞아 보였다.

The checks were there, so failures do get caught. But the log prints "correct" right underneath the failure line, which misleads whoever reads it. We found it by running it. Read on the page the code looked right, because every check was present.

고친 방법은 에러 개수를 표시해두고 안 늘었을 때만 찍는 것이다.

The fix is to mark the error count and only print when it has not moved.

고친 것은 변수 하나, 표시, 조건이다. 표시와 조건은 almost_full 쪽과 almost_empty 쪽에 한 벌씩 들어갔다.

The fix is one variable, a mark and a condition; the mark and condition go in once for the almost_full side and once for the almost_empty side.

한 줄 정리. 셋 다 설계가 아니라 testbench 에서 났다. 이 Lab 에서 제일 오래 붙들고 있었던 것도 testbench 다. 설계는 논문이 이미 풀어놨기 때문이다. 검증이 왜 따로 직군인지가 Lab 하나에서 이미 보인다.

In one line. All three were in the testbench, not the design. The testbench is also what took the longest, because the paper had already solved the design. Why verification is a separate job is visible from one lab.

Are FULL and EMPTY Mealy or Moore

The report asks this. The answer is Moore.

근거는 한 줄이다. wfull 과 rempty 는 always_ff 로 등록된 출력이다. 어느 순간에 보든 그 값은 flip-flop 에 저장된 것이고, flip-flop 이 담고 있는 것은 포인터라는 상태에서 계산된 값이다. 지금 이 순간의 입력(winc, rinc)이 바뀐다고 출력이 즉시 따라 바뀌지 않는다. 그게 Moore 의 정의다.

The reason is one line: wfull and rempty are outputs registered by always_ff. Whenever you look, the value is what a flip-flop holds, and what the flip-flop holds was computed from state, the pointers. Changing an input this instant (winc, rinc) does not move the output immediately. That is what Moore means.

데모에서 나올 만한 반문. "그런데 wfull_val 은 wbinnext 로 계산하고, wbinnext 에는 winc 가 들어가잖아요. 입력에 걸리는 거 아닌가요?"

맞다. winc 는 wfull 에 영향을 준다. 다만 다음 엣지에서다. 그건 다음 상태를 정하는 논리이고, 모든 순차 회로의 다음 상태는 입력에 걸린다. Mealy 와 Moore 를 가르는 건 다음 상태가 아니라 지금의 출력이 입력을 직접 보느냐다. wfull 은 안 본다.

The likely demo follow-up. "But wfull_val is computed from wbinnext, and wbinnext includes winc. Doesn't that make it depend on an input?"

Yes, winc affects wfull, but only at the next edge. That is next-state logic, and every sequential circuit's next state depends on its inputs. What separates Mealy from Moore is not the next state but whether the present output looks at an input directly. wfull does not.

같은 기준으로 Part 2 를 보면 재밌다. even_odd_top 안의 do_pop = Read_en && avail 은 입력을 직접 보는 Mealy 식 신호다. 그런데 모듈의 출력 Data_out 은 그걸 한 번 등록해서 내보내므로 모듈 밖에서 보면 Moore 다. 동기 FIFO 의 empty 는 조합 논리지만 카운터(상태)만 보므로 이것도 Moore 다. 조합이냐 등록이냐가 아니라 입력을 보느냐가 기준이다.

Apply the same test to Part 2 and it gets interesting. Inside even_odd_top, do_pop = Read_en && avail is a Mealy-style signal that looks straight at an input. But the module's output Data_out registers it once before leaving, so from outside the module it is Moore. The synchronous FIFO's empty is combinational, yet it looks only at the counter, which is state, so it too is Moore. The test is not combinational versus registered; it is whether an input is being looked at.

Part 2 · 왜 이 설계인가

Part 2 · Why this design

세 가지를 정해야 했다. 회로의 모양, FIFO 의 깊이, 그리고 동기로 갈지 비동기로 갈지. 셋째는 정하지 않고 둘 다 만들어 재기로 했다.

Three decisions: the shape of the circuit, the depth of the FIFOs, and synchronous versus asynchronous. The third we did not decide. We chose to build both and measure.

1. 모양: parity 로 가르고 번갈아 꺼낸다

1. Shape: split by parity, take turns on the way out

먼저 과제가 무엇인지 그림 하나로 보자. 들어오는 순서는 뒤죽박죽이어도 나갈 때는 홀수와 짝수가 번갈아 나와야 하고, 같은 홀수끼리 · 짝수끼리는 들어온 순서를 지켜야 한다.

First, the task in one picture. Numbers can arrive in any mix, but on the way out odd and even must alternate, and odds among themselves, evens among themselves, must keep their arrival order.

그림 읽기Reading the picture

나가는 순서를 한 단계씩 따라가면 이렇다. 첫 입력 3 이 홀수라 홀수 차례로 시작한다.

  1. 홀수 차례 → 홀수 FIFO 의 머리 3 을 꺼낸다. 이제 짝수 차례
  2. 짝수 차례 → 짝수 FIFO 의 머리 4 (짝수 중 가장 먼저 온 것)
  3. 홀수 차례 → 7
  4. 짝수 차례 → 6
  5. 홀수 차례 → 9
  6. 짝수 차례 → 2

만약 어느 차례에 그 FIFO 가 비어 있으면, 반대쪽에 값이 있어도 꺼내지 않고 기다린다. 이것이 아래 판단 1 이다.

Follow the output one step at a time. The first input, 3, is odd, so it starts on the odd turn.

  1. Odd turn → take the odd FIFO's head, 3. Now it's even's turn
  2. Even turn → the even FIFO's head, 4 (the first even to arrive)
  3. Odd turn → 7
  4. Even turn → 6
  5. Odd turn → 9
  6. Even turn → 2

If the FIFO whose turn it is happens to be empty, nothing is taken, even if the other side has data; the circuit waits. That's decision 1 below.

이걸 회로로 옮기면 아래가 된다. 가르는 쪽은 비트 하나를 보는 조합 논리, 번갈아 꺼내는 쪽은 "지금 누구 차례인가" 하나만 기억하는 FSM 이다.

Turned into a circuit, it's the diagram below: the splitting side is combinational logic looking at one bit, and the alternating side is an FSM that remembers only "whose turn is it".

이 구조에서 설계자가 판단해야 하는 곳은 둘이다. 나머지는 힌트가 정해준다.

In this structure there are exactly two places where the designer has to decide something. The hints settle the rest.

판단 1. 차례인 쪽이 비었으면 반대쪽에 쌓여 있어도 멈춘다

Decision 1. If it is the empty side's turn, stall even if the other side is full

짝수 차례인데 짝수 FIFO 가 비었고, 홀수 FIFO 에는 30 개가 쌓여 있다고 하자. 소비자는 Read_en 을 올리고 기다린다. 홀수를 하나 내보내고 싶은 유혹이 생긴다. 그러면 안 된다. 직전 출력이 홀수였으므로 홀수가 두 번 연속 나간다. 설계의 유일한 약속이 깨진다.

Say it is the even turn, the even FIFO is empty, and the odd FIFO holds 30. The consumer raises Read_en and waits. There is a temptation to send an odd one. Don't. The previous output was odd, so that would be two odds in a row, breaking the circuit's one promise.

그래서 멈춘다. 상태도 안 뒤집고, Data_out 도 안 바꾼다. Lab 의 요구가 정확히 그것이다. "The circuit has to pause or stay in idle state if one of the FIFOs is empty and should not output a 0."

So it stalls. The state does not flip and Data_out does not change. That is exactly the lab's rule: "The circuit has to pause or stay in idle state if one of the FIFOs is empty and should not output a 0."

"0 을 내보내지 않는다" 는 Data_out 을 등록된 출력으로 만들면 저절로 지켜진다. 꺼낸 값만 실리고 멈춘 동안은 직전 값을 붙들고 있으므로, 비어 있는 FIFO 의 rd_data 가 뭐든 밖으로 새지 않는다. 조건문으로 0 을 막는 게 아니라 구조로 막는다.

"Never output a 0" follows for free once Data_out is a registered output. Only popped values are loaded, and while stalled it holds the last one, so whatever an empty FIFO's rd_data happens to be never leaks out. The 0 is not blocked by a condition; it is blocked by the structure.

포트 목록에 valid 신호가 없다. Lab 이 정해준 여섯 포트 중에 "이번 사이클에 진짜 값이 나왔다" 를 알리는 선이 없다. 멈춘 사이클과 나온 사이클이 밖에서는 구별이 안 된다. 우리는 포트를 늘리지 않았다. 대신 out_valid 를 모듈 안에만 두고 testbench 가 계층 참조(dut.out_valid)로 들여다본다. 인터페이스는 과제 명세 그대로 두고, 검증만 안을 본다.

There is no valid signal in the port list. Of the six ports the lab fixes, none says "a real value came out this cycle", so a stalled cycle and a productive one look identical from outside. We did not add a port. Instead out_valid lives inside the module only, and the testbench reads it by hierarchical reference (dut.out_valid). The interface stays exactly as specified; only verification looks inside.

판단 2. 첫 출력의 parity 는 첫 입력이 정한다

Decision 2. The first input decides the first output's parity

reset 직후 sel 을 짝수로 고정하면 어떻게 되나. 입력이 홀수로 시작하면 첫 짝수가 들어올 때까지 아무것도 못 내보낸다. 기능은 맞다. 교대도 지키고 순서도 지킨다. 그런데 느리고, 입력 3 7 4 … 이 4 3 … 으로 나온다.

What if sel is fixed to even after reset? If the input opens with an odd number, nothing can come out until the first even arrives. Functionally fine: alternation holds, order holds. But it is slow, and input 3 7 4 … comes out as 4 3 ….

그래서 started 라는 비트 하나를 두고, reset 이후 처음 들어온 데이터의 parity 로 sel 을 정한다. 상태는 여전히 둘이다. started 는 시작을 한 번 정하는 깃발일 뿐이다.

So there is one extra bit, started, and sel is set from the parity of the first item to arrive after reset. There are still two states; started is just a flag that fixes the start once.

In one line. do_pop = Read_en && !sel_empty is the whole circuit. Only on a pop does sel flip and Data_out change. Without a pop, nothing changes. That is precisely what "stall" means.

From then to cycle 40, 39 more evens (4, 6, …, 80) arrive and none can leave, because the circuit is stuck on the odd turn. Hence 39. The stall only ends when the first odd, 1, arrives at cycle 41. So the peak occupancy of one parity sits right against that parity's total count. That is why the lab insists "40 are even and 40 are odd … This is an important assumption."   • 16 slots: the slot number runs 0 to 15, and after 15 comes 0. 15 in gray is 1111 XOR 0111 = 1000; 0 is 0000. Only the top bit differs: one
  • 10 slots: the slot number runs 0 to 9, and after 9 comes 0. 9 in gray is 1001 XOR 0100 = 1101. Against 0000, three bits differ. Sample that step from another clock and, like the binary side of picture 2, you can catch nonsense such as 1100 or 0101

The heart of the synchronous FIFO

네 덩어리가 전부다. 실제로 일어나는 쓰기와 읽기, 카운터에서 바로 나오는 플래그, 손으로 되감는 포인터, 점유량 갱신.

Four pieces are all of it: the writes and reads that actually happen, flags straight off the counter, pointers rewound by hand, and the occupancy update.

카운터 폭에 함정이 하나 있다. 점유량은 0 부터 DEPTH 까지라 주소보다 한 칸 넓어야 한다. 깊이 40 이면 주소 $clog2(40) = 6 비트, 카운터도 $clog2(41) = 6 비트로 같다. 깊이 64 면 주소 6 비트, 카운터 $clog2(65) = 7 비트다. 2 의 거듭제곱에서만 한 비트가 더 필요하다. 그래서 폭을 DEPTH + 1 에서 따로 유도한다.

There is a trap in the counter width. Occupancy runs from 0 to DEPTH, one more value than there are addresses. At depth 40 the address is $clog2(40) = 6 bits and so is the counter, $clog2(41) = 6. At depth 64 the address is 6 bits but the counter is $clog2(65) = 7. Only at powers of two do you need the extra bit. So the width is derived separately from DEPTH + 1.

// 처음 짠 측정 루프// the measurement loop as first written
while (empty) begin
    @(posedge clk);
    n = n + 1;       // 여기서 empty 를 다시 읽는다// and empty is re-read right here

@(posedge clk) 에서 깨어난 그 순간, 설계의 always_ff 는 아직 값을 안 바꿨다. SystemVerilog 는 한 시각 안에서 일을 영역으로 나눠 처리하는데, <= 의 대입은 뒤쪽 NBA 영역에서야 실제로 반영된다. 그래서 empty 가 내려가는 바로 그 엣지에서 옛 값 1 을 읽고 한 번 더 돌았다. 동기 판은 empty 가 쓰기 엣지에서 이미 내려가 루프를 아예 안 탔으므로 영향이 없었다. 두 구현을 서로 다른 조건으로 잰 셈이다.

At the instant the loop wakes on @(posedge clk), the design's always_ff has not updated yet. SystemVerilog splits the work within one time step into regions, and a <= assignment only lands in the later NBA region. So on the very edge where empty falls, the loop read the old 1 and went round once more. The synchronous version was unaffected: its empty had already fallen on the write edge, so it never entered the loop. The two implementations were measured under different conditions.

고친 것은 한 줄이다. 엣지 뒤 1ns 를 기다린 다음 읽는다. 다시 재니 동기 0, 비동기 3. 트레이스와 맞는다.

처음에는 case 마다 최대 점유량만 쟀다. 결과는 두 구현이 거의 같았다. 최악 case 에서 둘 다 39. "비동기가 느리다" 를 보여주려고 만든 측정이 그걸 보여주지 못했다.

At first we measured only peak occupancy per case. The implementations came out nearly identical, both 39 in the worst case. A metric built to show "asynchronous is slower" did not show it.

따져보면 당연하다. 최대 점유량은 얼마나 쌓이나를 재지 얼마나 늦나를 재지 않는다. empty 가 3 사이클 늦게 풀리면 읽기가 3 사이클 늦게 시작하고 모든 게 뒤로 밀린다. 그건 곡선의 높이가 아니라 곡선이 끝나는 자리에 나타난다. 그래서 첫 쓰기부터 마지막 출력까지의 사이클을 더했고, 비동기가 case 마다 0 에서 5 사이클 늦다는 것이 바로 나왔다.

Obvious in hindsight. Peak occupancy measures how much piles up, not how late things are. If empty clears 3 cycles late, reading starts 3 cycles late and everything shifts right. That shows up not in the height of the curve but where it ends. So we added cycles from first write to last output, and the asynchronous version immediately showed up 0 to 5 cycles late per case.

1 번과 2 번은 트레이스가 없었으면 못 잡았다. 3 번은 숫자만 보고 알았지만, 앞의 둘은 테스트가 전부 통과하는 상태에서 숨어 있었다. 트레이스는 원래 이 페이지에 파형을 그리려고 붙인 것이다. 파형을 그리려고 값을 뽑았더니 그 값이 측정 도구를 검증했다. 같은 것을 두 가지 방법으로 재면 둘 중 하나가 틀렸을 때 보인다. 한 가지로만 재면 절대 안 보인다.

Problems 1 and 2 would never have been caught without the trace. Problem 3 showed up in the numbers alone, but the first two were hiding behind a fully passing test suite. The trace was added only so this page could draw waveforms. Pulling values out to draw them ended up auditing the measuring tools. Measure the same thing two ways and you see when one is wrong. Measure it one way and you never will.

Making the alternation visible at a glance

두 parity 줄을 비교하자. 입력 쪽은 들쭉날쭉하다. 이 구간에서만 홀수가 다섯 연달아(55, 21, 19, 29, 1), 짝수가 넷 연달아(54, 42, 74, 38) 온다. 출력 쪽은 출력이 나올 때마다 정확히 한 번씩 뒤집힌다. 이 회로가 하는 일 전부가 이 두 줄의 차이다. 출력이 끊긴 구간에서는 out_parity 도 가만히 있다. 멈춰 있는 동안 data_out 이 안 바뀌기 때문이다.

Compare the two parity rows. The input side is ragged: within this window alone, five odds in a row (55, 21, 19, 29, 1) and four evens in a row (54, 42, 74, 38). The output side flips exactly once per output. Everything this circuit does is the difference between those two rows. Where output pauses, out_parity sits still too, because data_out does not change while stalled.

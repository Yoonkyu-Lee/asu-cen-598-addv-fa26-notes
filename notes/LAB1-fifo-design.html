문제: 두 클럭이 서로를 모른다

The problem: the two clocks know nothing about each other

FIFO 가 가득 찼는지 알려면 쓰기 포인터와 읽기 포인터를 비교해야 한다. 그런데 쓰기 포인터는 wclk 으로 돌고 읽기 포인터는 rclk 으로 돈다. 비교하려면 한쪽이 상대 영역으로 건너가야 하고, 건너가는 순간이 사고 지점이다.

To know whether the FIFO is full you have to compare the write pointer with the read pointer. But the write pointer runs on wclk and the read pointer on rclk. Comparing means one of them has to cross, and the crossing is where the accident happens.

그 구조가 치르는 값

What that structure costs

gray code 와 동기화기는 공짜가 아니다. 쓰기 쪽에서 일어난 일이 읽기 쪽에 도달하는 데 시간이 걸린다. 얼마나 걸리는지는 레지스터를 몇 개 지나느냐로 결정된다. 세어보면 넷이다. 그런데 첫째는 쓰기 엣지 그 자체에서 잡으므로, 쓰기 뒤로 세면 세 엣지다.

Gray code and synchronisers are not free. Something that happens on the write side takes time to reach the read side, and how long is decided by how many registers it passes through. Count them: four. But the first captures on the write edge itself, so counted after the write, it is three edges.

아래는 그 레지스터 넷을 1 비트로 줄인 모형이다. 실물은 포인터가 여러 비트이고 비교기도 더 복잡하지만, 지연을 만드는 것은 레지스터의 개수라서 1 비트로 줄여도 그 수는 그대로다.

Below is a one-bit model of those four registers. The real pointers are several bits wide and the comparison is more involved, but what creates the delay is the number of registers, and that number survives the reduction.

한 줄 정리. 쓰기가 일어나고 나서 rempty 가 풀릴 때까지 레지스터 넷을 지난다. 포인터 자신, 동기화기 1 단, 2 단, 그리고 rempty 가 등록된 출력이라 한 번 더. 첫째가 쓰기 엣지에서 잡으므로 쓰기 뒤로 세 엣지다. Part 2 가 이걸 실제로 쟀고, 거기까지 가는 데 두 번 틀렸다. 14 절에 있다.

In one line. Between a write happening and rempty clearing there are four registers: the pointer itself, synchroniser stage one, stage two, and one more because rempty is a registered output. The first captures on the write edge, so it is three edges after the write. Part 2 measured this, and got it wrong twice on the way. Section 14 has the story.

이게 버그가 아니라는 것이 중요하다. 늦게 풀리는 rempty 는 "데이터가 있는데 없다고 말하는" 쪽으로 틀린다. 그래서 읽는 쪽이 없는 데이터를 읽는 일은 절대 안 생긴다. 손해는 처리량뿐이다. CDC 회로가 틀리는 방향을 이렇게 한쪽으로 몰아두는 것이 설계의 요령이고, Cummings 논문이 하는 일이 바로 그것이다.

It matters that this is not a bug. A late rempty errs towards "there is data but I am saying there is none," so the reader can never read data that is not there. The only cost is throughput. Forcing a CDC circuit to fail in one direction only is the craft here, and it is exactly what the Cummings paper does.

이건 우리가 정한 게 아니라 Lab 이 지정했다. "Assert these flags when the FIFO is 3/4th full or 3/4th empty respectively." 깊이 16 이므로 almost_full 은 12 개에서, almost_empty 는 남은 것이 4 개일 때 선다.

We did not pick this; the lab specified it: "Assert these flags when the FIFO is 3/4th full or 3/4th empty respectively." At depth 16 that means almost_full at 12 entries and almost_empty when 4 are left.

쓸모는 미리 알려주는 것이다. 위에서 본 대로 플래그가 건너오는 데 시간이 걸리므로, wfull 이 설 때까지 기다렸다가 멈추면 이미 늦을 수 있다. 3/4 에서 미리 알려주면 producer 가 브레이크를 밟을 여유가 생긴다.

Their use is advance warning. As we just saw, flags take time to cross, so waiting for wfull before stopping can be too late. A warning at 3/4 gives the producer room to brake.

Lecture 5 노트의 깊이 4 FIFO 도구로 포인터가 한 바퀴 도는 것을 눌러보면, full 과 empty 가 왜 비트 하나로 갈리는지가 손에 잡힌다. 여기서는 다시 만들지 않는다.

Drive the depth-four FIFO in the Lecture 5 note through a full wrap and you will feel why one extra bit separates full from empty. No point rebuilding it here.

논문에 없는 부분: 3/4 를 어떻게 아나

The part the paper does not have: how do you know you are at 3/4

이게 Part 1 에서 유일하게 새로 생각해야 했던 조각이다. 논문의 wfull 은 포인터 두 개를 비교만 한다. 같으면 비었고, MSB 만 다르고 나머지가 같으면 가득 찼다. 몇 개 들어 있는지는 안 센다. 비교만으로는 "3/4" 를 말할 수 없다.

This is the one piece of Part 1 that had to be worked out. The paper's wfull only compares two pointers: equal means empty, differing only in the MSB means full. It never counts how many entries are in there, and a comparison alone cannot say "3/4".

그래서 점유량을 실제로 계산하게 만들었다. 문제는 포인터가 gray code 라서 그냥 빼면 안 된다는 것이다. gray 는 산술이 성립하지 않는다. 먼저 binary 로 되돌려야 한다.

So the design was made to compute the occupancy. The snag is that the pointers are in gray code, and you cannot subtract those. Gray code does not do arithmetic. It has to go back to binary first.

// fifo_wptr.sv
wq2_rbin   = gray2bin(wq2_rptr);   // 건너온 읽기 포인터를 binary 로// the read pointer that crossed, back to binary
wused_next = wbinnext - wq2_rbin;   // 이제야 뺄 수 있다// now it can be subtracted

almost_full_val = (wused_next >= ALMOST_FULL_LEVEL);

gray2bin 은 bin[i] = bin[i+1] ^ gray[i] 를 MSB 부터 훑는 function automatic 이다. ALMOST_FULL_LEVEL 은 (3 * DEPTH) / 4 로 깊이에서 유도한다. 깊이를 바꾸면 문턱도 같이 따라간다.

gray2bin is a function automatic that sweeps bin[i] = bin[i+1] ^ gray[i] down from the MSB. ALMOST_FULL_LEVEL is derived from the depth as (3 * DEPTH) / 4, so changing the depth moves the threshold with it.

이 계산은 공짜가 아니다. 뺄셈기 하나와 비교기 하나가 wclk 의 임계 경로에 붙는다. 논문이 굳이 비교만으로 wfull 을 만든 이유가 여기 있다. 비교는 싸고 뺄셈은 비싸다. 요구사항이 3/4 플래그를 요구하지 않았다면 이 로직은 안 넣는 게 맞다.

This calculation is not free. A subtractor and a comparator join the critical path on wclk. That is exactly why the paper builds wfull out of a comparison alone: comparison is cheap, subtraction is not. Without a requirement for 3/4 flags, this logic should not be there.

interface 는 메모리에만 썼다

The interface is on the memory only

요구사항이 "in FIFO or memory block" 이라 둘 중 하나면 된다. 메모리를 골랐다. 메모리가 주고받는 것이 wdata · rdata · waddr · raddr · wclk · wclken · wfull 로 묶음이 뚜렷해서 modport 로 방향을 정하기 깔끔하기 때문이다. FIFO 최상위는 클럭이 둘이라 한 interface 로 묶으면 오히려 어느 클럭 소속인지가 흐려진다.

The requirement says "in FIFO or memory block", so either will do. We chose the memory. What it exchanges is a tight bundle: wdata, rdata, waddr, raddr, wclk, wclken, wfull, which makes the modport directions clean. The FIFO top level has two clocks, and bundling it into one interface would only blur which signal belongs to which clock.

// 12 개를 넣고// push 12

Two problems.

  2. 출력 문구가 상수 문자열이다. 무엇이 일어나든 "3/4 full" 이라고 찍는다.

The fixed version checks both sides of the threshold.

같은 실험을 다시 하면 이제 실패한다. "almost_full asserted early: high at 11 of 16 entries, expected low until 12."

Run the same experiment now and it fails: "almost_full asserted early: high at 11 of 16 entries, expected low until 12."

문턱을 localparam 으로 뽑아 설계와 같은 식으로 적은 것도 같은 이유다. 깊이를 바꿨을 때 설계와 테스트가 조용히 갈라지지 않게.

The threshold is pulled out into a localparam written the same way the design writes it, for the same reason: change the depth and the design and the test must not drift apart in silence.

almost_empty 쪽은 한 줄이 더 필요하다. 이 플래그는 읽기 영역에 있고 건너온 쓰기 포인터로 계산된다. 쓰기가 끝난 직후에 바로 판정하면 아직 도착 안 한 포인터로 재게 된다. 그래서 검사 전에 wait (!almost_empty) 로 포인터가 건너온 것을 확인하고 시작한다. 03 절의 네 단 지연이 testbench 를 여기서 물어뜯는다.

The almost_empty side needs one extra line. That flag lives in the read domain and is computed from the write pointer after it crosses. Judge it immediately after writing and you are measuring against a pointer that has not arrived. So the check begins with wait (!almost_empty) to confirm the pointer landed. The four-stage delay from section 03 bites the testbench right here.

1. Test 3 이 영영 안 끝났다

1. Test 3 never finished

동시 읽기·쓰기 테스트가 멈춘 채로 안 끝났다. 에러도 안 나고 그냥 돌기만 했다.

The simultaneous read/write test hung. No error, it just kept running.

원인은 시작 조건이었다. 읽기 프로세스와 쓰기 프로세스를 동시에 띄웠는데, 그 순간 FIFO 가 비어 있었다. read_word 는 rempty 가 내려가기를 기다리는데, 첫 데이터가 들어와서 동기화기 두 단을 건너오기 전까지는 rempty 가 안 내려간다. 읽기가 먼저 기다리기 시작하면 그 기다림 안에서 영영 나오지 못한다.

The cause was the starting condition. The read and write processes were launched together, and at that instant the FIFO was empty. read_word waits for rempty to fall, but rempty does not fall until the first item has been written and has crossed both synchroniser stages. If the reader starts waiting first, it never gets out of that wait.

고친 방법은 동시 구간에 들어가기 전에 FIFO 에 몇 개를 미리 넣어두는 것이다. 그러면 읽기가 첫 사이클부터 꺼낼 것이 있다.

The fix is to preload a few entries before entering the simultaneous phase, so the reader has something to take from the first cycle.

이게 설계 버그가 아니라 testbench 버그라는 게 중요하다. 설계는 맞게 동작했다. "비었으니 읽지 마라" 라고 정확히 말하고 있었다. testbench 가 그 말을 듣고도 포기할 줄 몰랐던 것이다. 실물 consumer 라면 rempty 를 보고 그 사이클을 건너뛰지 무한정 기다리지 않는다.

It matters that this is a testbench bug, not a design bug. The design behaved correctly; it was saying "empty, do not read" exactly as it should. The testbench heard that and did not know how to give up. A real consumer would look at rempty and skip the cycle rather than wait forever.

FULL 과 EMPTY 는 Mealy 인가 Moore 인가

The report asks this. The answer is Moore.

근거는 한 줄이다. wfull 과 rempty 는 always_ff 로 등록된 출력이다. 어느 순간에 보든 그 값은 flip-flop 에 저장된 것이고, flip-flop 이 담고 있는 것은 포인터라는 상태에서 계산된 값이다. 지금 이 순간의 입력(winc, rinc)이 바뀐다고 출력이 즉시 따라 바뀌지 않는다. 그게 Moore 의 정의다.

The reason is one line: wfull and rempty are outputs registered by always_ff. Whenever you look, the value is what a flip-flop holds, and what the flip-flop holds was computed from state, the pointers. Changing an input this instant (winc, rinc) does not move the output immediately. That is what Moore means.

데모에서 나올 만한 반문. "그런데 wfull_val 은 wbinnext 로 계산하고, wbinnext 에는 winc 가 들어가잖아요. 입력에 걸리는 거 아닌가요?"

맞다. winc 는 wfull 에 영향을 준다. 다만 다음 엣지에서다. 그건 다음 상태를 정하는 논리이고, 모든 순차 회로의 다음 상태는 입력에 걸린다. Mealy 와 Moore 를 가르는 건 다음 상태가 아니라 지금의 출력이 입력을 직접 보느냐다. wfull 은 안 본다.

The likely demo follow-up. "But wfull_val is computed from wbinnext, and wbinnext includes winc. Doesn't that make it depend on an input?"

Yes, winc affects wfull, but only at the next edge. That is next-state logic, and every sequential circuit's next state depends on its inputs. What separates Mealy from Moore is not the next state but whether the present output looks at an input directly. wfull does not.

같은 기준으로 Part 2 를 보면 재밌다. even_odd_top 안의 do_pop = Read_en && avail 은 입력을 직접 보는 Mealy 식 신호다. 그런데 모듈의 출력 Data_out 은 그걸 한 번 등록해서 내보내므로 모듈 밖에서 보면 Moore 다. 동기 FIFO 의 empty 는 조합 논리지만 카운터(상태)만 보므로 이것도 Moore 다. 조합이냐 등록이냐가 아니라 입력을 보느냐가 기준이다.

Apply the same test to Part 2 and it gets interesting. Inside even_odd_top, do_pop = Read_en && avail is a Mealy-style signal that looks straight at an input. But the module's output Data_out registers it once before leaving, so from outside the module it is Moore. The synchronous FIFO's empty is combinational, yet it looks only at the counter, which is state, so it too is Moore. The test is not combinational versus registered; it is whether an input is being looked at.

Part 2 · 왜 이 설계인가

Part 2 · Why this design

세 가지를 정해야 했다. 회로의 모양, FIFO 의 깊이, 그리고 동기로 갈지 비동기로 갈지. 셋째는 정하지 않고 둘 다 만들어 재기로 했다.

Three decisions: the shape of the circuit, the depth of the FIFOs, and synchronous versus asynchronous. The third we did not decide. We chose to build both and measure.

1. 모양: parity 로 가르고 번갈아 꺼낸다

1. Shape: split by parity, take turns on the way out

이 구조에서 설계자가 판단해야 하는 곳은 둘이다. 나머지는 힌트가 정해준다.

In this structure there are exactly two places where the designer has to decide something. The hints settle the rest.

판단 1. 차례인 쪽이 비었으면 반대쪽에 쌓여 있어도 멈춘다

Decision 1. If it is the empty side's turn, stall even if the other side is full

짝수 차례인데 짝수 FIFO 가 비었고, 홀수 FIFO 에는 30 개가 쌓여 있다고 하자. 소비자는 Read_en 을 올리고 기다린다. 홀수를 하나 내보내고 싶은 유혹이 생긴다. 그러면 안 된다. 직전 출력이 홀수였으므로 홀수가 두 번 연속 나간다. 설계의 유일한 약속이 깨진다.

Say it is the even turn, the even FIFO is empty, and the odd FIFO holds 30. The consumer raises Read_en and waits. There is a temptation to send an odd one. Don't. The previous output was odd, so that would be two odds in a row, breaking the circuit's one promise.

그래서 멈춘다. 상태도 안 뒤집고, Data_out 도 안 바꾼다. Lab 의 요구가 정확히 그것이다. "The circuit has to pause or stay in idle state if one of the FIFOs is empty and should not output a 0."

So it stalls. The state does not flip and Data_out does not change. That is exactly the lab's rule: "The circuit has to pause or stay in idle state if one of the FIFOs is empty and should not output a 0."

"0 을 내보내지 않는다" 는 Data_out 을 등록된 출력으로 만들면 저절로 지켜진다. 꺼낸 값만 실리고 멈춘 동안은 직전 값을 붙들고 있으므로, 비어 있는 FIFO 의 rd_data 가 뭐든 밖으로 새지 않는다. 조건문으로 0 을 막는 게 아니라 구조로 막는다.

"Never output a 0" follows for free once Data_out is a registered output. Only popped values are loaded, and while stalled it holds the last one, so whatever an empty FIFO's rd_data happens to be never leaks out. The 0 is not blocked by a condition; it is blocked by the structure.

포트 목록에 valid 신호가 없다. Lab 이 정해준 여섯 포트 중에 "이번 사이클에 진짜 값이 나왔다" 를 알리는 선이 없다. 멈춘 사이클과 나온 사이클이 밖에서는 구별이 안 된다. 우리는 포트를 늘리지 않았다. 대신 out_valid 를 모듈 안에만 두고 testbench 가 계층 참조(dut.out_valid)로 들여다본다. 인터페이스는 과제 명세 그대로 두고, 검증만 안을 본다.

There is no valid signal in the port list. Of the six ports the lab fixes, none says "a real value came out this cycle", so a stalled cycle and a productive one look identical from outside. We did not add a port. Instead out_valid lives inside the module only, and the testbench reads it by hierarchical reference (dut.out_valid). The interface stays exactly as specified; only verification looks inside.

판단 2. 첫 출력의 parity 는 첫 입력이 정한다

Decision 2. The first input decides the first output's parity

reset 직후 sel 을 짝수로 고정하면 어떻게 되나. 입력이 홀수로 시작하면 첫 짝수가 들어올 때까지 아무것도 못 내보낸다. 기능은 맞다. 교대도 지키고 순서도 지킨다. 그런데 느리고, 입력 3 7 4 … 이 4 3 … 으로 나온다.

What if sel is fixed to even after reset? If the input opens with an odd number, nothing can come out until the first even arrives. Functionally fine: alternation holds, order holds. But it is slow, and input 3 7 4 … comes out as 4 3 ….

그래서 started 라는 비트 하나를 두고, reset 이후 처음 들어온 데이터의 parity 로 sel 을 정한다. 상태는 여전히 둘이다. started 는 시작을 한 번 정하는 깃발일 뿐이다.

So there is one extra bit, started, and sel is set from the parity of the first item to arrive after reset. There are still two states; started is just a flag that fixes the start once.

아래는 FSM 만 떼어낸 모형이다. FIFO 두 개는 "머리에 무엇이 있고 비었는가" 로만 줄였다. 실물은 깊이 40 이지만 교대와 멈춤은 머리만 봐도 다 보인다.

Below is the FSM on its own. The two FIFOs are reduced to "what is at the head, and is it empty". The real ones are 40 deep, but alternation and stalling are fully visible from the heads alone.

한 줄 정리. do_pop = Read_en && !sel_empty 한 줄이 이 회로의 전부다. 꺼낼 때만 sel 이 뒤집히고 Data_out 이 바뀐다. 못 꺼내면 아무것도 안 바뀐다. 그게 "멈춘다" 의 정확한 뜻이다.

In one line. do_pop = Read_en && !sel_empty is the whole circuit. Only on a pop does sel flip and Data_out change. Without a pop, nothing changes. That is precisely what "stall" means.

2. 깊이: 왜 16 이 아니라 40 인가

The contract that makes them swappable: fifo_q

module fifo_q #(
    parameter int DATA_WIDTH = 8,
    parameter int DEPTH      = 64
)(
    input  logic                  clk, rst_n,
    input  logic                  wr_en,
    input  logic [DATA_WIDTH-1:0] wr_data,
    input  logic                  rd_en,
    output logic [DATA_WIDTH-1:0] rd_data,   // 지금 머리에 있는 값// whatever is at the head right now
    output logic                  full, empty
);

가장 중요한 한 줄은 rd_data 의 뜻이다. "지금 머리에 있는 값" 이고 rd_en 은 그것을 꺼낸다. 반대로 "rd_en 을 주면 다음 사이클에 값이 나온다" 로 정할 수도 있었다. 어느 쪽이든 되지만 두 구현이 같은 뜻이어야 상위 모듈이 구현을 몰라도 된다. Part 1 의 메모리가 assign rdata = mem[raddr] 로 머리를 바로 보여주므로 그쪽에 맞췄다.

The line that matters most is what rd_data means: "whatever is at the head right now," and rd_en takes it. The alternative, "assert rd_en and the value appears next cycle," would also work. Either is fine, but both implementations must mean the same thing for the top level to stay ignorant of which one it has. Part 1's memory shows the head directly with assign rdata = mem[raddr], so we matched that.

동기 FIFO 의 핵심

The heart of the synchronous FIFO

// 가득 찼는데 쓰거나 비었는데 읽으라고 해도 무시한다// ignore a write when full, a read when empty
do_wr = wr_en && !full;
do_rd = rd_en && !empty;

// 카운터에서 바로 나온다. 동기화기가 없으니 늦을 이유가 없다// straight off the counter; no synchroniser, so no reason to be late
assign full  = (count == CNT_WIDTH'(DEPTH));
assign empty = (count == '0);

// 포인터를 손으로 되감는다. 그래서 DEPTH 가 2 의 거듭제곱일 필요가 없다// rewind the pointer by hand; that is why DEPTH need not be a power of two
wptr <= (wptr == PTR_WIDTH'(DEPTH - 1)) ? '0 : wptr + 1'b1;

// 같은 사이클에 읽고 쓰면 점유량은 그대로// read and write in the same cycle leave the count unchanged
unique case ({do_wr, do_rd})
    2'b10:   count <= count + 1'b1;
    2'b01:   count <= count - 1'b1;
    default: count <= count;
endcase

카운터 폭에 함정이 하나 있다. 점유량은 0 부터 DEPTH 까지라 주소보다 한 칸 넓어야 한다. 깊이 40 이면 주소는 $clog2(40) = 6 비트지만 카운터는 $clog2(41) = 6 비트다. 깊이 64 면 주소 6 비트, 카운터 $clog2(65) = 7 비트다. 2 의 거듭제곱에서만 한 비트가 더 필요하다. 그래서 폭을 DEPTH + 1 에서 따로 유도한다.

There is a trap in the counter width. Occupancy runs from 0 to DEPTH, one more value than there are addresses. At depth 40 the address is $clog2(40) = 6 bits and so is the counter, $clog2(41) = 6. At depth 64 the address is 6 bits but the counter is $clog2(65) = 7. Only at powers of two do you need the extra bit. So the width is derived separately from DEPTH + 1.

What the asynchronous wrapper does

세 가지뿐이다. wclk 과 rclk 에 같은 clk 을 물리고, 두 reset 에 같은 rst_n 을 물리고, almost_full · almost_empty 를 안에서 끊는다. 클럭을 묶어도 안쪽의 동기화기는 그대로 남는다. 회로가 자기가 한 클럭으로 돌고 있다는 것을 모르기 때문이다. 03 절의 지연은 여기서도 그대로 산다.

Three things only: feed the same clk to wclk and rclk, the same rst_n to both resets, and leave almost_full / almost_empty unconnected inside. Part 2 · Where we got stuck

셋이다. 그중 둘은 같은 버그였다. 둘 다 설계가 아니라 재는 쪽에 있었고, 둘 다 엣지에서 언제 읽느냐의 문제였다.

Three. Two of them were the same bug: both in the thing doing the measuring, not the design, and both a question of when you read relative to the edge.

1. empty 지연: 예측 2, 첫 측정 4, 진짜 3

1. Empty latency: predicted 2, first measured 4, actually 3

비동기 wrapper 를 처음 돌리기 전에 empty_latency 를 예측해 뒀다. 동기화기가 두 단이니 2. 측정은 4 가 나왔다. 틀린 예측을 설명하려고 레지스터를 세어보니 넷이었다. 쓰기 포인터, 동기화기 두 단, 등록된 rempty. 깔끔하게 맞아떨어졌다. 그게 함정이었다.

How we found out. The +TRACE added for this page logged the top-level circuit every cycle. Both implementations make their first write at cycle 1, but the first output came at cycle 2 synchronously and cycle 5 asynchronously. A gap of 3. That disagreed with the FIFO-level 0 versus 4. One of them was wrong.

// 처음 짠 측정 루프// the measurement loop as first written
while (empty) begin
    @(posedge clk);
    n = n + 1;       // 여기서 empty 를 다시 읽는다// and empty is re-read right here
end

@(posedge clk) 에서 깨어난 그 순간, 설계의 always_ff 는 아직 값을 안 바꿨다. SystemVerilog 는 한 시각 안에서 일을 영역으로 나눠 처리하는데, <= 의 대입은 뒤쪽 NBA 영역에서야 실제로 반영된다. 그래서 empty 가 내려가는 바로 그 엣지에서 옛 값 1 을 읽고 한 번 더 돌았다. 동기 판은 empty 가 쓰기 엣지에서 이미 내려가 루프를 아예 안 탔으므로 영향이 없었다. 두 구현을 서로 다른 조건으로 잰 셈이다.

At the instant the loop wakes on @(posedge clk), the design's always_ff has not updated yet. SystemVerilog splits the work within one time step into regions, and a <= assignment only lands in the later NBA region. So on the very edge where empty falls, the loop read the old 1 and went round once more. The synchronous version was unaffected: its empty had already fallen on the write edge, so it never entered the loop. The two implementations were measured under different conditions.

고친 것은 한 줄이다. 엣지 뒤 1ns 를 기다린 다음 읽는다. 다시 재니 동기 0, 비동기 3. 트레이스와 맞는다.

The fix is one line: wait 1 ns after the edge, then read. Re-measured: synchronous 0, asynchronous 3. It agrees with the trace.

제일 위험했던 것은 4 에 붙인 설명이다. "레지스터가 넷이라 4" 는 레지스터 수로는 맞다. 그래서 설득력이 있었고, 그래서 아무도 측정을 의심하지 않았다. 틀린 숫자에 맞는 설명을 찾는 건 쉽다. 이걸 잡은 건 설명의 논리가 아니라 독립적인 두 번째 측정이었다.

The most dangerous part was the explanation attached to 4. "Four registers, so 4" is correct as a register count. That made it convincing, and that is why nobody doubted the measurement. Finding a plausible story for a wrong number is easy. What caught it was not the logic of the story but an independent second measurement.

2. 점유량 추적기가 다음 엣지의 꺼내기를 미리 셌다

2. The occupancy tracker counted the next edge's pop early

트레이스의 첫 줄부터 이상했다. cycle 1 에 짝수 2 가 들어왔는데 occ_even 이 0 이었다. 1 이어야 한다.

The trace looked wrong from its first line: even value 2 arrived at cycle 1, yet occ_even read 0. It should be 1.

testbench 는 점유량을 상위 모듈의 wr_en 과 rd_en 을 세서 얻는다 (12 절). 이걸 posedge 1ns 뒤에 읽고 있었다. 쓰기 쪽 Write_en 은 testbench 가 negedge 까지 붙들고 있으니 1ns 뒤에 읽어도 이번 엣지의 값이다. 그런데 꺼내기 쪽 do_pop 은 조합 신호라서 엣지가 지나면 바뀐 sel 과 바뀐 점유량으로 다시 계산된다. 그래서 이번 엣지의 쓰기와 다음 엣지의 꺼내기를 한데 셌다.

The testbench gets occupancy by counting the top level's wr_en and rd_en (section 12), and it was reading them 1 ns after the posedge. On the write side, the testbench holds Write_en until the negedge, so 1 ns later it is still this edge's value. But do_pop on the read side is combinational: once the edge passes it is recomputed from the new sel and the new occupancy. So it counted this edge's write together with the next edge's pop.

검증은 또 트레이스로 했다. out_valid 는 등록된 출력이라 "그 엣지에 실제로 꺼냈다" 와 정확히 같다. 그걸로 점유량을 독립적으로 다시 세니 여덟 run 중 다섯에서 최대 점유량이 1 에서 2 달랐다.

The check, again, was the trace. out_valid is a registered output, so it means exactly "a pop happened on that edge." Recounting occupancy from it independently, five of the eight runs had a peak off by 1 or 2.

3. 첫 측정이 두 구현을 가르지 못했다

3. The first metric could not tell the implementations apart

처음에는 case 마다 최대 점유량만 쟀다. 결과는 두 구현이 거의 같았다. 최악 case 에서 둘 다 39. "비동기가 느리다" 를 보여주려고 만든 측정이 그걸 보여주지 못했다.

At first we measured only peak occupancy per case. The implementations came out nearly identical, both 39 in the worst case. A metric built to show "asynchronous is slower" did not show it.

따져보면 당연하다. 최대 점유량은 얼마나 쌓이나를 재지 얼마나 늦나를 재지 않는다. empty 가 3 사이클 늦게 풀리면 읽기가 3 사이클 늦게 시작하고 모든 게 뒤로 밀린다. 그건 곡선의 높이가 아니라 곡선이 끝나는 자리에 나타난다. 그래서 첫 쓰기부터 마지막 출력까지의 사이클을 더했고, 비동기가 case 마다 0 에서 5 사이클 늦다는 것이 바로 나왔다.

Obvious in hindsight. Peak occupancy measures how much piles up, not how late things are. If empty clears 3 cycles late, reading starts 3 cycles late and everything shifts right. That shows up not in the height of the curve but where it ends. So we added cycles from first write to last output, and the asynchronous version immediately showed up 0 to 5 cycles late per case.

1 번과 2 번은 트레이스가 없었으면 못 잡았다. 3 번은 숫자만 보고 알았지만, 앞의 둘은 테스트가 전부 통과하는 상태에서 숨어 있었다. 트레이스는 원래 이 페이지에 파형을 그리려고 붙인 것이다. 파형을 그리려고 값을 뽑았더니 그 값이 측정 도구를 검증했다. 같은 것을 두 가지 방법으로 재면 둘 중 하나가 틀렸을 때 보인다. 한 가지로만 재면 절대 안 보인다.

Problems 1 and 2 would never have been caught without the trace. Problem 3 showed up in the numbers alone, but the first two were hiding behind a fully passing test suite. The trace was added only so this page could draw waveforms. Pulling values out to draw them ended up auditing the measuring tools. Measure the same thing two ways and you see when one is wrong. Measure it one way and you never will.

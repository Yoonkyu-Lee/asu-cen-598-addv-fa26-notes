결론부터

The short version

2부 검증의 첫 강의이고 녹화 강의다. 주제는 SystemVerilog 가 Verilog 위에 검증을 위해 얹은 것이다. 소프트웨어에서 빌려온 것(data type, OOP, thread), 하드웨어 검증을 위해 만든 것(stimulus, checking, coverage), 그리고 두 세계를 잇는 다리(interface, virtual interface). 오늘 코드는 UVM 이 아니라 순수 SV 다. Lecture 3 이 합성되는 절반이었다면 이건 합성되지 않는 절반이다.

The first lecture of Part 2, verification, and a recorded one. Its subject is what SystemVerilog adds on top of Verilog for verification: features borrowed from software (data types, OOP, threads), features built for hardware verification (stimulus, checking, coverage), and the bridge between the two worlds (interfaces, virtual interfaces). Today's code is plain SV, not UVM. If Lecture 3 was the half that synthesizes, this is the half that does not.

handle 과 polymorphism

Handles and polymorphism

슬라이드 15~19쪽. class 는 property 와 method 를 가진 type 이고, new() 가 실행 중에 object 를 만든다. 변수에는 handle 이 들어가므로 b = a; 는 object 를 복사하지 않고 같은 object 를 둘이 가리키게 한다. destructor 는 없고 아무도 안 가리키는 object 는 알아서 치워진다. extends 로 자식 class 를 만들고, 부모에서 virtual 로 선언한 method 는 handle 의 type 이 아니라 가리키는 object 의 type 으로 판을 고른다.

Slides 15 to 19. A class is a type with properties and methods, and new() builds an object at run time. Variables hold handles, so b = a; copies no object; it makes both point at the same one. There is no destructor; objects nothing points to are reclaimed automatically. extends makes a child class, and a method the parent declares virtual picks its version by the type of the object pointed at, not the handle's type.

그림 읽기Reading the picture
  1. 왼쪽 상자의 이름표 p : Packet, e : ErrPkt 는 "handle 이름 : 선언한 type" 이다. p 는 Packet type 으로 선언한 handle 이다
  2. 왼쪽 판, 전. p 와 e 가 각자 자기 type 의 object 를 가리킨다. Packet object 의 Data 0000600d 는 SetData(32'h0000_600d) 에서 왔고, ErrPkt object 의 deadbeef 는 ErrPkt 의 생성자가 넣었다. %x 는 32 비트를 16진수 여덟 자리로 찍으므로 앞의 0 이 붙어 0000600d 가 된다
  3. 오른쪽 판, 후. p = e; 는 e 가 가리키는 곳을 p 에 복사한다. 부모 type 의 handle 이 자식 object 를 가리키는 것은 허용된다. ErrPkt 는 Packet 이기도 하기 때문이다. 원래 Packet object 는 이제 아무 handle 도 가리키지 않아서 점선으로 그렸다. 슬라이드 16쪽 말대로 시뮬레이터가 알아서 치운다
  4. 초록 줄. 이제 p.PrintData() 가 ErrPacket:: 판을 부른다. p 의 선언 type 은 여전히 Packet 인데도 그렇다. PrintData 가 virtual 이라 handle 의 type 이 아니라 가리키는 object 의 type 을 보고 고르기 때문이다. 이것이 슬라이드의 "Base class handle can call derived class' implementation" 이다
  5. 주황 줄. virtual 을 빼면 선택이 handle 의 type 으로 정해져 Packet:: 판이 불린다. Data 값은 ErrPkt object 의 것(deadbeef)이 그대로 찍힌다. object 는 바뀌었는데 method 만 부모 것이 도는 셈이다
  1. The left-hand labels p : Packet and e : ErrPkt read "handle name : declared type". p is a handle declared with type Packet
  2. Left panel, before. p and e each point at an object of their own type. The Packet object's Data 0000600d comes from SetData(32'h0000_600d); the ErrPkt object's deadbeef was put there by ErrPkt's constructor. %x prints 32 bits as eight hex digits, so the leading zeros make it 0000600d
  3. Right panel, after. p = e; copies where e points into p. A parent-type handle may point at a child object, because an ErrPkt is also a Packet. The original Packet object now has no handle pointing at it, so it is dashed; as slide 16 says, the simulator reclaims it
  4. The green line. p.PrintData() now calls the ErrPacket:: version, even though p is still declared as a Packet. Because PrintData is virtual, the choice follows the type of the object pointed at, not the type of the handle. That is the slide's "base class handle can call derived class' implementation"
  5. The amber line. Without virtual, the choice follows the handle's type and the Packet:: version runs. The Data printed is still the ErrPkt object's (deadbeef): the object changed, but the parent's method runs on it
함정 · virtual 은 셋이다Trap · there are three virtuals

무엇 앞에 붙느냐로 갈린다. virtual function 은 polymorphism, virtual class 는 직접 object 를 못 만드는 abstract class(Backup 61쪽), virtual dut_if vif 는 interface 를 가리키는 handle 이다. 뜻이 서로 다르다.

It depends on what it is placed in front of. virtual function is polymorphism, virtual class is an abstract class you cannot instantiate (backup slide 61), and virtual dut_if vif is a handle to an interface. Three different meanings.

thread 와 동기화

Threads and synchronisation

슬라이드 21~24쪽. testbench 는 여러 일을 동시에 해야 하므로 fork 로 thread 를 띄운다. 시뮬레이터 안에서 번갈아 도는 것이지 CPU 코어에서 진짜로 동시에 도는 것은 아니다. 다시 모으는 방법이 셋이다.

Slides 21 to 24. A testbench must do several things at once, so it launches threads with fork. They take turns inside the simulator rather than running truly in parallel on CPU cores. There are three ways to bring them back together.

그림 읽기Reading the picture
  1. 맨 윗줄 parent: fork 를 실행한 process. 검은 점이 fork 를 만난 순간이다
  2. A, B, C 분홍 막대: fork ... join 사이에 적힌 문장 하나하나가 각자 thread 가 된다. 막대 길이가 그 thread 가 도는 시뮬레이션 시간이다. 세 판 모두 같은 길이로 그렸다
  3. 회색 점선: 부모가 기다리는 구간
  4. 초록 화살표와 resumes: 부모가 join 다음 줄로 넘어가는 순간. join 은 가장 긴 C 가 끝날 때, join_any 는 가장 짧은 A 가 끝날 때, join_none 은 기다리지 않고 바로다
  5. 아래 첫 줄은 슬라이드 21쪽 빨간 상자의 문장이다. 둘째 줄은 슬라이드에 없는 보충이다. join_any 뒤에도 B 와 C 는 죽지 않고 계속 돈다. join_none 으로 띄운 thread 는 LRM 규칙상 부모가 무언가를 기다리며 멈추거나 끝날 때 비로소 돌기 시작한다. 셋째 판은 부모가 곧 멈춘다고 보고 막대를 fork 지점에서 그렸다
  1. The top line, parent: the process that executes fork. The black dot is the moment it meets fork
  2. The pink bars A, B, C: each statement between fork and join becomes its own thread. Bar length is how long it runs in simulation time. All three panels use the same lengths
  3. The grey dotted line: the stretch where the parent waits
  4. The green arrow and "resumes": the moment the parent moves on past the join. join waits for the longest, C; join_any for the shortest, A; join_none moves on at once
  5. The first line underneath is the sentence in slide 21's red boxes. The second line is a supplement: after join_any, B and C are not killed; they keep running. Threads launched by join_none, per the LRM, only start once the parent blocks on something or finishes; the third panel assumes the parent blocks soon after and starts the bars at the fork point

thread 사이에는 도구 셋이 있다. semaphore 는 열쇠(get/put)로 공유 자원을 한 번에 하나만 쓰게 하고, event 는 ->ev 로 울리고 @ev 로 기다리며, mailbox 는 FIFO 와 event 를 합친 우편함이다. 슬라이드 24쪽의 read-modify-write 는 두 thread 가 같은 pkt object 하나를 쓰기 때문에 semaphore 가 필요하다. 주소가 달라도 그렇다.

Between threads there are three tools. A semaphore uses keys (get/put) so a shared resource is used by one thread at a time; an event is rung with ->ev and awaited with @ev; a mailbox is a postbox combining a FIFO and an event. Slide 24's read-modify-write needs a semaphore because both threads use the same single pkt object, even though their addresses differ.

함정 · disable fork 의 범위Trap · the reach of disable fork

disable fork 는 방금의 fork 만이 아니라 이 process 의 살아 있는 자손 전부를 죽인다. 먼저 띄워 둔 monitor 도 같이 죽을 수 있다. 슬라이드에 없는 LRM 보충이다.

disable fork kills not just the latest fork but every live descendant of this process, possibly including a monitor launched earlier. An LRM supplement, not on the slides.

virtual interface

The virtual interface

슬라이드 26~28쪽. interface 는 "똑똑한 전선 다발" 이다(Lecture 3). 그런데 interface 는 시뮬레이션 전에 정해지는 하드웨어 쪽 물건이라 class 안에 둘 수 없다. 그래서 class 는 virtual interface, 즉 interface instance 를 가리키는 handle 을 갖는다.

Slides 26 to 28. An interface is "an intelligent bundle of wires" (Lecture 3). But an interface is a hardware-side thing fixed before simulation, so a class cannot contain one. Instead the class holds a virtual interface, a handle pointing at an interface instance.

그림 읽기Reading the picture
  1. module top 틀: 슬라이드 26쪽 오른쪽의 module top 이다. 안의 네 상자가 다 여기서 instance 로 만들어진다
  2. forever #10 clk: clock 을 10 시간 단위마다 뒤집는다. 그 clk 와 rst 가 아래 화살표로 interface 의 포트에 들어간다(dut_if dut_if_inst(clk, rst);). 슬라이드 그림의 clk, rst 두 화살표가 이것이다
  3. 가운데 회색 상자 interface dut_if: Data, Addr, req, done, rw 신호를 묶은 다발. 이름 아래 dut_if_inst 가 instance 이름이다. 회색인 것은 testbench 쪽(분홍)과 DUT 쪽(파랑)이 같이 쓰는 다발이라서다
  4. 양옆 port 화살표: dut dut_inst(dut_if_inst); 와 testbench tb_inst(dut_if_inst); 가 같은 instance 를 양쪽 module 의 포트에 꽂는다. 신호를 하나하나 잇던 02절과 달리 다발 하나를 꽂는다
  5. 오른쪽 점선 틀: ve 라는 handle 이 가리키는 VifExample object. top 의 initial 이 new(dut_if_inst) 로 만든다(슬라이드 28쪽). 이때 넘긴 dut_if_inst 가 생성자에서 this.vif = vif; 로 저장된다
  6. 분홍 화살표: object 안의 vif 는 interface 를 품지 않고 가리킬 뿐이다. 그래서 class 안에서 vif.req = 1; 이라고 쓰면 실제로 dut_if_inst.req 가 바뀌고, DUT 가 그 값을 본다. @(posedge vif.done) 은 DUT 가 올린 done 을 기다린다. 이것이 슬라이드의 "control/observe" 다
  1. The module top frame: slide 26's module top, where all four boxes inside are instantiated
  2. forever #10 clk: flips the clock every 10 time units. That clk and rst go down the arrow into the interface's ports (dut_if dut_if_inst(clk, rst);), the two arrows labelled clk and rst on the slide
  3. The grey box in the middle, interface dut_if: the bundle of Data, Addr, req, done and rw. dut_if_inst under it is the instance name. It is grey because the testbench side (pink) and the DUT side (blue) share it

randomization 과 constraint

Randomization and constraints

슬라이드 30~35쪽. stimulus 는 active(명령을 넣는다)와 passive(DUT 의 사건에 반응한다)로 나뉜다. 이 passive 는 Lecture 2 가 reactive 라고 부른 것이고, 신호를 읽기만 하는 passive monitor 와는 다른 뜻이다. 값은 class 의 rand 변수에 constraint 를 걸고 randomize() 로 만든다. 실패하면 0 을 돌려주고 변수는 이전 값이므로 반환값을 확인한다. 발표자 노트는 $random 을 쓰지 말라고 한다. constraint 는 inside(집합), dist(가중치), implication(조건) 셋이다. dist 의 범위 가중치가 함정이다.

Slides 30 to 35. Stimulus is active (drive commands in) or passive (react to DUT events). This passive is what Lecture 2 called reactive, unrelated to a read-only passive monitor. Values come from rand variables in a class, bounded by a constraint, filled by randomize(). On failure it returns 0 and the variables keep their old values, so check the return. The speaker notes say not to use $random. Constraints come in three shapes: inside (a set), dist (weights) and implication (a condition). The range weight in dist is the trap.

그림 읽기Reading the picture

:= 는 범위 안의 값 하나하나에 그 가중치를 준다. [100:200] 에는 100 부터 200 까지 101 개의 값이 있으므로 범위 전체의 가중치는 20 × 101 = 2020 이다. 왼쪽 판의 가중치 합은 50 + 2020 + 30 = 2100 이다.

슬라이드의 숫자 50, 20, 30 은 합이 100 이라서 퍼센트처럼 보이지만, := 로 쓴 이상 실제로는 왼쪽 판처럼 범위가 96% 를 가져간다. 0 과 250 같은 모서리 값을 일부러 자주 보려던 의도라면 정반대가 된다. 단일 값(0, 250)에서는 := 와 :/ 가 같다. 차이는 범위에서만 난다. :/ 는 LRM 에 있는 보충이다.

:= gives the weight to every value in the range. [100:200] holds 101 values (100 through 200), so the whole range weighs 20 × 101 = 2020. The left panel's weights add up to 50 + 2020 + 30 = 2100.

:/ splits the weight across the range. The whole range gets 20, each value 20 / 101. The right panel sums to 50 + 20 + 30 = 100, so the numbers read directly as percentages: 0 at 50%, the range at 20% (0.20% per value), 250 at 30%.

The slide's 50, 20 and 30 add up to 100 and look like percentages, but written with := the range actually takes 96%, as in the left panel. If the intent was to hit corner values like 0 and 250 often, the result is the opposite. For single values (0, 250) := and :/ are the same; the difference only appears on ranges. :/ is a supplement from the LRM.

checking, coverage, testbench

Checking, coverage, the testbench

슬라이드 37~50쪽. checking 은 두 층이다. signal level 은 assertion(assert property (@(posedge Clk) $rose(Req) |-> ##[2:20] Ready);, "req 가 오르면 2~20 cycle 안에 ready"), behavioral 은 scoreboard, FSM checker, register checker. coverage 는 code coverage(줄, toggle, FSM, branch. 공짜지만 빠진 기능을 못 본다)와 functional coverage(covergroup 이나 cover property 로 직접 짠다)다. covergroup 은 coverpoint 의 값을 bin 에 나눠 세고, cross 는 조합을 센다(47쪽 예는 3 × 3 = 9 칸). sample() 을 불러야만 센다. 슬라이드 50쪽이 이것들을 한 그림에 모은다.

Slides 37 to 50. Checking has two layers: signal level means assertions (assert property (@(posedge Clk) $rose(Req) |-> ##[2:20] Ready);, "if req rises, ready within 2 to 20 cycles"); behavioral means scoreboards, FSM checkers and register checkers. Coverage is code coverage (line, toggle, FSM, branch; free, but blind to missing features) and functional coverage (written by hand as covergroups or cover properties). A covergroup sorts a coverpoint's values into bins, and a cross counts combinations (slide 47's example has 3 × 3 = 9). Nothing is counted unless sample() is called. Slide 50 gathers all of this into one picture.

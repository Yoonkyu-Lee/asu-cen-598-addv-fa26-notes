Transaction 과 sequencer

The transaction and the sequencer

4쪽 "Old Way"(Lecture 16 에도 나온 그림)는 test 가 tb_top.dut.signalA 같은 계층 경로로 핀을 직접 흔든다. 경로에 묶이고, 무엇을 보낼지와 어떻게 흔들지와 정답이 한 블록에 섞인다.

Slide 4's "Old Way" (also in Lecture 16) has the test wiggle pins directly through hierarchical paths like tb_top.dut.signalA: tied to paths, with what to send, how to wiggle and the right answer mixed in one block.

  • 5쪽 transaction dut_ctrl: reset→signalA, address(8 bit)→signalB(16 bit, 위 8 bit 는 0), data_in→signalC, dout→data_out(monitor 가 채운다). ack 에는 field 가 없다(사건일 뿐). field 는 `uvm_field_int(f, UVM_ALL_ON) 로 등록해 copy, compare, print 같은 method 를 자동으로 얻는다
  • Slide 5's transaction dut_ctrl: reset→signalA, address (8 bits)→signalB (16 bits, upper byte 0), data_in→signalC, dout→data_out (filled by the monitor). ack has no field; it's just an event. Fields registered with `uvm_field_int(f, UVM_ALL_ON) get copy, compare, print and friends automatically
  • 7쪽 sequencer: uvm_sequencer #(dut_ctrl) 을 상속하고 constructor 와 `uvm_component_utils 만. 본문이 없다
  • Slide 7's sequencer: extend uvm_sequencer #(dut_ctrl), add a constructor and `uvm_component_utils. No body
함정 · 이름이 비슷한 짝Trap · look-alike pairs

object 냐 component 냐로 가른다. transaction 과 sequence 는 object(new(name), `uvm_object_utils), sequencer, driver, monitor, agent, env 는 component(new(name, parent), `uvm_component_utils). sequence 는 주문서, sequencer 는 접수대다. 그리고 이 덱의 transactor 는 agent 안의 낱개 부품(driver, monitor 등)이다. Lecture 2, 13 과 약어 사전은 transactor 를 agent 와 같은 것으로 썼다.

Split them by object or component. Transactions and sequences are objects (new(name), `uvm_object_utils); sequencers, drivers, monitors, agents and envs are components (new(name, parent), `uvm_component_utils). A sequence is the order form; the sequencer is the order desk. And in this deck a transactor is an individual part inside an agent (driver, monitor and so on), whereas Lectures 2 and 13 and the glossary used it as a synonym for agent.

Driver 와 handshake

The driver and the handshake

8쪽의 네 단계: transaction type 을 parameter 로 class 선언(uvm_driver #(dut_ctrl)), constructor, virtual interface handle 얻기, run_phase loop(item 받기, 해석, 핀 몰기, item 놓기). uvm_driver 에는 seq_item_port 와 req/rsp 가 이미 있다(슬라이드는 port 를 sequence_item_port 로 잘못 적었다). run_phase 는 앞 phase 가 끝나면 자동으로 시작한다.

Slide 8's four steps: declare the class with the transaction type parameter (uvm_driver #(dut_ctrl)), write the constructor, get the virtual interface handle, and loop in run_phase (take an item, interpret, drive pins, release the item). uvm_driver already has seq_item_port and req/rsp (the slide misspells the port as sequence_item_port). run_phase starts automatically after the earlier phases.

호출Call누가Who언제 멈추나When it blocks
get_next_item(req)driveritem 이 올 때까지until an item arrives
item_done()driver멈추지 않는다. 보낸 sequence 를 풀어 준다doesn't; releases the sending sequence
start_item(t)sequence (다음 강의)sequence (next lecture)driver 가 달라고 해서 grant 가 나올 때까지until the driver asks and a grant is issued
finish_item(t)sequence (다음 강의)sequence (next lecture)driver 가 item_done 할 때까지until the driver calls item_done

vif 는 위(top module 이나 test)가 db 에 set 하고 driver 가 꺼낸다. 9쪽은 uvm_resource_db 의 read_by_name 을 쓰고 결과를 확인하지 않는다. 흔한 형태는 uvm_config_db 의 get 과 실패 시 `uvm_fatal 이다.

The vif is set into the db from above (top module or test) and fetched by the driver. Slide 9 uses uvm_resource_db's read_by_name without checking the result; the common form is uvm_config_db's get with a `uvm_fatal on failure.

함정 · 9쪽 driverTrap · slide 9's driver

driver 가 item 마다 objection 을 올렸다 내린다. run_phase 는 objection 이 모두 내려가면 끝나므로, 시간 0 에 아무도 안 올렸거나 item 사이에 0 이 되면 일찍 끝날 수 있다. 흔한 방식은 test(또는 sequence)에서 올리고 내리는 것이다. 또 두 열 배치 때문에 run_phase 가 endclass 뒤에 놓여 보인다. 실제로는 class 안이다. item_done 을 빼먹으면 UVM_ERROR 가 나고 sequence 가 finish_item 에서 못 나온다(자세한 판 12절).

The driver raises and drops an objection per item. run_phase ends when every objection is dropped, so with nothing raised at time 0, or the count touching zero between items, it can end early. The usual way is to raise and drop in the test (or sequence). Also, the two-column layout puts run_phase after endclass; it belongs inside the class. Forget item_done and you get a UVM_ERROR and a sequence stuck in finish_item (full note §12).

Monitor, active/passive, agent

Monitor, active/passive, agent

  • 10~11쪽 monitor: uvm_monitor 는 내장 TLM 도, parameter 도 없는 빈 class 다. constructor 에서 uvm_analysis_port #(dut_ctrl) 을 직접 만들고, loop 에서 신호 변화를 기다려 새 transaction 을 만들고 채워 write() 한다. analysis port 는 연결된 모두에게 방송하는 function 이다(Lab 4 의 mailbox 는 소비자 하나). 11쪽 @(dut_vif.ack) 은 양쪽 edge 에 깨어나 펄스 하나에 transaction 이 둘 나온다
  • Slides 10 to 11, the monitor: uvm_monitor is an empty class, no built-in TLM, no parameter. Create a uvm_analysis_port #(dut_ctrl) in the constructor; in the loop wait for signal changes, build a new transaction, fill it and write() it. An analysis port is a function that broadcasts to every subscriber (Lab 4's mailbox had one consumer). Slide 11's @(dut_vif.ack) wakes on both edges, so one pulse gives two transactions
  • 12쪽 active/passive: 신호를 바꾸면 active(driver), 보기만 하면 passive(monitor). SoC 단계에서 다른 블록이 입력을 몰면 driver 를 끄고 monitor 만 쓴다
  • Slide 12, active/passive: alters signals is active (driver), only observes is passive (monitor). At SoC level, when another block drives the inputs, turn the driver off and keep the monitor
  • 13~14쪽 agent: uvm_active_passive_enum {UVM_PASSIVE=0, UVM_ACTIVE=1}. build_phase 에서 monitor 는 늘, driver 와 sequencer 는 active 일 때만 create. connect_phase 에서 active 면 drv.seq_item_port.connect(seqr.seq_item_export)
  • Slides 13 to 14, the agent: uvm_active_passive_enum {UVM_PASSIVE=0, UVM_ACTIVE=1}. build_phase always creates the monitor, the driver and sequencer only when active; connect_phase does drv.seq_item_port.connect(seqr.seq_item_export) when active

Lab 6(APB agent, assertion)가 이 모양이다. Lecture 10 의 APB 를 transaction 으로 정하고 이 순서로 agent 를 짠다. 과제 문서가 나오면 그쪽이 기준이다.

Lab 6 (APB agent, assertions) has this shape: define Lecture 10's APB as a transaction and build the agent in this order. Once the handout is out, it is the authority.

Magic, env, factory

The magic, the env, the factory

15쪽의 질문Slide 15's question답Answer
is_active 는 어떻게 들어오나How does is_active get set?field macro 로 등록되어 resource database 에서 조회할 수 있고, super.build_phase 가 그 값을 넣는다. super 를 안 부르면 안 들어온다registered by the field macro so it can be looked up in the resource database, and super.build_phase applies the value. Skip super and it never arrives
왜 new() 가 아니라 create()Why create(), not new()?factory 를 거쳐야 나중에 type 을 바꿔칠 수 있다going through the factory lets the type be swapped later
왜 port 를 export 에 connectWhy connect port to export?driver 의 port 가 요청하고 sequencer 의 export 가 큐에서 다음 item 을 내준다. connect 가 둘을 짝짓는다the driver's port requests, the sequencer's export serves the next queued item, and connect pairs them
  • 16~17쪽 env: agent, scoreboard, coverage 를 build_phase 에서 만들고, connect_phase 에서 monitor 의 analysis port 를 scoreboard 에 잇는다. 17쪽은 scoreboard 를 my_agent::type_id::create 로 만드는 오타가 있고, coverage 는 연결하지 않았다
  • Slides 16 to 17, the env: create the agent, scoreboard and coverage in build_phase; connect the monitor's analysis port to the scoreboard in connect_phase. Slide 17 has a typo creating the scoreboard with my_agent::type_id::create, and never connects coverage
  • 18~20쪽 factory: `uvm_*_utils 가 type 을 registry 에 올리고 create() 를 만든다. factory 는 만들기 전에 override 를 확인한다(global 또는 instance). 20쪽: test1 이 set_type_override_by_type(usb2_driver::get_type(), usb3_driver::get_type()) 을 걸면, agent 코드는 그대로인데 usb3_driver 가 만들어진다. override 는 create 전에, override type 은 원래 type 의 자식이어야 한다
  • Slides 18 to 20, the factory: `uvm_*_utils registers the type and defines create(). Before building, the factory checks for overrides (global or instance). Slide 20: test1 sets set_type_override_by_type(usb2_driver::get_type(), usb3_driver::get_type()), and with the agent's code untouched a usb3_driver gets built. The override must come before the create, and the override type must be a child of the original

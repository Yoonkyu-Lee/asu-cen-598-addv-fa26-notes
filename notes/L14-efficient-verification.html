// 1. checking inside stimulus: self-checking test// 1. checking inside stimulus: a self-checking test
push(8'h42);
pop(got);
if (got !== 8'h42) $error("pop: exp 42 got %h", got);

// 2. coverage inside stimulus: directed test 가 직접 sample// 2. coverage inside stimulus: the directed test samples by hand
covergroup cg_occ; occ_cp: coverpoint count { bins empty = {0}; bins full = {16}; } endgroup
cg_occ cg = new();
repeat (16) begin push($urandom); cg.sample(); end

// 3. checking inside coverage: 0 이 나오면 sample 순간 오류// 3. checking inside coverage: a 0 is an error at sample time
addr_cp: coverpoint addr { illegal_bins zero = {0}; bins low = {[1:63]}; }

// 4. coverage within checking: property 문법으로 횟수를 센다// 4. coverage within checking: property syntax, counting hits
full_then_pop: cover property (@(posedge clk) full ##1 pop);
코드 읽기Reading the code
  1. push, pop, count, full 은 FIFO testbench 를 가정한 이름이다. !== 는 4-state 비교라서 got 이 x 여도 틀린 것으로 잡는다. != 를 쓰면 x 와의 비교 결과가 x 라서 if 가 그냥 지나간다
  2. covergroup 에 clocking event 를 안 적었으므로 저절로는 sample 하지 않는다. test 가 cg.sample() 을 부를 때마다 그 순간의 count 를 센다. bin 은 empty(0)과 full(16) 둘이다. 16 은 깊이 16 짜리 FIFO 를 가정한 값이다
  3. illegal_bins zero = {0} 은 coverage 점수에서 빠지는 대신, 0 이 sample 되면 시뮬레이터가 run-time 오류를 낸다
  4. full ##1 pop 은 "full 인 cycle 바로 다음 cycle 에 pop" 이다. assert 가 아니라 cover 라서 실패는 없고, 일어난 횟수만 coverage 보고서에 남는다
  1. push, pop, count and full assume a FIFO testbench. !== is a 4-state compare, so it flags got being x as wrong. With !=, comparing against x yields x and the if just falls through
  2. The covergroup has no clocking event, so it never samples on its own. Each time the test calls cg.sample() it counts the count of that moment. There are two bins, empty (0) and full (16); 16 assumes a 16-deep FIFO
  3. illegal_bins zero = {0} drops out of the coverage score, and if a 0 is sampled the simulator raises a run-time error
  4. full ##1 pop means "a pop in the cycle right after a full cycle." It's a cover, not an assert, so it never fails; it only records how often it happened in the coverage report

함정 · cover property 와 assert propertyTrap · cover property vs assert property

구별 기준: 일어나면 무엇이 되나. 둘은 property 문법이 똑같다. assert property 는 property 가 깨지면 오류를 내고(checking), cover property 는 property 가 성립하면 횟수를 하나 올린다(coverage). 슬라이드가 cover property 를 "coverage within checking" 이라고 부르는 이유가 이것이다. checking 의 문법을 빌렸을 뿐 일은 coverage 다. cover property 는 아무리 0 번이어도 실패하지 않는다. 0 번이면 coverage 보고서에 구멍으로만 남는다.

The criterion: what happens when it occurs. The property syntax is identical. assert property raises an error when the property fails (checking); cover property bumps a count when it holds (coverage). That's why the slide calls cover properties "coverage within checking": the syntax is borrowed from checking, the job is coverage. A cover property never fails, even at zero hits. Zero only shows up as a hole in the coverage report.

같은 쌍이 반대쪽에도 있다. illegal_bins 는 coverage 문법인데 일은 checking 이다. ignore_bins 는 같은 자리에 있어도 아무 오류도 안 낸다. 약어 사전의 ignore_bins · illegal_bins 항목 참조.

The mirror pair exists too: illegal_bins is coverage syntax doing a checking job, while ignore_bins in the same spot raises nothing. See ignore_bins · illegal_bins in the glossary.

왼쪽 위에서 시작해 시계 방향으로 돈다.

  1. sequence → driver, 화살표 "item": sequence 는 "무엇을 보낼지" 를 transaction 단위로 만든다. UVM 은 그 한 덩어리를 sequence item 이라고 부르고, 그래서 화살표 이름이 item 이다. 칸 아래 stimulus 가 이 칸이 stimulus 의 자리라는 표시다
  2. 점선 칸 "initial block / bring-up stimulus": 슬라이드의 둘째 줄. reset 을 걸고 레지스터 몇 개를 쓰는 정도의 첫 동작은 sequence 를 짜기 전에 initial 블록에 바로 쓸 수 있다. 점선은 "정식 자리는 아니지만 가능" 이라는 뜻으로 그렸다
  3. driver → interface, "pins": driver 가 transaction 을 클럭에 맞춘 신호 변화로 바꿔 interface 의 신호에 싣는다
  4. interface → DUT, "drive": interface 의 신호가 DUT 의 입력 포트다
  5. interface 안의 두 칸: assertions(checking)와 cover prop.(cover property, coverage). 슬라이드가 coverage 와 checking 둘 다에 "can also be in interfaces" 라고 적은 것이 이 두 칸이다. 신호 몇 개, 클럭 몇 개 사이의 관계라서 핀이 다 모여 있는 interface 가 제자리다
  6. DUT → interface, "outputs": DUT 의 출력도 같은 interface 의 신호로 나온다
  7. interface → monitor, "pins": monitor 는 신호를 보기만 하고 transaction 으로 되묶는다. 칸 아래 basic checks, cov 는 슬라이드의 "some basic checking in monitors" 와 "can go in monitors" 둘이다
  8. monitor → scoreboard, coverage class, "txn": txn 은 transaction 의 줄임이다. 두 화살표가 같은 transaction 을 두 곳에 나눠준다. scoreboard 는 그것을 정답과 비교하고(checking), coverage class 는 그것으로 covergroup 을 sample 한다(coverage). 둘 다 슬라이드의 "separate" 칸이다

그림에 self-checking stimulus 는 따로 그리지 않았다. 01절의 1번처럼 sequence 나 initial 블록 자체가 기대값을 들고 비교하는 경우라서, 위의 두 stimulus 칸 안에 들어간다.

Start top left and go clockwise.

  1. sequence → driver, arrow "item": a sequence builds "what to send" as transactions. UVM calls each one a sequence item, hence the arrow's name. The stimulus under the box marks it as a stimulus home
  2. The dashed box "initial block / bring-up stimulus": the slide's second line. First moves such as asserting reset and writing a few registers can go straight into an initial block before any sequence exists. Dashed means "not the official home, but allowed"
  3. driver → interface, "pins": the driver turns a transaction into clocked signal changes on the interface
  4. interface → DUT, "drive": the interface signals are the DUT's input ports
  5. The two boxes inside the interface: assertions (checking) and cover prop. (cover property, coverage). These are the slide's "can also be in interfaces" for coverage and checking alike. They relate a few signals across a few clocks, and the interface is where all the pins meet
  6. DUT → interface, "outputs": the DUT's outputs come out on the same interface
  7. interface → monitor, "pins": a monitor only watches the signals and regroups them into transactions. The basic checks, cov under it are the slide's "some basic checking in monitors" and "can go in monitors"
  8. monitor → scoreboard and coverage class, "txn": txn is short for transaction. The two arrows hand the same transaction to two places. 왜 이렇게 나누나. 슬라이드에는 이유가 안 적혀 있다. 이 노트의 보충이다. 칸을 나누면 칸 하나만 바꿔 끼울 수 있다. test 를 바꿀 때 sequence 만, 다른 DUT 에 붙일 때 interface 와 driver 만, 정답이 바뀌면 scoreboard 만 고친다. 반대로 scoreboard 가 interface 신호를 직접 들여다보면 interface 가 바뀔 때 scoreboard 도 고쳐야 한다. Lab 4 릴리스 덱이 이것을 예제 네 개로 보여준다. scoreboard 가 interface 를 직접 보는 판과 monitor 가 scoreboard 를 아는 판에 "bad for reuse" 를 붙이고, monitor 는 transaction 을 mailbox 에 넣기만 하고 scoreboard 가 거기서 꺼내 가는 판을 "Do something like this" 로 고른다.

Why split it this way? The slide doesn't say; this is supplementary. Separate boxes mean you can swap one box at a time: a new test changes only the sequence, a new DUT only the interface and driver, a new expected behaviour only the scoreboard. If the scoreboard peeks at interface signals directly, every interface change drags the scoreboard along. The Lab 4 release deck shows this with four examples. It tags the version where the scoreboard watches the interface, and the one where the monitor knows about the scoreboard, as "bad for reuse," and picks the version where the monitor only drops transactions into a mailbox for the scoreboard to collect: "Do something like this."

답 보기Show answer

코드 읽기Reading the code
  1. $test$plusargs("VERBOSE"): 명령줄에 +VERBOSE 가 있는지만 본다. 있으면 0 이 아닌 값, 없으면 0 을 돌려준다. 값은 안 읽는다. 켜고 끄는 스위치용이다
  2. $value$plusargs("NUM_PACKETS=%d", num_packets): 첫 인자는 찾을 이름(NUM_PACKETS=)과 읽을 형식(%d)을 붙여 쓴 것이다. 명령줄에 +NUM_PACKETS=100 이 있으면 = 뒤의 100 을 10 진수로 읽어 num_packets 에 넣고 0 이 아닌 값을 돌려준다
  3. 찾지 못하면 0 을 돌려주고 변수는 건드리지 않는다. 그래서 if (!...) 안에서 기본값 10 을 넣는다. 슬라이드의 // default 주석이 이 자리다
  4. "TEST=%s" 는 같은 원리로 문자열을 읽는다. +TEST=memory_test 면 test_name 이 "memory_test", 없으면 "basic"

슬라이드의 명령 ./simv +VERBOSE +NUM_PACKETS=100 +TEST=memory_test 로 돌리면 Verbose mode enabled 가 찍히고, num_packets 는 100, test_name 은 "memory_test" 다. 아무 plusarg 없이 ./simv 만 치면 아무것도 안 찍히고 10 과 "basic" 이다.

  1. $test$plusargs("VERBOSE"): checks only whether +VERBOSE is on the command line. Nonzero if so, zero if not. It reads no value: it's for on/off switches
  2. $value$plusargs("NUM_PACKETS=%d", num_packets): the first argument glues the name to look for (NUM_PACKETS=) to the format to read (%d). If +NUM_PACKETS=100 is on the command line, it reads the 100 after = as decimal into num_packets and returns nonzero
  3. If not found it returns zero and leaves the variable alone. That's why the default 10 is set inside if (!...), where the slide's // default comment sits
  4. "TEST=%s" reads a string the same way: with +TEST=memory_test, test_name is "memory_test"; without it, "basic"

Run the slide's command ./simv +VERBOSE +NUM_PACKETS=100 +TEST=memory_test and you get Verbose mode enabled, num_packets = 100 and test_name = "memory_test". Run plain ./simv and nothing prints, with 10 and "basic".

그림 읽기Reading the picture

  2. $info, "prints": 메시지만 찍는다. IEEE 1800 은 "특정한 severity 가 없는 정보성 메시지" 라고 한다
  3. $warning, "prints": run-time warning. 역시 찍기만 한다. 표준은 도구가 warning 을 꺼 둘 수 있게 해도 된다고 한다
  4. $error, "prints, run goes on": run-time error 를 찍지만 시뮬레이션은 계속 간다. 그 아래 errors: 1 (if counted) 는 "누군가 세고 있으면 1" 이라는 뜻이다. 순수 SV 에서는 testbench 가 직접 세야 하고, UVM 은 report server 가 센다
  5. $fatal, "prints, run ends": run-time fatal error 를 찍고 그 자리에서 시뮬레이션을 끝낸다. non-zero exit 는 표준의 "terminates the simulation with an error code" 다. regression 스크립트가 이 종료 코드를 보고 실패로 센다
  6. 점선 구간 "실행되지 않는 구간": $fatal 뒤에 있던 stimulus 와 check 는 하나도 돌지 않는다. 그 뒤에 버그가 더 있어도 이번 실행에서는 안 보인다

네 task 모두 $display 와 달리 파일 이름, 줄 번호, 계층 경로, 시뮬레이션 시간을 메시지에 붙인다. 표준이 그렇게 정했다. 로그에서 "어디서 터졌나" 를 바로 찾을 수 있는 이유다.

  1. From t=0 rightward simulation time flows. The four ticks are the moments each task fires; positions are illustrative and carry no values
  2. $info, "prints": just prints. IEEE 1800 calls it an informative message with no specific severity
  3. $warning, "prints": a run-time warning, also print-only. The standard allows tools to let warnings be suppressed
  4. $error, "prints, run goes on": prints a run-time error, but the simulation keeps going. The errors: 1 (if counted) below means "1, if someone is counting." In plain SV the testbench has to count; in UVM the report server does
  5. $fatal, "prints, run ends": prints a run-time fatal error and ends the simulation on the spot. non-zero exit is the standard's "terminates the simulation with an error code," which regression scripts read as a failure
  6. The dashed stretch, "never simulated": the stimulus and checks after $fatal never run. Bugs further on stay invisible in this run

Unlike $display, all four tasks attach the file name, line number, hierarchical scope and simulation time to the message, because the standard says so. That's how you find "where did it blow up" straight from the log.

Lab 2 testbench 는 첫 불일치에서 $fatal 이었다. 기대하는 쓰기가 일곱 개뿐이고 하나가 틀리면 뒤가 다 밀리는 test 라서 그게 맞았다.

The criterion: is the next cycle worth simulating? A testbench that only calls $error and never judges PASS/FAIL at the end can print errors and still end with "TEST PASSED." In plain SV the testbench has to count errors and decide. Turn every mismatch into $fatal instead and the run stops at the first bug and never sees the next. An overnight regression ends having found one. The usual choice: count mismatches with $error, and save $fatal for situations where carrying on is useless. The Lab 2 testbenches hit $fatal on the first mismatch, which was right there: only seven expected writes, and one wrong one shifts everything after it.

  1. clk: rising edges at x = 100, 260, 420, 580, falling edges at 180, 340, 500, 660. One period is 160 px
  2. data: what the testbench feeds the DUT. Where the two lines cross (x = 180, 500) the value changes: old to 8'h42, then to next. 8'h42 is 8-bit hex 42, i.e. 0100_0010, borrowed from slide 10's code
  3. TB applies (x = 180, pink): the slide's upward arrow. On the falling edge the testbench changes data
  4. DUT samples (x = 260, blue): the slide's top label. On the next rising edge the DUT samples data, which has already been sitting at 8'h42 for half a period. Nothing changes at the same instant, so there's no race
  5. TB observes (x = 340, pink): the slide's downward arrow. On the following falling edge the testbench reads the DUT's output, after the rising-edge result has had half a period to settle
So the testbench drives and observes on the edge half a period away from the DUT's. Simple, but it assumes the DUT's input paths settle within half a period, and @(negedge clk) spreads all over the testbench.
B (slide 10)
  1. clk: the same clock as A
  2. posedge (x = 260, blue): the clocking block's reference edge, clocking cb @(posedge clk) in the code
  3. sample #1ns before (x = 244, pink): default input #1ns. Clocking block inputs (done, result) are read as their value 1 ns before the rising edge. With 16 px = 1 ns, 260 − 16 = 244
  4. done: a DUT output. In RTL it flips from 0 to 1 right at the rising edge (x = 260). But sampling happened at 244, hence sampled 0: the intf.cb.done the testbench reads at this edge is 0. The new 1 is read at the next edge
  5. drive #2ns after (x = 292, pink): output #2ns. Clocking block outputs (req, data) hit the real signals 2 ns after the rising edge: 260 + 2 × 16 = 292. That's where data goes from old to 8'h42. The DUT samples it at the next rising edge (420)
A and B are the same idea: drive away from the DUT's sampling edge, and read the value from just before it. A spaces it by half a period by hand; B declares the spacing once, in the clocking block.

슬라이드 10쪽의 정의. Defines when a testbench samples and drives interface signals relative to a clock, avoiding race conditions between the DUT and testbench. 코드 둘을 그대로 옮겼다. 주석은 슬라이드의 것이다.

  
Slide 10's definition: defines when a testbench samples and drives interface signals relative to a clock, avoiding race conditions between the DUT and testbench. Both code blocks as on the slide, comments included.


interface dut_if(input logic clk);

    logic req;
    logic [7:0] data;
    logic done;
    logic [7:0] result;

    clocking cb @(posedge clk);
        default input #1ns output #2ns;

        output req, data;     // TB drives these 2 ns AFTER posedge
        input  done, result;  // TB samples these 1 ns BEFORE posedge
    endclocking

endinterface

initial begin
    @(intf.cb);

    intf.cb.req  <= 1'b1;
    intf.cb.data <= 8'h42;

    $display("done = %b", intf.cb.done);
end

  

    코드 읽기Reading the code
    
  1. clocking cb @(posedge clk);: 이름이 cb 인 clocking block. 기준은 clk 의 상승 엣지다. interface 안에 둔다
  2. default input #1ns output #2ns;: 이 블록 안의 input 은 엣지 1 ns 전에 샘플하고 output 은 엣지 2 ns 뒤에 구동한다. 이 간격을 skew 라고 부른다. 적지 않으면 표준의 기본값은 input #1step(엣지 직전 시간 단위), output #0 이다
  3. output req, data; 와 input done, result;: 방향은 testbench 에서 본 방향이다. testbench 가 내보내는 것이 output, 받는 것이 input. DUT 의 포트 방향과 반대다
  4. @(intf.cb);: clocking block 의 엣지, 즉 clk 상승 엣지 하나를 기다린다. intf 는 dut_if 의 instance(또는 virtual interface) 이름이다
  5. intf.cb.req <= 1'b1;: clocking block 을 거친 구동. 반드시 <= 를 쓴다. 지금 바로가 아니라 output skew 만큼 뒤, 그림 B 의 x=292 에 실린다
  6. $display("done = %b", intf.cb.done);: intf.cb.done 은 이번 엣지 1 ns 전에 샘플한 값이다. 그림 B 대로라면 done = 0 이 찍힌다. 방금 넣은 req 에 대한 응답이 아니다. 그 응답은 빨라야 다음 엣지 이후에 보인다
슬라이드는 timeunit 이나 `timescale 을 생략했다. #1ns 처럼 단위를 붙여 적었으므로 그대로 동작하지만, 시간 정밀도가 1 ns 보다 굵게 잡혀 있으면 값이 반올림된다.

    
  1. clocking cb @(posedge clk);: a clocking block named cb, referenced to the rising edge of clk, placed inside the interface
  2. default input #1ns output #2ns;: inputs in this block are sampled 1 ns before the edge, outputs driven 2 ns after. These offsets are called skew. If omitted, the standard's defaults are input #1step (one time unit before the edge) and output #0
  3. output req, data; and input done, result;: directions are as the testbench sees them: what the testbench sends is output, what it receives is input. The opposite of the DUT's port directions
  4. @(intf.cb);: waits for one clocking event, i.e. one rising edge of clk. intf is the name of a dut_if instance (or virtual interface)
  5. intf.cb.req <= 1'b1;: a drive through the clocking block, always with <=. It lands not now but one output skew later, at x = 292 in panel B
  6. $display("done = %b", intf.cb.done);: intf.cb.done is the value sampled 1 ns before this edge. Per panel B it prints done = 0. It is not the response to the req just driven; that shows up at the next edge at the earliest
The slide leaves out timeunit or `timescale. Because the skews carry units (#1ns) they still work, but if time precision is coarser than 1 ns the values get rounded.

The same one-line release, and the outcome differs by about a clock depending on the signal kind. If the DUT acted on that 1 in the meantime, you get "I released it, so why did this happen?"

  

  

  함정 · force 는 지우기 전까지 이긴다Trap · force wins until you take it off
  
구별 기준: release 했나. force 는 그 신호에 대한 설계의 모든 대입을 이긴다. release 를 빠뜨린 force 하나가 test 끝까지 DUT 를 묶어 두면, 그 뒤의 실패와 통과가 전부 가짜가 된다. 그리고 위 그림처럼 release 뒤에도 variable 은 잠깐 force 값을 들고 있다. 그래서 force 는 짧게, 쓰고 바로 release, 경로는 한곳에. 04절 XMR 의 규칙과 같다. 또 하나, force 는 testbench 가 DUT 를 설계에 없는 방식으로 움직인다. force 로 만든 상태가 실제 회로에서 도달 가능한 상태인지는 따로 따져야 한다.

  
The criterion: did you release it? A force beats every design assignment to that signal. One force without its release keeps the DUT tied up to the end of the test, and every pass or fail after it is fake. And as the picture shows, a variable still holds the forced value briefly after release. So: force briefly, release right after, keep paths in one place, the same rule as §04's XMRs. One more: force moves the DUT in ways the design never would. Whether a state you reached by force is reachable in real hardware is a separate question.

The second and third columns are this note's examples. The slide's How? has three lines: use XMRs, disable checks, disable constraints. In code:

    코드 읽기Reading the code
    
  1. dut.u_ram.mem[5][3]: dut 안의 u_ram instance 안의 배열 mem 의 5 번 원소의 3 번 비트. 04절의 XMR 로 쓰기를 한 것이다. force 가 아니라 한 번 대입이므로 설계가 그 줄을 다시 쓰면 사라진다. 메모리에 저장된 값이 우주선 같은 것에 맞아 바뀐 상황(soft error)을 흉내 낸다
  2. $assertoff(0, ...) 와 $asserton(0, ...): IEEE 1800 의 assertion 제어 task. 첫 인자 0 은 "지정한 것과 그 아래 전부" 라는 뜻이다. 정상 test 에서 "ECC 오류가 나면 안 된다" 를 지키던 assertion 이 이 test 에서는 오류가 나는 것이 정답이라 꺼야 한다. 슬라이드의 Disable checks 가 이것이다
  3. @(posedge dut.ecc_err_irq);: 대신 기대하는 반응, 오류 interrupt 가 오르는지를 기다린다. 실제 test 에서는 timeout 을 같이 건다. 안 오르면 영원히 기다리기 때문이다
  4. constraint_mode(0): 이름 붙은 constraint 하나를 끈다(Lecture 12 의 19절). 그 뒤 randomize() 는 불법 opcode 도 고를 수 있다. void'(...) 는 반환값을 일부러 버린다는 표시다
이름(u_ram, a_no_ecc_error, ecc_err_irq, c_legal_opcode)은 전부 예다.

    
  1. dut.u_ram.mem[5][3]: bit 3 of element 5 of the array mem, inside instance u_ram, inside dut. That's a write through an XMR from §04. It's a one-time assignment, not a force, so it disappears if the design rewrites that row. It mimics a stored value flipped by, say, a cosmic ray (a soft error)
  2. $assertoff(0, ...) and $asserton(0, ...): IEEE 1800's assertion-control tasks. The first argument 0 means "the named item and everything below it." The assertion that guards "no ECC error" in normal tests must be off here, because in this test an error is the right outcome. That's the slide's Disable checks
  3. @(posedge dut.ecc_err_irq);: waits for the reaction you expect instead, the error interrupt rising. Real tests pair this with a timeout, or a missing interrupt waits forever
  4. constraint_mode(0): switches off one named constraint (Lecture 12, §19). After that randomize() may pick illegal opcodes. void'(...) marks the return value as deliberately ignored
All names (u_ram, a_no_ecc_error, ecc_err_irq, c_legal_opcode) are examples.

  

  

  함정 · error injection 과 bug injectionTrap · error injection vs bug injection
  
구별 기준: 이 test 로 누구의 정확성을 확인하나. 슬라이드 13쪽의 error injection 은 올바른 DUT 에 나쁜 입력이나 나쁜 상태를 넣고 DUT 가 잘 대처하는지를 본다. 검증 대상은 DUT 다. 반면 Lab 4 처럼 plusarg 로 DUT 에 버그를 일부러 심고 켜는 것은 checker 가 그 버그를 잡는지를 본다. 검증 대상은 testbench 다. 둘 다 "일부러 망가뜨린다" 라서 섞이지만 기대하는 결과가 반대다. error injection test 는 통과해야 맞고, 버그를 심은 실행은 실패해야 맞다. 버그를 심었는데 testbench 가 통과시키면 그 checker 는 구멍이 있는 것이다.

  
The criterion: whose correctness does the test check? Slide 13's error injection feeds bad input or bad state to a correct DUT and checks that the DUT copes. The DUT is under test. Planting a bug in the DUT and switching it on with a plusarg, Lab 4 style, checks that the checker catches it. The testbench is under test. Both are "breaking things on purpose," so they blur, but the expected outcomes are opposite: an error-injection test should pass, a planted-bug run should fail. If you plant a bug and the testbench still passes, the checker has a hole.

  
슬라이드 12쪽의 fault injection 은 force 로 고장을 흉내 내는 것이라 error injection 과 거의 같은 자리에서 쓰인다. 이 덱 안에서는 둘을 따로 정의하지 않는다.

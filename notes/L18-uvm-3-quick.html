Item 과 sequence

The item and the sequence

  • 4쪽 item: 보낼 field 는 rand, DUT 가 채우는 출력 field 는 rand 아님. constraint 로 합법 범위를 묶고 solve ... before 로 확률을 옮긴다. solve 는 답의 집합은 그대로 두고 분포만 바꾼다. 슬라이드의 reset field 는 그냥 rand 라 randomize 한 item 의 약 절반이 reset 이다
  • Slide 4's item: fields that are sent get rand; output fields the DUT fills don't. Constraints bound the legal range and solve ... before shifts the odds without changing the solution set. The slide's reset field is plain rand, so about half of all randomized items are resets
  • 5쪽 sequence: uvm_sequence #(item) 을 상속, 이름만 받는 constructor, `uvm_object_utils. 일은 body() 에 적고, req 는 base class 에 이미 있다. `uvm_declare_p_sequencer 는 sequencer 의 멤버가 필요할 때만 쓴다(`uvm_do 에는 불필요)
  • Slide 5's sequence: extend uvm_sequence #(item), name-only constructor, `uvm_object_utils. Work goes in body(); req already exists in the base class. `uvm_declare_p_sequencer is needed only to reach sequencer members (not for `uvm_do)
3

`uvm_do 와 hierarchical sequence

`uvm_do and hierarchical sequences

  • 6쪽: `uvm_do(req) = `uvm_create + randomize() + `uvm_send. sequence 안에서만 쓴다. UVM 1.2 소스의 실제 순서는 create(factory), start_item, randomize, finish_item 이고, finish_item 은 driver 의 item_done 까지 기다린다(Lecture 17 의 handshake)
  • Slide 6: `uvm_do(req) = `uvm_create + randomize() + `uvm_send, only inside a sequence. The real order in the UVM 1.2 source is create (factory), start_item, randomize, finish_item, and finish_item waits for the driver's item_done (Lecture 17's handshake)
  • 7쪽: `uvm_do_with(req, {...}) 는 randomize 에 inline constraint 를 더한다(대신하지 않는다)
  • Slide 7: `uvm_do_with(req, {...}) adds inline constraints to the randomize (never replaces)
  • 8쪽: `uvm_do 를 다른 sequence 에 쓰면 만들고, 그 rand 변수를 randomize 하고, 같은 sequencer 에서 start 한다. 자식은 차례로 끝까지 돈다. depth 가 한 겹마다 1 씩 는다
  • Slide 8: `uvm_do on another sequence creates it, randomizes its rand variables and starts it on the same sequencer. Children run to completion in turn; depth goes up by one per layer
함정 · 조용히 지나가는 실패Trap · failures that slip by

`uvm_do* 의 randomize 가 실패하면 warning(RNDFLD) 하나만 찍고 item 을 그대로 보낸다. 실패한 randomize 는 값을 안 바꾸므로 새 item 의 0 이 간다. 그리고 with 블록 안의 이름은 randomize 되는 object 쪽에서 먼저 찾는다. sequence 의 변수를 가리키려면 local:: 을 쓴다. 8쪽의 this.addr 는 이 점에서 의심스럽다(시뮬레이터로 미확인).

If a `uvm_do* randomize fails, it prints one warning (RNDFLD) and sends the item anyway; a failed randomize changes nothing, so the fresh item's zeros go out. And names in a with block are looked up in the object being randomized first; use local:: to mean the sequence's variable. Slide 8's this.addr is doubtful on this count (not checked on a simulator).

4

Test

The test

  • 9쪽: sequence 는 object, test 는 component. test 하나가 시나리오 하나(env 설정 + 돌릴 sequence 선택). build_phase 에서 env 를 짓고, run_phase 에서 sequence 를 고르고 시작한다
  • Slide 9: sequences are objects, the test is a component. One test, one scenario (env configuration + choice of sequences). Build the env in build_phase; select and start sequences in run_phase
  • 10쪽: `uvm_component_utils, type_id::create("env", this), run_phase 의 raise, seq.start(env.agt.seqr), drop, report_phase 의 `uvm_info(..., UVM_MEDIUM). 슬라이드는 sequence 를 new() 로 만드는데, 그러면 factory override 가 안 먹는다. type_id::create 가 낫다
  • Slide 10: `uvm_component_utils, type_id::create("env", this), raise, seq.start(env.agt.seqr), drop in run_phase, and `uvm_info(..., UVM_MEDIUM) in report_phase. The slide builds the sequence with new(), which escapes factory overrides; type_id::create is better
5

묶고, 컴파일하고, 돌린다

Package, compile, run

  • 11쪽 package 둘: testbench 내용(item, 부품, env)과 sequence/test 를 나누기를 권한다. 각자 import uvm_pkg::*; 와 `include "uvm_macros.svh", test 쪽이 env 쪽을 import. class 파일은 한 package 에만 include 한다(두 곳이면 서로 다른 type 이 된다)
  • Slide 11, two packages: splitting testbench content (item, parts, env) from sequences/tests is recommended. Each has import uvm_pkg::*; and `include "uvm_macros.svh"; the test side imports the env side. Include each class file in one package only (in two, they become different types)
  • 12~13쪽 tb_top: SVTB 의 "glue logic". package 를 import, DUT 와 interface 를 instance, uvm_resource_db 에 virtual interface 를 set, run_test(). 13쪽은 sigA~dout 의 선언이 없어 1 bit implicit net 이 되면 16, 32 bit 신호가 잘린다
  • Slides 12 to 13, tb_top: the SVTB "glue logic". Import the packages, instantiate the DUT and interface, set the virtual interface in uvm_resource_db, call run_test(). Slide 13 never declares sigA to dout, so as 1-bit implicit nets they'd truncate the 16- and 32-bit signals
  • 14쪽 컴파일: UVM, RTL, interface, tb_top, package 를 하나의 elaborated model 로. package 는 그것을 import 하는 파일보다 먼저(슬라이드는 tb_top 을 앞에 적었다). VCS 라면 -ntb_opts uvm-1.2
  • Slide 14, compile: UVM, RTL, interface, tb_top and packages into one elaborated model. Packages before the files importing them (the slide lists tb_top first). With VCS, -ntb_opts uvm-1.2
  • 15쪽 실행: +UVM_TESTNAME=... 로 test 를 고른다. run_test 가 그 이름으로 factory 에서 test 를 만들고(instance 이름 uvm_test_top), phase 를 돌리고, $finish. 다시 컴파일하지 않는다
  • Slide 15, run: +UVM_TESTNAME=... picks the test. run_test builds it from the factory by name (instance name uvm_test_top), runs the phases, then $finish. No recompile

Sub-phase 와 print

Sub-phases and print

  • 16쪽: reset 전용 sequence 를 reset_phase 에서, 트래픽을 main_phase 에서 띄운다. phase 마다 objection 을 따로 올린다. UVM 은 이것을 run-time phase 라고 부르고 run_phase 옆에서 동시에 돈다
  • Slide 16: launch a reset-only sequence from reset_phase and traffic from main_phase, with an objection per phase. UVM calls these run-time phases, and they run alongside run_phase, at the same time
  • 17쪽: driver 에서 req.print(). field macro 로 등록한 field 와 begin_time, depth, parent sequence, sequencer 가 표로 찍힌다. print() 는 verbosity 를 안 탄다. 끄고 켜려면 `uvm_info(id, req.sprint(), UVM_HIGH)
  • Slide 17: req.print() in the driver prints the field-macro fields plus begin_time, depth, parent sequence and sequencer as a table. print() ignores verbosity; to switch it, use `uvm_info(id, req.sprint(), UVM_HIGH)
함정 · 물려받은 run_phaseTrap · the inherited run_phase

16쪽 test 는 10쪽 test 를 상속하고 run_phase 를 덮지 않는다. 그러면 부모의 sequence 가 시간 0 에 reset sequence 와 같이 같은 sequencer 에 줄을 서서, 트래픽이 reset 보다 먼저 갈 수 있고 main 의 트래픽과 섞인다. 빈 run_phase 로 덮거나, 부모를 sequence 없는 base test 로 둔다.

Slide 16's test extends slide 10's and doesn't override run_phase. The parent's sequence then queues on the same sequencer together with the reset sequence at time 0, so traffic can go before the reset and mixes with main's traffic. Override with an empty run_phase, or make the parent a base test with no sequences.

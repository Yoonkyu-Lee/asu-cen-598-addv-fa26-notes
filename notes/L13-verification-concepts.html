줄Line슬라이드의 예Slide's example이 줄이 답하는 질문The question it answers

세 예가 같은 state X 를 두고 서로 다른 질문을 한다는 것이 요점이다. stimulus 줄은 X 로 가는 입력 순서를, checking 줄은 X 에 들어갔을 때 E 가 1 이어야 한다는 판정을, coverage 줄은 X 에 실제로 들어갔다는 사실 자체를 적는다. checking 이 한 번도 실패하지 않았어도 coverage 줄이 비어 있으면 X 에 한 번도 안 갔다는 뜻이고, 그러면 checking 이 통과한 것은 아무 의미가 없다. 이 이야기가 11절의 vacuous pass 에서 그대로 다시 나온다.

The point is that all three examples ask different questions about the same state X. The stimulus line gives the input sequence that leads to X, the checking line the judgment that E must be 1 on entering X, and the coverage line the bare fact that X was entered. If checking never failed but the coverage line is empty, X was never visited, and the passing check means nothing. The same story returns as the vacuous pass in §11.

슬라이드 3쪽은 상자 셋을 원으로 이은 그림 하나다. Stimulus, Checkers, Coverage. 원으로 이은 것은 셋 중 하나만 빠져도 검증이 성립하지 않는다는 뜻으로 읽으면 된다. Lecture 2 의 16절이 같은 그림을 "검증의 삼각대" 로 풀었다. 한 줄씩 다시 붙이면 이렇다.

Slide 3 is a single picture of three boxes joined in a circle: Stimulus, Checkers, Coverage. Read the circle as drop any one and verification no longer holds. Lecture 2, §16 unpacked the same picture as the verification tripod. One line each:

  • stimulus 만 있으면 DUT 가 무엇을 했는지 아무도 판정하지 않는다. 돌기만 하고 끝난다
  • Stimulus alone: nobody judges what the DUT did. It just runs
  • checking 이 없으면 틀린 출력이 나와도 테스트가 통과한다
  • No checking: a test passes even when the output is wrong
  • coverage 가 없으면 checking 이 다 통과해도 무엇을 시험했는지 모른다. 중요한 상황을 한 번도 안 겪었을 수 있다
  • No coverage: even with every check passing, you don't know what was tested. The important situations may never have happened

1 은 stimulus(무엇을 어떻게 넣나, 그리고 넣을 값의 범위를 묶는 constraint). 2 는 checking(scoreboard 가 할 판정). 3 은 coverage("봤다" 가 핵심 단어다. 판정이 아니라 일어났는지를 센다). 4 는 checking 이고, 이런 시간 조건은 assertion 으로 쓰기 좋다(09절). 구별 기준은 동사다. 넣는다 / 맞아야 한다 / 봤다.

1 is stimulus (what to apply and a constraint on the values). 2 is checking (a judgment a scoreboard makes). 3 is coverage ("saw" is the key word: it counts that something happened, not whether it was right). 4 is checking, and timing conditions like this are natural assertions (§09). The verb decides: apply / must be / saw.

Hierarchical verification

슬라이드 9쪽. 검증은 한 번에 칩 전체를 하지 않는다. Unit-level, Sub-system level, Top-level 세 층으로 나눠서 아래부터 한다. 그리고 그 아래 두 줄이 왜 agent 가 필요한지를 이 층 구조로 설명한다.

Slide 9: you don't verify a whole chip in one go. You split it into unit-level, sub-system level and top-level and work from the bottom up. The two lines below explain, through these levels, why agents are needed.

  • Reuse. 아래 층에서 만든 agent 와 checker 를 위 층에서 다시 쓴다
  • Reuse. Agents and checkers built at a lower level are reused higher up
  • Emulate another block that would have been on that interface. unit 하나만 떼어 검증하면 그 unit 의 이웃 블록이 없다. 그 자리에 agent 를 세워서 이웃인 척시킨다
  • Emulate another block that would have been on that interface. When you pull out one unit, its neighbours are missing, so an agent stands in and pretends to be the neighbour

왜 진짜 이웃 RTL 을 붙이지 않나. 슬라이드의 답이 둘이다. "Could have used the RTL or a simpler version of the unit. But that may not be ready or may be buggy." 이웃 RTL 은 아직 없거나 버그가 있을 수 있다. 그리고 "You only need the interface behavior anyway. Using an agent provides more controllability and observability." 필요한 것은 이웃의 interface 동작뿐이고, agent 는 진짜 RTL 보다 원하는 대로 움직이게 하기(controllability) 쉽고 무엇이 오갔는지 보기(observability) 쉽다. 예를 들어 이웃 RTL 은 응답을 늘 3 사이클 만에 주지만 agent 는 1 사이클에도, 50 사이클에도 줄 수 있다.

Why not attach the real neighbour RTL? The slide gives two answers. "Could have used the RTL or a simpler version of the unit. But that may not be ready or may be buggy." And "You only need the interface behavior anyway. Using an agent provides more controllability and observability." All you need is the neighbour's interface behaviour, and an agent is easier to steer (controllability) and easier to watch (observability) than real RTL. A real neighbour may always answer in 3 cycles; an agent can answer in 1 or in 50.

All three panels share a background. The dashed rectangle (all inputs) is every combination you could put on the input pins; the solid rounded rectangle (legal) inside is what the spec allows. The amber diamond (corner) at the top right is a legal but rare case on the boundary, such as "a read and a write in the same cycle at the moment the FIFO is full". Each dot is one test input: pink dots are legal, amber dots illegal.

  1. Directed: only four dots. A person picked them, so one hits the corner exactly (pink ring), but the rest of the space is nearly empty: "4 cases, 1 hits the corner"
  2. Randomized: of 13 dots, 7 are inside legal (pink) and 6 are outside (amber). If the DUT misbehaves on those, the spec never promised anything for them, so it may not be a bug: "failures may be bogus". The corner is missed
  3. Constrained random: all 12 dots are inside legal, because constraints filter the illegal ones. Yet the corner is still empty: random lands rarely on rare places. "corner still missed" is the slide's hard-to-hit

So the slide's prescription is the right panel plus the left panel's one ring. Cover the bulk with constrained random, pin the corner with a directed test. Coverage tells you which corners are still empty (§15).

답 보기Show answer

(가)는 constrained random. 쓰기 확률, 읽기 확률, 데이터 값만 constraint 로 정해 두면 길이는 마음대로 늘어난다. (나)는 corner case 라서 무작위로는 드물다. 깊이만큼 먼저 쓰고 그 다음 사이클에 둘을 같이 거는 directed test 로 만든다. 또는 쓰기 확률을 높게 치우친 random 으로 full 에 자주 닿게 하는 방법도 있다. 어느 쪽이든 "full 에서 동시 접근을 봤다" 는 coverage 항목을 같이 둬야 실제로 일어났는지 안다.

(a) is constrained random: fix the write probability, read probability and data values with constraints and run as long as you like. (b) is a corner case, rare under random, so make it with a directed test: write up to the depth, then issue both in the next cycle. Alternatively, bias the random toward writes so it reaches full often. Either way, add a coverage item "saw simultaneous access while full" so you know it really happened.

  $error("randomize failed");                     //    불법 길이: 0 또는 33~63//    illegal length: 0 or 33..63

CPU 처럼 상태가 많은 설계에서 많이 쓰인다(17절의 Lecture 15 예고 참조).

An irritator is stimulus that stirs up activity unrelated to the feature under test, in the background, to harass the DUT. For example: while testing loads and stores, inject interrupts at random moments, have another master add traffic on the same bus, invalidate cache lines (snoops), or toggle clock gating. The aim is rare overlaps. If §04's corner case is "one feature at its extreme", an irritator goes after "two things landing in the same cycle". It is common for state-heavy designs like CPUs (see the Lecture 15 preview in §17).

  2. The compare per cycle row checks cycle by cycle. Cycle 2: both A, ok. Cycle 4: the model expects B, the DUT emits nothing, ERR. Cycle 5: the DUT emits B, the model expects nothing, ERR again. Cycle 6: both C, ok. Two mismatches
  3. The boundary-accurate model knows no cycle numbers, only "A, B, C must come out in this order". That's why its three boxes sit in a queue at the left instead of in cycle columns
  4. The compare in order row: each time the DUT emits something, compare it with the front of the model's queue. A = A, B = B, C = C, all ok

So the usual practice is to check data and order at the boundary level and to put timing promises in separate assertions (§09). That's common practice, not something the slide says.

셋째 줄: grant 가 막 올라간 tick($rose(gnt)) 다음 tick 에(|=>) grant 가 0 이어야 한다. 그러면 1 인 tick 이 정확히 하나다. 넷째 줄: req 인 tick 부터 1~5 tick 뒤 사이에 gnt 나 abort 가 한 번은 1 이어야 한다. "within 5" 를 1~5 로 읽었고, 같은 tick 도 허용하려면 ##[0:5] 다. 이런 경계를 정하는 것이 assertion 을 쓰는 사람의 몫이고, 스펙 문장이 모호하면 설계자에게 묻는다.

Third line: on the tick after (|=>) grant has just risen ($rose(gnt)), grant must be 0, so it is high for exactly one tick. Fourth line: from a tick with req, gnt or abort must be 1 at least once 1 to 5 ticks later. "Within 5" is read as 1 to 5 here; to allow the same tick, write ##[0:5]. Pinning down such boundaries is the assertion writer's job, and when the spec sentence is ambiguous you ask the designer.

SV 의 immediate assertion(assert (expr);)은 절차 코드 안에서 그 줄이 실행될 때 한 번 보는 것이고(05절 함정), combinatorial 조건을 담을 수는 있지만 같은 말이 아니다. 시험에서 "zero-time = immediate" 로 등호를 그으면 틀린다.

The criterion: the slide sorts by what it says; SV sorts by how it's evaluated. Slide 23's "combinatorial" means the property's content has no time in it. Such properties are still usually written as assert property (@(posedge clk) ...), a concurrent assertion sampled every clock, like the first two lines above. SV's immediate assertion (assert (expr);) is checked once when that line of procedural code runs (§05's trap). It can hold a combinatorial condition, but the two terms are not the same. Equating "zero-time" with "immediate" on a quiz is a mistake.

구별 기준: weak 냐 strong 이냐. 이건 슬라이드 밖의 보충이다. IEEE 1800(2009 판부터)은 assert property 안에 쓴 sequence 를 따로 적지 않으면 weak 로 해석한다. weak 는 "지금까지 본 것으로는 아직 틀렸다고 할 수 없다" 면 성립으로 친다. ##[0:$] gnt[0] 는 아무리 오래 기다려도 "앞으로 올 수 있다" 가 남으므로, 시뮬레이션이 끝날 때 기다리던 시도는 실패로 보고되지 않는다. 24쪽의 "end-of-sim 을 무한으로 친다" 를 실제로 하려면 strong(##[0:$] gnt[0]) 이나 s_eventually gnt[0] 처럼 strong 으로 써야 한다. 시뮬레이터는 보통 끝나지 않은 시도를 따로 표시해 주니(도구마다 다르다) 그 목록을 봐야 한다. 그래서 실무에서 starvation 을 시뮬레이션으로 잡을 때는 31쪽처럼 마감을 넣은 safety 판을 많이 쓴다.

The criterion: weak or strong. This is a supplement beyond the slides. IEEE 1800 (since the 2009 edition) interprets a sequence inside assert property as weak unless told otherwise. Weak holds as long as "what has been seen so far can't yet prove it false". However long you wait, ##[0:$] gnt[0] can still "come later", so an attempt still waiting when the simulation ends is not reported as a failure. Simulators usually list unfinished attempts separately (tool-dependent), and that list is worth reading. That's why starvation is often caught in simulation with a safety version that has a deadline, as on slide 31.

Vacuous passes and assertion coverage

32쪽 제목이 질문이다. All my assertions pass, now what? 첫 덩어리: An assertion has never "fired". 그게 무슨 뜻인가. "Does not necessarily mean that it can't be violated!" 시뮬레이션이 모든 경우를 다 돌린 것(exhaustive)이 아니라면 그렇고, "which in practice it never will be". 그리고 "It might not have fired because it was never active." 애초에 검사할 상황이 한 번도 안 왔을 수 있다.

Slide 32's title is a question: all my assertions pass, now what? First block: an assertion has never "fired". What does that mean? "Does not necessarily mean that it can't be violated!", not unless simulation was exhaustive, "which in practice it never will be". And "It might not have fired because it was never active." The situation it checks may never have come up.

가운데 줄이 정리다. Assertions can either fire & pass, fire & fail, or never fire (vacuous pass). 슬라이드가 셋을 초록, 빨강, 파랑으로 칠했다. 처방은 Bring in assertion coverage! 아래 코드 두 줄이 그 처방이다.

The middle line sums it up: assertions can either fire & pass, fire & fail, or never fire (vacuous pass), coloured green, red and blue on the slide. The prescription is bring in assertion coverage!, and the two lines of code below are that prescription.

assert property ( (sel1 || sel2) |=> ack );     // 검사// the check
cover property  ( sel1 || sel2 );               // 검사의 왼쪽이 실제로 참이 된 횟수// how often the check's left side was actually true

슬라이드는 클럭(@(posedge clk))을 생략했다. 실제로는 직접 쓰거나 default clocking 으로 정해 둔다. 첫 줄은 "sel1 이나 sel2 가 1 인 tick 의 다음 tick 에 ack 가 1" 이다(|=> 는 다음 tick, |-> 는 같은 tick). 둘째 줄은 그 왼쪽(antecedent)만 떼어 cover 를 건 것이다. cover 가 0 이면 첫 줄은 한 번도 fire 하지 않았고, 그 "통과" 는 아무것도 증명하지 않는다.

The slide omits the clock (@(posedge clk)); in practice you write it or set it once with default clocking. The first line says "on the tick after sel1 or sel2 is 1, ack is 1" (|=> is next tick, |-> same tick). The second line covers only its left side (the antecedent). If that cover reads 0, the first line never fired, and its "pass" proves nothing.

Theorem proving 은 수리 논리로 설계가 스펙을 만족함을 증명한다. 이 강의의 assertion 과 이어지는 것은 가운데, property checking 이다. 35~36쪽이 그것을 FPV(Formal Property Verification)라고 부른다.

  
The speaker note attached to slide 4 belongs here by content. It explains the three techniques: equivalence checking compares two representations of a design (e.g., RTL and gate-level) for identical behaviour, used to confirm synthesis, place and route or ECOs broke nothing; model checking explores all possible states of the design to see whether properties (no deadlock, safety, liveness) hold; theorem proving proves with mathematical logic that the design meets its spec. The one that connects to this lecture's assertions is the middle one, property checking, which slides 35 and 36 call FPV (Formal Property Verification).

  

  함정 · "100% functional correctness" 는 무엇에 대한 100% 인가Trap · 100% functional correctness of what
  
구별 기준: 증명된 것은 설계가 아니라 property 다. 같은 발표자 노트가 formal 의 장점으로 "100% Functional Correctness" 를 든다. 정확히는 적어 둔 property 가, 적어 둔 assume 아래에서 100% 성립한다는 뜻이다. property 를 빠뜨렸으면 그 부분은 증명된 적이 없고, assume 이 너무 좁으면 실제로 올 입력을 배제한 채 증명한 것이다. "formal 로 증명했다" 는 말을 들으면 무엇을, 어떤 assume 아래서를 묻는다. 이건 일반적인 주의이고 슬라이드의 말은 아니다.

  
The criterion: what gets proven is the property, not the design. The same speaker note lists "100% Functional Correctness" as a benefit of formal. Precisely, it means the properties you wrote hold 100% under the assumptions you wrote. A missing property was never proven, and an overly narrow assume proves things while excluding inputs that will really arrive. When you hear "we proved it formally", ask what, and under which assumes. This is a general caution, not the slide's words.

41쪽은 제목 Crosses 아래 두 단어, ignore_bins, illegal_bins 뿐이다. 문법은 Lecture 12 의 12절에서 봤다. cross 는 두 coverpoint 의 조합을 세고, bin 수는 각 coverpoint 의 bin 수를 곱한 것이다. 14절의 카운터 버그를 잡는 covergroup 을 이 노트가 써 보면 이렇다.

  
Slide 41 is the title Crosses over two words, ignore_bins, illegal_bins. The syntax was in Lecture 12, §12: a cross counts combinations of two coverpoints, and its bin count is the product of theirs. Here is a covergroup, written by this note, that would catch §14's counter bug.


covergroup cg_ops @(posedge clk iff rst_n);       // reset 중에는 세지 않는다// don't count during reset
  wr: coverpoint (wr_en && !full);             // 받아들여진 쓰기: 0 또는 1// an accepted write: 0 or 1
  rd: coverpoint (rd_en && !empty);            // 받아들여진 읽기: 0 또는 1// an accepted read: 0 or 1
  wr_x_rd: cross wr, rd {                       // 2 x 2 = 4 칸// 2 x 2 = 4 bins
    ignore_bins idle = binsof(wr) intersect {0} &&
                       binsof(rd) intersect {0};   // (0,0) 은 안 센다: 3 칸// skip (0,0): 3 bins left
  }
  flags: coverpoint {full, empty} {
    illegal_bins both = {2'b11};                 // 가득 차면서 비었다: 나오면 오류// full and empty at once: error if seen
  }
endgroup

(wr, rd) = (1, 0)쓰기만write only찼다hit

cross 점수는 3 칸 중 2 칸, 67% 다. code coverage 는 100% 였는데 functional 은 빈칸 하나를 정확히 가리킨다. 두 단어의 차이는 이렇다. ignore_bins 는 "이 조합은 관심 없다" 라서 세지도 않고 분모에서도 뺀다. illegal_bins 는 "이 조합은 일어나면 안 된다" 라서 나오는 순간 오류를 낸다. 위 flags 의 2'b11 처럼 일종의 assertion 역할도 한다.

  
The cross scores 2 of 3 bins, 67%. Code coverage said 100%; functional coverage points straight at the one empty cell. The difference between the two words: ignore_bins means "not interested in this combination", so it's neither counted nor in the denominator. illegal_bins means "this combination must never happen", so it errors the moment it shows up; like flags's 2'b11 above, it doubles as a kind of assertion.

  
어디서 sample 하나Where to sample

  
42쪽은 Sampling Covergroups: Where to sample is important 한 줄이다. covergroup 은 sample() 이 불리거나 지정한 clock 이 올 때만 센다(Lecture 12 의 12절). 그 시점을 잘못 고르면 숫자가 거짓말을 한다. 흔한 경우 셋이다.

  
Slide 42 is one line: Sampling Covergroups: where to sample is important. A covergroup counts only when sample() is called or its clock fires (Lecture 12, §12). Pick the moment badly and the numbers lie. Three common cases:

  
    
    
  • 요청 시점이 아니라 받아들여진 시점에. 위 코드가 wr_en 이 아니라 wr_en && !full 을 센 이유다. full 일 때의 wr_en 은 DUT 가 버린 요청이다. 그걸 "쓰기" 로 세면 일어나지 않은 일을 센 것이다. handshake 가 있는 버스라면 valid 와 ready 가 둘 다 1 인 사이클이다
    • 
    
  • When accepted, not when requested. That's why the code above counts wr_en && !full, not wr_en. A wr_en while full is a request the DUT dropped; counting it as a "write" counts something that never happened. On a handshake bus, it's the cycle where valid and ready are both 1
    • 
    
  • reset 중에는 세지 않는다. 위의 iff rst_n 이 그것이다. reset 중의 값은 의미 없고, flags 처럼 reset 값이 특이한 신호는 엉뚱한 칸을 채운다
    • 
    
  • Not during reset. That's the iff rst_n above. Values during reset mean nothing, and signals with odd reset values (like the flags) fill the wrong bins
    • 
    
  • clock 마다냐, transaction 마다냐. 매 clock 에 sample 하면 아무 일 없는 사이클이 수없이 세져서 비율이 왜곡된다. transaction 단위 항목은 monitor 가 transaction 을 하나 완성했을 때 sample() 한다. 02절 그림에서 Coverage 가 Monitor 뒤에 있는 이유다
    • 
    
  • Per clock or per transaction. Sampling every clock counts countless idle cycles and skews the ratios. Transaction-level items are sampled when a monitor completes a transaction, which is why Coverage sits after the Monitor in §02's picture

Merge 와 exclusion list
Merging and exclusion lists

  
43쪽. Coverage Merge: .. And do not count coverage for failing tests. 회귀 테스트는 수백, 수천 개의 test 를 따로 돌리고, 각 test 가 coverage 파일을 하나씩 남긴다. 그것들을 합친 것(merge)이 프로젝트의 coverage 다. 그리고 실패한 test 의 coverage 는 합치지 않는다. Lecture 2 의 16절이 같은 규칙을 이미 적었다. 44쪽 Exclusion Lists 는 제목만 있다.

  
Slide 43: Coverage Merge: .. and do not count coverage for failing tests. A regression runs hundreds or thousands of tests separately, each leaving a coverage file; merging them gives the project's coverage. And failing tests' coverage is not merged. Lecture 2, §16 already stated the same rule. Slide 44, Exclusion Lists, is title only.

위의 b0~b5 가 coverage 의 bin 여섯 칸이다. 가로줄 위가 test 별 결과, 아래가 합친 결과다.
  1. test1 (pass) 는 b0, b1 을, test2 (pass) 는 b1, b3 을 채웠다. b1 은 둘 다 채웠지만 합칠 때는 "한 번 이상" 만 따지므로 1 칸이다
  2. test3 (FAIL) 은 b4, b5 를 채웠지만 amber 다. checker 가 실패를 냈다는 것은 그 run 에서 DUT 가 틀리게 동작했거나 testbench 가 틀렸다는 뜻이다. 그 run 이 b4, b5 를 "겪었다" 고 해도 그 상황에서 DUT 가 옳았다는 증거가 아니다. 그래서 not merged
  3. merged (passing): 통과한 test1 과 test2 만 합친다. b0, b1, b3 이 1, b2, b4, b5 가 0. 3/6 = 50%
  4. with exclusion b2: 리뷰해 보니 b2 는 이 설정에서 일어날 수 없는 칸이라 exclusion list 에 올렸다(excl). 분모에서 빠지므로 3/5 = 60%
  5. 맨 아래 줄: test3 을 합쳤다면 b4, b5 가 채워져 5/6 = 83% 가 됐을 것이다. 틀리게 동작한 run 이 점수를 33 포인트 올린 셈이다. 43쪽이 막으려는 것이 이것이다
그림의 b4 와 b5 는 아직 통과한 test 로는 안 채워졌다. test3 의 버그를 고친 뒤 다시 돌려 통과해야 그 칸이 비로소 찬다.

    
b0 to b5 on top are six coverage bins. Above the horizontal line are per-test results, below it the merged result.
  1. test1 (pass) filled b0 and b1; test2 (pass) filled b1 and b3. Both filled b1, but merging only asks "at least once", so it's one bin
  2. test3 (FAIL) filled b4 and b5, but in amber. A checker failure means that in that run the DUT behaved wrongly or the testbench was wrong. Even if the run "experienced" b4 and b5, that's no evidence the DUT was right there. Hence not merged
  3. merged (passing): only the passing test1 and test2 are merged. b0, b1, b3 are 1; b2, b4, b5 are 0. 3/6 = 50%
  4. with exclusion b2: review found b2 can't occur in this configuration, so it went on the exclusion list (excl). Out of the denominator: 3/5 = 60%
  5. Bottom line: merging test3 would have filled b4 and b5 for 5/6 = 83%, a 33-point gain from a run that behaved wrongly. That is what slide 43 guards against
b4 and b5 are not yet filled by any passing test. Only after test3's bug is fixed and it reruns clean do those bins count.

Full namecoverage merge, exclusion list (or coverage exclusion); the slides give only the names

        
One linemerging combines many tests' coverage into one. An exclusion list removes unreachable or uninteresting coverage items from the denominator

        
Whenmerging automatically after every regression; exclusions when coverage stalls near 100% and the remaining holes are reviewed one by one

        
Whomerging by regression scripts and the coverage tool; exclusions proposed by verification engineers and reviewed and signed off with the designers

        
Easy to confuseExclusion is the easiest way to raise the score, which makes it the most dangerous. Exclude a reachable bin as "unreachable" and the hole vanishes from the number, so every exclusion records its justification. ignore_bins (§15) removes items in code when writing a covergroup; exclusion lists mostly remove code-coverage items on the tool side

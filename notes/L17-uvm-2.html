옛날 방식: test 가 핀을 직접 흔든다

The old way: the test wiggles pins itself

4쪽 오른쪽은 이 강의 내내 쓰는 DUT 다. tb_top 안에 dut 가 있고, 입력이 셋(signalA 1 bit, signalB 16 bit, signalC 32 bit), 출력이 둘(ack 1 bit, dout 32 bit)이다. 이름이 일부러 의미가 없다. 무엇을 하는 회로인지는 중요하지 않고 port 의 모양만 중요하다는 뜻으로 읽힌다.

The right side of slide 4 is the DUT used throughout the lecture: dut inside tb_top, with three inputs (signalA 1 bit, signalB 16 bits, signalC 32 bits) and two outputs (ack 1 bit, dout 32 bits). The names are deliberately meaningless; what the circuit does doesn't matter, only the shape of its ports.

왼쪽이 "Old Way" 다. test module 의 initial 블록 하나가 tb_top.dut.signalA 같은 계층 경로로 DUT 의 입력을 직접 쓰고, 시간을 기다리고, ack 를 기다린 뒤 dout 을 기대값과 비교해 $display 로 통과를 찍고 $finish 한다. 슬라이드는 "Old Way" 라는 이름표만 붙이고 무엇이 나쁜지는 말로 적지 않았다. 다음 쪽부터 하는 일을 거꾸로 읽으면 이 노트가 보기에 문제는 넷이다.

The left side is the "Old Way": a single initial block in a test module writes the DUT's inputs directly through hierarchical paths like tb_top.dut.signalA, waits, waits for ack, compares dout with an expected value, prints a pass with $display and calls $finish. The slide only labels it "Old Way" and doesn't spell out what's wrong. Reading the rest of the deck backwards, this note sees four problems.

  1. 경로와 port 이름에 묶인다. tb_top.dut.signalB 는 Lecture 14 의 XMR 이다. DUT 가 다른 계층에 들어가거나 port 이름이 바뀌면 test 를 다 고친다
  2. Tied to paths and port names. tb_top.dut.signalB is an XMR from Lecture 14; move the DUT in the hierarchy or rename a port and every test needs editing
  3. 무엇을 보낼지, 어떻게 핀을 흔들지, 무엇이 정답인지가 한 블록에 섞였다. 하나만 바꾸고 싶어도 셋을 다 만진다
  4. What to send, how to wiggle pins, and what's correct are mixed in one block. Changing one means touching all three
  5. 값이 손으로 박혀 있다. 32'habcd_6789 같은 상수뿐이라 randomize 할 자리가 없다
  6. Values are hard-coded. Constants like 32'habcd_6789 leave no place to randomize
  7. 다른 단계에서 못 쓴다. SoC 단계에서 이 DUT 의 입력을 다른 블록이 몰면 이 test 는 통째로 쓸모가 없다. 07절의 passive 가 이 문제의 답이다
  8. Useless at another level. At SoC level, when another block drives this DUT's inputs, the whole test is useless. §07's passive mode is the answer to this

02

Transaction: port 를 class 로 옮긴다

The transaction: moving ports into a class

5쪽의 첫 단계는 port 를 동작 수준에서, struct 처럼 다시 적는 것이다. 핀 이름(signalA)이 아니라 그 핀이 하는 일의 이름(reset)으로 적는다. 다음 단계에서 그 field 들을 uvm_sequence_item 을 상속한 class 에 넣고, field macro 로 감싼다. 슬라이드의 class 이름은 dut_ctrl 이다.

Slide 5's first step is to restate the ports at a behavioural level, like a struct: named for what the pin does (reset), not what it's called (signalA). The next step puts those fields in a class extending uvm_sequence_item and wraps them with field macros. The slide's class is called dut_ctrl.

그림 읽기Reading the picture

왼쪽 분홍 상자는 testbench 쪽 class, 오른쪽 파란 상자는 DUT 의 port 다. 오른쪽 숫자는 방향(in/out)과 폭(bit 수)이다. 줄마다 짝을 읽으면 이렇다.

  1. reset → signalA(1 bit → 1 bit). 슬라이드는 signalA 를 reset 으로 쓰기로 정했다. 9쪽 driver 는 reset 이 1 인 item 을 받으면 signalA 를 0 으로 내렸다가 1ns 뒤 1 로 올린다. 즉 active-low reset 펄스다. field 값 1 이 "reset 을 하라" 이고 핀 값 0 이 "reset 중" 이라 둘의 극성이 반대다
  2. address → signalB(8 bit → 16 bit). 폭이 다르다. 8 bit 값을 16 bit 핀에 대입하면 SystemVerilog 는 위 8 bit 를 0 으로 채운다. 예를 들어 address = 8'hA5 면 signalB = 16'h00A5 다. 그래서 이 transaction 으로는 signalB 의 위 8 bit 를 영영 몰 수 없다. 슬라이드가 이 차이를 설명하지는 않는다
  3. data_in → signalC(32 → 32). 그대로 옮긴다
  4. dout → data_out(32 → 32). 방향이 반대다. DUT 의 출력이므로 driver 가 몰 수 없고, monitor 가 핀을 읽어 이 field 를 채운다(11쪽). 그래서 이 field 는 보낼 때는 의미가 없고 관찰할 때만 의미가 있다
  5. ack 에는 field 가 없다. 11쪽 monitor 는 ack 의 변화를 "지금 읽어라" 는 신호로만 쓴다. 값이 아니라 사건이라 transaction 에 담지 않았다

즉 transaction 의 field 는 핀의 목록이 아니라 "한 번의 거래에서 의미 있는 값" 의 목록이다. 그래서 폭, 이름, 극성, 방향이 핀과 달라도 된다. 그 차이를 메우는 것이 driver 와 monitor 의 일이다.

The pink box on the left is a testbench class; the blue box on the right is the DUT's ports, with direction (in/out) and width in bits. Row by row:

  1. reset → signalA (1 bit → 1 bit). The slide decides signalA is the reset. Slide 9's driver, given an item with reset = 1, pulls signalA to 0 and raises it to 1 after 1ns: an active-low reset pulse. Field value 1 means "do a reset" and pin value 0 means "in reset", so the polarities are opposite
  2. address → signalB (8 bits → 16 bits). The widths differ. Assigning an 8-bit value to a 16-bit pin zero-fills the upper 8 bits, so address = 8'hA5 gives signalB = 16'h00A5. This transaction can never drive signalB's upper byte. The slide doesn't comment on the mismatch
  3. data_in → signalC (32 → 32): carried straight across
  4. dout → data_out (32 → 32). The direction is reversed. It's a DUT output, so no driver can drive it; the monitor reads the pin and fills this field (slide 11). The field means nothing when sending, only when observing
  5. ack has no field. Slide 11's monitor uses a change on ack only as the cue "read now". It's an event, not a value, so it isn't stored

So a transaction's fields aren't a list of pins but a list of the values that matter in one exchange. Width, name, polarity and direction can all differ from the pins; bridging that gap is the driver's and monitor's job.

Sequence vs sequencer

구별 기준은 "object 냐 component 냐" 하나다. sequence(uvm_sequence)는 item 을 몇 개, 어떤 값으로, 어떤 순서로 보낼지를 담은 object 다. 실행할 때 만들고 끝나면 버린다. sequencer 는 testbench 계층에 붙박인 component 로, sequence 와 driver 사이의 창구다. 비유하면 sequence 는 주문서, sequencer 는 주문 접수대다. 이 덱에는 sequence 가 나오지 않는다(약어 사전의 Sequence (UVM) 항목, Lecture 14 의 02절). 21쪽이 test 를 돌리는 법을 다음 강의로 넘겼으므로 거기서 나올 것으로 보인다.

The one test is object or component? A sequence (uvm_sequence) is an object describing how many items to send, with what values, in what order; it's made when run and discarded after.   1. driver: get_next_item(). driver 의 loop 가 시작하자마자 다음 item 을 달라고 한다. 아직 아무도 안 보냈으니 여기서 멈춘다(아래 회색 막대 "waiting"). task 라서 멈출 수 있다
  2. sequence: start_item(). sequence 가 "보낼 게 있다" 고 sequencer 에 줄을 선다. driver 가 이미 기다리고 있으므로 sequencer 가 바로 grant(보라 화살표, 차례를 준다)를 내린다. 보라색인 이유는 이 판정이 UVM 라이브러리 안에서 일어나기 때문이다
  3. set fields. grant 를 받은 뒤에 item 의 값을 정한다(보통 randomize()). 값을 늦게 정하는 이유는 보내기 직전의 상태를 반영할 수 있어서다
  4. sequence: finish_item(). item 을 sequencer 에 넘긴다(분홍 꺾은선 "item"). sequencer 는 그것을 driver 에게 내준다("req"). 그 순간 driver 의 get_next_item 이 returns req, 즉 req 변수에 그 item 의 handle 을 담고 돌아온다. 반대로 sequence 는 finish_item 안에서 멈춘다(위 회색 막대 "waiting in finish_item()")
  5. driver → pins, "vif". driver 가 req 를 해석해 virtual interface 로 signalB, signalC 를 쓴다. 파란 막대가 핀이 몰리는 동안이고, 이때 실제로 시뮬레이션 시간이 흐른다(9쪽의 #1ns 같은 지연)
  6. driver: item_done(). "이 item 은 끝났다". 분홍 화살표 unblocks 가 sequence 쪽으로 올라가 finish_item() returns, sequence 가 다음 item 으로 넘어간다
  7. driver: get_next...(다시 get_next_item). loop 의 처음으로 돌아가 또 멈춘다. 보낼 것이 더 없으면 driver 는 여기서 영원히 멈춰 있다. driver 의 loop 는 스스로 끝나지 않고, 시뮬레이션의 끝은 아래 objection 이 정한다

정리하면 누가 기다리나가 핵심이다. driver 는 item 이 올 때까지(get_next_item), sequence 는 driver 가 그 item 을 다 쓸 때까지(finish_item) 기다린다. 그래서 sequence 는 driver 보다 앞서 나갈 수 없다. 12절 도구로 한 단계씩 밟아볼 수 있다.

Four rows, four players, time running right. Read left to right in the order things happen.

  1. driver: get_next_item(). As soon as the driver's loop starts, it asks for the next item. Nobody has sent one, so it blocks here (the grey "waiting" bar). It's a task, so it can block
  2. sequence: start_item(). The sequence queues up at the sequencer: "I have something to send". The driver is already waiting, so the sequencer immediately issues a grant (violet arrow: your turn). Violet because that decision happens inside the UVM library
  3. set fields. The item's values are decided after the grant, usually by randomize(), so they can reflect the state just before sending
  4. sequence: finish_item(). The item goes to the sequencer (pink path "item"), which hands it to the driver ("req"). At that moment the driver's get_next_item returns req: it comes back with that item's handle in req. The sequence, meanwhile, blocks inside finish_item (top grey bar)
  5. driver → pins, "vif". The driver interprets req and writes signalB and signalC through the virtual interface. The blue bar is the time the pins are driven; simulation time actually passes here (delays like slide 9's #1ns)
  6. driver: item_done(): "this item is finished". The pink unblocks arrow rises to the sequence, finish_item() returns, and the sequence moves to its next item
  7. driver: get_next... (get_next_item again). Back to the top of the loop, blocked again. With nothing more to send, the driver stays blocked forever. Its loop never ends on its own; the objections below decide when simulation ends

The point is who waits for whom. The driver waits for an item (get_next_item); the sequence waits for the driver to finish with it (finish_item). So a sequence can never run ahead of its driver. §12's tool lets you step through it.

Where the virtual interface comes from

9쪽의 driver 는 "dut_if_ptr" 라는 이름으로 저장된 virtual interface 를 꺼내기만 한다. 누가 그것을 넣는지는 이 덱에 없다. 보통은 DUT 와 interface 를 instance 한 top module 이 시뮬레이션 시작 때 넣는다. Lecture 12 의 08절에서 virtual interface 는 "top 이 실제 instance 를 넘겨주지 않으면 null" 이었다. UVM 에서는 그 넘겨주기를 component 의 constructor 인자가 아니라 전역 저장소로 한다. Part I(Lecture 16 의 11절)이 그 장치로 uvm_resource_db 의 set 과 read_by_name 을 소개했다. agent 와 env 가 그 사이에 몇 겹 끼어 있어도 손으로 한 칸씩 전달할 필요가 없다.

Slide 9's driver only retrieves a virtual interface stored under the name "dut_if_ptr"; who stores it isn't in this deck. Normally the top module that instantiates the DUT and interface stores it at the start of simulation. In Lecture 12, §08, a virtual interface was "null unless top hands over a real instance". UVM does that handover through a global store instead of constructor arguments (Part I, Lecture 16 §11, introduced uvm_resource_db's set and read_by_name for it), so however many layers of agent and env sit in between, nobody has to pass it down by hand.

class my_driver extends uvm_driver #(dut_ctrl);
  `uvm_component_utils(my_driver)
  virtual dut_signals vif;

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    if (!uvm_config_db #(virtual dut_signals)::get(this, "", "vif", vif))
      `uvm_fatal("NOVIF", "no virtual interface for this driver")
  endfunction

  task run_phase(uvm_phase phase);
    forever begin
      seq_item_port.get_next_item(req);   // item 이 올 때까지 멈춘다// blocks until an item arrives
      if (req.reset) begin                // active-low reset 펄스// active-low reset pulse
        vif.signalA = 1'b0;
        #1ns vif.signalA = 1'b1;
      end else begin
        vif.signalB = req.address;        // 8 bit 를 16 bit 에: 위 8 bit 는 0// 8 bits into 16: upper byte is 0
        vif.signalC = req.data_in;
      end
      seq_item_port.item_done();          // 보낸 sequence 의 finish_item 을 푼다// releases the sender's finish_item
    end
  endtask
endclass

module tb_top;
  import uvm_pkg::*;
  dut_signals dif();                      // 진짜 interface instance// the real interface instance
  my_dut dut(.signalA(dif.signalA), .signalB(dif.signalB), .signalC(dif.signalC),
             .ack(dif.ack), .dout(dif.dout));
  initial begin
    uvm_config_db #(virtual dut_signals)::set(null, "*", "vif", dif);
    run_test();                           // test 를 고르고 phase 를 돌린다. 다음 강의// picks the test and runs the phases; next lecture
  end
endmodule

set 의 "*" 는 "어느 component 든 이 이름으로 찾으면 준다" 는 scope 다. 실제 프로젝트에서는 "uvm_test_top.env.agt.*" 처럼 좁혀서 같은 type 의 agent 여럿에 서로 다른 interface 를 준다. run_test() 와 `include "uvm_macros.svh" 같은 준비는 이 덱 밖이다.

Monitor 와 analysis port

The monitor and the analysis port

10쪽이 monitor 를 짜는 순서다. 1. constructor 를 쓰고 그 안에서 TLM analysis port 를 만든다. 2. virtual interface 의 handle 을 얻는다. 3. run_phase loop 에서 a. interface 신호의 변화를 기다리고, b. transaction 을 만들고, c. 신호를 transaction 에 옮겨 적고, d. analysis port 에 쓴다. 오른쪽 첫 줄은 슬픈 얼굴을 달고 이렇게 말한다. uvm_monitor 에는 내장 TLM 기능이 없고, 따로 하는 일도 없으며, parameter 를 받는 class 도 아니다. driver 와 달리 port 를 우리가 직접 만들어야 하는 이유다. 둘째 줄은 driver 와 같다. run_phase 는 앞 phase 가 끝나면 자동으로 시작한다.

Slide 10 is the recipe for a monitor: 1. write the constructor and create a TLM analysis port in it; 2. get the virtual interface handle; 3. in a run_phase loop, a. wait for interface signal changes, b. create a transaction, c. transcribe the signals into it, d. write it to the analysis port. The first bullet on the right comes with a sad face: uvm_monitor has no built-in TLM features, no unique features at all, and isn't a parameterised class. That's why, unlike the driver, you make the port yourself. The second bullet matches the driver's: run_phase starts automatically after the earlier phases.

11쪽 코드는 그 순서다. constructor 에서 trans_port = new("trans_port", this) 로 port 를 만들고(port 는 TLM 부품이라 factory 가 아니라 new 로 만든다), connect_phase 에서 driver 와 똑같이 vif 를 꺼낸다. loop 는 매번 transaction 을 새로 만들고, @(dut_vif.ack) 로 ack 의 변화를 기다리고, objection 을 올리고, signalB, signalC, dout 을 address, data_in, data_out 에 옮기고, objection 을 내린 뒤 trans_port.write(my_trans) 한다.

Slide 11's code follows that order. The constructor builds the port with trans_port = new("trans_port", this) (ports are TLM parts, built with new, not the factory), and connect_phase fetches the vif exactly as the driver did. The loop makes a fresh transaction each time, waits for a change on ack with @(dut_vif.ack), raises an objection, copies signalB, signalC and dout into address, data_in and data_out, drops the objection, then calls trans_port.write(my_trans).

즉 mailbox 는 "한 사람에게 건네주기", analysis port 는 "방송하기" 다. monitor 가 누가 듣는지 몰라도 되게 만든 것이 핵심이고, Lab 4 의 06절에서 sv_style_4 가 mailbox 로 이루려던 것(monitor 가 scoreboard 를 모르게 하기)을 한 걸음 더 간 것이다.

  1. Left, Lab 4. The monitor put()s into a mailbox and the scoreboard get()s from it. A mailbox stores things, and what one consumer takes is gone. To give coverage the same transaction you'd need a second mailbox and a second put. That's what the two grey lines, "one consumer per entry" and "task: can block, stores items", mean
  2. Right, UVM. The violet square at the monitor's right edge is the port (analysis port). The monitor calls write(t) once, and every subscriber connected to it (scoreboard, coverage, the dashed "subscriber N") gets the same transaction handle
  3. The dashed subscriber N: any number of subscribers, zero included. Used passively with nobody attached, the monitor code doesn't change
  4. "function: never blocks" at the bottom: write is a function, not a task. No time passes and it never waits. A subscriber that wants to process slowly must keep its own FIFO (§10)

A mailbox is "hand it to one person"; an analysis port is "broadcast". The point is that the monitor needn't know who's listening, one step further than what Lab 4, §06's sv_style_4 achieved with a mailbox (a monitor that doesn't know the scoreboard).

함정 · @(ack) 는 두 번 깨어난다Trap · @(ack) wakes up twice

11쪽의 @(dut_vif.ack) 는 edge 를 지정하지 않았다. SystemVerilog 에서 @(신호) 는 값이 바뀔 때마다 깨어난다. ack 가 0→1→0 으로 펄스를 한 번 치면 0→1 에서 한 번, 1→0 에서 한 번, transaction 이 둘 나온다. 둘째 것은 ack 가 내려간 뒤의 값을 담으니 scoreboard 가 받으면 가짜 불일치가 난다. 거래 하나에 transaction 하나를 원하면 @(posedge vif.ack) 처럼 edge 를 정한다. 덧붙여 11쪽 monitor 는 signalA(reset)를 읽지 않으므로 이 monitor 로는 reset item 이 관찰되지 않고, signalB 16 bit 를 8 bit field 에 넣으면 위 8 bit 는 버려진다. 위 예는 [7:0] 으로 잘라 그것을 드러냈다.

Slide 11's @(dut_vif.ack) names no edge. In SystemVerilog @(signal) wakes on every value change, so one 0→1→0 pulse on ack wakes it at 0→1 and again at 1→0: two transactions. The second holds values from after ack fell, a false mismatch waiting for the scoreboard. For one transaction per exchange, pick an edge as in @(posedge vif.ack). Also, slide 11's monitor never reads signalA (reset), so reset items aren't observed, and putting 16-bit signalB into an 8-bit field drops the upper byte; the example above makes that explicit with [7:0].

Lab 4 의 monitor 가 여기서 일한다. Lab 4 의 06절 monitor 는 핀을 보고 transaction 을 만들어 mailbox 에 넣었고, 07절 scoreboard 가 그것을 꺼냈다. UVM 판에서 바뀌는 것은 출구 하나다. mailbox 대신 analysis port, put 대신 write. "transaction 은 매번 새로 만든다" 는 Lab 4 의 함정은 그대로 살아 있다. 11쪽 코드도 loop 안에서 매번 new 한다.

Lab 4's monitor is at work here. In Lab 4, §06 the monitor built transactions from pins and put them in a mailbox, and the §07 scoreboard took them out. In UVM only the outlet changes: an analysis port instead of a mailbox, write instead of put. Active and passive

12쪽이 transactor 를 둘로 가른다. interface 신호를 바꾸는 것은 active(uvm_driver), 보기만 하는 것은 passive(uvm_monitor). 오른쪽 아래가 왜 이 구별이 필요한지다. 다른 검증 환경이나 다른 단계에서는 driver 를 꺼야 할 수 있지만, 그때도 monitor 는 쓸모가 있다.

Slide 12 splits transactors in two: one that alters interface signals is active (uvm_driver); one that only observes is passive (uvm_monitor). The lower right says why the split matters: in other verification environments or levels the driver may be disabled, but the monitor can still serve a purpose.

Say Lab 3's systolic matmul has a block that writes configuration registers over APB. (a) The APB agent in a testbench verifying the matmul block alone. (b) The same APB agent in an SoC testbench with the CPU and bus attached, where the CPU drives APB from a real program. What do you set each to?

답 보기Show answer

(가) active. APB 를 몰 사람이 testbench 밖에 없으니 agent 의 driver 가 APB master 노릇을 해야 한다. (나) passive. APB 는 CPU 와 bus 가 몬다. driver 가 있으면 진짜 master 와 신호를 다투게 된다. monitor 만 남겨 APB 위의 transaction 을 기록하고, block 단계에서 쓰던 scoreboard 와 coverage 를 그대로 단다. 구별 기준은 "그 interface 를 모는 진짜 회로가 이 testbench 안에 있나" 하나다.

(a) Active. Nothing outside drives APB, so the agent's driver has to act as the APB master. (b) Passive. The CPU and bus drive APB; a driver would fight the real master over the signals. Keep only the monitor to record APB transactions and hang the block-level scoreboard and coverage on it. The one test: is there real logic in this testbench driving that interface?

1. is_active 의 값은 어떻게 들어오나

1. How does is_active get its value?

슬라이드의 답은 두 단계다. (1) is_active 를 field automation macro 로 등록했기 때문에 그 변수가 중앙 UVM resource database 에서 조회할 수 있는 대상이 됐다. (2) uvm_component 의 build_phase 가(super.build_phase 로 불려서) resource database 에서 is_active 를 덮어쓸 값을 찾아 넣었다. 즉 누군가 db 에 "이 agent 의 is_active 는 PASSIVE" 라고 넣어 두면, agent 코드는 한 줄도 안 바꾸고 passive 가 된다.

The slide's answer has two steps. (1) Registering is_active with the field automation macro made it something the central UVM resource database can be queried for. (2) uvm_component's build_phase, called through super.build_phase, looked up an override for is_active in the resource database and applied it. So if someone stores "this agent's is_active is PASSIVE" in the db, the agent goes passive without a line of its code changing.

보충 둘. 첫째, UVM 1.2 클래스 레퍼런스에서 (2) 를 하는 method 이름은 apply_config_settings 이고, field macro 로 등록된 field 에만 작동한다. 둘째, 앞 절에서 말했듯 uvm_agent 는 자기 build_phase 에서 is_active 를 따로 찾아 읽기도 한다. 슬라이드의 길과 이 길 모두 super.build_phase(phase) 를 불러야 일어난다는 점은 같다.

Two supplements. First, in the UVM 1.2 class reference the method doing step (2) is apply_config_settings, and it only acts on fields registered with field macros. Second, as the previous section said, uvm_agent's own build_phase also looks is_active up directly. Both routes share one condition: they only happen if you call super.build_phase(phase).

2. 왜 new() 가 아니라 ::type_id::create() 로 만들었나

2. Why ::type_id::create() instead of new()?

::type_id::create() 로 만들면 UVM factory 에게 그 class 의 constructor 를 불러 달라고 부탁하는 것이다. 슬라이드는 "more on this later" 로 넘겼고, 11절이 그 뒷이야기다. 미리 결론만 적으면, factory 를 거치면 다른 사람이 나중에 "이 type 대신 저 type 을 만들어라" 고 바꿔칠 수 있다. new() 로 만들면 그 길이 막힌다.

Building with ::type_id::create() asks the UVM factory to call that class's constructor. The slide says "more on this later", and §11 is the rest of the story. The conclusion up front: going through the factory lets someone else later say "build that type instead of this one". Calling new() shuts that door.

3. 왜 drv.seq_item_port.connect(seqr.seq_item_export) 인가

3. Why drv.seq_item_port.connect(seqr.seq_item_export)?

uvm_driver 에는 sequence item 을 하나씩 요청하는 기능을 구현한 TLM port 가, uvm_sequencer 에는 그 요청을 받아 큐에서 다음 item 을 꺼내 주는 기능을 구현한 TLM export 가 처음부터 들어 있다. TLM 의 connect() method 가 둘을 짝지어 이 통신이 되게 한다. 짝을 짓기 전에는 driver 의 get_next_item 이 부를 상대가 없다.

uvm_driver comes with an embedded TLM port implementing the request for each sequence item; uvm_sequencer comes with an embedded TLM export that services each request by fetching the next item in its queue. TLM's connect() method couples the two so that conversation can happen. Until then the driver's get_next_item has nobody to call.

The factory and type overrides

카탈로그에서 만든다 (18쪽)Building from a catalogue (slide 18)

18쪽의 비유는 foundry 다. factory 는 카탈로그(등록된 type 의 목록)를 보고 그 자리에서 물건을 만들어 주는 공장이다. `uvm_object_utils(type) 이나 `uvm_component_utils(type) 로 type 을 등록할 때마다 그 type 이 중앙 registry 에 올라간다. 이 macro 들은 그 class 에 create() method 도 만들어 준다. 그래서 type_id::create() 를 부르면 factory 에게 그 class 의 new() 를 불러서 object 를 만들어 달라고 요청하게 된다.

Slide 18's metaphor is a foundry: the factory looks at a catalogue (the list of registered types) and builds items on the fly. Each time a type is registered with `uvm_object_utils(type) or `uvm_component_utils(type), it's added to a central registry. These macros also define a create() method for the class, so calling type_id::create() asks the factory to construct the object by calling new() on the class.

그런데 먼저 (19쪽)But first (slide 19)

19쪽 제목은 "But First…". factory 는 만들기 전에 registry 에 요청된 type override 가 있는지 먼저 본다. 다른 component 가 전역(global) override 나 특정 instance override 를 걸어 두었으면, type_id::create() 는 요청받은 class 대신 override 된(파생) class 를 자동으로 바꿔 넣어 만든다. 그래서 아래쪽 코드(agent 같은 것)를 고치지 않고 실행 시점에 component 를 갈아 끼울 수 있다.

Slide 19 is titled "But First…". Before building, the factory checks the registry for any requested type overrides. If another component has requested a global or an instance-specific override, type_id::create() automatically substitutes the override (derived) class and builds that instead. So components can be swapped at run time without modifying lower-level code, such as agents.

  2. 2. usb2_driver::type_id::create(my_agent → factory). agent 는 아무것도 모른 채 늘 하던 대로 usb2_driver 를 달라고 한다. agent 코드에는 usb3 라는 글자가 한 번도 안 나온다
  3. 3. new()(factory → usb3_driver). factory 는 표를 보고 usb2_driver 대신 usb3_driver 의 constructor 를 부른다. 오른쪽 상자 "the object actually built" 가 실제로 생긴 것이다. 20쪽 나무에서 usb2_driver 에 X 가 쳐진 이유다
  4. 4. handle into usb2_driver usb_drv(usb3_driver → my_agent). 만들어진 usb3_driver 의 handle 이 agent 의 usb2_driver 형 변수 usb_drv 에 들어간다. 부모 형 변수에 자식 object 를 담는 것이라 문법상 문제가 없고, run_phase 는 virtual 이라 usb3 의 것이 돈다(Lecture 12 의 05절 polymorphism)

순서가 핵심이다. 1 이 2 보다 먼저 일어나야 한다. 반대로 되면 factory 가 표를 볼 때 아직 아무것도 안 적혀 있어서 usb2_driver 가 그대로 만들어진다. 그리고 4 가 성립하려면 usb3_driver 가 usb2_driver 를 상속해야 한다. 상속 관계가 아니면 create 안에서 형 변환이 실패한다.

  1. 1. set_type_override (test1 → factory). test1's build_phase writes "when asked for usb2_driver, give usb3_driver" into the factory's override table. "Runs first" on test1's box means build runs top-down, so the test is built before the agent
  2. 2. usb2_driver::type_id::create (my_agent → factory). The agent, knowing nothing, asks for a usb2_driver as always; the string usb3 never appears in its code
  3. 3. new() (factory → usb3_driver). The factory checks the table and calls usb3_driver's constructor instead. The box "the object actually built" is what really exists, which is why slide 20's tree crosses out usb2_driver
  4. 4. handle into usb2_driver usb_drv (usb3_driver → my_agent). The new usb3_driver's handle lands in the agent's usb2_driver variable usb_drv. A child object in a parent-typed variable is legal, and since run_phase is virtual, usb3's version runs (Lecture 12, §05, polymorphism)

Order is everything: step 1 must come before step 2. The other way round, the table is still empty when the factory looks, and a plain usb2_driver gets built. And for step 4 to work, usb3_driver must extend usb2_driver; without that inheritance the type conversion inside create fails.

현장 감각 · override 가 안 먹는다In practice · the override doesn't take

동료가 만든 test 가 set_type_override_by_type(my_driver::get_type(), err_driver::get_type()) 을 거는데, 로그를 보면 계속 my_driver 가 돈다. 코드를 봤더니 (가) agent 가 drv = new("drv", this); 로 만들고 있다, (나) test 가 env = my_env::type_id::create(...) 다음 줄에서 override 를 건다, (다) err_driver 가 uvm_driver #(dut_ctrl) 을 직접 상속한다. 각각 원인이 되나.

A colleague's test sets set_type_override_by_type(my_driver::get_type(), err_driver::get_type()), yet the log shows my_driver running. Looking at the code: (a) the agent builds it with drv = new("drv", this);, (b) the test sets the override on the line after env = my_env::type_id::create(...), (c) err_driver extends uvm_driver #(dut_ctrl) directly. Is each one a cause?

답 보기Show answer

(가) 원인이다. new 는 factory 를 안 거치므로 override 표를 아무도 안 본다. 15쪽의 둘째 질문이 바로 이것이다. (나) 이 경우는 원인이 아니다. 헷갈리기 쉬운데, env 를 create 해도 env 의 build_phase 는 test 의 build_phase 가 끝난 뒤에 돈다. agent 와 driver 는 그때 만들어지므로 override 는 늦지 않다. 다만 습관으로는 override 를 먼저 거는 편이 읽기 쉽다. (다) 원인이다(다른 모양으로). err_driver 가 my_driver 를 상속하지 않으면 my_driver 형 변수에 담을 수 없어 create 안의 형 변환이 실패한다. 조용히 무시되는 게 아니라 fatal 로 멈출 것이다. 구별 기준은 둘이다. factory 를 거치나, 자식 type 인가.

(a) A cause. new bypasses the factory, so nobody consults the override table; that's slide 15's second question. (b) Not a cause here, though it looks like one: creating the env doesn't run the env's build_phase until the test's build_phase has finished, and the agent and driver are built then, so the override isn't late. Setting overrides first is still the more readable habit. (c) A cause, in a different way. If err_driver doesn't extend my_driver, it can't go in a my_driver variable and the type conversion in create fails: not silently ignored but a fatal stop. Two tests decide it: does it go through the factory, and is it a child type?

Lecture 12 의 polymorphism 이 여기서 일한다. factory override 는 05절의 inheritance 와 virtual method 위에 서 있다. "부모 형 handle 에 자식 object 를 담으면 virtual method 는 자식 것이 돈다" 가 전부고, factory 는 누가 자식 object 를 만들지를 코드 밖(test)에서 정하게 해 줄 뿐이다. Lecture 14 의 error injection 을 test 마다 다르게 거는 흔한 길이 이것이다.

Lecture 12's polymorphism is at work here. Factory overrides stand on §05's inheritance and virtual methods: "put a child object in a parent-typed handle and the child's virtual methods run" is the whole trick, and the factory just lets something outside the code (the test) decide who builds the child object. It's a common way to vary Lecture 14's error injection test by test.

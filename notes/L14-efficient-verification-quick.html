무엇을 어디에

What goes where

슬라이드 2쪽 Mixed 는 네 짝이다. checking inside stimulus 는 self-checking test(test 가 기대값을 스스로 들고 비교), coverage inside stimulus 는 directed test 안에서 cg.sample(), checking inside coverage 는 illegal_bins(값이 떨어지면 오류), coverage within checking 은 cover property(assertion 문법으로 횟수를 센다. 실패는 없다). 슬라이드 3쪽은 각 기둥의 자리를 적는다. 아래 그림이 그것이다.

Slide 2, Mixed, has four pairs. Checking inside stimulus is a self-checking test (the test carries and compares its own expected values); coverage inside stimulus is cg.sample() inside a directed test; checking inside coverage is illegal_bins (a value landing there is an error); coverage within checking is cover property (assertion syntax counting hits; it never fails). Slide 3 gives each pillar its homes, drawn below.

그림 읽기Reading the picture
  1. sequence(stimulus) → "item" → driver → "pins" → interface → "drive" → DUT. item 은 UVM 의 sequence item, 즉 transaction 한 덩어리다
  2. 점선 initial block: reset 같은 bring-up stimulus 는 initial 블록에 바로 써도 된다
  3. interface 안의 assertions(checking)와 cover prop.(cover property, coverage): 신호 몇 개의 관계는 핀이 모인 interface 에 둔다
  4. DUT → "outputs" → interface → "pins" → monitor. monitor 는 보기만 하고, 칸 아래 basic checks, cov 처럼 간단한 check 와 coverage 를 둘 수 있다
  5. monitor → "txn"(transaction) → scoreboard(checking)와 coverage class(coverage). 슬라이드가 "separate" 라고 부른 부품 둘이다
  1. sequence (stimulus) → "item" → driver → "pins" → interface → "drive" → DUT. An item is a UVM sequence item, one transaction
  2. The dashed initial block: bring-up stimulus such as reset can go straight into an initial block
  3. assertions (checking) and cover prop. (cover property, coverage) inside the interface: relations among a few signals belong where the pins meet

  5. monitor → "txn" (transaction) → scoreboard (checking) and coverage class (coverage), the two "separate" components on the slide
함정 · sequence 가 둘이다Trap · two kinds of sequence

여기 "stimulus 는 sequence 에" 의 sequence 는 UVM 의 stimulus class 다. assertion 안의 SVA sequence(신호의 시간 패턴)와 이름만 같다. 문맥이 driver 면 UVM, assertion 이면 SVA.

The sequence in "stimulus goes in sequences" is UVM's stimulus class. It only shares a name with the SVA sequence (a time pattern of signals) inside assertions. Driver context means UVM; assertion context means SVA.

실행에 손대기

Reaching into a run

Plusargs(4쪽). ./simv +VERBOSE +NUM_PACKETS=100 +TEST=memory_test. $test$plusargs("VERBOSE") 는 있나 없나만 보고, $value$plusargs("NUM_PACKETS=%d", n) 은 값을 읽는다. 못 찾으면 0 을 돌려주고 변수는 그대로라서 if (!...) n = 10; 으로 기본값을 둔다. 쓸모는 build once, run many times. 두 함정이 있다. vcs +define+X 는 컴파일 옵션이라 plusarg 가 아니고, $test$plusargs 는 앞부분만 맞아도 참이라 +VERBOSE=0 도 verbose 를 켠다.

Plusargs (slide 4): ./simv +VERBOSE +NUM_PACKETS=100 +TEST=memory_test. $test$plusargs("VERBOSE") checks presence only; $value$plusargs("NUM_PACKETS=%d", n) reads a value. Not found returns 0 and leaves the variable alone, so defaults go in with if (!...) n = 10;. The point: build once, run many times. Two traps: vcs +define+X is a compile option, not a plusarg; and $test$plusargs is true on a prefix match, so +VERBOSE=0 also turns verbose on.

XMR(5쪽). $display("PC = %h", top.cpu0.pc); 처럼 포트를 안 거치고 계층 경로로 내부를 본다. IEEE 1800 의 이름은 hierarchical reference. 슬라이드의 단점은 Brittle(instance 이름이 바뀌면 깨진다)과 Not so good for reuse, 그리고 `define 이나 macro 로 경로를 한곳에 모으는 것.

XMRs (slide 5): $display("PC = %h", top.cpu0.pc); looks inside by hierarchical path without ports. IEEE 1800 calls it a hierarchical reference. The slide's issues: brittle (an instance rename breaks it), not so good for reuse, and `defines or macros to gather the paths in one place.

force / release(12쪽). force dut.blah.blah.sig1 = 1'b1; 은 설계가 무엇을 주든 그 값으로 덮어쓰고, release 로 푼다. 쓰임은 fault injection, 도달하기 어려운 corner case, 디버그. IEEE 1800 기준으로 net 은 release 하면 바로 driver 값으로 돌아가지만, variable 은 다음 대입까지 force 값을 들고 있다.

force / release (slide 12): force dut.blah.blah.sig1 = 1'b1; overrides whatever the design drives; release lets go. Uses: fault injection, hard-to-reach corner cases, debugging. Per IEEE 1800 a net returns to its driver's value at release, but a variable keeps the forced value until its next assignment.

Error injection(13쪽). memory bit 뒤집기, packet 깨기, invalid opcode, 응답 빠뜨리기 같은 special test 로 DUT 가 회복하거나 interrupt 로 알리는지 본다. 방법은 XMR, check 끄기(일부러 낸 오류를 실패로 잡지 않게, 예: $assertoff), constraint 끄기(constraint_mode(0) 로 불법 값을 허용). Lab 4 의 "심은 버그" 와 반대 방향이다. error injection 은 DUT 를 시험해서 통과해야 맞고, 심은 버그는 checker 를 시험해서 실패해야 맞다.

Error injection (slide 13): special tests (flip a memory bit, corrupt a packet, force an invalid opcode, drop a response) to check the DUT recovers or flags an interrupt. How: XMRs, disabling checks (so the deliberate error isn't flagged as a failure, e.g. $assertoff), disabling constraints (allow illegal values with constraint_mode(0)). It's the opposite of Lab 4's planted bugs: error injection tests the DUT and should pass; a planted bug tests the checker and should fail.

C 와 메시지

C and messages

PLI 와 DPI(6쪽). PLI = Programming Language Interface, DPI = Direct Programming Interface. PLI 의 tf, acc, vpi 루틴은 사용자 정의 system task, Verilog 계층의 객체 접근과 조작, 시뮬레이션 제어를 한다. DPI 는 import "DPI-C" 로 C 함수를 SV 함수처럼 부를 뿐이다(Lecture 12 의 15절). C 파일은 VCS 명령줄에 바로 주거나, shared object(.so)로 먼저 컴파일해서 명령줄에 준다. Lab 4 의 C 정답 모델이 이 길로 들어간다.

PLI and DPI (slide 6). PLI = Programming Language Interface, DPI = Direct Programming Interface. PLI's tf, acc, vpi routines do user-defined system tasks, access and manipulation of Verilog hierarchy objects, and simulation control. DPI just calls a C function like an SV one via import "DPI-C" (Lecture 12, §15). C files go straight on the VCS command line, or are compiled into a shared object (.so) first and named there. Lab 4's C reference model comes in this way.

Message severity(7쪽). $info/UVM_INFO, $warning/UVM_WARNING, $error/UVM_ERROR, $fatal/UVM_FATAL. 아래로 갈수록 무겁다. IEEE 1800 기준으로 앞의 셋은 찍고 계속 가고, $fatal 만 시뮬레이션을 끝낸다. 넷 다 파일, 줄, scope, 시간을 메시지에 붙인다. 순수 SV 에서 $error 개수는 testbench 가 직접 세서 PASS/FAIL 을 판정해야 한다. $display("ERROR") 는 severity 가 없어 아무도 세지 않는다.

Message severity (slide 7): $info/UVM_INFO, $warning/UVM_WARNING, $error/UVM_ERROR, $fatal/UVM_FATAL, heavier as you go down. Per IEEE 1800 the first three print and carry on; only $fatal ends the simulation. All four attach file, line, scope and time. In plain SV the testbench must count $errors itself to judge PASS/FAIL. $display("ERROR") has no severity, so nobody counts it.

자세한 판의 07절에서 plusarg 를 골라 simv 를 흉내 내며 $error 와 $fatal 의 차이를 직접 볼 수 있다.

§07 of the full note lets you pick plusargs, mock-run simv and see the $error versus $fatal difference first hand.

시간과 시뮬레이션 수준

Timing and simulation level

Black-box vs. white-box(8쪽). black-box 는 spec 만 알고 입출력만 본다. spec 위반을 찾지만 실패 위치를 좁히기 어렵다. white-box 는 RTL 전체와 내부 신호를 본다. 구현 버그를 찾지만 common-mode(RTL 과 TB 가 같은 버그) 위험이 있다. 슬라이드의 Gray-Box 는 이름만 있다. 흔히 판정은 바깥, 관찰은 일부 안이라는 뜻으로 쓴다.

Black-box vs. white-box (slide 8). Black-box knows only the spec and watches only inputs and outputs: it finds spec violations but struggles to localize failures. White-box sees the full RTL and internal signals: it finds implementation bugs but risks common-mode issues (RTL and TB share a bug). The slide's Gray-Box is a name only; it's commonly used for verdicts from outside with some observation inside.

시간 어긋남과 clocking block(9~10쪽). TB 와 DUT 가 같은 엣지에서 바꾸고 읽으면 race 가 난다. 9쪽의 답은 TB 가 하강 엣지에 넣고 다음 하강 엣지에 보는 것, 10쪽의 답은 clocking block 이다.

Time offsets and clocking blocks (slides 9 to 10). If TB and DUT change and read on the same edge, you get a race. Slide 9's answer: the TB drives on the falling edge and observes on the next one. Slide 10's answer: a clocking block.

그림 읽기Reading the picture
  1. A: clk 의 상승 엣지는 x=100, 260, 420, 580, 하강 엣지는 180, 340, 500, 660. TB applies(180, 하강)에서 data 가 old 에서 8'h42(8 비트 16 진수 42 = 0100_0010)로 바뀌고, DUT samples(260, 상승)에서 DUT 가 그 값을 읽고, TB observes(340, 하강)에서 TB 가 출력을 본다. data 는 500 에서 next 로 바뀐다. 값이 바뀌는 순간과 읽는 순간이 반 주기씩 떨어져서 race 가 없다
  2. B: 같은 clock 의 posedge(260)가 기준이다. sample #1ns before(244 = 260 − 16)에 input 을 샘플한다. DUT 출력 done 은 260 에서 0 → 1 이지만 244 에서 읽었으므로 sampled 0, 즉 이 엣지에서 intf.cb.done 은 0 이다. drive #2ns after(292 = 260 + 32)에 output 이 실려 data 가 old 에서 8'h42 로 바뀌고, DUT 는 그것을 다음 엣지(420)에 읽는다
  1. A: clk rises at x = 100, 260, 420, 580 and falls at 180, 340, 500, 660. At TB applies (180, falling) data changes from old to 8'h42 (8-bit hex 42 = 0100_0010); at DUT samples (260, rising) the DUT reads it; at TB observes (340, falling) the TB reads the output. Data moves to next at 500. Changes and reads are half a period apart, so there's no race
  2. B: the reference is the same clock's posedge (260). Inputs are sampled at sample #1ns before (244 = 260 − 16). The DUT output done goes 0 → 1 at 260, but it was read at 244, hence sampled 0: intf.cb.done is 0 at this edge. Outputs land at drive #2ns after (292 = 260 + 32), where data goes from old to 8'h42; the DUT reads it at the next edge (420)

Gate-level simulation(11쪽). RTL 대신 synthesis 가 낸 netlist 를 같은 testbench 로 돌린다. 잡는 것은 RTL 과 netlist 의 불일치, RTL 이 숨긴 X-propagation 과 초기화 문제, reset 과 power-up, timing 의존 동작, synthesis 가 넣은 gated clock 같은 로직. 종류는 zero delay 와 timing simulation(SDF, Standard Delay Format 으로 지연을 입힌다). timing GLS 는 STA 를 대신하지 않는다. test 가 지나간 경로만 본다.

Gate-level simulation (slide 11): run the synthesized netlist instead of RTL under the same testbench. It catches RTL/netlist mismatches, X-propagation and initialization problems RTL hides, reset and power-up issues, timing-dependent behaviour, and logic synthesis adds, such as gated clocks. Types: zero delay and timing simulation (delays applied from an SDF, Standard Delay Format, file). Timing GLS doesn't replace STA; it only sees the paths tests exercise.

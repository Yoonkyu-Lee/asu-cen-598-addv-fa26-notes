# 두 FIFO 구현 비교

같은 상위 모듈, 같은 testbench 로 FIFO 만 갈아끼워 잰 값이다.
리포트의 *"Explain how you determined the size of FIFOs"* 와 구현 선택의 근거가 된다.

환경: Apporto RHEL 8.6 (`nc-asu6-l06`), VCS `W-2024.09-SP2-3`, 2026-09-22 측정.
`DATA_WIDTH = 8`. 깊이는 구현마다 다르다. **그 차이 자체가 결과 하나다.**

| 구현 | 깊이 | 왜 |
|---|---|---|
| `sync` | **40** | 필요한 만큼만. 2의 거듭제곱일 필요가 없다 |
| `async` | **64** | gray code 포인터가 2의 거듭제곱을 강제한다. 40을 못 쓴다 |

24칸 x 8비트 = 192 플롭이 FIFO 하나당 논다. FIFO 가 둘이니 **384 플롭**이다.
이게 비동기 FIFO 를 그대로 재사용했을 때 치르는 첫 번째 값이다.

## 1. `empty_latency`

빈 FIFO 에 한 개 쓰고 나서, **쓰기가 실린 엣지 뒤로 몇 엣지가 지나야** `empty` 가 내려가나.
`tb/tb_fifo_q.sv` 가 잰다. **두 구현을 가르는 핵심 숫자다.**

| 구현 | 측정값 |
|---|---|
| `sync` | **0 사이클** |
| `async` | **3 사이클** |

**상위 회로 트레이스가 같은 숫자를 독립적으로 보여준다.** 첫 쓰기는 두 구현 모두 cycle 1
인데 첫 출력이 동기는 cycle 2, 비동기는 cycle 5 다. 차이가 3 이다.

### 예측 2, 첫 측정 4, 진짜 3

**두 번 틀렸다.**

| | 값 | 무엇을 셌나 |
|---|---|---|
| 작업 전 예측 | 2 | 동기화기 두 단만 셌다 |
| 첫 측정 | 4 | testbench 가 엣지 직후 옛 값을 읽어 한 번 더 셌다 |
| 진짜 | **3** | 쓰기 엣지 뒤로 세 엣지 |

**레지스터는 넷이 맞다.** 다만 첫째가 쓰기 엣지 그 자체에서 잡는다.

| 레지스터 | 잡는 엣지 |
|---|---|
| 쓰기 포인터 자신 | 쓰기 엣지 |
| 동기화기 1 단 | 쓰기 뒤 1 |
| 동기화기 2 단 | 쓰기 뒤 2 |
| `rempty` (등록된 출력) | 쓰기 뒤 3 |

`async_fifo` 의 `rempty` 는 조합 출력이 아니라 `always_ff` 로 등록된다. Cummings 논문이
*"All module outputs are registered for simplified synthesis using time budgeting"* 라고
밝힌 설계 의도이고, 그 대가가 여기서 한 사이클 더 붙는 형태로 나타난다.

**예측이 틀린 이유.** 동기화기라는 이름이 붙은 것만 셌다. 신호가 쓰기 쪽에서 읽기 쪽
플래그까지 가며 지나는 flip-flop 을 전부 세야 한다.

**첫 측정이 틀린 이유.** 측정 루프가 `@(posedge clk)` 직후에 바로 `empty` 를 읽었다.
그 순간에는 설계의 `always_ff` 가 아직 값을 안 바꿨다 (NBA 영역이 뒤에 온다). 그래서
`empty` 가 내려가는 바로 그 엣지에서 옛 값 1 을 읽고 한 번 더 셌다. 동기 판은 `empty` 가
쓰기 엣지에서 이미 내려가 루프를 안 타므로 영향이 없었다. **두 구현을 서로 다른 조건으로
잰 셈이었다.** 엣지마다 1ns 기다린 뒤 읽도록 고쳤다.

**찾은 방법.** 상위 회로 트레이스의 첫 출력 차이가 3 이라 FIFO 레벨의 0 대 4 와 어긋났다.
처음에 4 를 설명하려고 "레지스터 넷" 을 세었는데, **그 설명이 맞는 척을 했다.** 레지스터 수는
맞았지만 엣지 수를 세는 기준이 달랐다. 독립적인 두 번째 측정이 없었으면 못 잡았다.

## 2. 상위 회로

`tb/tb_even_odd.sv`. 네 case 를 두 구현에 똑같이 태웠다. **여덟 번 다 통과했다.**

`cycles` 는 첫 쓰기부터 마지막 출력까지다. `peak` 은 각 FIFO 의 최대 점유량이고,
testbench 가 상위 모듈의 `wr_en` / `rd_en` 을 세서 직접 잰다. FIFO 안을 안 들여다보는
이유는 두 구현이 점유량을 서로 다른 모양으로 들고 있기 때문이다. 같은 잣대가 필요했다.

### sync (깊이 40)

| test | out | peak_even | peak_odd | cycles |
|---|---|---|---|---|
| `case9_skew` | 80/80 | **39** | 24 | 139 |
| `case9_random` | 80/80 | 11 | 13 | 106 |
| `case8` | 80/80 | 21 | 20 | 322 |
| `case7` | 80/80 | 4 | 5 | 87 |

### async (깊이 64)

| test | out | peak_even | peak_odd | cycles |
|---|---|---|---|---|
| `case9_skew` | 80/80 | **39** | 26 | 144 |
| `case9_random` | 80/80 | 12 | 15 | 109 |
| `case8` | 80/80 | 21 | 20 | 322 |
| `case7` | 80/80 | 6 | 7 | 90 |

### 읽는 법

**비동기가 매번 느리다. 3에서 5 사이클.**

| test | sync | async | 차이 |
|---|---|---|---|
| `case9_skew` | 139 | 144 | +5 |
| `case9_random` | 106 | 109 | +3 |
| `case8` | 322 | 322 | 0 |
| `case7` | 87 | 90 | +3 |

차이의 출처가 `empty_latency` 다. 비동기 판은 데이터가 들어와도 `empty` 가 3 사이클
늦게 풀리므로 읽기가 그만큼 늦게 시작하고, 전체가 뒤로 밀린다.

**`case9_random` 과 `case7` 의 차이는 정확히 3 이다.** `empty_latency` 그대로다.

**`case9_skew` 만 5 다.** 트레이스로 어디서 벌어지는지 봤다. 짝수 40 개가 먼저 와서 두 구현
모두 홀수를 기다리며 멈추는데, 첫 홀수가 들어온 뒤 **재시작이 동기 cycle 42, 비동기 cycle 45**
로 3 늦다. 그 다음부터는 같은 속도로 도는데, 소비자의 읽기 패턴이 10 클럭 중 2 클럭을 쉬므로
3 늦게 시작한 쪽은 **쉬는 창을 하나 더 넘겨야** 끝난다. 그게 +2 다.

`case8` 만 0인 것이 오히려 이 설명을 뒷받침한다. `case8` 은 읽기가 4클럭당 1개로
느려서 **회로가 읽기에 묶여 있다.** 시작이 3 사이클 늦어도 소비자가 어차피 그보다
더 느리게 요청하므로 흡수된다. 병목이 FIFO 가 아닐 때는 FIFO 를 고쳐도 소용없다는,
Lecture 7 의 그 이야기다.

`peak` 도 비동기가 0 에서 2 높다. 같은 이유다. 배출이 늦게 시작하니 그동안 더 쌓인다.

**`case8` 은 두 구현이 `peak` 도 `cycles` 도 완전히 같다.** 읽기가 병목인 회로에서는
FIFO 의 시작 지연이 어디에도 흔적을 남기지 않는다. 두 숫자가 같은 이야기를 한다.

### 측정 도구가 처음에는 틀렸다

**2026-09-22 에 처음 적은 `peak` 값 여덟 쌍 중 다섯이 틀렸다.** 위 표는 고친 값이다.

| run | 처음 적은 값 | 고친 값 |
|---|---|---|
| sync `case9_random` | 10 / 13 | **11** / 13 |
| async `case9_skew` | 39 / 25 | 39 / **26** |
| async `case9_random` | 12 / 14 | 12 / **15** |
| async `case8` | 22 / 22 | **21 / 20** |
| async `case7` | 5 / 6 | **6 / 7** |

원인은 testbench 의 점유량 추적이 **posedge 1ns 뒤**에 `wr_en` / `rd_en` 을 읽은 것이다.
쓰기(`Write_en`)는 negedge 까지 붙들려 있어서 엣지 뒤에 읽어도 같다. 그런데 꺼내기(`do_pop`)는
조합 신호라 **엣지 뒤의 상태로 다시 계산**된다. 그래서 이번 엣지의 쓰기와 **다음 엣지의
꺼내기**를 한데 셌다. 대부분 1 작게 나왔고, 비동기 `case8` 은 오히려 크게 나왔다.

**찾은 방법.** 학습 노트용으로 붙인 `+TRACE` 가 사이클마다 `out_valid` 를 남긴다.
`out_valid` 는 등록된 출력이라 "그 엣지에 실제로 꺼냈다" 와 정확히 같다. 그걸로 점유량을
독립적으로 다시 세니 추적기 값과 어긋났다. **측정 도구를 다른 측정으로 검증한 셈이다.**

**고친 방법.** posedge 이벤트 그 순간에 읽는다. 그 시점에는 설계의 `always_ff` 가 아직 값을
안 바꿨으므로(NBA 영역이 뒤에 온다) 이 엣지가 실제로 쓰는 값을 읽게 된다. 고친 뒤 트레이스로
다시 세면 여덟 run 전부 **행 단위로 차이가 0** 이다.

**영향.** 깊이를 정한 `peak_even = 39` 는 두 구현 모두 처음부터 맞았다. 결론은 안 바뀐다.
`cycles` 도 이 추적기와 무관해서 그대로다. 바뀐 것은 비교 표의 세부 숫자다.

## 3. 그래서 무엇을 제출하는가

**동기 FIFO 판이다.** 이유가 셋이고, 셋 다 위에 숫자가 있다.

| | sync | async |
|---|---|---|
| 깊이 | 필요한 40 | 64로 올려야 함 (+384 플롭) |
| `empty` 가 풀리는 데 | 0 사이클 | 3 사이클 |
| 처리 시간 (`case9_skew`) | 139 | 144 |
| RTL 줄 수 | 93 (주석 포함) | Part 1 7개 파일 + wrapper |
| 이 회로에 CDC 가 있나 | 없다 | 없다 |

마지막 줄이 핵심이다. **Part 2 는 클럭이 하나다.** 비동기 FIFO 가 값을 치르고 사주는
것은 클럭 경계를 안전하게 건너는 능력인데, 여기에는 건널 경계가 없다. 그래서 그 값이
순수한 손해로만 남는다.

Lab 도 둘 다 인정한다.

> For this part of the lab, you do not need an asynchronous FIFO. So, you can either
> design a synchronous FIFO or just use the asychronous FIFO designed in part 1.
> No points will be deducted either way.

**감점은 없지만 회로는 달라진다.** 그 차이를 추측이 아니라 재서 확인한 것이 이 문서다.

## 4. 기능 동등성

비교가 성립하려면 두 구현이 같은 계약을 지켜야 한다. 둘 다 확인됐다.

| 항목 | sync | async |
|---|---|---|
| 깊이만큼 채우면 `full` | 통과 | 통과 |
| 넣은 순서대로 배출 | 통과 | 통과 |
| 동시 읽기/쓰기 24쌍 순서 유지 | 통과 | 통과 |
| 다 빼면 `empty` | 통과 | 통과 |
| 상위 회로 4 case | 통과 | 통과 |

**클럭을 하나로 묶어도 비동기 FIFO 는 기능적으로 맞다.** 보수적일 뿐이다.
이게 확인되기 전까지는 비교 계획 자체가 성립하지 않는 상태였다.

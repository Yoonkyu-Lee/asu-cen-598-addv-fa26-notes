# Lab 기록 페이지

**같이 필요한 스킬**
- HTML 규격은 `note-html`. **이 스킬만 읽고 페이지를 만들면 안 된다**
- 시뮬레이션 카드(`.sim`)를 쓰면 `docs/superpowers/specs/2026-09-13-hands-on-primer-design.md`
- 강의 노트를 같이 손대면 `write-note`

**이 스킬만으로 끝나는 것**: 무엇을 쓸지 정하는 것. 절 구조, 경계 확정, 무엇을 싣고 무엇을 안 싣는지

판단이 갈리면 `CLAUDE.md` 가 이긴다.

## 이건 공략이 아니다

같은 `LAB{N}-*.html` 파일명 아래 **장르가 둘**이다. 섞지 않는다. Lab 하나에 페이지는 하나다.
정리글을 쓰면 그 Lab 의 공략 페이지를 **대체한다** (Lab 2 가 그렇게 했다, 2026-10-15).

|---|---|---|
| 언제 쓰나 | 과제를 받고 **풀기 전** | 과제를 **끝낸 뒤** |

| 정렬 | 요구사항 항목 순서 | **문제 → 해결 순으로 개념을 세운 뒤, 구현 · 검증 · 합성 · 막힌 곳** |
| 중심 | 다음 수 | **왜 그 구조여야 하는지, 그리고 주어진 것과 얹은 것의 차이** |

**기준 페이지는 `notes/LAB1-fifo-design.html` 이다.** 2026-10-15 에 사용자가 따로 쓰던 v2 판을

**왜 정리가 필요한가.** Lab 이 성적의 45% 다. 그런데 끝나고 나면 zip 과 PDF 만 남고,
**무엇이 주어진 것이고 무엇을 직접 한 것인지**가 제일 먼저 사라진다. 몇 년 뒤 이력서에
"비동기 FIFO 를 설계했다" 라고 쓸 때 그게 논문 코드를 옮긴 건지 직접 구상한 건지
본인도 모르면 안 된다. **그 경계를 기록하는 것이 이 장르의 존재 이유다.**

Part 2 부터는 앞에 **`Part 2 ·`** 를 붙인다. `<h2 class="grp">` 로 묶지 않는다.

| 절 | 분류 | 내용 |
|---|---|---|
| 00 | 설명서 요약 | Lab 이 시킨 것. **원문을 싣지 않는다.** 원문의 번호를 그대로 살려서, 뒤 절이 "요구사항 2 번" 이라고 가리킬 수 있게 한다. 원본 Notion 링크 |

| 02~ | `해결 1` · `문제 2` · `해결 2` · `판정` · `대가` … | 문제와 해결을 번갈아. 해결마다 **무엇의 어느 부분을 막는지**, 그리고 그 대가 |

| | `구현 · …` | 우리가 직접 판단한 곳마다 한 절. 짧은 발췌와 도해 |

| | `합성 · …` | 숫자마다 어느 실행에서 나왔는지. 코드에서 셀 수 있는 것은 세어서 맞춘다 |
| | `막힌 곳 · …` | 일어난 순서대로. 틀린 예측, 잘못 읽은 스펙, 재현이 안 된 숫자 |
| | `Part 2 · …` | Part 2 도 같은 순서. 첫 절에 **해야 할 일 한 장**과 **주어진 것**을 둔다 |
| 끝 | `남은 질문` (있으면) | 이 Lab 이 확인하지 않은 것과, 확인하려면 무엇을 하면 되는지 |

**절 번호는 `.sec-num` 에 두 자리로 적는다.** `data-slide` 를 붙이지 않는다. `reader.js` 를 넣지 않는다.
Lab 은 슬라이드가 출처가 아니다.

### 개념 절에서 쓰는 두 장치

- **"그림 읽기"** (`.def` + `.tag`): 도해마다 바로 뒤. 그림의 값을 한 단계씩 풀어 쓴다.
  규칙은 `write-note` 의 "반드시 지켜야 할 규칙" 절이 단일 출처다
- **"여기서 의문"**: 독자가 품을 질문을 하나 세우고 바로 답한다. 이 페이지의 대화체가 여기서 나온다

### 절을 비워두지 않는다

**막힌 곳이 "특별히 없었다" 로 끝나면 아직 정리가 안 된 것이다.** 정말 안 막혔을 리 없다.
커밋 로그와 대화를 다시 본다. 틀린 예측, 잘못 읽은 스펙, 두 번 짠 코드, 재현되지 않은 숫자가
전부 여기 들어간다. **개념 절에 대안이 없으면** 구현을 먼저 하고 이유를 나중에 붙인 것이다.
"그냥 그렇게 했다" 밖에 안 나오면, 무엇과 무엇 중에 골랐는지부터 적는다.
## 01. 주어진 것을 기억에 의존해 적지 않는다

**이 장르에서 제일 틀리기 쉬운 곳이고, 틀리면 페이지 전체가 거짓이 된다.**

`git` 이 단일 출처다. Lab 작업 저장소에서 **출발점을 먼저 커밋해 놓는다.**

```
커밋 1   주어진 것 그대로 (스타터 코드, 또는 참조한 공개 코드)
커밋 2   우리가 얹은 것
```

그러면 `git diff 커밋1 커밋2 --stat` 이 곧 **"무엇을 했는가" 의 답**이다. 기억이 아니라.

**스타터가 없으면 없다는 것을 증명한다.** 어디를 찾아봤는지 적는다.
Lab 1 이 그런 경우였고 `lab1/part1/SOURCE.md` 가 그 기록이다.
강사가 제공한 게 없고 Lab 페이지가 논문을 가리키기만 하면, **그 논문 코드가 출발점**이고
그것을 그대로 커밋한 것이 기준선이 된다.

### 세 칸 표로 적는다

```
| 파일 | 주어진 것 | 바뀐 것 | 왜 |
```

"왜" 칸이 핵심이다. **요구사항 어느 줄 때문에 바뀌었는지**를 적는다.
"SystemVerilog 로 고쳤다" 가 아니라 "요구사항이 `always_ff` 를 명시해서" 다.

### 없어진 파일도 적는다

`fifo1.v` → `async_fifo.sv` 처럼 **이름이 바뀐 것**은 diff 에서 삭제 + 추가로 보인다.
표에서는 한 줄로 묶고 이름이 바뀌었다고 밝힌다. 안 그러면 실제보다 많이 한 것처럼 보인다.

## 02. 무엇을 싣고 무엇을 안 싣는가

**이 저장소는 Public 이고 GitHub Pages 로 서빙된다. 여기 올리는 건 인터넷에 게시하는 것이다.**
Lab 작업 저장소는 Private 이다. **둘을 헷갈리면 사고가 난다.** 단일 출처는 `CLAUDE.md` 의
"커밋하는 것과 안 하는 것" 절이다.

**2026-10-15 결정. Lab 코드는 Lab 저장소에서만 푸시하고, 이 저장소는 노트만 싣는다.**
2026-09-22 에 내렸던 "코드를 `code/lab{N}/` 로 올리고 `codeview.js` 뷰어로 페이지에 전부 싣는다" 를
사용자가 거둬들였다. 코드 뷰어와 그 빌드 스크립트는 지웠다.

| 대상 | 싣나 |
|---|---|
| 공개된 출처의 코드 (논문, 표준 문서, 강의 슬라이드) | **O.** 출처를 밝히고 짧게 인용 |
| 주어진 코드 · 우리가 얹은 코드 | **발췌만.** 설명에 필요한 몇 줄을 `pre.code` 로. 파일 전문을 붙이지 않는다 |
| testbench 전문, 파일 사본 | **X** |
| 과제 문제지 원문 | **X.** 00 절은 요약으로 쓴다. 문구 자체가 논점일 때만 짧게 인용 |
| 파형 | **O.** 우리 시뮬레이션 결과다 |
| 측정 숫자와 표 | **O** |
| 도해, 설계 근거, FSM, 계산 | **O.** 여기가 이 페이지의 값어치다 |
| 파트너와의 역할 분담 | **X.** 그건 제출 리포트 몫이다 |

**발췌는 "논문 · 파일명 · excerpt", "submitted · 파일명 · excerpt" 처럼 출처를 단다.** 줄였으면
"condensed" 라고 밝힌다. Lab 1 08 절의 두 판 나란히 보기가 본보기다.

**왜 전문을 안 싣나.** 아직 진행 중인 과목의 채점 대상이다. 전문을 게시하면 다음 학기 학생이
그대로 쓴다. 그리고 2 인 1 조 과제라 **파트너의 코드까지 같이 게시하는 것**이 된다.
**코드는 이해의 결과물이지 이해 자체가 아니다.** 몇 년 뒤 이 페이지를 읽고 Private 저장소를 열면
코드가 읽힌다. 그 순서가 맞다.

## 03. 방향 절이 이 페이지를 학습 자료로 만든다

개념 절(01 부터 구현 절 전까지)이 없으면 이 페이지는 그냥 변경 이력이다.

- **대안을 먼저 적는다.** 무엇과 무엇 중에 골랐나. 안 고른 쪽이 왜 졌나
- **그때 몰랐던 것을 숨기지 않는다.** 나중에 알고 보니 전제가 틀렸으면 그것도 기록이다
- **숫자로 정한 것은 계산 과정을 전부 적는다.** 답만 적으면 몇 년 뒤 재현이 안 된다
- 도해와 인터랙티브를 **여기에 몰아 넣는다.** 구현 절이 아니라 방향 절이다

### 개념 도해를 먼저, 한 개념에 한 장

Lab 1 첫 판은 방향 절 그림이 "binary 는 네 비트, gray 는 한 비트" 한 장뿐이었다. 사용자가
**"딱 봐서는 이해할 수 없다, 비전문가도 알아먹을 설명이 부족하다"** 며 돌려보냈다.
그 그림은 답을 보여줬지 **문제를 보여주지 않았다.** 다시 쓴 순서가 기준이다.

1. **과제 자체를 그림 하나로.** 입력이 무엇이고 출력이 무엇이어야 하나 (예: 숫자가 들어와
   두 줄로 갈라졌다가 번갈아 나간다). 회로 블록도는 그 다음이다
2. **문제가 일어나는 순간을 그린다.** 해결책보다 먼저. "바뀌는 중에 다른 clock 이 찍으면
   있지도 않은 11 이 잡힌다" 처럼 **구체적인 값**으로. 일상 비유가 있으면 한 줄 곁들인다
3. **해결책마다 한 장.** 무엇이 문제의 어느 부분을 막는지가 보이게
4. **왜 그래도 안전한가 / 그 대가는 무엇인가를 따로 그린다.** 설계의 요령은 대개 여기 있다
5. **개념을 코드 위치에 대응시키는 표**로 닫는다. 칸마다 파일과 신호 이름을 적는다

주어진 코드가 있으면 **그 코드 전체의 블록도**를 구현 절에 두고, 주어진 것과 얹은 것을 색으로 가른다.
그림 안의 글자는 영어 라벨만 두고 설명은 figcaption 에 쓴다. 전문 용어가 처음 나오는 그림은
캡션에서 한 문장으로 풀어준다.

**도해마다 바로 뒤에 "그림 읽기" (`.def` + `.tag`) 를 둔다.** 그림의 값을 한 단계씩 풀어 쓰는 곳이다.
규칙은 `write-note` 의 "반드시 지켜야 할 규칙" 절이 단일 출처다. 생략하지 않는다.


### 예측과 측정을 나란히 놓는다

**이 장르의 시그니처다.** 설계 전에 예측한 값이 있으면 적고, 측정값을 옆에 놓는다.
**틀렸으면 틀렸다고 적는다.** 맞춘 것보다 틀린 것이 몇 배 값지다.

```
| | 예측 | 측정 | 차이의 이유 |
```

측정 없이 "~일 것이다" 만 적힌 숫자는 **적지 않는다.** 이 저장소의 다른 규칙과 같다.
근거 없는 주장은 사용자가 바로 잡아낸다.

## 04. 결과 절: 파형은 붙이는 게 아니라 읽는 것이다

스크린샷만 붙이면 값이 없다. 파형 하나마다 셋을 붙인다.

1. **어디를 보라.** 신호 이름과 대략의 시각. "여기" 라고만 쓰지 않는다
2. **그 순간 회로 안에서 무슨 일이 일어났나.** 회로도나 코드 조각과 짝지어 쓴다
3. **그래서 무엇이 확인됐나.** 요구사항 어느 줄이 이걸로 증명되나

**주석은 이미지 위에 구우지 않는다.** 파형 PNG 를 `figure` 에 넣고 **설명은 HTML 로 옆에 둔다.**
그래야 이중 언어가 되고 다크모드에서 안 깨지고 나중에 고칠 수 있다.
이미지에 구운 글씨는 그 셋이 다 안 된다.

### 파형은 트레이스에서 그린다

Verdi 스크린샷을 붙이지 않는다. testbench 에 `+TRACE` 를 붙여 사이클마다 CSV 한 줄을
흘리게 하고, `scripts/wavesvg.py` 로 SVG 를 그린다. 다크모드와 이중 언어가 그냥 된다.
Apporto 에서 돌리고 CSV 를 Lab 저장소에 커밋해 `git pull` 로 받아오면 된다.

```bash
python scripts/wavesvg.py wave --csv t.csv --time cycle --from 0 --to 60 \
  --signals "write_en:bit:ver,data_in:bus:ver,out_valid:bit:sig,data_out:bus:sig" \
  --marks "1=1,41=2" --label "..." --out frag.svg
python scripts/wavesvg.py occ --csv t.csv --series "occ_even:sig,occ_odd:sig:dash" --out occ.svg
```

**파형의 색은 역할로 준다.** testbench 가 미는 신호는 `ver`(분홍), 설계가 내놓는 신호는
`sig`(파랑), 클럭은 `clk`(갈색). 읽을 자리 마커는 `--sel` 이다. **파형에 amber 와 green 을
쓰지 않는다.** 버그와 통과 전용이다. 둘 다 설계인 곡선 두 개는 색이 아니라 실선·점선으로 가른다.
Lab 1 에서 처음에 홀수 FIFO 곡선을 분홍으로, 마커를 amber 로 칠했다가 다 고쳤다.

### 트레이스로 측정 도구를 검증한다

**이 장르에서 제일 값진 발견이 여기서 나왔다.** 트레이스는 파형을 그리려고 붙이지만,
뽑아놓고 보면 **testbench 가 재는 숫자를 독립적으로 다시 셀 수 있다.** 등록된 출력
(`out_valid` 같은 것)은 "그 엣지에 실제로 일어났다" 와 정확히 같아서 검산 기준이 된다.

Lab 1 에서 이걸로 **측정 버그 둘**을 잡았다. 둘 다 테스트는 전부 통과하는 상태였다.

| 읽고 싶은 것 | 읽는 시점 | 틀리게 읽으면 |
|---|---|---|
| 이 엣지가 **쓰는** 값 | 엣지 그 순간 (`@(posedge)` 직후, 지연 없이) | 엣지 뒤 조합 신호가 다음 엣지 값으로 바뀌어 한 칸 미리 센다 |
| 이 엣지가 **만든** 값 | 엣지 조금 뒤 (`#1`) | NBA 전이라 옛 값을 읽어 한 칸 늦게 센다 |

**측정 숫자를 리포트나 페이지에 싣기 전에 트레이스로 한 번 검산한다.**
틀린 숫자에 맞는 설명은 쉽게 찾아진다. Lab 1 의 "레지스터가 넷이라 4" 가 그랬다.
진짜는 3 이었다.

**RTL 시각화는 파형과 짝을 이룰 때만 값이 있다.** 블록도만 따로 그리면 방향 절과 겹친다.
결과 절의 블록도는 **파형에 보이는 신호가 회로 어디를 지나는지** 를 보여주는 것이어야 한다.

## 05. 인터랙티브: 어느 장치를 쓰나

세 장치가 있고 **용도가 다르다.** 규격은 `note-html` 이 단일 출처다.

| 장치 | 이 장르에서의 쓰임 | 어느 절 |
|---|---|---|
| `.sim` | "이 코드가 이 회로이고 이렇게 돈다" 를 반 클럭씩 | 방향, 결과 |
| `.anim` | 여러 프레임에 걸친 시나리오를 밟아본다 | 방향, 결과 |
| `.play` | 독자가 값을 넣고 결과를 본다 (계산기, 탐색기) | 방향, 총정리 |

### 축소 모형으로 만든다

**실물 크기를 넣으려 하지 않는다.** `.sim` 의 회로 노드는 격자 위 박스라
깊이 40 짜리 메모리를 그릴 수 없고, 값 계산이 `1 << bits` 라 폭도 제한된다.

**깊이 2~4, 폭 2~3 비트로 줄인다.** 그리고 **줄였다는 것을 카드에 밝힌다.**
줄여도 보여주려는 동작이 살아 있으면 그게 맞는 모형이다. 살지 않으면 그 개념은
`.sim` 으로 보여줄 것이 아니다. **도해로 간다.**

Lab 1 이 실제 사례다. 실물은 깊이 40 · 64 지만 동기화기 지연과 포인터 비교는
깊이 4 에서 그대로 보인다. 반면 40 칸이 차오르는 것 자체가 논점인 곳은 `.sim` 이
아니라 **점유량 그래프**여야 한다.

### "RTL 과 같다" 고 쓰려면 먼저 대조한다

인터랙티브 모형이 RTL 과 같은 규칙으로 돈다고 적고 싶으면, **먼저 같은 모형을 스크립트로
짜서 실제 트레이스와 행 단위로 맞춘다.** 한 줄이라도 어긋나면 그 문장을 쓰지 않는다.
Lab 1 의 깊이 계산기는 이 대조를 통과한 뒤에 JS 로 옮겼고, 그 과정에서 **본문의 안내
문구 하나가 틀렸다는 것**이 드러났다.

### 이미 있는 도구를 다시 만들지 않는다

강의 노트가 같은 개념의 인터랙티브를 이미 갖고 있으면 **링크한다.**
L05 에 깊이 4 짜리 FIFO 도구가 있는데 Lab 기록에서 또 만들면 둘이 갈라진다.
**Lab 페이지는 강의 노트가 안 다루는 것만 만든다.** 이 Lab 에서 실제로 부딪힌 것.

## 06. 총정리

**마지막에 위젯을 억지로 만들지 않는다.** Lab 1 정리는 `남은 질문` 절로 끝난다.
Part 를 가로지르는 것(구조 탐색기, 비교판, 경로 추적)이 자연스럽게 나오면 마지막 절에 두고,
아니면 표와 도해로 끝낸다. 요약 표만 있는 것은 위젯이 아니다.

**자동 검사는 이걸 못 잡는다.** Lab 1 을 쓰고 나서 트레이스와 대조하니 이런 것들이 틀려 있었다.

## 08. 검증

```bash
node scripts/verify.mjs   notes/LAB{N}-{kebab}.html    # exit 0 이어야 통과
node scripts/langcheck.mjs notes/LAB{N}-{kebab}.html
node scripts/simcheck.mjs notes/LAB{N}-{kebab}.html    # .sim 이 있으면
node scripts/animshot.mjs notes/LAB{N}-{kebab}.html    # .anim 이 있으면
```

`readercheck.mjs` 는 **안 돌린다.** 리더가 없다.

**`glossary.html` 과 `index.html` 을 고칠 때 두 가지를 조심한다.**

- **남의 미커밋 작업이 섞여 있을 수 있다.** 그러면 통째로 커밋하지 말고 HEAD 사본에 내
  변경만 적용한 뒤 `git hash-object -w --no-filters <사본>` 과
  `git update-index --cacheinfo 100644,<sha>,<경로>` 로 올린다. 작업 트리는 그대로 둔다
- **`glossary.html` 은 한 파일 안에 CRLF 와 LF 가 섞여 있다.** 통째로 정규화해서 다시 쓰면
  수십 줄이 바뀐 것처럼 보인다. 줄 단위로 `splitlines(keepends=True)` 해서 끼우고,
  끼우는 줄의 줄바꿈은 바로 앞 줄을 따른다

**glossary 에 이 페이지가 붙인 이름을 넣지 않는다.** Lab 1 의 "empty latency", "parity
쏠림" 은 설명하려고 붙인 말이지 업계 용어가 아니다. 용어 지어내기 금지 규칙 그대로다.

**`verify.mjs` 에 Lab 전용 검사가 하나 있다.** 강의 노트가 `LAB{N} Task {번호}` 를
언급하면 Lab 페이지에 `data-task="{번호}"` 가 있는지 대조한다. Task 로 나뉘지 않는
Lab (Part 로 나뉘는 경우) 은 `data-task` 를 안 쓰면 되고, 그러면 이 검사가 조용히 통과한다.
**`write-note` 스킬에 "`LAB*.html` 도 보도록 스크립트를 고친다" 라고 적혀 있는데
이미 고쳐져 있다.** 그 줄은 낡았다.

**도해 스크린샷을 전부 눈으로 연다.** 이 장르는 도해가 많아서 특히 새기 쉽다.

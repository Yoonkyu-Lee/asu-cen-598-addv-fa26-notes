# Lab 제출 하네스

## 목적

제출물은 Notion 설명서의 Deliverables 목록으로 채점된다. 파트너가 쓴 초안과 코드는 팀의 제출물이다.
내 일은 넷뿐이다.

1. 설명서가 요구하는데 **빠진 것**을 채운다
2. **사실과 어긋나는 것**을 고친다
3. 남은 Part 를 **설명서가 요구하는 만큼** 구현하고 싣는다
4. 제출 전에 파트너가 **무엇을 확인해야 하는지** 목록으로 만든다

"더 낫게", "더 엄밀하게", "더 공정한 비교", "내 방식이 표준" 은 일이 아니다.
이 목적을 쥐고 있으면 사전 승인이 필요 없다. 대신 **아래 셀프 검증을 전부 통과해야 끝난 것이다.**

## 하지 않는 것

- **labs 저장소의 `archive/` 를 읽지 않는다.** 폐기된 시도다. 경로를 열거나 검색 결과로 들여다보는 것도 하지 않는다.
  그 결과와 나중에 대조하기 위해 독립적으로 다시 하는 것이다
- 바깥으로 나가는 일은 하기 전에 묻는다: 파트너에게 공유, Drive 업로드, 제출, 데모 예약
- labs 저장소는 private, notes 저장소는 public 이다. 리포트, 파트너 원본, 설명서 원문은 labs 에만 둔다

## 기준

| 순위 | 무엇 | 어디 |
|---|---|---|
| 1 | Notion Lab 설명서 원문 | labs 저장소 `lab{N}/spec/handout.txt`. 근거는 `handout.txt:줄번호` 로 인용 |
| 2 | 파트너 원본 (받은 그대로) | `lab{N}/partner/`. 받은 커밋 해시와 sha1 을 `RUNS.md` 맨 위에 |
| 3 | 강의가 준 코드와 스크립트 | `lab{N}/given/` 과 설명서가 가리키는 경로 |

- `handout.txt` 가 없거나 Notion 이 바뀌었으면 **먼저 다시 받는다.** 블록 하나를 한 줄로 저장하고,
  페이지 전체 텍스트와 대조해서 빠진 문장이 없는지 확인한다
- release 덱이나 강의 슬라이드는 배경이다. 설명서와 다르면 설명서가 이긴다
- **사실**이란 위 코드를 **설명서가 정한 방법**으로 돌린 결과다. 설명서가 방법을 정하지 않았으면
  **과목이 준 스크립트를 그대로** 돌린 결과다. 스크립트에서 채우라고 비워 둔 자리(`<Add paths ...>`)만 채운다

## 판정

변경 후보는 하나도 빠짐없이 다섯 중 하나로 분류하고, **고치기 전에** 장부에 적는다.

| 분류 | 조건 | 행동 |
|---|---|---|
| **A 빠진 요구** | 설명서 Deliverables 의 한 줄을 초안이 충족하지 않는다 | 채운다. 초안의 관례로 |
| **B 사실 위반** | 초안의 문장·숫자·코드가 사실과 다르다. 증거를 재현했다 | 틀린 토큰만 고친다 |
| **C 그 외** | A 도 B 도 아니다 | **손대지 않는다.** 말할 가치가 있으면 검토 목록에 |
| **D 설명서 충돌** | 초안의 방식 자체가 설명서 문장과 어긋난다 | **손대지 않는다.** 검토 목록 맨 위에 줄 번호와 함께 |
| **U 사용자 결정** | 사용자가 채팅에서 관례를 바꾸라고 지시했다 (예: 코드 블록, 고정폭 신호 이름) | 지시대로 하되 **문장은 바꾸지 않는다.** 날짜와 사용자 말을 장부 근거 칸에 적고, G2 가 잡는 새 서식이 전부 이 줄로 설명되어야 한다 |

**B 로 적기 전에 셋을 다 확인한다.** 하나라도 걸리면 C 다.

1. **파트너의 방법으로 파트너의 값을 먼저 재현했는가.** 재현되면 그 값은 그 방법 안에서 참이다
2. **다른 정의, 다른 범위의 정당한 값은 아닌가.** 셈 범위가 다른 IPC, top 과 core 처럼 대상이 다른 합성
3. **내 증거가 설명서의 방법에서 나왔는가.** 내가 고른 top, 클럭, sweep, 가정한 입력 지연에서 나온 숫자는 증거가 아니다

**한계가 있는 숫자는 틀린 숫자가 아니다.** 한계는 C 로 검토 목록에 간다. 숫자를 바꾸지 않는다.

## 관례

**편집 전에** 초안의 관례를 `lab{N}/CONVENTIONS.md` 에 적는다. `docx_diff.py --dump` 출력과 실제 읽기로 만든다.

- 문체: 인칭, 시제, 말투, 문단 길이, 절 제목 방식, 절 순서
- 서식: 글꼴, 크기, 정렬, 들여쓰기, 목록을 쓰는가, 코드를 어떻게 싣는가
- 그림: 배치(inline 인가, anchor 와 wrap 인가), 크기, 캡션이 있는가
- **waveform: 캡처 범위(어떤 신호, 몇 사이클, 줌), 주석 방식(그림 위 텍스트상자인가, 화살표인가, 그림에 박았는가),
  주석 문장의 말투와 길이, 그림 앞뒤 안내 문장.** Lab 2 첫 시도가 여기서 무너졌다
- 표: 행과 열 구성, 단위 표기

규칙은 셋이다.

- **B 는 문장 안에서 틀린 토큰만 바꾼다.** 문장을 다시 쓰지 않는다. run 서식도 그대로 둔다
- **A 로 새로 넣는 것은 초안에서 가장 비슷한 것의 관례를 그대로 복제한다.** 새 형식을 만들지 않는다.
  waveform 을 새로 실으면 파트너 waveform 과 같은 배치, 같은 주석 방식, 같은 말투다
- 파트너 그림은 바이트 그대로 둔다. 그림 내용이 사실과 다를 때만 B 로, 같은 관례로 다시 찍는다

코드도 같다. **같은 zip 에 들어가는 코드의 기준은 파트너 코드**다. 이름, 포트 선언, 블록 구성, 주석의 형식과 밀도까지.
편집 전에 파트너 코드에서 실제로 세어 `CONVENTIONS.md` 의 코드 절에 적는다. 다른 Lab 의 스타일 문서나
"주석 없음" 같은 예전 규칙은 제출 코드에 적용하지 않는다. 설명서가 "document your code well" 로 문서화를 채점한다.

## 코드

- 파트너 코드는 A, B 만 바꾼다. 쓰이지 않는 줄 정리, 주석 문구, 파형 덤프 형식, 검사 강화, README 재작성은 C
- 설명서 ZIP 목록의 항목이 없으면 A 다. 있고 동작하면 C 다. "Makefiles (if any)" 는 없어도 충족이다
- 새 Part 는 설명서 Your Tasks 와 Deliverables 만 한다. 테스트 형식은 파트너 테스트를 따른다
- 검증용 내부 도구(어셈블러, ISS 등)는 써도 된다. **제출물에는 넣지 않는다.** 설명서가 요구하지 않는다

## Apporto

시뮬레이션, 합성, 파형과 터미널 캡처는 Apporto 에서 한다. **같은 폴더의 `apporto.md` 를 먼저 읽는다.**
browse 운용, Guacamole 좌표, 터미널 스크린샷 규칙(배너 금지, 프롬프트 포함, 자르지 않기)이 거기 있다.

## 측정

- 측정마다 설명서 줄을 먼저 인용한다. 줄이 없으면 과목 스크립트를 그대로 쓴다
- 실행마다 `lab{N}/RUNS.md` 에 한 줄: 날짜, 디렉토리, 명령, given 스크립트와의 diff, 결과를 담은 출력 줄
- 리포트에 들어가는 **모든 숫자**는 RUNS.md 의 한 줄을 가리킬 수 있어야 한다.
  arrival 인지 주기인지, 어느 top 인지, 몇 MHz 목표인지가 그 줄에 있다
- 설명서에 없는 측정은 하지 않는다. 궁금하면 사용자에게 말로 묻는다. 리포트에 싣지 않는다

## 작업 파일 (labs 저장소, private)

| 경로 | 내용 |
|---|---|
| `lab{N}/spec/handout.txt` | 설명서 원문 |
| `lab{N}/partner/` | 파트너 원본. 받은 그대로. 고치지 않는다 |
| `lab{N}/submit/part1/`, `part2/` | zip 에 들어갈 코드 |
| `lab{N}/report/` | 작업 중인 docx. 파트너 docx 를 복사해서 그 위에서 고친다 |
| `lab{N}/CONVENTIONS.md` | 관례 목록 |
| `lab{N}/LEDGER.md` | 변경 장부 |
| `lab{N}/RUNS.md` | 실행 기록 |
| `lab{N}/REVIEW.md` | 파트너 검토 목록 |

장부 한 줄의 형식이다. 근거 칸이 비면 그 변경은 하지 않는다.

| # | 파일·위치 | 원래 | 바꾼 것 | 분류 | 근거 (`handout.txt:줄` 또는 RUNS 번호와 출력) |
|---|---|---|---|---|---|

## 셀프 검증

**끝났다고 말하기 전에 전부 돌리고, 결과를 사용자에게 그대로 보고한다.** 하나라도 실패면 끝난 게 아니다.

| # | 게이트 | 통과 조건 |
|---|---|---|
| G1 | 리포트 diff: `python docx_diff.py partner/원본.docx report/결과.docx` | 나온 changed region 하나하나가 장부의 줄과 1:1 로 맞는다. 장부에 없는 region 이 하나라도 있으면 실패 |
| G2 | 관례 검사: `python docx_diff.py --style partner/원본.docx report/결과.docx` | 0 블록. 0 이 아니면 각 블록이 원본 관례를 어긴 이유를 장부에 근거로 댈 수 있어야 한다. 못 대면 실패 |
| G3 | 코드 diff: `git diff --no-index --ignore-cr-at-eol partner/풀어둔곳 submit/` | 모든 hunk 가 장부의 줄과 맞는다 |
| G4 | B 재현: 장부의 B 줄마다 증거 명령을 새로 돌린다 | 같은 출력. 그 명령이 설명서 방법이다 |
| G5 | 숫자 출처: 결과물의 숫자를 전부 뽑아 RUNS.md 나 파트너 원본과 대조 | 출처 없는 숫자가 없다 |
| G6 | 독립 반론: 새 하위 에이전트에게 `handout.txt`, 파트너 원본, 결과물, G1·G3 출력만 준다. **장부는 주지 않는다** | 에이전트가 변경마다 A/B/C/D 와 근거를 낸다. 내 장부와 다른 줄은 증거로 해소한다. 해소 못 하면 그 변경을 되돌리거나 검토 목록으로 |
| G7 | 요구 충족표: 설명서 Deliverables 줄마다 결과물의 어디가 충족하는지 | 빈 칸은 REVIEW.md 의 "남은 일"로 |
| G8 | 눈으로 보기: Word 로 PDF 를 뽑아 **쪽마다** 보고, 파트너 원본 PDF 의 같은 쪽과 나란히 본다 | 텍스트상자·화살표가 그림에서 밀리거나 겹치지 않는다. 새 쪽이 파트너 쪽과 같은 모양이다. 파일만 봐서는 배치 문제가 안 보인다 |

G6 의 에이전트에게는 "더 나은 리포트를 제안하라"가 아니라
**"설명서나 재현된 증거로 정당화되지 않는 변경, 관례를 벗어난 새 내용, 출처 없는 숫자를 찾아라"** 를 시킨다.

## 파트너 검토 목록 (`REVIEW.md`)

제출 전에 파트너에게 넘길 것이다. 순서는 이렇다.

1. **D**: 설명서와 충돌하는 초안의 방식. 줄 번호와 함께. 고칠지는 팀이 정한다
2. **A, B**: 바꾼 것 전부. 줄마다 "원래 → 바꾼 것, 근거, 확인해 달라는 것"
3. **C 중 말할 가치가 있는 것**: 숫자의 한계 같은 관찰. 리포트는 안 바뀌었다고 명시
4. **남은 일**: G7 의 빈 칸. 손으로 그려야 하는 것, 기여 요약, 데모 예약 화면처럼 사람이 해야 하는 것

## 반례: Lab 2 첫 시도에서 실제로 틀린 것

같은 코드로 다른 지표가 나온 것은 측정 체계 탓이 아니었다. **측정 대상을 내가 바꿨다.**

| 한 일 | 분류가 틀린 이유 |
|---|---|
| core(`mips`)만 합성하고 `instr` 입력 지연 0.1 ns 를 가정 | 설명서와 과목 스크립트는 `top`. 내가 만든 방법이라 증거가 아니다 |
| 파트너의 top 합성 숫자를 "무효"로 판정 | 그대로 재현됐다. 한계(imem 제거)는 C 였다 |
| 1.25 ns(800 MHz sweep 의 주기)를 critical path 칸에 | 다른 종류의 숫자. 옆 칸 1.00 ns 는 top 의 arrival 이었다 |
| "둘 다 core 합성에서 나왔다"고 적음 | 거짓. G5 가 있었으면 잡혔다 |
| 파트너 IPC 를 다른 셈 범위로 재계산 | 파트너 값은 자기 범위에서 맞았다. C |
| waveform 재캡처, 주석을 그림에 박고 번호 목록·Figure 캡션 | 파트너는 Word 텍스트상자와 화살표, 캡션 없음, 대화체. 관례 위반. G2 가 82 블록을 잡는다 |
| README 재작성, VCD 를 FSDB 로, testbench 검사 추가, 주석 수정 | 전부 C |
| Part 2 에 Verification 과 "Cost in area and clock" 절 | Part II Deliverables 에 없다 |

`docx_diff.py` 는 그 시도의 결과물을 파트너 초안과 대조해서 위 변경을 전부 잡는 것으로 시험했다.
